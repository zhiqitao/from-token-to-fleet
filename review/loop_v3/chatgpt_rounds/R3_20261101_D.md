# Publishing Readiness Review — *From Token to Fleet*

**Reviewed artifact:** `from-token-to-fleet-v20260913(20261101-021630).pdf`  
**Review date:** 2026-10-31 (US Pacific) / 2026-11-01 UTC  
**Extent:** 429 PDF pages, 26 numbered chapters, Appendix A, references, reproducibility notes, worksheet; 57 figure-bearing pages.  
**Decision:** **NOT YET READY FOR RELEASE / PRINT APPROVAL**. This is a strong, unusually careful technical draft, but the verified defects below affect the validity of an important model-selection exercise and the reliability of certain teaching statements. It also needs a separate printer-specific proof.

## 1. Review scope and epistemic limits

- Examined the embedded PDF text, page metadata, fonts, links and text-size distributions; surveyed rendered pages for all **57 identified numbered figures**; and inspected selected dense figures, tables, and worked-example pages at higher zoom. Cross-checked core canonical-scenario arithmetic and selected vendor claims with first-party online sources.
- **PDF page numbers** are used throughout; for numbered chapters the printed page number is generally **PDF page minus 20** (e.g., PDF 66 = printed p. 46). Preface and front-matter references use PDF pages.
- This is a critical editorial/technical assessment **of the supplied snapshot**, not a claim that every line of its roughly 1.1 million extracted characters was formally verified, every image glyph was inspected at physical print size, or every external citation was independently reproduced. No hardware benchmark, source-repository build, signed manifest, or actual KDP print proof was provided. Such unperformed tests are explicitly called out.
- Labels: **P0 Release blocker**, **P1 major/required before publishing**, **P2 important improvement**, **P3 polish**. “Verified” means contradicted by a cited page, arithmetic or rendering. “Qualification” means the manuscript explicitly labels its own limitation, but the release decision depends on closing it. “External” means independently checked with a vendor/source page.

## 2. Executive assessment

**What is working well:** The book has a clear token → workload → resource → deployment → fleet → architect reasoning spine. The canonical 70B full-MHA reference is plainly designated a conservative teaching model, not a representative contemporary 70B model. It carefully distinguishes actual measurements from assumptions, and repeatedly warns that the 21-host peak screen, API/cloud/self-host economics, and multi-region SLA are not equivalent to an SLO-certified deployment. Key arithmetic spot checks (2.62 MB/token, 24.9 GB for 9,500 tokens, 17 full-context slots, 6/21 host screening counts, $155,816.93 monthly cost, and the ~7.49M-request frozen-fleet crossover) reconcile under the explicitly stated inputs.

**Why release should be held:** A flagship Chapter 3 mini-case makes the opposite recommendation to its own weight-memory arithmetic and biases the comparison with an optional routing-GPU assumption; Figure 3.4 contains two contradictory quantities; Chapter 17 has an inconsistent generalization of Little’s Law to KV residency, and uses contradictory lower-/upper-bound terminology; Table 15-1 labels invented congestion indicators as MFU. There are also broken central cross-references and avoidable diagram and table production problems.

**Release gate:** Correct all P1 items, rewrite and retest the Chapter 3 exercise, reconcile the fleet sizing terminology in Chapters 16–17 and 20, re-render affected figures, then complete a real trim-size print proof and reproducibility/sources audit. Do not lower the technical standard to preserve a publication date.

## 3. Priority findings

### P1-01 — Chapter 3 reaches a conclusion contradicted by its memory comparison — VERIFIED

**Location:** PDF pp. 55–57 (Tables 3-1/3-2), 63–66 (mini-case, Table 3-3, Figure 3.4); especially PDF **p. 64**, printed p. 44.

**Evidence:** The text compares a constructed dense model **70B × 2 = 140 GB resident** with a Mixtral-like illustrative MoE **47B × 2 = 94 GB resident**; each uses the same assumed KV attention geometry. Table 3-3 repeats the 140/94 GB contrast, while the mini-case says the MoE challenger **“does not cut the memory budget”** and is rejected for that reason. Yet it has already cut *weight* residency by **46 GB (32.9%)**. The premise that MoE *sparsity alone* does not reduce KV is correct; the inference that this **different, smaller-total-parameter MoE** cannot cut overall memory is not.

**Required correction:** State both findings, without collapsing them: (a) given the constructed weight counts, resident *weights* decrease from 140 to 94 GB; (b) with the same assumed attention geometry and request length, the *KV* allocation is unchanged. Compare **weights + KV + runtime + routing/communication overhead at the actual target quality and SLO**. A fair model choice must establish equivalent task quality and concurrency/goodput, which this exercise does not. Rewrite the verdict as **“candidate not selected yet; quality, placement and measured service goodput unresolved”** or explicitly invent a valid, quantified constraint under which the dense model wins. The unsupported blanket rejection must go.

**Additional bias in same example:** PDF p. 64 adds **“a GPU dedicated to the routing dispatcher”** as an illustrative assumption and then uses that to reject the MoE. Such a dedicated GPU is **not a universal architectural requirement** for top-k MoE serving. Routing and expert execution can be integrated into the serving runtime; expert parallelism has configuration-specific communication costs. Compare an actual single-host or expert-parallel arrangement before adding an extra GPU. See external vLLM fused-MoE implementation and expert-parallel documentation below.

### P1-02 — Figure 3.4 contradicts its own derivation; its prose mislabels shared parameters — VERIFIED

**Location:** PDF **p. 66**, Figure 3.4, its caption and following explanation.

The rendered **MoE** panel says **“active per token ≈ 28 GB”**, but Table 3-2, Table 3-3, the caption and the accompanying prose give **12.8B active parameters × 2 B = 25.6 GB**. Use **25.6 GB**, if retaining the declared 12.8B worked model. Also replace the caption phrase **“top-2 experts plus always-on weights (~12.8B)”**: the **12.8B is total active**; the always-on contribution in Table 3-2 is approximately **1.4B**, with ~11.4B from the two selected expert groups. These must not be conflated. Make the labels **“resident weights ≈ 94 GB / per-token active-weight bytes ≈ 25.6 GB”** explicitly distinguish storage from work.

**Arithmetic check:** `2×5.7B + 1.4B = 12.8B`; `12.8B×2 = 25.6GB`; `47B×2 = 94GB`; `25.6/94 ≈ 27.2%`. The diagram's **28 GB** does not follow these premises.

### P1-03 — KV-residency Little’s-Law population is specified inconsistently — VERIFIED CONCEPTUAL RISK

**Location:** PDF pp. **272–275** (printed pp. 252–255), especially p. 273 subsystem table and definition, p. 274 capacity formula, and p. 279 architecture consequence. The same distinction matters for the Chapter 16 cost case and Chapter 20 fleet result.

**What is correct:** PDF p. 273 explicitly says a queued request does **not** occupy a KV slot, and **only model-execution occupancy** should drive KV-residency sizing. It distinguishes planning time (~10 s), queue time, prefill/decode execution (~8.6 s), and the actual host-resident population.

**Problem:** The immediately following generic formula describes `W` as the **“full service time (end-to-end: prefill + decode + any tool/orchestration overhead)”** (p. 273), and p. 279 instructs `N = ceil(λ_peak × W / (C × utilization_target))` with the **“full per-request service time”** including tool/orchestration. That is not generally the KV-holding time: tool waits, planning, request queues, and inter-turn eviction/compaction may not retain accelerator KV. Conversely, some schedulers keep KV resident during non-generation gaps. The correct quantity is the **mean interval for which a request occupies that specific KV resource under a defined cache/admission policy**; it may or may not equal full end-to-end latency. The narrative should not let readers transplant `λ × W_e2e` directly into a GPU cache slot count.

**Required rewrite:** Define distinct quantities `W_e2e`, `W_queue`, `W_GPU-exec`, `W_KV-resident`, and `W_tool-held-if-any`. For a stable admitted population, derive `E[L_KV] = λ_admitted × E[W_KV-resident]`; use the cache-size distribution, per-rank placement and the chosen allocation/admission policy to size memory. Independently calculate phase-specific capacity and **SLO-passing goodput**; the deployable host count is the maximum of the applicable capacity and tail-latency requirements, not simply the algebraic KV screen. The 8.6-second reference remains acceptable as a **conditional scenario** if the book explicitly assumes that it equals the mean KV-holding duration for this execution model.

**Related statistical caution:** Little’s Law uses **mean** occupancy and **mean** residence time at steady state. An instruction such as “size for the 95th-percentile latency and token scenario” (p. 279) may be a deliberate safety heuristic, but must not be presented as a direct Little’s-Law identity with a p95 substituted for `E[W]`. Treat p95/p99 as a separate stochastic/tail-memory constraint or load-test outcome.

### P1-04 — The same `C/W` rate is called both an upper bound and a lower bound — VERIFIED

**Location:** PDF pp. **252–253**, **274–275**. On p. 275 the text correctly states that the 2.0 req/s/host figure is an **analytical upper bound** under an idealized prefill budget, but also calls `C/W` a **“planning lower-bound screen”** in the preceding paragraph. Chapter 16 calls it a **KV/service-time screen** and an **“upper-order planning estimate”**.

**Fix:** Use one precise phrase everywhere: **“KV-slot-based analytical *upper bound on admitted request completion rate, conditional on an assumed mean KV residency time*.”** It is a *necessary capacity screen*, not a lower guaranteed rate, a measured server throughput, or an SLO goodput estimate. After independently measuring prefill/decode co-scheduling and queues, report measured sustainable SLO-goodput as the deployment basis. A lower bound on *required host count* can be derived from an upper bound on *per-host rate*, but that is the **other direction** of the inequality; spell it out.

### P1-05 — Table 15-1 misuses MFU as an arbitrary congestion label — VERIFIED

**Location:** PDF **p. 249**, printed p. 229, Table 15-1 and footnote.

The table column is **“MFU (%)”**, with **12 / 38 / 52**, while the following paragraph explicitly says these are **not achieved MFU** and that 52% is a **“demand-side label”** denoting congestion. MFU is a technical utilization ratio; relabeling an arbitrary workload-regime indicator as MFU teaches readers to compare quantities that are not the same metric. It also clashes rhetorically with Chapter 8's measured-versus-planning MFU discipline.

**Fix:** Either calculate actual consistent MFU proxies from a specified FLOP-rate/peak-rate numerator and denominator, or change the column to **“Illustrative load pressure (dimensionless score / labeled scenario)”**, giving the chosen scale and justification. A percent congestion score without defined denominator is particularly risky. Do not call it MFU.

### P1-06 — Canonical SLA, TCO, and solution recommendation remain intentionally unmatched — QUALIFICATION / RELEASE GATE

**Locations:** PDF pp. **75**, **253**, **259–263**, **273–275**. The canonical workload requires multi-region active-active **99.9%**, whereas costed host configurations are single-region, modeled, often 21-host **zero spare**, and lack measured p95 TTFT/TPOT goodput. This discrepancy is **not hidden**: the book explicitly warns “UNPRICED / NOT VALIDATED,” “NOT COMPARABLE,” and “NOT COMMITTABLE.” That honesty is a strength.

**Remaining issue for a book promising a *defensible architecture*:** The flagship end-to-end scenario never closes on an SLA-matched, tested, priced solution. The manuscript can publish such an unresolved case **only if the learning objective is clearly an honest stop at a decision gate**; otherwise it must add a worked multi-region N+failover capacity and cost extension plus explicit acceptance criteria. Stronger teaching option: provide a full **conditional ADR** with a table showing missing measured inputs, an illustrative region-failure capacity test, and a final **defer procurement** outcome—not a rhetorically implied selection. Keep the caveat prominently attached to every cost figure in executive summaries and figures.

### P2-08 — Chapter 16 mini-case claims too much for its simplified recommendation — VERIFIED EDITORIAL RISK

**Location:** PDF **p. 264**, printed p. 244, §16.8.

The startup exercise says that **“only one term can flip”** the self-host-vs-API decision—the opportunity cost of its half-engineer—and concludes to choose API despite the lower modeled self-host cash cost. The opportunity-cost arithmetic works under its **own** assumptions, but the exclusivity claim ignores other decision terms emphasized earlier in the same chapter: quality parity, peak throughput/SLO-goodput, regional availability, burst occupancy, hardware procurement risk, operational resilience, and financing/capital constraints. Even for a deliberately scoped mini-case, “the only remaining *modeled* term within this equal-capability assumption set” would be more defensible. Recast the verdict as conditional rather than universally causal. The 0.5-FTE implied salary is already explicitly hypothetical; preserve that label.

### P2-09 — Chapter 1 and Chapter 22 reverse the token metaphor — VERIFIED

### P2-14 — Physical print preparation must be treated as a different deliverable — REQUIRED PREFLIGHT

The PDF is **US Letter (612×792 pt / 8.5×11 in)**, with a designed front cover on PDF p. 1 and 429 pages altogether. It has embedded fonts, searchable text, no encryption, and accessible link destinations, and the pages generally have sensible outer margins. However:

Verify mirrored gutters on all pages *at final trim* and complete KDP's live preview and a mailed proof. Confirm black-and-white/grayscale intelligibility of blue/red/green encoding, figure line weight, image rendering, page order and pagination.
4. A PDF metadata preflight and font embedding check **do not** substitute for a printed proof. Chart labels, thin dashes, and contrasting dot patterns require actual paper confirmation.

## 9. Proposed replacement wording for the two central fixes

**Chapter 3 mini-case (replacement core conclusion):**

> Under this deliberately controlled attention geometry, the 47B-total MoE candidate lowers resident FP16 weights from 140 GB to about 94 GB and lowers active per-token weight work to about 25.6 GB. It does **not** lower KV cache bytes per token, because that quantity is set here by the shared attention geometry and KV precision. The lower weight residency is real but does not establish that the MoE is the better serving choice: task quality, per-host placement, expert dispatch and interconnect costs, achievable batching, and measured SLO-goodput remain to be compared. A separate routing GPU is an optional design hypothesis, not a requirement. The decision is therefore unresolved until the candidates are benchmarked under matched conditions.

**Chapter 17 capacity passage (replacement methodological conclusion):**

> For the cache-admission screen, let `W_KV` be the **mean time a request occupies accelerator KV memory**, including only waiting or tool intervals during which the serving policy deliberately keeps its KV blocks allocated. Under stable throughput, the mean number of KV-resident requests is `λ_admitted × E[W_KV]`. A host's memory capacity `C_KV` imposes the necessary bound `λ_admitted ≤ C_KV / E[W_KV]`, before accounting for per-rank imbalance, variable context lengths, prefill/decode interference and allocation overhead. The canonical 8.6-second value is an illustrative proxy for `E[W_KV]`, **not a measured service curve**. Queueing latency, p95/p99 SLO-goodput and failover must be assessed separately and may require more hosts.
