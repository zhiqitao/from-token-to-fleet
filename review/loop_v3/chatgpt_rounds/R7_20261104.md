## 0. Scope and standard of this pass

The bar is a reliable professional architecture textbook: quantitative claims must survive independent recomputation; diagrams must explain the mechanism rather than merely decorate it; a reader must distinguish estimates from measured deployment capacity; the print file must comply with the chosen publishing channel. A single wrong cross-chapter derivation is more consequential than many grammar defects.

**Evidence inspected:** complete searchable PDF text and structure across all 451 pages; all numbered figure pages in full-page visual contact sheets (57 numbered figure pages in total, including the two prefatory diagrams); enlarged checks on selected high-load diagrams; source/metadata/font/link/trim preflight; deep arithmetic on the canonical 70B RAG case, memory, compute, fleet, agent, communication and TCO examples. A few current service claims were spot-checked against primary vendor pages (see §6). This is **not** a claim that every word on all 451 pages was manually line-edited at full print zoom or that every linked external URL was independently opened. Production still needs a full physical grayscale/color proof and the tests specified below.

**PDF page convention:** Chapters start on PDF p.22, printed p.2. For most numbered body pages, **PDF page = printed page + 20**. Figure 1 in the preface is PDF p.15 / printed p.ix. The issue locations below specify both page systems when potentially ambiguous.

### Severity

- **P0 — publication blocker:** internally inconsistent derivation or result that can change a real decision; should be corrected and regression-tested before print.
- **P1 — high priority:** misleading quantitative model, missing feasibility condition, or publication-channel compliance risk.
- **P2 — significant improvement:** pedagogical, visual, traceability, precision, or safety-of-interpretation concern.
- **P3 — copy/production polish:** unambiguous localized correction.

### Executive assessment

The central strength is real: the token → workload → memory/compute/communication → serving → architecture → cost → fleet → ADR spine is coherent. The book often catches mistakes that many technical guides make: distinguishing 70B parameters from active MoE parameters, raw KV storage from engine allocation, a throughput *bound* from SLO-goodput, mean KV residency from end-to-end latency, and a vendor-reported result from reproduced measurement. The chapter 16/17 non-agentic host count, when read with its narrow assumptions, is considerably more disciplined than a naïve “one 8×H100 server can do 40 rps” claim.

However, a **new cluster of cross-chapter errors exists in the agentic execution trace and fleet calculation**. The underlying per-call event ledger is better than the summary formula: the summary fails to carry every model invocation into the latency calculation and several integer host counts prematurely round a time input. These are structural self-review failures: adding more caveats to a wrong computed result will not repair it.

**Release decision:** fix A-01 through A-04 and N-01, rerun all connected chapter/figure/table outputs, then redo numerical proofs. Treat PRINT-01 as a separate mandatory KDP/print-export gate. All others should be addressed before the final proof, but need not hold the quantitative rework hostage.

## 1. Verified numerical and conceptual issues

### A-01 · P0 · Agentic service time counts four model calls but only one prefill

**Location:** Ch.19 §19.4.1, PDF pp.315–318 / print pp.295–298; §19.4.3, PDF p.319 / print p.299; Table 19-1 PDF p.329 / print p.309; Ch.17 §17.8 PDF pp.295–298 / print pp.275–278.

**Observed manuscript facts:** the T=3 trace explicitly has **four** model invocations, with pure call input lengths **9,200; 10,065; 10,930; 11,795** tokens. Ch.19 correctly sums these as **41,990 model input tokens**, with **495 total model output tokens**. It explicitly calls this a **no-prefix-cache / no-reuse** execution-trace case. Yet the service-time formula takes only one `T_prefill(I(T))` and reports `W(3)=1.08 + 0.025×495 + 3×0.133 = 13.854 s` (also referenced as ≈13.8 s in Ch.17). Its “larger context” correction to ≈14.2 s scales the **last** prefill, but still omits the first three calls' prefill work.

**Independent re-derivation, keeping the book's own simple *linear prefill* assumption:**

```
inputs      = [9200, 10065, 10930, 11795]
sum(inputs) = 41990
prefill     = (41990 / 9200) * 1.08 s  = 4.92926 s
output      = 495 * 0.025 s            = 12.375 s
tools       = 3 * 0.133 s              = 0.399 s
W_full      = 4.92926 + 12.375 + 0.399 = 17.70326 s
```

The revised **≈17.70 s** is a model **within the author's simplified assumptions**, not measured SLO latency. A quadratic causal attention contribution would need to be recomputed, not silently ignored. If the intention is to reuse the KV prefix across calls, explicitly select a *different* retention/cache policy and compute only genuinely incremental prefill; it cannot simultaneously be the declared no-reuse case.

**Why it matters:** Ch.17's 100-rps T=3 FP16 KV fleet screen uses the ~13.8 s figure. Under the same conservative 13 whole slots/host and policy `u×ρ=0.70×0.95=0.665`, replacing service time with the simplified no-reuse `17.7033 s` would give `ceil(100×17.7033/(13×0.665)) = 205` **working** hosts, vs the printed 160. With tool waits excluded from KV holding (a separate, explicitly selected policy) the `17.3043 s` GPU-only proxy gives 201 working hosts. Both are illustrative all-T=3 screens, **not** an assertion that an actual measured fleet needs 205 hosts. The point is that the book's numerical answer materially changes when it reconciles its own event trace.

**Required edit:** make a **single trace evaluator** authoritative. For every invocation record `input_tokens`, `new_output_tokens`, `prefill_cache_hit_tokens`, `prefill_processed_tokens`, `decode_time`, `tool_wait`, `KV_held_during_wait`, and `KV_release/reload`. Derive *task latency*, *mean KV holding time*, *peak KV* and *billed tokens* separately. Retest Ch.17/19 tables, Fig.19.2/19.3 explanatory labels, TCO/fleet consequences, and Ch.26 agent patterns. Show both no-reuse and reuse scenarios; do not interpolate informally between them.

**Acceptance test:** using T=3 and cache-hit ratio zero, a unit test must enumerate four prefill events; published `W` must equal the sum of the four event costs and all other counted events. With a fully reusable prefix, assert a different and separately labeled result.

### A-02 · P0 · Premature rounding changes integer fleet decisions

**Location:** Ch.17 §17.8 and Table 17-2, PDF pp.295–298 / print pp.275–278; Ch.19 Table19-1, PDF p.329 / print p.309.

Ch.19 states the underlying T=3 service time is **13.854 s**. Ch.17 substitutes displayed **13.8 s** before multiplying by traffic and applying `ceil(...)`. Integer host counts must instead use the unrounded value until after the ceiling.

| Traffic and geometry | Printed result using 13.8 s | Corrected using stated 13.854 s | Formula (working hosts) |
|---|---:|---:|---|
| 40 rps, T=3, FP16, C=13 | 64 | **65** | `ceil(40×13.854/(13×0.665))` |
| 100 rps, T=3, FP16, C=13 | 160 | **161** | `ceil(100×13.854/(13×0.665))` |
| 200 rps, T=3, FP16, C=13 | 320 | **321** | `ceil(200×13.854/(13×0.665))` |
| 100 rps, T=3, FP8, C=27 | 77 | **78** | `ceil(100×13.854/(27×0.665))` |
| 200 rps, T=3, FP8, C=27 | 154 | **155** | `ceil(200×13.854/(27×0.665))` |

These corrections concern **only the premature-rounding defect while holding the old 13.854-s assumption fixed**; A-01 then requires a more fundamental recalculation. No two-stage rounding is permissible for host counts. The claimed 78-host “77 working + one spare” FP8 design in §17.8 becomes **79 total under the old unrounded assumption** (78 working + one spare), before repairing A-01.

**Required edit:** all calculations should use full-precision source variables; only rendered labels round. A regression test compares the table's integer counts against the exact expression. Add a “rounded display must not feed downstream arithmetic” invariant for every `ceil`, `floor`, threshold and tier selection.

### A-03 · P1 · Fallback ledger's excluded-work calculation removes the whole fallback, not only failed work

**Location:** Ch.19 §19.8, PDF pp.327–328 / print pp.307–308.

The chapter's own 100-request ledger is arithmetically consistent up to:

```
68 × 19,630 + 25 × 30,625 + 5 × 42,485 + 2 × 39,890
= 2,392,670 model tokens
```

But the text says excluding *fallback's failed-attempt work* lowers cost per 98 completed requests from **24,415** to **23,601**, a difference of **814**. The `23,601` figure is actually `(2,392,670 − 2×39,890)/98` — it removes **all** fallback tokens, including each fallback's final single-shot reply. Failed pre-fallback work per fallback is `39,890−9,500=30,390` tokens. Excluding only those wasted attempts gives `(2,392,670 − 2×30,390)/98 ≈23,795`, a difference of **620**, not 814.

There is also a denominator-policy ambiguity. Are the 2 fallback replies completed requests, lower-quality completed responses, or failures excluded from the successful-task count? The numerator includes all 100, while “98 completed” appears to exclude all fallbacks, even though each fallback is described as executing a single-shot answer. These are different KPIs:

- **Tokens per submitted request:** `2,392,670/100 = 23,926.7`.
- **Tokens per completed request:** numerator / **number of genuinely successful requests**, measured under the agreed quality/success definition; cannot choose 98 solely because 2% took a fallback route.
- **Wasted failed-attempt tokens:** `2×30,390 = 60,780` per illustrative 100-task cohort.
- **Total fallback-route tokens:** `2×39,890 = 79,780` per cohort.

**Required edit:** define successful completed task, submitted request, fallback-route completion, and failed work separately; repair the 23,601 / +814 sentence; put both denominators and a quality gate in the table. Audit every later cost-per-useful-answer and throughput statement using this result.

### A-04 · P1 · A 12% retained-context increase is easy to mistake for a 12% compute/token cost increase

**Location:** Ch.19 §19.4.1–19.4.2, PDF pp.315–318 / print pp.295–298; mini-case conclusion PDF p.328 / print p.308.

The derivation itself explicitly knows the difference: `α(T)` is **retained context size**; it is not all model-processed/billed tokens. The T=3 event-level ledger states **42,485 model tokens = 4.47×** the 9,500-token single shot with no prefix cache, despite the final accumulated context being only **12,095 tokens = 1.27×**. The **distribution-weighted** 100-task ledger yields **23,926.7 tokens per submitted request ≈2.52×** the baseline under its no-reuse accounting, not ~1.12×.

Nevertheless, the mini-case conclusion says the agentic layer “added an expected ~12% token overhead” before mentioning caching and quality. If readers lift that line into a capacity/cost slide, they can radically underbudget work. The qualification exists 10–12 pages earlier, but the conclusion and table should remain independent of that context.

**Required edit:** rewrite the takeaway as: “Expected retained-context *length* increases ~12%; actual summed model tokens across invocations in this illustrative no-prefix-reuse request mix increase ~152% per submitted request (2.52×); billed spend depends on prefix cache and provider rates.” Track token quantities in an explicitly labeled three-column takeaway (retained/processed/billed), not a single overloaded word “tokens.”

### N-01 · P1 · Network latency decomposition double-counts/incorrectly classifies serialization

**Location:** Ch.17 §17.4.4, PDF p.290 / print p.270.

The text defines `t_net = t_fixed + t_transfer + t_queue`, then says `t_fixed = RTT + serialization`, including “time to serialize the payload onto the wire” and asserting this “does not shrink as D grows.” It separately defines `t_transfer = D/B_effective`. **Payload serialization is proportional to D** and is already represented by the `D/B` transfer term in this simple model. As written, it is both called fixed and potentially counted twice.

**Required edit:** use `t_net ≈ t_propagation/RTT + t_protocol_fixed + D/B_effective + t_queue` with clearly declared start/stop clocks. If the intent is to include fixed header/control serialization in `t_protocol_fixed`, specify header bytes and avoid calling that *payload* serialization. Recalculate the 5 MB / 50 MB examples if an actual double count was used. Provide a 0-B/5-MB/50-MB monotonic unit test.

### M-01 · P1 · Single-request “3×H100 fits” cell ignores implementable placement/sharding

**Location:** Ch.7 fit table, PDF p.124 / print p.104.

The row **“fits 3×H100 at 9.2K? yes”** follows solely from `164.1 GB < 240 GB` aggregate memory. This is a necessary *pool-capacity* screen, not an execution result. A canonical hidden dimension of **8192** does not split evenly into three naive tensor-parallel shards (`8192/3` is not integral), and actual attention-head partition, runtime, workspace and topology support are not specified. The chapter correctly warns elsewhere that aggregate capacity is not placement proof, making the “yes” table especially misleading.

**Required edit:** change the answer to **“passes aggregate bytes only; viable TP=3 placement not established”**. Separate three gates: (1) aggregate bytes, (2) per-rank allocation/shard compatibility, (3) working engine/kernel/topology benchmark. The same caveat should qualify the “8×H100 at 128K? yes, barely” cell — a nominal pool check alone never establishes a supported runtime configuration.

### S-01 · P1 · Nominal TTFT budget allocates 100% of budget to only two components

**Location:** Ch.4 Table4-2, PDF p.80 / print p.60; Ch.4 latency section PDF p.84 / print p.64; Preface PDF p.19 / print p.xiii.

The canonical **TTFT target = 1.20 s** and modeled retrieval **0.12 s** yield a residual **1.08 s** for prefill. The book explicitly acknowledges positive queue, tokenizer/transfer and first-decode-step terms, and correctly calls the target aspirational. But once `1.08 s` is labeled the “prefill compute budget,” the budget has **zero** time left for those other terms. Adding merely a caveat does not make a feasible strict TTFT budget.

**Required edit:** define `TTFT_e2e = retrieval + admission/queue + tokenization/transfer + prefill + first decode`, allocate positive provisional allowances to all components (or explicitly state `1.08 s` is a **two-term-only upper cap, not a feasible deployed prefill target**), and tie admission/queue to the actual p95 target. Example: do not impose arbitrary external numbers; use a symbolic `budget_prefill ≤ 1.08 s − B_other` until measurement supplies `B_other`. All downstream “meets 1.2 s” language needs a named tested workload and end-to-end timing.

### F-01 · P1 · Worst-case agentic fleet uses a p95-turn scenario as if it were the mean resident time

**Location:** Ch.17 §17.8 and Table17-2, PDF pp.295–298 / print pp.275–278; Ch.19 turn mix, PDF pp.315–328 / print pp.295–308.

Ch.17 lucidly explains that Little's Law uses **mean** `E[W_KV-resident]`, *not* p95 time. The agentic example nevertheless takes **T=3 (95th percentile of turn count)**, places the T=3 service time and T=3 peak KV length into every request, and calls the resulting `λ×W(T=3)` “in-flight concurrency.” That is legitimate as a **conservative all-requests-at-T=3 stress scenario**, but it is *not* the mean population actually implied by the provided distribution. It is not a strict worst case either if the 2% fallback jobs do multiple failed model invocations **plus** the final fallback invocation.

**Required edit:** present distinct ledgers for (a) the distribution-weighted mean KV residency and mean resident bytes, including fallback attempts, (b) a T=3 stress cohort, and (c) the extreme fallback route and tail SLO. The mean needs sequence-specific time and allocation; `E[bytes×time]` is often a more informative memory load than `E[time]×p95 bytes`. For host provisioning, preserve the discrete allocation/fragmentation gate plus real trace admission tests. Do not substitute a percentile into a mean equality while calling the result a measured/typical population.

### T-01 · P2 · A “candidate, not committable” analysis needs a fully worked measurement-to-decision closing example

**Location:** Chs.12, 14, 16, 17, 22 and 25; particularly Ch.17 decision state PDF p.294 / print p.274.

The conservative decision state (“candidate screened; not committable; regional availability, failover, SLO-goodput and matched-scope costs pending”) is epistemically responsible. But a handbook that teaches a defensible architecture should show **at least one completed worked decision with real or reproducible small-scale measured evidence**, alongside the analytical teaching case. Otherwise the main spine reaches a disciplined *unvalidated proposal*, not a complete example of professional sign-off.

**Required edit:** include a compact evidence-to-ADR appendix or worked case with workload generator, test conditions, trace schema, a real set of measurements, confidence/variation, SLO pass/fail, and the exact recorded choice. It may be a small model on a small local system; do not pretend those measured values extrapolate to 8×H100. The important demonstration is the *transition* from hypothesis to evidence and decision.

### T-02 · P2 · TCO comparison remains unmatched on availability and burst capacity

**Location:** Ch.16 §§16.3–16.5, printed pp.235–255; Fig.16.1 print p.253.

The book responsibly labels the cloud paid-host-hour case an **occupancy input** and explicitly warns that 21-host single-region self-host, elastic cloud and managed API are **not apples-to-apples** at the canonical 99.9% multi-region requirement. These warnings are positive. Still, headline charts/tables sit directly next to price rankings and a break-even crossing. Readers may retain the ranking while ignoring the caveat.

**Required edit:** place a *feasibility/status* column **before** price comparisons, with three states: `validated comparable`, `planning-only incomparable`, `fails requirement`. Keep the current plot as a clearly separate sensitivity teaching chart. Add a candidate-cost chart only after the same region count, failover, warm capacity, SLO-goodput, support, data-egress and pricing time horizon are assigned.

### T-03 · P2 · Qualitative performance promises occasionally outrun the book's measurement rules

**Location:** Ch.20 mini-case, PDF p.340 / print p.320; related Ch.20 metric table PDF p.335 / print p.315.

The mini-case calls an added scheduler p99 ≤5% “comfortably achievable,” while also stating the system has no measured scheduler distribution. A median (or nominal ~0.5 ms) dispatch figure cannot establish p99. The book's evidence discipline requires this to be an SLO hypothesis, not an achieved prediction. Similar “typical” latency/failover statements throughout fleet chapters should be checked for an underlying measured distribution or explicitly assumed target.

**Required edit:** replace with a target (`must be demonstrated in load test`), and define numerator/denominator for the 5%-of-request-time metric on the **same request population**.

## 3. Figure and visual-quality audit

### Global print/visual findings

- Across the numbered figure pages inspected, the diagrams have a generally coherent design language, meaningful headings, an unusually strong habit of qualifying data as *illustrative* or *analytical*, and no obvious clipping outside the PDF page. In many cases, the captions carry more evidence than the chart itself: good for intellectual honesty, but visually tiring when every plot ends in a dense multi-paragraph caption.
- **Figure captions are sometimes doing three jobs** (figure description, evidence ledger and legal caveat). Keep a short caption (what, geometry, source) and move longer derivations/status reconciliations into an adjacent numbered note. This is especially important in Figs.8.2, 16.1, 17.1, 19.2, 20.1, 26.1 and Appendix figures.
- **Grayscale/photocopy check not yet cleared:** plot series in Figs.3.4, 7.5, 16.1, 19.2, 20.1, 26.1 and A.1/A.2 rely partly on hue. Several already use markers/hatching, which helps; use distinct line patterns and hatches for **every** semantically distinct data class so a grayscale proof conveys the same distinctions. Test print at actual trim size, not 200%-zoom PDF.
- Use annotation-free labels in the plot area where possible; both figures and captions repeat the phrase “not measured” many times. A consistent small status strip (`ANALYTICAL — not a benchmark`) can reduce repetitive clutter while retaining intellectual honesty.
- Figure 17.1 and the charts of host count should specify the *exact source arithmetic used to round the host count*; A-02 makes these diagrams release-sensitive.
- Spot-check text size, arrow landing points, plot legend contrast and mathematical glyphs at a **physical 100% proof**. The screen contact sheets do not substitute for printed proof approval.

## 7. Preventing the next self-review from rediscovering different arithmetic defects

The issue is not just a missing warning: the manuscript contains an excellent **per-call ledger** and a conflicting **summary service-time equation**. The work should be made mechanically self-consistent.

### Required numerical single-source-of-truth

Create one typed scenario and task-trace object with these noninterchangeable fields:

```text
Workload:
  arrival_rate_peak, arrival_rate_average, arrival_process
  request_count_calendar, billing_calendar, p95/p99 target
Model geometry:
  total_params, active_params, attention_layer_types
  hidden_dim, q_heads, kv_heads, head_dim, kv_dtype
  quantization_scales, weight_sharding_plan, KV_sharding_plan
Host:
  usable_HBM_per_rank, sharding constraints, runtime_reserve
  observed_prefill_goodput, observed_decode_goodput
Execution event (repeatable):
  model_call_id, context_before_call, processed_prefill_tokens
  reused_prefill_tokens, generated_tokens, model_call_latency
  tool_call_id, tool_wait, KV_held_during_wait, KV_size/time
  success_class, fallback_status, cached_vs_billed tokens
Policies:
  context_compaction, prefix_cache, eviction, failed_attempt handling
  u, rho, N_minus_1, multi_region, reserve, availability
Outputs:
  task_tokens_processed, billed_tokens, useful-task rate
  max_resident_bytes, mean_KV_byte_seconds, task/service latency
  p95/p99 by request class, independent prefill/decode/KV/communication screens
  ceil/floor host counts (never rounded inputs), scoped TCO
```

Each table/figure/caption should be generated from these objects; manually typed “reconciliation” paragraphs must not override a computed result. If T=3 has four calls in the trace, that many calls must appear in the service-time graph; if a reused prefix suppresses three prefills, the engine/caching policy must say so and record its memory consequences.

### Adversarial tests that the review loop must deliberately run

1. **Four-call conservation:** for each T, check `sum(call.input)` vs `task_input`, `sum(call.output)` vs `task_output`, and *sum(each call's measured/modelled prefill latency)* vs `task_prefill_latency`.
2. **Cache extremes:** rerun at 0%, partial, and 100% prefix reuse. Assert processed tokens decrease only by explicitly reused tokens and that memory/time transitions are consistent.
3. **Fallback accounting:** if 2% tasks use 3 failed turns plus a final fallback, sum **all** failed-attempt tokens and all final-answer tokens, then compute separate per-submitted/per-completed/per-successful metrics.
4. **Integer boundary fuzzing:** vary service time by ±0.01 s near every `ceil` cutoff. Fail if displayed rounded strings are used as numeric inputs.
5. **Mean-vs-quantile check:** recompute `E[KV-byte-seconds]` from every trace class; prohibit using p95 `W` as the mean Little's-law input without a clearly labeled conservative stress bound.
6. **Placement feasibility:** if a device count passes aggregate HBM but heads/layers or shards cannot be placed evenly, emit `capacity-passes / execution-unverified`, never `fits=yes`.
7. **TTFT budget closure:** sum all measured/assumed positive components; require `sum(p95 budget allocations) ≤ end-to-end budget`, with proper warning that independently measured p95 components do not trivially add to p95 end-to-end.
8. **Network double-count test:** varying payload D changes only explicitly D-dependent transmission terms; no “fixed payload serialization” remains.
9. **Evidence flip:** run all tables in `analytic` and `measured` modes, and ensure no measured status survives if source data is removed.
10. **Figure/caption hash:** fail the release if a figure's data hash, caption, table, page reference, or appendix provenance status points to a different scenario revision.
11. **Monochrome regression:** convert each plotted figure to grayscale and verify categorical distinctions with patterns or line styles, not just colors; check minimum font/line widths.
12. **KDP production proof:** inspect upload warnings for each page after the print-specific export, confirm trim/bleed/gutter, and use physical proof for smallest figure text.

The acceptance principle is **not** that all reviews find zero new nitpicks. It is that the highest-risk claims have explicit invariants and a frozen proof ledger, and any source change reruns the dependent calculations automatically.
