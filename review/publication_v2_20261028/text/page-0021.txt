1.1.1. Tokenization
Tokenization splits a string into an ordered list of integer IDs from the model’s vocabulary (typically 
tens of thousands, up to ~256k entries). The split is data-driven: learned from a large corpus, byte-
pair encoding (BPE) repeatedly merges the most frequent adjacent byte/subword pairs until the 
vocabulary is built, so the boundaries are wherever the corpus statistics happened to fall — not where a 
grammarian would put them. Two practical consequences follow. First, text is generally recoverable 
from its token IDs under the specified tokenizer (the detokenizer inverts the encoding), but the 
segmentation does not correspond cleanly to words or semantics: the characters of architecture 
and architect may or may not share a token depending on corpus frequency. The encode/decode 
round-trip is usually lossless for the byte-level mapping, but the token boundaries are not semantically 
meaningful. Second, token counts are not proportional to character counts in any fixed way. 
[1P][FACT] A high-frequency English word is often one token (verifiable on most vendor tokenizer 
demos — e.g. common words like the, we, run render as single tokens); a rare technical term, a long 
digit string, or dense code is frequently several. The “one token ≈ 4 characters” rule of thumb is 
for rough estimation of general-English prose, never a law — we confirm against the model’s own 
tokenizer before pricing anything.
1.1.2. Context window
The context window is the maximum sequence length the model can condition on at a given 
generation step — that is, the total of the retained input/prefix and the tokens generated so far. It is a 
hard service constraint at the configured limit: exceed it and the request fails or must be truncated. 
(This is the engine-configured maximum, not a law of physics — some models use sliding-window or 
rolling attention that retains only a bounded recent context, and a few support positional-scaling or 
provider-side context extension, so the model’s positional capability and the serving stack’s configured 
cap can differ; the distinction is developed in Ch 7 and Ch 22.) Current-gen models commonly ship 
windows ranging from roughly 8K up to a million-plus tokens, varying by model and vendor ([1P]
[FACT] vendor model cards, e.g. 128K/1M+ windows as of 2026); the advertised number is a fixed, 
checkable property of the model we choose — verify it on the card, never assume it from the family 
name. Note there are three related but distinct limits: the model-advertised maximum (the card’s 
window), the engine-configured maximum (what the serving stack is set to allow, which can be lower 
to bound memory), and the request-level available input budget (the advertised window minus the 
reserved generation budget and any positional-scaling or provider-API cap). The context window
