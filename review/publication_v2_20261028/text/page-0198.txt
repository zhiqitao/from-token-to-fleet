15.4. Measurement
To validate the mental model we instrument the serving stack with three metric families: (a) 
token latency percentiles (p50, p95, p99) per request type, (b) GPU utilization (SM active, memory 
bandwidth via Nsight), and (c) KV cache size over time. A minimal benchmark runs 40 rps with 
warm‑up, records the p95 token latency, and measures the GPU memory fraction consumed by KV 
cache. Repeating with different batch sizes (1, 4, 16, 32) reveals the throughput‑latency knee. The 
illustrative numbers below are scenario values to be measured on the target stack, not vendor or 
published figures: beyond batch‑4 the p95 latency typically rises (implying a knee near batch 4) 
because kernel launch overhead is amortized but inter‑request token interleaving increases cache 
thrashing. On the FlashAttention “traffic reduction” claim, be precise about the units: one 
often sees a FlashAttention‑class kernel reported at a different achieved HBM bandwidth than a naive 
SDPA kernel (illustratively ~150 GB/s vs ~400 GB/s for 9,500‑token contexts). That is a rate, not a 
byte count. A bandwidth figure alone does not establish that fewer bytes/request were transferred 
— it only shows the kernel’s achieved memory throughput. To claim a traffic reduction, compare 
the bytes transferred per request (or read/write transaction counters) under a matched workload; 
the FlashAttention advantage shows up there as fewer materialized/intermediate bytes, not as a 
low raw bandwidth. And separate the two cache concepts: “cold‑start KV warm‑up” (populating 
the KV-cache blocks for a new context) is different from “model‑weight loading” (streaming the 
140 GB weights into HBM) and from CUDA/JIT kernel warm‑up. A 70B cold‑start that reuses cached 
weights is far faster than one that must load them from scratch — but these are distinct effects, not 
one number. Set these illustrative figures from the target host’s profiler before quoting them as fact.
