Parallelism: Splitting the Model Across Machines
10.6. Architecture Consequence
The parallelism strategy is forced by the binding constraint, and that constraint is usually 
memory for large models:
• A model that exceeds one GPU’s memory must split weights → TP (within a node, on 
NVLink) or PP (across nodes, low comm). Which one depends on whether the model fits a 
node: fits one node → TP among its GPUs; spans nodes → PP across them, with TP inside 
each node.
• A workload with high throughput demand (like the canonical ~10 rps / 40 rps) that fits one 
replicable model → DP to scale batch across GPUs, accepting the gradient-sync cost only if it 
trains/fine-tunes. For pure inference the canonical 70B fits one 8×H100 node, so parallelism is 
often unnecessary at the single-host baseline.
• MoE models (if chosen per Ch3) push toward EP, because the full expert set must be resident 
(the active count sets compute per token, not residency) and EP shards the experts across 
GPUs.
• The canonical answer: for the book’s ~70B/8×H100 scenario, no cross-host model parallelism 
is required at the baseline (intra-host TP=8 is still needed to fit the 140 GB model across the 
eight 80 GB GPUs); parallelism becomes the tool when the model or workload outgrows one 
node. The architect escalates through TP (in-node) → PP (cross-node) → DP (replicating a 
fitting model) in that order.
