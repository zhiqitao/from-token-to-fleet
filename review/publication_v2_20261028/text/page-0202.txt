Speculative decoding. The idea is to turn one slow serial step into a draft-then-verify pair. A 
small, cheap draft model proposes a candidate sequence of tokens; the larger target model then 
verifies all of them in a single batched forward pass, accepting the ones that match its own distribution. 
The loop is: draft → propose candidates → target verifies → accept a prefix → continue from the last 
accepted token. Why this can be faster: the expensive part of decode is not the arithmetic per token 
but the serialization — each target-model step streams the weights from HBM. If the draft can propose 
k tokens that the target accepts in one verification pass, the target’s expensive weight-stream is spent 
once on k tokens instead of k times on one — a genuine reduction in HBM round-trips (the same 
resource the FlashAttention discussion is about, but at the whole-model scale). Why it is not free: the 
draft costs extra compute, the verification pass itself has cost, and the acceptance rate (how many 
of the proposed tokens the target actually accepts) decides the win — a low acceptance rate means 
the draft and verification are spent for almost nothing. It is therefore workload/model/hardware 
dependent: a draft that closely matches the target (or a workload that is highly predictable) accepts 
more. No published speed-up is portable: a “6×” from one model/paper is a statement about 
that evaluation, not a guarantee for a different model or serving stack — measure it on the target 
workload or treat it as a hypothesis.
One subtlety about “matching its own distribution”: the target does not simply accept the draft 
tokens that happen to agree. Under stochastic sampling, accepting a proposed token outright (rather 
than by the exact-speculative-sampling correction that re-weighs each accepted and rejected token by 
the target’s posterior) can bias the output distribution away from the target model’s true distribution. 
The distribution-preserving result holds only when each proposed token is accepted or rejected by the 
exact acceptance/sampling procedure (the modified-rejection-sampling step of Leviathan et al., “Fast 
Inference from Transformers via Speculative Decoding,” arXiv:2211.17192; see the Sources chapter), 
which re-normalizes the continuation at each step. For greedy/argmax decoding the agreement test 
is exact; for temperature/prompt-driven sampling it is not, and the acceptance criterion must be the 
correction procedure, not mere token equality.
Chunked prefill. A very long prompt produces a large prefill operation that can monopolize the 
compute for hundreds of milliseconds, stalling concurrent latency-sensitive decode work. Chunked 
prefill splits that prefill into smaller pieces and interleaves them with decode steps in the scheduler, 
so the GPU keeps serving decode between prefill chunks instead of blocking on one burst. The causal 
chain: long prompt → large prefill → scheduler/resource monopolization → decode interference 
→ TTFT and TPOT both degrade → chunked prefill as a scheduling mechanism to bound the 
per-phase burst. The trade-off is not “smaller is better”: a smaller chunk reduces the decode stall 
but adds scheduler overhead (more per-chunk bookkeeping, potentially lower prefill throughput 
from less parallelism within a chunk), so chunk size is an empirically-chosen middle — measure the 
goodput/latency knee rather than assume.
