20.8. End-of-Chapter Mini-Case: Aggregate rps, Marginal Cost, and an Infeasible 
SLO
Scenario: A RAG Q&A fleet serves 2,000 users with the canonical parameters: 5% concurrent, 10 rps 
average / 40 rps peak, ~9,200 in-tokens + ~300 out-tokens per query, 70B dense FP16 model, 8×H100 
per host, 8 hosts total.
Question: What is the fleet’s aggregate rps capacity under the canonical KV/latency bound, and 
what is the marginal cost per rps when scaling from 8 to 16 hosts? Is an end-to-end 99th-percentile 
latency under 100 ms even feasible for this workload — and if not, what can the scheduler bound?
Solution (illustrative algebra — the per-host figure below is an [ILLUSTRATIVE] estimate for 
showing the fleet math; the real per-host rps must come from a deployment benchmark, Chapter 14, 
and is bounded by KV residency per Chapter 17):
• Per-host request rate — the KV/latency bound (Ch. 17 basis). A host holds ~17.5 concurrent 
full-context requests (the KV-residency ceiling, Chapter 17; byte-accurate 17.51, conservative 
integer floor 17) and each request is in service ~8.6 s (1.08 s prefill + ~7.5 s decode of 300 output 
tokens at ~25 ms/token, Chapter 8). So a host serves C/W ≈ 17.5 / 8.6 ≈ 2.0 requests/s at steady 
state. This is the defensible capacity number: it is derived from concurrency × service time 
(Little’s law), not from dividing a token throughput by tokens per request. (Do NOT divide 
~35,000 tokens/s by ~9,500 tokens/request to get ~3.7 req/s — that would require ~32 concurrent 
requests, which the ~17.5-request KV ceiling cannot hold.)
• Fleet aggregate (8 hosts): 8 × 2.0 ≈ 16 req/s, which is below the canonical 40-rps peak. On 
this binding bound the idealized minimum is ⌈40 / 2.0⌉ = 20 hosts; allowing ~5% scheduling 
loss (the same ρ ≈ 0.95 factor used elsewhere in this chapter and in Ch 17) raises this floor to 
40 / (2.0 × 0.95) ≈ 21.1 → 22 hosts. (The KV-residency bound, Chapter 17, is satisfied at far 
fewer hosts — ~5 at the 10-rps average — but the throughput/latency bound binds here, so the 
larger requirement governs.)
• Marginal cost (real basis): adding one host at ~$20/hr (cloud, [ILLUSTRATIVE]) buys ~2.0 
req/s, so marginal cost ≈ $20 ÷ 2.0 = $10 per req/s per hour. (The earlier illustrative $0.012 
figure assumed 250 req/s per host — a ~120× understatement that comes entirely from the 
impossible latency; with a real multi-second service time per request the per-host rate is ~2.0, 
not 250.)
• Algebra practice (kept [ILLUSTRATIVE]): the per-host 250 rps / fleet 2,000 rps / $0.012 
per rps arithmetic is retained only to show the structure of the fleet math (marginal host cost 
÷ marginal capacity). It deliberately uses a hypothetical per-host rps that is not achievable for 
this 9.2K-in/300-out workload; the architect must substitute the measured per-host rate from a 
Chapter 14 deployment benchmark, or the ~2.0 req/s bound derived here.
