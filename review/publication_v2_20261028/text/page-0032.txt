Timing convention (used throughout the book). We attribute the first sampled token to prefill: 
prefill = processing the prompt + sampling token 1, and decode = the per-token loop that begins 
with token 1 as its first input and produces token 2 onward. This is the standard TTFT convention — 
time-to-first-token includes the first token’s sampling, so the first token is the last output of prefill, 
not the first output of decode. (Some engines split this differently — e.g. counting the first token’s 
forward pass as the first decode step — but the difference is one token’s worth of latency, and every 
formula and figure in this book uses the convention above.)
Decode is the per-token generation that follows. After prefill, each new token only attends to the 
cached keys and values from the prefix plus all previously generated tokens. In the batch-1-equivalent 
weight-streaming model we use for this first-pass arithmetic, the per-step cost has two parts: the 
weight-read (the entire model weight matrix from HBM, constant in context length because the 
auto-regressive pass reuses the same parameters every step) and the attention over the growing 
KV cache (linear in context length, since each new token attends to all cached keys/values). At the 
canonical operating point the weight-read dominates, so the per-step cost is approximately constant 
in context length — but that is a regime statement, not an identity; the attention term grows with 
context and is the one that eventually binds at long context (Ch 8, Ch 22). (In a real serving stack, 
batching and weight-read amortization change this per-request picture substantially; that is the 
subject of later chapters.)
The critical architectural insight, at the canonical low-batch operating point: prefill tends to be 
compute-bound (high arithmetic intensity — the whole prompt is processed in one parallel pass), 
while decode tends to be bandwidth-bound (low weight-reuse efficiency — the 140 GB weight matrix 
is re-read every step for a single token). These are the typical bottlenecks, and confusing them is the 
most common architectural misstep. But neither is a universal physical law: the characterization is 
an operating-point property of model × workload × kernel × hardware (batch size, attention length, 
and kernel fusion all shift it), and the roofline framework in Ch 8 is what identifies which regime a 
given kernel actually sits in.
One detail the figure makes explicit is when a token’s K/V enters the cache. The first decode 
step, precisely: (a) prefill populates the cache with the prefix K/V and samples the first token; (b) 
that first token is the input that seeds the decode loop (the green initialize path in Fig 2.1); (c) each 
decode step takes one input token, runs the transformer on it — which computes and appends 
that input token’s K/V to the cache — attends over the cached K/V, and samples the next token 
from the logits; (d) the sampled next token is the output of this step and the input of the following 
step, whose forward pass then computes and appends its K/V. A token’s K/V therefore enters the 
cache on the step in which it is the input, not on the step in which it is sampled.
