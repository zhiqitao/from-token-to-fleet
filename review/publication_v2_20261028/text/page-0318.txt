26.2. Mental Model
The central mental model is the Pattern-Measurement-Feedback Loop. Every pattern in the 
library is paired with:
• FACT — a verified runtime quantity (e.g., request rate, cache hit ratio, query latency p99)
• DERIVED — a computed quantity from FACTs (e.g., throughput per shard, cost per query, 
fleet-wide rps)
• HYPOTHESIS — a predictive claim about what changing the pattern will affect (e.g., “increas­
ing replication factor from 3 to 5 will reduce tail latency by X%”)
The loop operates as: instrument → observe FACT → compute DERIVED → validate HYPOTH­
ESIS → adjust pattern. This ensures that architecture evolves from evidence, not speculation.
What a [1P] tag does and does not mean. The statuses above (FACT / DERIVED / HYPOTHE­
SIS) describe what a number claims to be; a separate provenance axis describes where it came from. 
[1P] marks a first-party source — the original method paper authored by the method’s creators, or 
a hardware-vendor specification (technical report, model card, or official documentation). It names 
whose claim a number is; it does not by itself assert a validated deployment benchmark. Keep the 
four categories distinct: (a) an original method paper by the method’s creators, (b) a hardware-vendor 
specification, (c) a third-party evaluation (the book’s [2°] secondary provenance), and (d) an own 
measured run ([LAB]/[MEASURED] — Axis-1 provenance plus the Axis-3 measurement status, both 
defined in the Sources, Method, and Reproducibility chapter). Of these, [1P] covers (a) and (b) only 
— a first-party source is a vendor or paper author’s figure, which must be re-verified against the 
current source or re-measured on the architect’s own hardware before it is treated as a validated 
deployment result. Note that the canonical 70B teaching model is not a [1P] model: being constructed 
(Ch 4, Table 4-2) it carries [ILLUSTRATIVE][ASSUMPTION], reserving [1P] for named, traceable 
first-party specifications.
