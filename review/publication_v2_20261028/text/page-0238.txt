18.2. Mental Model
The fleet operates as a cost-aware load balancer with three decision layers:
Table 18-1 — Fleet routing decision hierarchy: capability filter → cost/SLO gate → fallthrough.
Layer
Question
Decision
Capability filter
Does any model in the fleet meet 
the request’s feature 
requirements?
Eliminate models that lack the 
feature (e.g., context window too 
small, no tool-use).
Cost/SLO gate
Among remaining models, which 
minimizes weighted cost = 
α·token_cost + β·latency_cost?
Route to the cheapest suitable 
model; adjust α,β per deployment 
mode (interactive vs. batch).
Fallthrough
If all suitable models are at 
capacity, what is the next-best 
alternative?
Queue, degrade quantization, or 
escalate to the next tier.
The weighting (α,β) is deployment-context dependent. A chat UI tolerates ~200 ms of added 
service latency per request; a batch ETL job tolerates ~2 s per request but demands lower token cost. 
These are per-request service-latency thresholds for the short-prompt routing scenario — the chat 
figure sits under the chapter’s ≤500 ms interactive threshold (§18.3.4) — not the canonical TTFT/TPOT 
SLO (Ch 4); the canonical TPOT budget of ~25 ms is a per-token quantity and is not what these 
per-request figures measure.
18.3. Worked Example
Scenario: ~2,000 users, ~5% concurrent (≈100 simultaneous), ~10 rps average / ~40 rps peak. Total 
token volume per request: ~9,200 in + ~300 out. Base hardware: 8×H100, 640 GB total VRAM. Model 
families: a 70B dense FP16, a 70B MoE (16 experts, 2 active), and a family of 8-bit/4-bit quantized 
models (70B equivalent).
