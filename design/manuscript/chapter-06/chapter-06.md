# Chapter 6 — Measuring What Matters: From Telemetry to Architecture Decisions

## The Architect's Question

After this chapter we should be able to walk into a running inference system, read its metrics, and answer a deceptively hard question: *is this system meeting its obligations, and if not, which lever do we pull?* Teams commonly instrument the wrong thing — model capability and offline quality — and then are blind when a real workload misbehaves. This chapter builds the metric hierarchy that turns raw telemetry into architecture decisions: what to log, what each number means, how to read a latency *distribution* instead of a mean, and how to tell bandwidth-bound from compute-bound purely from the counters. After this chapter, "the system felt slow" becomes a falsifiable, diagnosable claim.

## 1. Concept

### The Metric Hierarchy

Not all numbers are equal. We organize serving telemetry into three layers, each answering a different question and each consumed by a different role:

1. **Workload metrics** — what the system is being *asked* to do. Requests per second (rps) and the token profile (input length, output length, context length). These are the independent variables — the *offered* load; we do not control them, we characterize them. Concurrency is not a workload input: it is a serving-side quantity derived from the arrival rate and the time in system (Little's law), so it belongs with queue depth on the scheduler side, not in this layer. The chain is population (active users) → arrival rate λ → in-flight requests (λ·W) → resident KV slots (Ch 4 §3, §6), and every link after λ is derived. Fig 6.1's workload box therefore carries only offered quantities — the request rate λ (rps) and the token profile. For the canonical enterprise-Q&A RAG workload these are fixed by canonical scenario (Ch 4, Table 4-2): ~10 rps average with ~40 rps peaks, ~9,200 input + ~300 output tokens per request.

2. **Serving metrics** — how *well* the system performs under that workload. Time-to-first-token (TTFT), time-per-output-token (TPOT), inter-token latency, and **goodput** (tokens per second that actually meet the SLO). These are the dependent variables; they are what the SLO is written against — the canonical design budgets are TTFT 1.2 s / TPOT ~25 ms, and the SLOs written against them are p95 TTFT ≤ 2 s and p95 TPOT ≤ 35 ms (Ch 4, Table 4-1 Latency row; Canonical Workload box). **Queue depth** is not one of them: it is a scheduler state, a leading indicator that helps explain these serving metrics.

3. **Resource metrics** — *why* performance is what it is. HBM bandwidth utilization, FLOP utilization / model FLOPs utilization (MFU), KV cache occupancy, and memory pressure. These reveal the binding constraint.

The discipline this chapter works toward: **never jump from a workload metric straight to a serving metric, or a serving metric straight to a hardware conclusion.** The causal direction is *workload → resource demand → serving behavior* (the workload's token profile drives the resource demand; the resource supply shapes how the model behaves). Diagnosis runs the other way: a slow response (serving) is diagnosed by asking whether the kernel is bandwidth- or compute-bound (resource), which is only meaningful given the token profile (workload). Skipping a layer produces superstition — "it's slow, let's buy GPUs" — instead of a mechanism.

### Why the Wrong Metric Persists

Teams default to measuring what they already have dashboards for: model quality (accuracy, ROUGE, benchmark scores) and average latency. Both are dangerously incomplete. Quality is the *goal* and a *feasibility gate* — a fast or cheap architecture that fails the quality bar is disqualified before performance even matters — but it is not the *bottleneck* that explains a resource or latency failure once quality is acceptable; that is the role of the serving metrics. Average latency is a single scalar that hides the tail that actually violates SLAs. The entire thesis of this chapter is that the metric that drives an architecture decision is usually **not** the metric the model card advertises.

## 2. Mental Model

The three metric layers form a **diagnostic chain**, like the layers of the OSI stack in miniature:

- **Workload** is the *traffic* — what we are asked to do.
- **Serving** is the *service* — how well we did it.
- **Resource** is the *engine* — how hard the machine is working, and on what.

(The listing order here is by *role* — independent inputs, dependent outputs, explanatory engine. It is not the causal order: causation flows workload → resource → serving, which is how Fig 6.1 stacks them top to bottom. The two orderings are different and both intentional.)

When something breaks, we read upward: a p95 TTFT breach (serving) forces us to look at the resource layer first (resource: is prefill queuing because we're FLOP-bound?) and then the token profile (workload: did context length grow?). The causal direction follows the system, not the diagnosis: the workload generates resource demand, and the resource supply shapes serving behavior — so when numbers are healthy, the chain shows the system meets the SLO under the observed workload.

The mental model also warns against **one number standing in for many different things**. "Throughput" without a qualifier is meaningless: is it requests per second, tokens per second, or *goodput* — tokens per second that arrived before the SLO deadline? We commit to always qualifying.

## 3. Worked Example

### Latency Is a Distribution, Not a Mean

A very common measurement error is reporting (and SLO-ing) the *average* latency. Figure 6.2 shows a synthetic request stream: the body of requests follows a log‑normal distribution centered near 0.8 s (99% of observations), with a 1% straggler cluster at 5.0 s [ILLUSTRATIVE][ASSUMPTION] (a synthetic mixture, author-chosen). That combination is deliberately *not* a two‑point "99% at 0.8, 1% at 5" distribution; it is a realistic spread, so the percentiles below are read off the plotted histogram rather than guessed. The plotted stream is a synthetic sample of N = 10,000 requests — 99% drawn from a log‑normal with median 0.8 s and log-scale dispersion σ ≈ 0.12 (generated as exp(μ + σZ), with μ = ln 0.8 and Z standard normal), 1% a straggler cluster at 5.0 s — and the percentiles are read by linear interpolation on the sorted sample. The two-point approximation of the mean is
$$
\mathbb{E}[L] \approx 0.99 \times 0.8 + 0.01 \times 5.0 \approx 0.84 \text{ s}
$$
— looks fine. Three *different* quantities circulate in this paragraph, so we fix them once here, at first presentation, because they are not interchangeable. (a) The two-point approximation above substitutes the 0.8 s median for the whole 99% body: 0.99 × 0.8 + 0.01 × 5.0 = 0.842 s (the display above rounds it to 0.84 s). (b) The analytic mean of the mixture as specified is slightly higher, because a log-normal with median 0.8 s and log-scale dispersion σ = 0.12 has mean 0.8 × exp(σ²/2) ≈ 0.8058 s: 0.99 × 0.8058 + 0.01 × 5.0 ≈ 0.848 s. (c) The *sample* mean of this particular draw of N = 10,000 is 0.85 s — the value Fig 6.2 displays — and it is draw-dependent in the same way the sample p99 is: another draw moves the last digit, while the population value does not move. The percentiles below are read off this sample, not off the distribution.

Read off the sample, the long tail looks like this: p50 ≈ 0.80 s, p90 ≈ 0.94 s, p95 ≈ 0.99 s, and p99 ≈ 1.33 s [ILLUSTRATIVE][DERIVED]. Every one of these is a property of the N = 10,000 *sample*, not of the distribution: the population p99 of this 99 % log‑normal + 1 % straggler mixture is 5.0 s. The sample p99 is knife-edge — one straggler moves it. With exactly 100 stragglers (1 % of 10,000) the interpolated sample p99 is 1.33 s. With 101 of 10,000 a straggler sits at rank 9,900 itself, both interpolation endpoints become 5.0 s draws, and the sample p99 is 5.0 s.

*Reproducibility (percentile interpolation).* The p99 position is 1 + (N−1) × 0.99 = 9,900.01, i.e. one hundredth of the way from rank 9,900 to rank 9,901. In this draw the sorted values are rank 9,900 = 1.30 s and rank 9,901 = 5.0 s. Rank 9,900 is the largest non-straggler draw, because the 100 stragglers occupy ranks 9,901–10,000. The interpolated p99 is therefore 1.30 + 0.01 × (5.0 − 1.30) = 1.337 s — the percentile line falls just past the end of the body, in the empty gap between it and the first straggler. The two-decimal display 1.33 s used here and in Fig 6.2 truncates this value; rounded to two decimals it is 1.34 s, so read 1.33 s as a truncation, not a rounding.

The mean hides the tail; percentiles expose it — but notice how far one has to go to expose *this* tail. Under the canonical p95 TTFT SLO of ≤ 2 s, **even this sample's p99 (≈ 1.33 s) still looks healthy — the population p99 is 5.0 s, sitting on the straggler cluster.** Request latency ≥ TTFT, so a p95 TTFT-ceiling line drawn on request latency flags a superset of TTFT violations. The 5 s stragglers are the top 1% of the stream — in this sample they sit *between* the 99th and 100th percentile, so the interpolated p99 line alone does not bring them into view. Only the p99.9 / maximum reading (or the full distribution) surfaces them. This is the sharper lesson: a tail can hide not just behind the mean but behind any single percentile, and the choice of which percentile to SLO against matters. It is why we log the full distribution and also watch the *outlier fraction* (how much probability mass sits beyond the SLO line), not just one percentile.

Why the mean is not a signal. The same request stream of 99% @ 0.8 s + 1% @ 5 s reported as a single number looks healthy. The two-point approximation gives 0.84 s (≈ 0.848 s for the mixture as specified); the simulated stream's *sample* mean is 0.85 s. Yet the population p99 paints a very different picture against the 2 s p95 TTFT ceiling (the SLO itself is stated at p95, Ch 4) — a ceiling above the 1.2 s design budget, not a second budget. Log the distribution; SLO against the percentile.

Apply this to the canonical workload. We budget TTFT ≤ 1.2 s (retrieval ~120 ms + prefill ~1.08 s), with a p95 ceiling of ≤ 2 s that the budget relaxes to. Suppose a flash crowd (the ~40 rps peak) causes prefill requests to queue on a fleet provisioned at the full-utilization compute screen (~19 hosts under Ch 8 §3 case (i), ~22 under case (ii)) — that screen is not an SLO-goodput guarantee, so residual queueing under bursts can still push p95 TTFT above target. If on average the batch is well-behaved, p50 TTFT might sit at ~1.0 s [canonical scenario][ASSUMPTION] — a supposition about a well-behaved batch, not a queueing-model result. But the jobs that arrive behind ~1–2 same-time prefill requests each pay the full 1.08 s prefill of the job(s) ahead of them, so p95 TTFT drifts to ~2.5 s [canonical scenario][DERIVED]: 1.0 s + one full 1.08 s prefill ≈ 2.1 s, and part of a second prefill on top of that ≈ 2.5 s. *(Fleet scope: this 1–2-jobs-ahead illustration is the fleet-sized case. On a single 8×H100 host at the same 40 rps peak, prefill demand is ~18.6× that host's sustained capacity — Ch 8 §3, Table 8-1 — so the queue is unbounded and p95 TTFT grows until admission control intervenes; the 2.5 s figure does not describe that case.)* The *average* says "fine"; the *p95* says "we just violated our SLO." We hence log p50, p90, p95, and p99 independently and run the SLO against the percentile, never the mean. ### Goodput vs Raw Throughput

Deploying a higher-throughput configuration can *reduce* goodput: goodput = raw_rate × compliant_fraction, where the compliant fraction is the share of emitted tokens whose arrival time is within the SLO deadline for their request — so a throughput increase helps goodput only if the compliant fraction holds. Concretely: suppose we enable larger dynamic batching to raise raw tokens/s from 50 tok/s to 70 tok/s, but the batch window pushes p95 TTFT from 1.8 s to 2.3 s — above the 2 s SLO. (Register: the 50 tok/s baseline is Ch 5's single-stream illustrative point and the 70 tok/s figure is a batched configuration. The pair is therefore a cross-register comparison, not a like-for-like batch-to-batch measurement; the goodput arithmetic below holds at either register.) Scenario A [ILLUSTRATIVE][DERIVED]: if all of the extra 20 tok/s land in the tail that misses the SLO, the compliant fraction falls to f = 48 ÷ 70 ≈ 68.6 % (the split is derived below), and goodput is 70 × 0.686 ≈ 48 tok/s — level, not higher. Raw throughput is up 40%; **goodput** (tokens that met the SLO) is unchanged *in this case*, because the SLO-compliant token count did not grow.

The "unchanged" claim holds only when the extra tokens all land in the SLO-missing tail, i.e. the compliant fraction drops proportionally to the raw-rate gain. Scenario B [ILLUSTRATIVE][DERIVED]: if the compliant fraction falls from 96% to 94%, goodput is 50×0.96 = 48 vs 70×0.94 = 65.8 — it *rises* despite the p95 breach. Scenario C [ILLUSTRATIVE][DERIVED]: if the compliant fraction falls to 65% — a constructed split, not a measured stream — goodput is 70×0.65 = 45.5 tok/s — *below* the 48 tok/s baseline. The dividing line is the compliant fraction f at which the throughput gain cancels: 70 × f = 48, i.e. f ≈ 68.6%, so goodput falls only when the compliant fraction drops below ~69%. That is what Scenario A's "unchanged" result requires, and it is a 27-point collapse from 96%, not the 2-point drop of Scenario B. The three scenarios are therefore comparable only when each states its f: ~68.6% leaves goodput unchanged, below ~68.6% reduces it, 94% raises it. A p95 breach is a *configuration-level* acceptance signal. Request-level SLO-goodput is a separate measurement: compute it from the compliant fraction, not from the p95 alone.

*Scope note: the 50→70 tok/s pair is a cross-register comparison — 50 tok/s is Ch 5's single-stream illustrative point and 70 tok/s is a batched configuration — and both sit in the same low-batch decode range (Ch 5's illustrative basis, ~14–20 ms/token across the 50–70 tok/s range; canonical batch-1 is 40 tok/s at 25 ms/token), not the host's aggregate serving rate (Ch 15: ~8.5K tok/s prefill-side, ~35,000–56,000 tok/s batched) — the goodput argument holds at any consistent operating point.*

Goodput is the metric the customer experiences; raw throughput is what the GPU achieves. The architect optimizes goodput. This is why "faster" hardware or bigger batches do not trivially mean a better system.

### Detecting the Regime: Bandwidth-Bound vs Compute-Bound

The most decision-relevant resource question is: is this layer bandwidth-bound or compute-bound? We recall the arithmetic from Chapter 2:

- **Decode is HBM-bandwidth-bound at low batch.** The shard-invariant reason comes first: at batch 1 decode's arithmetic intensity is ~1.0 FLOP/byte (140 GFLOP / 140 GB), far below the ~295 FLOP/byte roofline ridge — this low intensity, not any single device's bandwidth total, is why decode is starved for weights regardless of sharding. Generating one token needs a full forward pass over the 70B weights of the **canonical 80-layer, hidden-8192, full-MHA 70B reference** = 140 GB (FP16) of reads per token — a **batch-1-equivalent** idealized weight-streaming read (one request's full weight pass), not a measured bytes-physically-read figure. As a concrete single-device illustration: within a ~25 ms TPOT budget, 140 GB / 0.025 s ≈ **5.6 TB/s** (batch-1-equivalent) exceeds an H100's ~3.35 TB/s peak [1P][FACT]. **Scope warning: this 5.6-vs-3.35 TB/s comparison is an *illustrative single-device roofline* argument, not the canonical 8×H100 host's actual deployment verdict.** The 5.6 TB/s is a *theoretical demand* that holds at batch 1 only, where one token pays the full weight read: the weights amortize across the b tokens of a step, so the required weight-read rate falls roughly as 140 GB ÷ (b × 0.025 s) — the 5.6>3.35 shortfall characterizes a batch-1 stream, not a batched server. Two scope notes keep this honest. First, 5.6 TB/s is the **aggregate** model-wide weight-read rate for a hypothetical single-device implementation; under tensor parallelism (the canonical 8×H100 host) the 140 GB is sharded, so each GPU only needs ~0.70 TB/s against its own 3.35 TB/s (~21% achieved HBM utilization — 0.70 TB/s ÷ 3.35 TB/s = 20.9%: the canonical 25 ms TPOT is a *budget* covering TP collectives, kernel inefficiency, sampling and scheduling, not a bandwidth-saturated point) — the single-device 5.6>3.35 bound does not itself show a per-GPU bandwidth shortfall. Second, the intensity reason stated first above is what makes this a roofline classification rather than a device verdict (the roofline and its ridge are developed in Ch 8). So the honest statement is: decode is memory-bound because its intensity is low and batching raises it, not merely because an aggregate 5.6 TB/s exceeds one GPU's 3.35 [canonical scenario][DERIVED]. (This is an operating-point property, not an identity, and it is a **weight-only** statement: at high batch decode climbs the intensity slope. With the canonical 9.2K KV re-read included, use one denominator rule — count the weight bytes and the KV bytes whenever both terms are in the numerator. At batch 1 the intensity is 164.1 GFLOP (140 projection + 24.1 attention; the attention term is 4·L·d_model·n_layers = 4 × 9,200 × 8,192 × 80 ≈ 24.1 GFLOP) ÷ (140 GB weights + 24.1 GB of canonical 9.2K FP16 KV) ≈ **1.0 FLOP/byte**. At batch 32 it is 32 × 164.1 = 5,251 GFLOP ÷ (140 + 32 × 24.1 = 911 GB) ≈ **5.8 FLOP/byte**, and it approaches the KV-only asymptote 164.1 ÷ 24.1 ≈ 6.8 FLOP/byte as batch grows. Every one of these values is far below the ~295 FLOP/byte ridge, so decode stays bandwidth-bound across this batch range — Ch 8.)

- **Prefill is compute-bound at the canonical long-prompt operating point.** The reason prefill lands on the compute plateau of the roofline is its high arithmetic intensity: the FLOPs per byte moved are far above the ~295 FLOP/byte ridge point (developed in Ch 8), so the compute units — not the HBM weight stream — are the binding resource. Only after establishing that regime do we check the deadline: the prefill pass for 9,200 input tokens costs ≈ 2 ×70e9 params × 9.2e3 tokens ≈ **1.29 PFLOP of linear (2NL) FLOPs** (the quadratic attention term adds ≈ 0.2 PFLOP at 9.2K — ≈ 1.5 PFLOP full-square total, Ch 22 Table 22-1), which against the ~1.08 s prefill budget implies a required rate of ≈ 1.19 PFLOPS — above a *single* H100's ~0.989 PFLOPS dense BF16 peak (FP16/BF16: same H100 peak) (1.19 > 0.989). But that 1.19-vs-0.989 comparison is a **single-device deadline/capacity illustration**, not the evidence that prefill is compute-bound: on the canonical 8×H100 host the aggregate peak is ~7.9 PFLOPS, so the host comfortably satisfies the rate — the "single H100 can't prefill a 9.2K prompt in 1.08 s" conclusion is about whether one arbitrarily-chosen GPU can meet the deadline, not about the kernel's roofline regime. Prefill being *compute-bound* (rather than bandwidth-bound) follows from its high arithmetic intensity, not from the 1.19-vs-0.989 comparison. [canonical scenario][DERIVED]

At the resource layer, the tell is utilization: a decode kernel pinned at ~95% of HBM bandwidth / ~30% of FLOPs [ILLUSTRATIVE][ASSUMPTION] — a hypothetical telemetry signature — is bandwidth-bound; a prefill kernel with ~90% FLOP utilization [ILLUSTRATIVE][ASSUMPTION] is compute-bound. **The same hardware, the same model — the boundary flips between prefill and decode.** This is precisely why Splitwise/DistServe (and Mooncake's KV-centric disaggregation) split prefill from decode onto different pools [S4][1P][FACT]: the bottleneck-regime difference is the primary motivation for disaggregation — see §6.6 for the conditions under which it pays. ### Reading Telemetry Into a Decision

A concrete dashboard-read → decision trace. We see: p95 TTFT climbing (serving), prefix-cache hit ratio low (resource: FLOP/reuse — prefill recomputation), and prefill queue depth growing (scheduler state — a leading indicator of the serving symptom, per §6.1.1). Workload is unchanged. Reading up the chain: low prefix-cache hit means many independent 9.2K prefixes are being prefill-processed from scratch on the ~40 rps peak — each ~1.29 PFLOP (case (i), linear-only) — aggregate prefill demand at the 40 rps peak is 40 × 1.29 ≈ 51.6 PFLOP/s against the 8×H100 sustained prefill capacity of ~2.77 PFLOP/s (35% MFU, Ch 8 §3, Table 8-1) — ~18.6× oversubscribed (the datasheet-peak ~7.9 PFLOPS gives ~6.5×, a theoretical ceiling only; under case (ii), full-square attention, the same 40 rps traffic peak at the same 35% MFU planning rate screens ~22 hosts — Ch 8 §3, case (ii)), consistent with the Ch 8 §3 case (i) 19-host screen at this peak, so the prefill queue grows until backpressure or prefix caching intervenes. The decision: enable prefix / RadixAttention-style caching (SGLang) or Automatic Prefix Caching (vLLM) so the byte-identical shared prefix is reused instead of re-prefilled — in the canonical workload (1,200 prompt + 8,000 per-query retrieved, Ch 4 Table 4-2) the byte-identical share is at most the fixed system/instruction portion of the ~1,200-token prompt, because the 8K retrieved block differs per query and the 1,200-token slot carries the query itself (Ch 4 Table 4-1), so ~13% of prefill FLOPs (the whole-slot case) is an upper bound on the cacheable fraction; prefix caching is therefore a partial mitigation, not the fix for the 40 rps prefill queue (§6.7 keeps the actual reduction [UNRESOLVED]). ## 4. Measurement

Three practical habits anchor the architect:

1. **Instrument the hierarchy, not just the app.** Deploy counters at all three layers from day one — rps and token profile (workload); TTFT/TPOT/goodput percentiles (serving); queue depth as a separate scheduler-side counter that explains them (§6.1.1); HBM bandwidth, FLOP/MFU, KV cache occupancy, memory pressure (resource). A system that only logs serving metrics cannot tell *why*; one that only logs resource metrics cannot tell *what it was asked*.

2. **Always qualify "throughput."** rps ≠ tokens/s ≠ goodput. The same number, three stories. State the SLO window (p95 ≤ 2 s TTFT) before quoting any rate, or the rate is meaningless.

3. **Log the distribution.** Capture p50/p90/p95/p99 for every latency metric, and the full token-length distribution (a 32K-tail context is a different workload than a 9.2K average). The mean is a summary, not a signal.

These habits answer the book's recurring question — *what would we actually measure here?* — with three layers of counters at the edge, before any architecture decision is committed.

## 5. Common Mistakes

- **SLO-ing the average.** A ~0.85 s mean (the figure's simulated stream; the two-point analytic approximation gives ~0.84 s — the figure's displayed value is used here) hides a 5 s tail. SLO against p95/p99, and watch the outlier fraction, not the mean.
- **Optimizing raw throughput when the SLO windows it.** Bigger batches raise raw tokens/s but can push TTFT past its deadline, erasing the throughput gain. Optimize goodput.
- **Jumping straight to "buy more GPUs."** A bandwidth-bound decode and a prefill-cost problem need different fixes; without the resource layer we guess.
- **Treating hardware peak as a ceiling we can hit.** H100's 3.35 TB/s is the theoretical HBM peak; real memory-bound kernels realize a fraction of it. Design headroom against real utilization, not the spec sheet.
- **Conflating model-quality metrics with serving metrics.** Accuracy is the goal; TTFT is the constraint. A slow, accurate model fails its SLO just as surely as a fast, wrong one.

## 6. Architecture Consequence

The metric hierarchy directly dictates architecture. For the canonical workload:

- **Bandwidth-bound decode + compute-bound prefill ⇒ P/D disaggregation** (Splitwise/DistServe/Mooncake) is a candidate remedy at scale when prefill/decode imbalance is large, scale is sufficient, and KV-transfer + extra pool/scheduling costs stay below the interference savings — costs include KV migration, added failure domains, and pool sizing; compare against colocated scheduling with chunked prefill. [S4][1P][FACT]
- **Repeat-prefix RAG ⇒ enable prefix caching** (RadixAttention/APC), which reuses the shared prompt prefix of the 9.2K prefills (~13% of prefill work in the canonical workload — an upper bound, §6.3.4; the 8K retrieved block is query-specific) and so partially defends the p95 TTFT against the 40 rps peaks. [S3][1P][FACT]
- **KV cache pressure ⇒ quantize or offload KV.** FP8 KV = raw tensor byte-halving = 1.31 MB/token (exactly 50% of FP16) [canonical scenario][DERIVED]; any block-allocation/metadata overhead is NOT vendor-measured here and must be filled by a deployment benchmark. (The vLLM FP8-KV blog's '54%' [S6] is a decode inter-token-latency (ITL) slope, not a memory ratio or footprint coefficient — on this book's own reading of that post's Table 3, not a vendor-stated interpretation [1P][HYPOTHESIS]; re-verify it against the post, as Ch 1 does at its KV-cache section.) And the vLLM KV-offloading connector (vLLM Team, "Inside vLLM's New KV Offloading Connector," 2026-01-08, vllm.ai/blog/2026-01-08-kv-offloading-connector [S7][1P][FACT] — a first-party vendor report, not an independent measurement) cuts TTFT by 2–22× in one warm-cache-hit/reuse benchmark: a single-request TTFT micro-benchmark on Llama-3.1-8B-Instruct at H100, in which the post states that the range depends on prompt size. That is a TTFT metric for cache-hit requests, not a generic cold-cache improvement — both are memory-layer fixes the telemetry would call for when KV occupancy nears capacity.
- **Speculative decoding where decode bandwidth is the wall** — the DFlash paper (Chen et al., "DFlash: Block Diffusion for Flash Speculative Decoding," ICML 2026; arXiv:2602.06036 — first-party to its authors) *reports* over 6× lossless acceleration, up to 2.5× over EAGLE-3, in its evaluated configurations [S5][1P][FACT], because it reduces weight reads per accepted token. These are paper-reported results, not portable serving-speed figures: treat them as performance claims to re-measure on the target workload, not as a guaranteed speedup.

## 8. End-of-Chapter Mini-Case: The Post-Lunch Slowdown: Reading Telemetry Up the Chain

An on-call architect is paged: "the internal Q&A tool got slow after lunch." The dashboard shows rps at the ~40 rps peak (workload, up from the 10 rps baseline), p95 TTFT at 2.4 s against a 2 s SLO (serving, breached), and KV cache occupancy at 85% (resource, memory pressure) with low prefix-hit ratio (resource, FLOP/reuse — prefill recomputation). Following the chain rather than guessing, the architect reads: an arrival-rate spike (workload, up to the ~40 rps peak) with repeated full 9.2K prefills (low prefix hit) drives prefill FLOP demand several times past the host aggregate capacity (compute-bound). The deployment had passed the single-request residency check — ~140 GB weights + ~24.9 GB KV ≈ 165 GB < 640 GB (Ch 7) — but was never sized for concurrency or for compute, let alone for the lunch peak: 10 rps already demands 10 × 1.29 ≈ 12.9 PFLOP/s of prefill, ≈ **4.7 host-equivalents** of one 8×H100 host's ~2.77 PFLOP/s sustained prefill capacity (Ch 8 §3, Table 8-1), and the 40 rps peak demands 40 × 1.29 ≈ 51.6 PFLOP/s ≈ **18.6 host-equivalents**. On the single host this mini-case assumes (deployed host count H = 1) that is a ~4.7× oversubscription at baseline and 18.6× at the peak (case (i), linear-only FLOP count); the fleet oversubscription at peak is 51.6 ÷ (H × 2.77) = 18.6/H, so an H-host fleet sized at 10 rps — H ≈ 6, set by the KV-residency screen rather than by prefill (86 in-flight ÷ 17 slots = 5.06 → 6 hosts, Ch 4 §3) — would be ~3.1× oversubscribed at the peak (51.6 ÷ (6 × 2.77) ≈ 3.1). The diagnosis is therefore stated against a named denominator: the peak demands ~18.6× *one host's* prefill capacity (18.6 host-equivalents); prefix caching is a partial mitigation (~13% of prefill FLOPs — an upper bound, §6.3.4: the cacheable fraction is smaller once the query tokens are excluded), not the fix. The resolution is capacity/scheduling — additional hosts, chunked prefill, admission control/backpressure, or P/D disaggregation. The architect re-checks the dashboard an hour later on the two instruments that would carry the attribution — the prefix-hit ratio and the prefill queue depth. The p95 TTFT reading there is *expected* to return under 2 s [ILLUSTRATIVE][HYPOTHESIS]: that is a screen-based expectation, not an observation, and the Ch 14 benchmark is what would confirm it. The screens attribute the repair to the *capacity/scheduling* change rather than to the cache: a ~13% prefill reduction alone cannot close an ~18.6 host-equivalent gap: against ~2.77 PFLOP/s of sustained capacity, the residual demand is **at least** ~44.9 PFLOP/s (51.6 × (1 − 0.13) — this assumes the ~13% upper bound is fully achieved, so the true saving is ≤ 13% and the true residual is ≥ 44.9), i.e. ≥ ~16.2 host-equivalents. That figure is bound-derived, not measured. Hosts were raised from H = 1 to H = 21. That is the capacity floor, which is the max of the named screens, not the prefill compute screen alone: case (i)'s prefill screen needs ⌈18.6⌉ = 19 hosts, but the KV-residency / Little's-Law screen needs ⌈344/17⌉ = 21 hosts at the peak and therefore binds (Ch 8 §3, case (i); Ch 17). That slot screen runs on this mini-case's own host geometry, not on an imported one: the residency check above already fixes the host at ~640 GB and the request slot at ~24.9 GB (9.5K tokens), so the same 436 GB KV budget and 17-slot whole-context ceiling apply (640 − 140 GB weights − ~64 GB runtime ≈ 436 GB; 436 ÷ 24.9 ≈ 17.5, floored to 17 — Ch 4 §6; Ch 17). H = 21 therefore follows from this case's own 344 in-flight peak, and it agrees with Ch 17's canonical screen because both use that one geometry; it is an ANALYTICAL floor screen, not a measurement, and not a benchmarked fleet size (Ch 17). At 21 hosts the 344 in-flight peak requests fit the 21 × 17 = 357 resident slots, and the peak prefill oversubscription falls from 18.6× to 51.6 ÷ (21 × 2.77) ≈ 0.9× (measured against the 21-host prefill capacity and before any cache saving; the ≤ 13% prefix-cache reduction can only lower it, so 0.9× is an upper bound on the post-cache ratio at this host count); the design intent is that admission control holds the residual queue inside the 2 s p95 TTFT SLO, with the ~13% prefill reduction from prefix caching contributing on top. That p95 restoration remains an [ILLUSTRATIVE][HYPOTHESIS] — an expectation from the analytical screens above, not a measurement, pending benchmark confirmation (Ch 14 measures the distribution; Ch 17 recomputes the fleet) — while goodput restoration is not claimed at all, because goodput is raw rate × compliant fraction and the p95 alone does not establish the compliant fraction. The asymmetry is deliberate: the p95 screen is named, the goodput claim is withheld.
