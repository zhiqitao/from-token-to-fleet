# Chapter 26 — The Solution Architect's Toolkit + Patterns Library

## The Architect's Question

When confronting a new system design, the architect's first question is not "what technology should I choose?" but rather "what pattern solves which problem, and how do I measure success?" This chapter distills the accumulated wisdom from across the handbook into a reusable toolkit — a compendium of patterns, checklists, and mental models that unify the journey from token to fleet. Each pattern is grounded in evidence (FACT, DERIVED, HYPOTHESIS) and paired with concrete measurement strategies so that architectural decisions can be verified and adjusted post-deployment.

## 1. Concept

The Solution Architect's Toolkit answers three concerns — scalability, reliability, and observability — and is organized as pattern templates plus measurement rather than as three separate taxonomies. Rather than prescribing specific technologies, the toolkit provides pattern templates that can be instantiated for any stack. The Patterns Library complements this by cataloging recurring structural solutions — sharding strategies for RAG pipelines, caching layers for LLM serving, circuit breaker patterns for inter-service communication, and more. Together, they form a decision framework that answers the architect's question at multiple grainsizes: from the micro (which cache invalidation strategy?) to the macro (how does sharding affect fleet-wide latency?).

## 2. Mental Model

The central mental model is the **Pattern-Measurement-Feedback Loop**. Every pattern in the library is paired with:

- **FACT** — a verified runtime quantity (e.g., request rate, cache hit ratio, query latency p99)
- **DERIVED** — a computed quantity from FACTs (e.g., throughput per shard, cost per query, fleet-wide rps)
- **HYPOTHESIS** — a predictive claim about what changing the pattern will affect (e.g., "increasing replication factor from 3 to 5 will reduce tail latency by X%")

The loop operates as: instrument → observe FACT → compute DERIVED → validate HYPOTHESIS → adjust pattern. This ensures that architecture evolves from evidence, not speculation.

**What a [1P] tag does and does not mean.** The statuses above (FACT / DERIVED / HYPOTHESIS) describe what a number *claims to be*; a separate *provenance* axis describes **where it came from**. **[1P]** marks a first-party **source** — the original method paper authored by the method's creators, or a hardware-vendor specification (technical report, model card, or official documentation). It names *whose* claim a number is; it does **not** by itself assert a validated deployment benchmark. Keep the four categories distinct: (a) an original method paper by the method's creators, (b) a hardware-vendor specification, (c) a third-party evaluation (the book's [2°] secondary provenance), and (d) an own measured run ([LAB]/[MEASURED] — Axis-1 provenance plus the Axis-3 measurement status, both defined in the Sources, Method, and Reproducibility chapter). Of these, [1P] covers (a) and (b) only — a first-party source is a vendor or paper author's figure, which must be re-verified against the current source or re-measured on the architect's own hardware before it is treated as a validated deployment result. Note that the canonical 70B teaching model is *not* a [1P] model: being constructed (Ch 4, Table 4-2) it carries [ILLUSTRATIVE][ASSUMPTION], reserving [1P] for named, traceable first-party specifications.

## 3. Worked Example — Capstone Scenario

Take the canonical deployment: ~2,000 registered users with ~5% concurrently active at peak (~100 concurrent *users*, a population measure), RAG Q&A over a 70B dense FP16 model. The architect faces three interlocked questions: how to scale inference, how to cache retrieved context, and how to keep the model-service latency under its SLO — here the model-service latency SLO is defined as **time-to-first-token (TTFT)**, and for the *retrieved-context/short-prompt* leg of this scenario we adopt a *stricter* p99 ≤ 800 ms TTFT target (a scenario input, not the canonical p95-TTFT ≤ 2 s of Ch 4: the capstone deliberately uses a harder tail target to exercise the patterns). This is a **TTFT** budget, not an end‑to‑end one — the canonical request's total end‑to‑end time is ~8.6 s (1.08 s prefill + ~7.5 s decode of 300 output tokens), and the per‑host ceiling is ~2.0 req/s (Ch 17/20), both of which still hold here. Do not read the sub‑second capstone figures as end‑to‑end request latency. (All the other numbers below are the canonical values established in Parts I–V — Ch 4's workload, Ch 7/15's KV and memory figures, Ch 17's fleet sizing — recalled here rather than re-derived, and this capstone shows how the toolkit's patterns compose them.)

**Pattern A — Inference Sharding.** [canonical scenario][DERIVED] — model FLOPs/token = 2N = 1.4 × 10¹¹; KV bytes/token = 2.62 MB (Ch 7, 22). The 70B model at FP16 requires ~140 GB of weights [ILLUSTRATIVE][DERIVED] — 70 × 10⁹ parameters × 2 B/parameter = 140 GB, the footprint Ch 22 and §25.4 also derive. Following the canonical setup, one serving host is an 8×H100 80 GB node, which dedicates ~140 GB to weights and leaves the rest of the 640 GB pool for KV cache and runtime. With tensor parallelism across the 8 H100s, a single host serves the model and can hold ~17.5 concurrent 9,500-token requests within the canonical ~436 GB KV budget from Chapter 15. [canonical scenario][DERIVED] — with the 8-way tensor parallelism across the node, decode latency is bandwidth-bound, so per-token throughput scales with the node's aggregate memory bandwidth rather than 8× the single-GPU rate. [canonical scenario][HYPOTHESIS] — adding a second host and load-balancing requests across two replicas yields < 5% additional per-request latency improvement because the bottleneck is concurrency/KV residency, not per-host throughput.

**Pattern B — Semantic Response Cache.** [ILLUSTRATIVE][ASSUMPTION] — 35% of queries repeat within 5-min windows (a scenario input to be measured on real traffic). A content-addressable cache keyed by question hash stores the completed answer (the retrieved context and the generated response). [canonical scenario][DERIVED] — a cache hit ratio of 35% reduces the number of requests that reach the LLM engine by 35%, directly lowering generation compute and operational cost; the embedding/retrieval step is also skipped for cache hits. [canonical scenario][HYPOTHESIS] — expanding the cache TTL from 5 to 15 minutes increases hit ratio to ~55% with negligible staleness risk, because user questions in a support session repeat within the same session.

**Pattern C — Circuit Breaker.** [ILLUSTRATIVE][ASSUMPTION] — model-service latency p99 degrades past the 800 ms SLO under concurrent load; downstream network jitter p99 = 120 ms (scenario inputs to be measured). [canonical scenario][DERIVED] — the diagnosed symptom: when a host's arrival rate exceeds the ~2.0 req/s per-host ceiling (Ch 17/20) — as the canonical ~40 rps peak (Ch 4) would if concentrated on one host — the request queue grows and queueing delay alone pushes TTFT p99 past the 800 ms SLO, the condition Pattern C exists for; Table 26-2's ~7% fallback rate is the modeled share of requests shed to the intent classifier during such excursions (FACT target < 10%). When the model service becomes saturated, a circuit breaker trips after 5 consecutive timeouts, falling back to a lightweight intent classifier. [ILLUSTRATIVE][ASSUMPTION] — circuit breaker activation reduces tail latency for remaining requests by 35% because the system sheds load before the model queue fills. [canonical scenario][HYPOTHESIS] — a grace-period of 2 seconds before auto-recovery prevents thrashing when load spikes are transient.

**Capstone Execution.** The architect instruments all three scenario quantities, observes the derived quantities in real time, and validates each HYPOTHESIS against measured traffic. The result: one 8×H100 serving host + a 35% semantic response cache + circuit breaker yields an illustrative **p99 TTFT ≈ 250 ms at ~48% lower generation cost** versus the ~450 ms uncached single-node baseline (one 8×H100 host, already tensor-parallel across its 8 GPUs) — the single capstone configuration, derived step by step in §26.8 and recorded as Table 26-2 (scenario outcome, not a measured benchmark). The Pattern-Measurement-Feedback Loop confirms the hypothesis that caching + load shedding is net positive, and the architect documents the configuration as a reusable pattern instance.

**Alternatives considered.** Two obvious alternatives were rejected against the canonical constraints. *Prefix caching alone* reuses prefill compute behind an exact-prefix match but still generates the answer, so the 35% repeat population keeps paying full decode — it does not skip the generation the semantic cache skips. *A second serving host with load balancing* is rejected because the bottleneck is concurrency/KV residency, not per-host throughput: Pattern A's own hypothesis puts the gain at < 5% per request, so a second host doubles the fleet for single-digit improvement. *Deeper continuous batching on the single host instead of sharding* raises throughput by lengthening the in-flight queue, adding queueing delay exactly where the p99 TTFT SLO binds (Ch 8's decode economics; Ch 15's congestion check). Sharding + semantic cache + circuit breaker wins because it attacks the baseline's own terms — model compute (sharding), the retrieval step (cache hits), and tail queueing (circuit breaker) — that each rejected option leaves in place.

## 4. Measurement

Quantitative verification is non-negotiable. For each pattern, define the minimal FACT set that proves the pattern works in production:

**Table 26-1** — The FACT set to measure for each pattern.

| Pattern | FACT 1 | FACT 2 | FACT 3 |
|---|---|---|---|
| Inference Sharding | GPU utilization % | per-GPU token latency p99 | All-Reduce time |
| Semantic Response Cache | hit ratio @ TTL=T | stale read rate | cache memory pressure |
| Circuit Breaker | timeout count / 30s | fallback activation rate | recovery grace-period latency |

Measurement must be continuous, not ad-hoc. Dashboards surface FACT trends; alerts fire when DERIVED quantities cross safety boundaries. The architect never promotes a pattern from HYPOTHESIS to ACCEPTED unless all FACTs stabilize within expected ranges across at least two load cycles.

## 5. Common Mistakes

- **Mistake 1: Measuring only HYPOTHESIS outcomes.** Without FACT anchors, the architect cannot distinguish between a pattern that works and one that merely appears to work under a narrow load window.
- **Mistake 2: Over-engineering before FACTs exist.** Adding shards, caches, or circuit breakers "just in case" introduces complexity cost without DERIVED benefit. Wait for the FACT to signal the need.
- **Mistake 3: Ignoring the cost DERIVED.** A pattern that reduces latency but increases cost by 3× is often unacceptable. Measure cost per query as a first-class FACT.
- **Mistake 4: Circular HYPOTHESIS validation.** Self-confirming predictions (e.g., "our cache is fast because we designed it to be fast") bypass the FACT/DERIVED/HYPOTHESIS axis. Always validate against observed FACTs.

## 6. Architecture Consequence

The toolkit's patterns do not exist in isolation. Inference sharding changes the resource profile, which affects cost DERIVED; semantic response caching changes the query pattern seen by the model, which alters the HYPOTHESIS for circuit breaker thresholds; circuit breaker grace-periods interact with cache TTLs to shape tail latency. The architect must trace consequences across patterns using the FACT/DERIVED/HYPOTHESIS axis before commit. A change that looks beneficial in isolation may degrade fleet-wide metrics when patterns interact.

## 7. What We Still Don't Know

- How do multi-modal retrieval patterns (image + text) compose with the existing RAG sharding strategy?
- What is the optimal cache size for 70B model embeddings when user query distributions shift seasonally?
- Can circuit breaker thresholds be auto-tuned from FACT streams without manual intervention?
- How does fleet-wide model versioning interact with per-shard caching, and what FACTs govern safe rollouts?

These open questions define the next research cycle. Each is framed as a HYPOTHESIS waiting for FACT instrumentation.

## 8. End-of-Chapter Mini-Case: The Capstone: Composing the Patterns

**Scenario.** A growing AI startup moves from a single-node prototype to a fleet serving ~3,000 users. The initial deployment is a 70B FP16 model on a single 8×H100 node (the canonical host). Note the per‑host ceiling: with the canonical ~8.6 s service time and C ≈ 17.5 KV‑resident requests, one host serves ~2.0 req/s (Ch 17/20) — so the figures below are expressed as **TTFT p99** on that host (the sub‑second latencies are time‑to‑first‑token, not end‑to‑end), and the rps is the ~2 req/s the host can actually sustain, not a multiple of it.

**Step 1 — Instrument.** FACTs collected: request rate ~2 rps (within the ~2.0 req/s per‑host analytical planning ceiling), GPU utilization 45%, per-query latency breakdown for a *baseline* (uncached) request: model compute 320 ms, I/O 80 ms, retrieval 50 ms — the RAG retrieval step every request pays. The baseline has **no cache installed**, so there is no cache-*miss* path in it; the 50 ms is plain retrieval, and Pattern B's hit path later covers the same ground (retrieval + lookup) without the engine. These components sum to a **~450 ms baseline TTFT**, which the capstone uses directly as the baseline **p99** scenario value (a scenario input, not a derived quantile of a distributed sample; a real baseline p99 must come from a measured latency distribution). Note the component values are *representative worst-case* estimates for a baseline request, and the ~450 ms is therefore the baseline TTFT figure used throughout; the per-query values are not a p99 of a separate measured distribution. Because the 50 ms retrieval term is part of the baseline, the headline **−44%** is measured against the full 450 ms path; excluding that term entirely (a 400 ms baseline) would report (400 − 250) / 400 = **37.5%** instead.

**Step 2 — Pattern Apply.** The architect applies Pattern A (inference sharding across an 8×H100 node) and Pattern B (semantic response cache with 5-min TTL). [canonical scenario][DERIVED] — sharding distributes the model across the node so decode lands in the bandwidth-bound regime; cache hit ratio 35% reduces the number of requests that reach the model engine from ~2.0 rps to ~1.3 rps (2.0 × (1 − 0.35) = 1.3). The TTFT and cost figures below are *scenario estimates* for this illustrative configuration, not measured values. **A weighted average of component latency values is a mean, not a quantile, so the capstone separates the two.** Under the transparent two-point model — a cache hit returns at a fixed ~50 ms (retrieval + cache lookup, no LLM prefill), and a cache miss is served by the engine at ~250 ms (a scenario value after the 35% lower arrival rate has settled the prefill queue) — the pooled latency has the CDF $F(50)=0.35$, $F(250)=1.0$. Its **mean** is $0.35\times50 + 0.65\times250 = 180$ ms, but its **p99 is 250 ms** (because the 0.99 quantile falls in the miss population: $0.35 < 0.99 \le 1.0$). So **mean TTFT ≈ 180 ms**. **p99 TTFT ≈ 250 ms** (the miss value, not a blend). **−44% TTFT** against the ~450 ms uncached p99 baseline — $(450-250)/450 \approx 44\%$. **−48% generation cost** — the admissible savings decompose as approximately $0.35$ (cache-hit queries at near-zero marginal generation cost) $+ 0.65\times0.20$ (the 65% that generate, at ~20% lower per-token cost from deeper continuous batching on the already-sharded engine) $= 48\%$. The previously-quoted ~55% included a separately-priced skipped-embedding saving that is not part of this cost ledger, so it is not used. These are *illustrative* scenario numbers to show how a hypothesis is formed; a real deployment must measure the actual cache-hit latency *distribution* (not a point mass), the prefill queue at 1.3 rps, and the per-query cost, and the three gains (cache, sharding, retrieval-skip) are *not* independent — they compound on the same request path, so they must not be added as if separable. The reproducible two-point model that yields these numbers is `render/capstone_calc.py`.

**Step 3 — Validate.** [canonical scenario][HYPOTHESIS] — "sharding + caching will keep TTFT p99 < 300 ms as the fleet grows from the canonical ~2,000 users to the capstone's ~3,000 users (1.5× — already ~3,000, not 3×)." Suppose a staged load test at ~3,000 users (the capstone's fleet size) reports TTFT p99 = 285 ms and cost per query down 48% — in this scenario these are illustrative values to show how a hypothesis is tested, not a real experiment the book ran. The hypothesis is accepted only on a genuine load test's numbers.

**Step 4 — Document.** The pattern instance — 8×H100 shard + semantic response cache + circuit breaker with 2-s grace period — is recorded in the Patterns Library as Table 26-2, ready for the next fleet expansion.

**A note on utilization targets.** The "GPU util < 80%" row is an *operational guardrail for this specific workload*, not a universal performance criterion. A GPU has many utilization figures — SM utilization, tensor-core utilization, HBM bandwidth utilization, NVLink utilization, memory-capacity occupancy — and which one matters is set by the workload's dominant constraint, not by the hardware (Ch. 8). Under an SLO-satisfying state, a GPU can sit at very different utilizations depending on whether the workload is prefill-bound (compute) or decode-bound (bandwidth/memory). The architect's question is therefore not "is utilization high enough?" but **"which resource is saturated when the SLO is satisfied, and does the pattern keep the fleet the right side of that saturation?"** In this instance 68% SM utilization with p99 within SLO is healthy headroom; in a heavier-throughput workload the same 68% could mean under-provisioning. State the SLO-bound resource, not a bare percentage.
