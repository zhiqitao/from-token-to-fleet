# Chapter 17 — From Server to Fleet

## The Architect's Question

Having established the single-host serving model — a 70B FP16 model on 8×H100 serving the canonical workload (Ch 4, Table 4-2) at ~10 rps average / ~40 rps peak — the natural next question is: when does one host cease to suffice, and how do we scale to a fleet? This chapter answers the architect's question: at what point must we move from a lone server to a coordinated fleet, and what are the quantitative trade-offs of that transition?

## 1. Concept

The transition from a single-server deployment to a fleet is not a qualitative leap but a quantitative threshold crossing. In the single-server model, all request routing, load balancing, and health monitoring occur within one process on one machine. The architect thinks in terms of request-per-second capacity, GPU memory utilization, and inference latency on that one host. As traffic grows, the single host hits limits in three domains: computational throughput (tokens/sec), GPU memory capacity, and inter-request interference (contention for shared resources such as NVMe I/O, PCIe bandwidth, and CPU). When any of these limits is breached, the fleet model introduces multiple identical hosts behind a load balancer, each independently serving a slice of the total traffic. The fleet model adds three new architectural ingredients: (a) a load balancer that distributes requests across hosts, (b) cross-host communication patterns when a request spans multiple machines, and (c) capacity planning that accounts for redundancy, failover, and the diminishing returns of horizontal scaling. The key insight is that horizontal scaling transforms per-host limits into system-wide capacities, but at the cost of added coordination overhead, state synchronization, and network budgeting.

## 2. Mental Model

We visualize the fleet as a two-level hierarchy. At the top level, a load balancer — either hardware (L7 switch) or software (NGINX, HAProxy, Cloud Load Balancer) — accepts inbound requests and routes them to one of N backend hosts. Each backend host runs an identical copy of the model and serves requests independently. At the bottom level, each host operates exactly as the single-server model does: a model engine accepting prompts, producing completions, and returning tokens to the load balancer, which forwards the response to the client.

The mental model introduces two new invariants. First, the **throughput invariant**: total system throughput ≈ N × throughput_per_host, reduced by a factor ρ that captures load‑balancer overhead, health‑check traffic, and imperfect distribution (typically ρ ∈ [0.85, 0.98] depending on LB sophistication). Second, the **memory invariant**: total GPU memory across the fleet is N × memory_per_host, but the per-host memory available for model weights and KV cache remains the same as the single-host case. The fleet does not increase the per-host model size; it increases the aggregate number of concurrent requests the system can serve by parallelizing across hosts.

A critical detail is the **session-affinity** decision. If user sessions must maintain conversation state (KV cache, accumulated tool outputs, retrieval context), the load balancer must route subsequent requests from the same user to the same host (sticky sessions). This reduces cross-host communication but limits the effective parallelism, because a popular user can pin a single host to capacity while other hosts stand underutilized. If sessions are stateless (the model is reloaded or KV cache is discarded between requests), any host can serve any request, and load distribution becomes even. The architect must choose between density (sticky sessions, higher per-host utilization) and evenness (stateless routing, lower per-host utilization but better load balance).

## 3. Worked Example

We continue from the canonical scenario (Ch 4, Table 4-2): ~10 rps average / ~40 rps peak, prompt ~9,200 input tokens + ~300 output, 70B-class dense FP16 model, 8×H100 host with 640 GB GPU memory. A single 8×H100 host's capacity is set by the *binding constraint* among GPU compute, HBM bandwidth, and KV cache memory. Let us verify with arithmetic, keeping the two quantities distinct: **aggregate HBM** (640 GB) is not the same as **KV-available memory** (640 − 140 GB weights − runtime/workspace reserve).

**Single-host concurrency capacity (KV-bound).** The per-token KV footprint for the canonical full-MHA reference geometry is 2 × layers × hidden × bytes = 2 ×80 ×8,192 ×2 = 2,621,440 B ≈ 2.62 MB/token (Chapter 7 canonical). Subtract the 140 GB FP16 weights and ~64 GB runtime/activations/workspace from the 640 GB pool, leaving ≈436 GB available for KV. Each request at 9,200 input + 300 output reserves a **9,500-token max** KV of 9,500 ×2.62 MB ≈ 24.9 GB (the initial 9.2K residency is 24.1 GB). A single host therefore holds C = 436 GB ÷ 24.9037 GB ≈ **17.5 concurrent requests** (byte-accurate; the conservative integer "requests that fit" floor is **17**, not 18 — 17.51 cannot round up for a hard fit) — using the canonical layer-complete κ. Computing κ from a single layer instead of all 80 would overstate the concurrency figure by two orders of magnitude.

**Viability at peak.** Peak traffic is 40 rps; with the canonical ~8.6 s per-request service time (1.08 s prefill + 7.5 s decode), Little's Law puts ≈ 40 × 8.6 ≈ **344 requests in flight**, against a KV capacity of ~17.5 per host (conservative integer floor 17). **A single host is not viable at peak even for the non-agentic canonical workload** — the fleet needs roughly ⌈344/17⌉ = **21 hosts** at 40 rps (**31 working hosts** at the 70% × 95% provisioning policy, **32 total with N−1** — Table 17-1), and more for growth to 100 rps. This flips the original conclusion: the fleet is not a distant luxury but a necessity at the canonical peak, driven by the product of service time (8.6 s) and arrival rate.

**KV compression is the first lever.** Switching KV to FP8 (κ ≈ 1.31 MB/token, raw byte-halving — exactly 50% of BF16 [ILLUSTRATIVE][DERIVED]) cuts the 9.5K max per-request KV to ≈12.45 GB and raises C to ≈35.0 concurrent per host (436 ÷ 12.45 ≈ 35.0; conservative integer floor 35), roughly doubling headroom before buying hardware. This is why the architect treats KV precision as a first-class capacity dial, not a cosmetic detail.

**Threshold for fleet expansion.** Suppose the agentic layer from Chapter 19 is added. Chapter 19's illustrative turn distribution puts 68% of requests terminating in T=1, 25% in T=2, 5% in T=3, and 2% exceeding the turn limit (falling back to single-shot). That makes the **median** turn count T=1 (68% of requests finish on the first turn) and the **95th percentile** T=3 (cumulative 68+25+5 = 98% by T=3). Each turn adds ~800 tokens of retrieved context (delta) and ~65 tokens of model-generated reasoning (gamma), so the effective per-request token count is
$$
I(T) = I_0 + T(\delta + \gamma) + O_\text{final} = 9{,}200 + T \times 865 + 300
$$

- Median (T=1): $I(1) = 9{,}200 + 1 \times 800 + 1 \times 65 + 300 = 10{,}365$ tokens
- 95th percentile (T=3): $I(3) = 9{,}200 + 3 \times 800 + 3 \times 65 + 300 = 12{,}095$ tokens
- Hypothetical extension (T=4, *if the turn limit were not enforced* — per Ch 19 the >2% that exceed the limit fall back to single-shot, so no request actually reaches T=4): $I(4) = 9{,}200 + 4 \times 800 + 4 \times 65 + 300 = 12{,}960$ tokens

The KV cache per request rises proportionally, and per-host concurrency capacity follows from the Ch 17 formula $C = M_{kv}/(I(T)\kappa)$:

- at T=1 (median): $10{,}365 \times 2.62 \text{ MB} \approx 27.2 \text{ GB/request} \Rightarrow C \approx 16$ concurrent (floor 16)
- at T=3 (95th): $12{,}095 \times 2.62 \text{ MB} \approx 31.7 \text{ GB/request} \Rightarrow C \approx 13.8$ concurrent (floor 13)
- at T=4 (hypothetical extension, turn limit not enforced): $12{,}960 \times 2.62 \text{ MB} \approx 34.0 \text{ GB/request} \Rightarrow C \approx 12.8$ concurrent (floor 12)

Even the *median* agentic request already drops a single host below the peak in-flight demand (C ≈ 16 < 344 at 40 rps, or 860 at 100 rps), so the fleet is required under almost any agentic assumption. **Scaling forecast (service-time-aware).** Because the canonical workload's service time is ~8.6 s — not a ~1 s latency — the in-flight concurrency at the 40 rps peak is λ_peak × W ≈ 40 × 8.6 ≈ **344 requests**, not 40. With FP16 KV (baseline C≈17.5, conservative integer floor 17), the fleet needs ⌈344/17⌉ = **21 hosts** at full utilization (**31** at the 70% × 95% provisioning policy, **32 total with N−1** — Table 17-1). Agentic turns make this strictly worse: each additional turn adds ~800 tokens of context (lowering C) and more generated tokens (raising W), so the agentic T=3 case needs a larger fleet still (C≈13.8 in the 95th-percentile case and a longer W). The load balancer distributes λ/N rps per host and λ·W/N concurrent per host, and each host's per-host KV usage must stay comfortably under its C. This is the fleet point: hosts are added because *concurrency in flight × KV-per-request* exceeds a single host's residency — and concurrency in flight must be computed from the full service time, not a target latency.

**Cross-host communication.** In the canonical scenario, requests are independent — no user session spans multiple hosts. If an agentic loop required retrieving results from a prior host (e.g., distributed retrieval), the system would need a coordination layer (Redis, gRPC, or message queue) with added latency. We quantify this below in the measurement section.

## 4. Measurement

We derive three planning quantities from the worked example and Chapter 19's illustrative turn-count distribution. These are not measurements from production traffic. A deployment must measure its own traffic distribution before using these quantities for provisioning.

### Per-host throughput and KV cache budget

Let N be the number of hosts, λ the incoming rps peak, T the random variable for agent turn count with distribution P(T), δ = 800 tokens per turn of retrieved context, γ = 65 tokens of model-generated reasoning per turn, and O_final = 300 final output tokens. The per-request token count is

$$
I(T) = I_0 + T \cdot \delta + T \cdot \gamma + O_\text{final}
$$

where I₀ = 9,200 is the baseline input tokens. The per-host concurrent‑request capacity in terms of KV cache is

$$
C = \frac{M_{kv}}{I(T) \cdot \kappa}
$$

where M_kv is the KV‑available memory — the portion of on‑host HBM left for KV after weights and runtime — and $\kappa = 2 \times n_\text{layers} \times d_\text{hidden} \times \text{bytes} \approx 2.62$ MB/token (2.5 MiB) is the per‑token KV footprint (Chapter 7 canonical; κ includes all layers — omitting the layer factor understates KV memory by orders of magnitude). For the canonical host, M_kv = 640 GB − 140 GB (FP16 weights) − ~64 GB (runtime/activations/workspace/NCCL) ≈ 436 GB. Dividing memory by bytes (not the byte‑divided‑by‑bytes collapse that trips unit analysis):

- For T = 0 (baseline, I = 9,500): C = 436 GB / (9,500 ×2.62 MB) ≈ 436/24.9037 ≈ **17.5 concurrent requests per host** (byte-accurate; the conservative integer "requests that fit" floor is **17**, not 18 — 17.51 cannot round up for a hard fit).
- For T = 1 (median, per the Chapter 19 distribution; 68% terminate on turn 1): C = 436 GB / (10,365 ×2.62 MB) ≈ 436/27.17 ≈ **16 concurrent requests per host**.
- For T = 3 (95th percentile; cumulative 98% by T=3): C = 436 GB / (12,095 ×2.62 MB) ≈ 436/31.71 ≈ **13.8 concurrent requests per host** (floor 13).
- For T = 4 (hypothetical extension beyond the enforced turn limit — Ch 19's >2% tail falls back to single-shot, so no request reaches T=4): C = 436 GB / (12,960 ×2.62 MB) ≈ 436/33.97 ≈ **12.8 concurrent requests per host** (floor 12).

These numbers are the KV-residency ceiling; measured concurrency may be lower if GPU throughput or bandwidth binds first, so the architect takes the min of the KV, compute, and bandwidth capacities.

**Define the subsystem boundaries before applying Little's Law — the populations are NOT the same.** The end-to-end "in-flight request" count differs from the number of sequences actually occupying accelerator resources, because a request passes through several subsystems with different residency times and different occupants. Five distinct time quantities appear in this chapter; they are **not** interchangeable, and each drives a different population:

| Time symbol | Definition | Canonical value | Population it drives (L = λ·W) |
|---|---|---|---|
| $W_{\mathrm{e2e}}$ (end-to-end) | the **full service time** as the user experiences it: queue + GPU execution + tool/orchestration + inter-turn gaps | ≈ 10 s planning round for the canonical non-agentic round; grows with turns | λ·W_e2e — requests in flight (user view) |
| $W_{\mathrm{queue}}$ | admission + queue wait before a GPU slot is free | unmeasured here | λ·W_queue — queued requests (no KV block reserved yet) |
| $W_{\mathrm{GPU\text{-}exec}}$ | prefill + decode while the sequence is executing on the GPU | ≈ 8.6 s (1.08 s prefill + 7.5 s decode, canonical 9.2K/300) | λ·W_GPU-exec — sequences executing on a host |
| $W_{\mathrm{tool\text{-}held}}$ | tool/orchestration (and inter-turn) gap during which the scheduler **keeps** the KV block | 0 when the engine releases KV at the step boundary; otherwise the retained gap | counts toward KV residency only if the block is retained |
| $W_{\mathrm{KV\text{-}resident}}$ | mean time a KV block is actually held: $W_{\mathrm{GPU\text{-}exec}}$ + any retained gap ($W_{\mathrm{tool\text{-}held}}$); queue time counts only if the admission policy pre-reserves blocks | ≈ 8.6 s **if and only if** the explicit assumption "KV is held only during GPU execution" holds (stated below) | $\mathrm{E}[L_{KV}] = \lambda_\mathrm{admitted} \times \mathrm{E}[W_{KV\text{-}resident}]$ — the population that must fit in cache |

**The KV population is its own derivation — E[L_KV] = λ_admitted × E[W_KV-resident].** The quantity that must fit in the KV pool is

$$\mathrm{E}[L_{KV}] = \lambda_\mathrm{admitted} \times \mathrm{E}[W_{KV\text{-}resident}]$$

where $\lambda_\mathrm{admitted}$ is the rate the host actually *admits* (equal to the arrival rate only while nothing is being shed or queued) and $\mathrm{E}[W_{KV\text{-}resident}]$ is the **mean** KV-holding time — a mean, never a percentile (tail rule below). Memory is then sized from that population by cache geometry and policy: slots per host = ⌊usable KV pool ÷ per-request KV at the sizing context⌋ (436 GB ÷ 24.9 GB ≈ 17.5 → whole-context floor 17 at T=0), then adjusted for the **rank/replication layout** (tensor-parallel rank count, and whether KV is sharded across ranks or replicated) and the **admission policy** (whole-context admission with no fractional slots; a prefix-cache hit or a pre-reserved block changes the effective holding time, not the byte geometry). The **deployable host count is the maximum of two requirements** — (i) the *capacity* requirement ⌈λ·E[W_KV-resident]/(C·u·ρ)⌉ and (ii) the *tail-latency* requirement N_SLO that holds p95/p99 TTFT, TPOT and success rate under concurrent arrival (unmeasured here; Chapter 14) — never the capacity screen alone. (The ρ = 0.95 scheduling/efficiency factor is the independent multiplier defined in Table 17-1; the ρ-omitted ⌈λ·E[W_KV-resident]/(C·u)⌉ is the superseded u-only screen.)

**Which one drives KV residency?** Only the KV-resident population $\mathrm{E}[L_{KV}] = \lambda_\mathrm{admitted} \times \mathrm{E}[W_{KV\text{-}resident}]$ holds KV slots — a queued request (λ·W_queue) is "in flight" from the user's view but does not yet reserve a KV block, and the orchestration/planning portion of $W_{\mathrm{e2e}}$ has not reached the host at all. The KV-residency ceiling C therefore bounds $\mathrm{E}[L_{KV}]$ (the resident sequences), not λ·W_e2e or λ·W_queue. The end-to-end time ($W_{\mathrm{e2e}}$ ≈ 10 s planning round, the quantity earlier drafts labeled W_plan) is the workload-level Little's-law basis used to derive the arrival rate from the population (Chapter 4); the mean KV-residency time ($\mathrm{E}[W_{KV\text{-}resident}]$ ≈ 8.6 s under the stated assumption) is the capacity-level Little's-law basis used to size the fleet (this chapter). The C/W shortcut is thus a *KV-residency* screen, valid only when the serving system is the bottleneck and no queue/planning backlog or released-KV tool gap changes the resident count — state that scope, and never quote C/W as a measured end-to-end goodput.

Two transplant errors to refuse explicitly. (i) **Do not put λ × W_e2e into KV slots.** End-to-end time includes queue, tool and inter-turn gaps that — under the stated assumption — hold no KV, so λ·W_e2e overstates the cache population and over-sizes the fleet; the KV formula takes λ_admitted × E[W_KV-resident] and nothing else. (ii) **Do not substitute a p95/p99 for E[W] in Little's Law.** Little's Law is a *mean* relation, E[L] = λ·E[W]; pairing a mean λ with a p95 W mixes moments and yields a number that is neither a mean population nor a percentile one. Tail percentiles enter as a *separate* stochastic constraint — the N_SLO tail-latency requirement above, and the p95/p99 measurement gates of Chapter 14 — never as the W inside λ·W.

If the peak traffic λ_peak = 40 rps, Little's Law gives the number of requests *in flight* as λ_peak × W, where **W must be the mean time the resource in question is actually held** — for the KV-slot screen that is $\mathrm{E}[W_{KV\text{-}resident}]$, which for this canonical workload is ~8.6 s (1.08 s prefill + ~7.5 s decode of 300 output tokens at ~25 ms/token, Chapter 8) **under the explicit assumption that KV is held only during GPU execution** — NOT a sub-second TTFT-type latency, and NOT $W_{\mathrm{e2e}}$ (which adds the tool/orchestration time that, under that assumption, holds no KV). Using a ~1 s "latency" here is the classic fleet-sizing error: it undercounts in-flight concurrency by roughly the ratio of service time to target latency (here ~8.6×). The minimum number of hosts is

$$
N_\text{min} = \left\lceil \frac{\lambda_\text{peak} \cdot W}{C \cdot u \cdot \rho} \right\rceil, \qquad N_\text{provisioned} = N_\text{min} + N_\text{spare}
$$

where $u$ is the utilization target, $\rho$ the load‑balancer/scheduling efficiency factor (§17.4), $N_\text{spare}$ the N−1 reserve host(s), and $W$ is $\mathrm{E}[W_{KV\text{-}resident}]$ — the **mean KV-holding time** (GPU execution: prefill + decode, plus any gap the scheduler keeps the block; queue time, tool waits and inter-turn gaps count only if the admission/eviction policy retains KV). The end-to-end $W_{\mathrm{e2e}}$ — which adds tool/orchestration overhead — is the user-view in-flight count and is **not** the W in this KV formula; the ~8.6 s used below is a **conditional scenario proxy** for $\mathrm{E}[W_{KV\text{-}resident}]$, valid only under the stated "KV held only during GPU execution" assumption. **This is the book's one provisioning formula; Chs. 16, 17, 20, the TCO and Fig 17.1 all use it, and its parameters are fixed by the single authoritative policy table below.** Every count it produces is an **analytical lower-bound screen, not measured SLO-goodput**.

**Why $u$ and $\rho$ are independent here — and the nested variant, stated so it cannot be confused with it.** The 70% is an *operational utilization ceiling on the host*; the 95% is a *separate load-balancer/scheduling efficiency loss* on top of it (§17.4: health checks, affinity skew, LB CPU). They are therefore applied as two factors. **If** the 70% had instead been measured *after* LB losses — i.e. $\rho$ already inside the net derate — the formula would set $\rho = 1$ and the same screen would read $\lceil 344/(17 \times 0.70)\rceil + 1 = 30$ hosts; this book makes **no** such claim, so $\rho = 0.95$ stays in the formula. The earlier 29-working / 30-total figures were exactly that $\rho$-omitted ($\rho = 1$) variant and are superseded. Recomputed at the canonical peak under this policy (each an analytical lower-bound screen, not measured SLO-goodput): ideal-active, zero derate, zero spare = **21**; $\rho$-only, zero spare = **22**; $u$-only, zero spare (the $\rho = 1$ variant) = **29**; **policy $u \times \rho$ working = 31, + $N_\text{spare}$ = 32 (KV-only, case (i))**; the independent full-square case (ii) prefill screen at the same policy = **⌈21.81/0.665⌉ + 1 = 34** (33 working + 1); case (i) = 29 and case (iii) = 32 at the same policy. FP8 KV is unchanged by the policy debate at the working level — $\lceil 344/(35 \times 0.70 \times 0.95) \rceil = \lceil 14.78 \rceil = 15$ working, 16 with the spare.

At the canonical peak:

- **KV-residency ceiling (C) is a per-host concurrency limit, not a fleet-size answer by itself.** A host holds C ≈ 17.5 concurrent full-context requests (computed above; conservative integer floor 17). The fleet size is governed by how many requests are *KV-resident at the peak*, which is λ_admitted × E[W_KV-resident] — equal to λ_peak × 8.6 s here only because admission is assumed to match the arrival rate and 8.6 s is the assumed mean KV-holding time.
- At λ_peak = 40 rps and W ≈ 8.6 s, in-flight concurrency ≈ 40 × 8.6 ≈ **344 requests**. With C ≈ 17.5 per host (FP16 KV) at full utilization, the minimum N = ⌈344/17⌉ = **21 hosts** (**31 working** at the 70% × 95% policy, **32 total with N−1** — Table 17-1) — the **KV screen alone, under case (i)**. The independent prefill compute screen (Ch. 8, 35% MFU) is a *separate* named screen: **19 hosts under case (i)** (⌈18.60⌉, linear-only), **21 under case (iii)** (⌈20.21⌉, causal-triangle), **22 under case (ii)** (⌈21.81⌉, full-square conservative). Under case (ii) the compute screen **binds above** the KV screen, so the capacity floor is **max(KV, compute) = 22 hosts** — and at the 70% × 95% + N−1 policy **⌈21.81/0.665⌉ + 1 = 34 hosts** under case (ii) versus **32** for KV-only (⌈344/11.305⌉ + 1). **19 / 21 / 22 / 32 / 34 are all illustrative planning screens under their stated FLOP-counting case and the 35% MFU assumption — NOT measured SLO-goodput.** This is the honest fleet size and matches the throughput/latency analysis in Chapter 20.
- **The 25 ms/token in W is the TPOT *budget*, not a measured per-step time.** The decode-bandwidth floor for the canonical 8×H100 host is 140 GB ÷ (8 × 3.35 TB/s) ≈ 5.2 ms/step, so a well-tuned decode can run well under the 25 ms SLO. The fleet number above therefore uses the *least-favourable* (budget) pole of the service time. The sensitivity band, holding prefill at 1.08 s and 300 output tokens: at 5.2 ms/step W ≈ 2.6 s (in-flight ≈ 106, ~7 hosts at full util); at 10 ms/step W ≈ 4.1 s (in-flight ≈ 164, ~10 hosts); at the 25 ms budget W ≈ 8.6 s (in-flight ≈ 344, ~21 hosts). Sizing at the 25 ms budget is the conservative choice; a measured per-step time from a Chapter 14 benchmark should replace it before committing hardware.
- Switching to FP8 KV (κ ≈ 1.31 MB/token, raw byte-halving — 50% of BF16, C ≈ 35.0 at T=0; conservative integer floor 35) raises per-host concurrency, cutting the fleet to a minimum N ≈ ⌈344/35.0⌉ = 10 at full utilization → **15 working hosts** at the 70% × 95% policy (⌈344/(35 × 0.70 × 0.95)⌉ = ⌈14.78⌉ = 15 — the same 15 the u-only screen gave, because the ceil absorbs the extra derate here) and **16 total with N−1**.

**Separate the two questions explicitly** — they are not interchangeable, and mixing them is the source of the under-sizing error:

1. **KV-only concurrency sizing** (does one host's KV budget hold the in-flight requests?): $N_{KV} = \lceil \lambda W / (C \cdot u \cdot \rho) \rceil$. This uses C (KV-residency ceiling) and the mean KV-holding time $\mathrm{E}[W_{KV\text{-}resident}]$ (the ~8.6 s proxy) — not $W_{\mathrm{e2e}}$ — with $u$ and $\rho$ exactly as Table 17-1 defines them.
2. **Full service-capacity sizing** (does the fleet's aggregate request rate clear the peak?): the same quantity when C/W is the per-host service rate — i.e. $N = \lceil \lambda / ((C/W) \cdot u \cdot \rho) \rceil$. Because Little's Law ties concurrency, service time and arrival rate, these two views coincide: $\lambda W / (C \cdot u \cdot \rho) = \lambda / ((C/W) \cdot u \cdot \rho)$ — **provided the same W (E[W_KV-resident]) is used on both sides**; mixing W_e2e on one side and the 8.6 s residency proxy on the other breaks the identity.

KV residency provides one capacity ceiling, but it is not a fleet-size answer by itself. When the canonical 300-token decode duration is included, Little's Law raises in-flight concurrency from the misleading "40 requests at 1 second" approximation to roughly **344 requests at 40 rps**, and the fleet must be sized to that.

**The fleet is governed by the *minimum* of several independent ceilings, not by KV alone.** `C/W` — and the KV-residency ceiling C that feeds it — is a *necessary* condition, not sufficient under mixed prefill/decode scheduling. An architect must take `min` of: (a) **KV-residency concurrency** C, (b) **prefill compute capacity** (the ~19,800 tok/s/host prefill screen of Ch. 8 — **case (i), linear-only**; ≈16,870 linear-equivalent tok/s under case (ii), full-square), (c) **decode bandwidth/compute capacity** (the HBM-bound decode roofline), and (d) the **observed p95-TTFT/TPOT SLO goodput** under a load test. A host may hold 17.5 KV-resident requests but never *serve* 17.5 at the quoted service time, because batch scheduling, prefill/decode interleaving, and tail latency couple the two.

*Small queueing counterexample.* Suppose a KV ceiling C = 17.5 and W = 8.6 s, so `C/W ≈ 2.0 req/s`. That is an *average occupancy bound*. If a burst of arrivals is shorter than the service-time spread, or if the prefill of some requests monopolizes the GPU and stalls decode, the *achieved* goodput can be well below 2.0 req/s even though the host holds 17.5 slots. Conversely, with prefix caching and batch-friendly load, achieved can exceed the naive bound at higher batch. The upshot: `C/W` is a **KV-slot-based analytical UPPER bound on admitted request completion rate, conditional on an assumed mean KV residency time** — a capacity screen only; its standing qualifiers (not a lower guaranteed rate, not a measured throughput, not an SLO goodput) are stated once in the **Evidence boundary** panel (Preface). The *lower* bound on host count derives FROM this upper bound on the per-host rate: a ceiling per host becomes a floor per fleet at exactly one step, N ≥ ⌈λ/(C/W)⌉ = ⌈λ·W/C⌉ (⌈40/(17/8.6)⌉ = ⌈20.24⌉ = 21). The fleet SLO-passing count comes from the measured goodput at the target p95 — not from `C/W`. State the line's assumptions (time-in-KV occupancy, overlap of phases, admission policy) explicitly in the sizing summary rather than presenting `C/W` as the achieved rate.

### Simultaneous feasibility check (prefill + decode coexistence)

The ~2.0 req/s/host ceiling assumes prefill and decode run on the same host at the same time. We check the prefill leg against the hardware.

- **(a) Prefill demand at 2 req/s.** 2.0 req/s × 9,200 input tokens = **18,400 input tokens/s per host** (2.0 × 9,200; the prefill leg of the ~2.0 req/s decomposition in the reconciliation box above).
- **(b) Idealized prefill ceiling.** 8 × 0.989 PF/s × 35% / (2 × 70e9) ≈ **19,780 tokens/s** (Chapter 8, 35% MFU, prefill-only — **case (i), linear-only FLOP convention**).
- **(c) The ratio.** 18,400 ÷ 19,780 ≈ **93%** under case (i). Prefill must run at ~93% of the idealized prefill ceiling.
- **(d) FLOP-counting sensitivity (same 35% MFU).** The ceiling is quoted in *linear-equivalent* tokens/s, so case (ii) (full-square, ×1.1723) lowers it to ≈16,870 tok/s and the ratio becomes 2 × 1.5099 ÷ 2.7692 ≈ **109%**; case (iii) (causal-triangle, ×1.0861) gives ≈18,210 tok/s and ≈**101%**. Under the conservative case the prefill leg alone *exceeds* the idealized ceiling at 2 req/s — so the headroom the ~93% implies is a property of the linear-only convention, not of the hardware.

This result is **[ANALYTICAL]**. It is a prefill-load check, not a measured rate. The ~93% (case (i)) leaves very little headroom. The host must also run decode. Prefill and decode coexist on the same hardware. Batch scheduling, prefill/decode interleaving, and interference consume the same compute. The idealized ceiling assumes no decode interference. The achieved MFU is below the 35% ideal. The real headroom is smaller than ~93%.

Therefore the ~2.0 req/s/host figure is a **KV-slot-based analytical UPPER bound on admitted request completion rate, conditional on an assumed mean KV residency time** — the same single phrase used in Chapters 16 and 20, one phrase with one meaning. It is a necessary capacity screen: **NOT** a lower guaranteed rate, **NOT** a measured throughput, **NOT** an SLO goodput, and **NOT** a claim that a host serves 2 req/s at SLO. The lower bound on host count (21) derives *from* this upper bound on the per-host rate — ⌈40 ÷ (17/8.6)⌉ = ⌈20.24⌉ = 21 — and never the other way around.

Before treating 2 req/s/host as deployable, measure the p95 TTFT, p95 TPOT, and SLO-goodput on a representative host. Bring a measured p95 TTFT/TPOT and SLO-goodput (Chapter 14) before treating 2 req/s/host as a deployable service rate. Until then, the sizing in this chapter is a planning bound.

### Load‑balancer overhead factor

Let ρ be the effective throughput fraction after load‑balancer effects. **These LB-efficiency values are [ILLUSTRATIVE][ASSUMPTION] engineering thresholds, not universal vendor-independent constants** — a well‑configured software LB (NGINX) typically achieves ρ ≈ 0.95, and a hardware L7 switch may achieve ρ ≈ 0.98, *but both must be measured on the target topology, workload, and sample duration before being trusted*. The overhead comes from: health‑check traffic (~1% of requests), session‑affinity hashing skew, and LB process CPU limits. The per-host throughput itself must come from a benchmark on the actual workload (tokens/context/batch) — it is an ILLUSTRATIVE proxy until measured. What is *derivable* is the KV‑residency ceiling C from §17.3; the LB overhead multiplies the schedulable fraction of that ceiling, and the ρ value should be replaced by a measured figure from a load test before it is used as a capacity coefficient. **In the provisioning formula (Table 17-1) ρ enters as that schedulable-fraction multiplier, independently of the 70% utilization target u — it is not folded into u and it is not a spare host.** In the worked example, the fleet is currently sized by KV capacity (§17.3), not by a fabricated tokens/s number: at T=3 (the 95th-percentile sizing point, per the chapter's own rule), FP16-KV C ≈ 13.8/host (436 GB ÷ (12,095 × 2.62 MB ≈ 31.7 GB) ≈ 13.8; conservative integer floor 13) sets the continuous ceiling. The product 13.8 × 0.95 ≈ 13.1 is a continuous relaxation only, not usable additional-host capacity. The host can admit at most 13 whole contexts. Applying the assumed throughput efficiency to that hard limit gives 13 × 0.95 = 12.35 as the slot-equivalent schedulable fraction per added host, not an integer admission count. Converting that coefficient to a request rate still requires the stated service time and workload assumptions.

### Cross-host interconnect budget

If a fraction φ of requests require cross-host data (e.g., distributed retrieval, shared vector index), each such request incurs an additional network round-trip and moves data volume D over the host-to-host network. **Three time terms must be separated before any D is divided by anything:**

$$
t_\text{net} = t_\text{fixed} + t_\text{transfer} + t_\text{queue}
$$

- $t_\text{fixed}$ — **RTT + serialization**: the round-trip/propagation floor plus the time to serialize the payload onto the wire; it does not shrink as D grows;
- $t_\text{transfer} = D / B_\text{effective}$ — the payload's transfer time at the path's effective goodput;
- $t_\text{queue}$ — queueing/scheduling wait on the shared link (load-dependent; zero only on an idle fabric).

**The 20 ms used below is the canonical *service* retrieval round trip** — the observed per-request duration of the retrieval service (the Ch 4 retrieval-latency class), **not a rack-line latency**: a bare intra-rack RTT is far shorter, and the 20 ms is the observed duration that *contains* $t_\text{transfer}$ and $t_\text{queue}$ in addition to $t_\text{fixed}$. Assuming an intra-rack 10 Gbps Ethernet backbone (10 Gbps = 1.25 GB/s):

$$
G_\text{per-req} = \frac{D}{t_\text{net}} = 5\text{ MB} / 0.02\text{ s} = 250\text{ MB/s} \approx 2\text{ Gbps}
$$

For D = 5 MB (top-5 retrieval snippets) and $t_\text{net}$ = 20 ms, $G_\text{per-req}$ = 250 MB/s ≈ 2 Gbps is an **effective per-request goodput** — payload ÷ observed round-trip duration — **not the instantaneous rate the link must carry**: the instantaneous rate while the payload moves is $D/t_\text{transfer} = D/(t_\text{net} - t_\text{fixed} - t_\text{queue}) \ge D/t_\text{net}$, so 250 MB/s is a *lower* bound on the burst rate and the link must be dimensioned for $D/t_\text{transfer}$. The two readings agree on the base case: moving 5 MB at the fabric's own 1.25 GB/s takes $t_\text{transfer}$ = 5 MB ÷ 1.25 GB/s = **4 ms**, comfortably inside the 20 ms observed duration once $t_\text{fixed} + t_\text{queue}$ take their share.

**The shared-link check is the aggregate offered byte rate against the link budget.** The fleet aggregate — the expected number of concurrent cross-host requests ($\varphi \cdot \lambda \cdot t_\text{net}$, by Little's Law, where $\lambda$ is the request arrival rate) times that per-request rate — is

$$
B_\text{agg} = \varphi \cdot \lambda \cdot D = 0.1 \times 40 \times 5\text{ MB} = 20\text{ MB/s} = 0.16\text{ Gbps}
$$

i.e. **20 MB/s of offered bytes against the shared 10 Gbps (1.25 GB/s) link budget — 1.6% of the link** — so the base case is benign on the aggregate, and the per-request effective goodput (250 MB/s ≈ 2 Gbps) sits ~5× under the same link rate.

But if φ scales to 0.5 (many distributed queries) and D grows to 50 MB, the aggregate offered byte rate becomes $0.5 \times 40 \times 50 = 1{,}000$ MB/s = 1 GB/s — **~80% of the 1.25 GB/s link budget** — and the transfer leg alone needs $t_\text{transfer}$ = 50 MB ÷ 1.25 GB/s = **40 ms**, which no longer fits the 20 ms observed duration: sustaining 50 MB inside 20 ms would require $D/t_\text{net}$ = 2,500 MB/s ≈ 20 Gbps, i.e. a link faster than the 10 Gbps fabric. Both the aggregate and the per-request requirement scale with φ and D.

This calculation shows that cross-host communication must be dimensioned on **two separate checks** — the *aggregate offered byte rate against the shared link budget* (φ·λ·D vs 1.25 GB/s) and the *per-request transfer leg against the observed duration* ($D/B_\text{effective}$ vs $t_\text{net} - t_\text{fixed} - t_\text{queue}$) — and that both scale with φ and D, even if the base case appears benign. ### Request traffic and model collectives are different populations

The retrieval budget above follows request arrivals: a fraction of requests moves a payload between hosts. A distributed model introduces different events. Tensor-parallel participants exchange partial results at layer boundaries; expert-parallel participants dispatch and combine routed tokens. Their payload and frequency follow the actual TP or EP communication group and execution schedule, not the total number of serving hosts. KV transfer follows a further boundary: ownership of a request's cached state. These populations need separate byte, frequency, and latency records before their loads are combined on a shared link.[^oct17-collective-groups]

Independent inference replicas do not perform a cross-fleet gradient all-reduce merely because more hosts are added. Conversely, request-driven retrieval traffic is not the whole network budget when a model spans devices or hosts. The capacity check accounts for each group's traffic, simultaneous schedules, and shared-link contention. Only exposed communication on the critical path adds directly to request latency; adding every collective duration again after counting overlapped execution would double-count time. ### Counter-scenarios: KV is not always the driver

The canonical case is *one* regime — a mid-context, mid-rate RAG workload where the KV-residency ceiling happens to be the binding constraint. Two counter-scenarios show that the method (compute λ·W/C with the real service time) transfers while the *conclusion* (KV binds) does not. **The formula is the method; the binding term is per-workload.**

**Counter-scenario A — short context, high batch: KV is not the host-count driver.** A code-completion-style workload is a clear case: ~500-token input, ~100-token output, but a very high arrival rate (say 200 rps peak) and a small model (7B, so weights are ~14 GB and the KV footprint per token is far lower). Here two things happen. First, per-request KV is tiny — a 600-token max-context against a small per-token κ is well under 1 GB, so the host holds hundreds of concurrent requests at the KV screen; C is *not* the ceiling. Second, the binding term becomes **decode bandwidth**: each generated token re-reads the full ~14 GB of weights, so the per-host decode token rate is capped by HBM bandwidth ÷ weight size, and at 200 rps × 100 output tokens the aggregate output-token demand dwarfs what any one host's bandwidth supplies. The host count is set by λ·O / (per-host token rate), *not* by KV residency. The fleet formula is unchanged; the binding term is bandwidth, not memory.

**Counter-scenario B — long context, low rate: memory dominates even below the KV screen.** A document-analysis workload is the opposite pole: ~128K-token input, ~50-token output, but a low rate (say 2 rps). Here the per-request KV is enormous — 128K tokens against the canonical κ is ~335 GB, which consumes most of the host's ~436 GB KV budget (already net of the 140 GB weights). Because even one request nearly fills the host, the fleet is sized almost one-request-per-host despite the low rate. Here memory is not just a ceiling — it is the *dominant* term, and the canonical brief-context C/W shorthand (which assumes many small requests share a host) does not apply at all.

**The transferable lesson.** In the canonical regime the host is KV-bound and sized by λ·W/C; in counter-scenario A it is bandwidth-bound and sized by output-token rate; in counter-scenario B it is memory-dominated and sized by aggregate context. The architect must identify which term binds *for the specific workload* before applying any single sizing formula — that is what makes the canonical scenario a method rather than a template.

## 5. Common Mistakes

1. **Ignoring KV cache growth from agentic loops.** A common mistake is to assume that adding an agentic layer barely changes per-request resource usage. As shown, each turn adds ~800 tokens of context, which linearly reduces concurrent‑request capacity. Forgetting this leads to under‑provisioning the fleet.

2. **Over‑relying on sticky sessions without load‑balance analysis.** Sticky sessions simplify cross‑host communication but can create hot‑spot hosts if a few users generate disproportionate traffic. Always measure the session‑affinity distribution on the actual workload. **A Gini coefficient exceeding 0.3 is an [ILLUSTRATIVE][ASSUMPTION] example threshold, not a universal constant** — the trigger to abandon sticky sessions depends on the workload, the tail-latency SLO, and the failure domain. Establish the skew threshold with a traffic replay/load test and tune it to the SLO, not to a fixed 0.3; measure per-host queueing, p95/p99 latency, and request drops to decide when stateless routing or session sharding is the appropriate response.

3. **Using raw rps to size the fleet.** Requests‑per‑second is necessary but not sufficient; the product of rps × average latency gives concurrent load, which must fit within KV cache capacity. A host serving 40 rps at 0.5 s latency carries 20 concurrent requests, whereas at 2 s latency it carries 80 — the same rps, very different resource usage.

4. **Under‑estimating load‑balancer overhead.** A 5% throughput reduction from ρ = 0.95 may seem small, but at the margin of capacity it can be the difference between fitting on N hosts and needing N+1. Always provision with ρ explicitly in the formula.

5. **Failing to model latency tail under spike traffic.** GPU inference time is not constant; under sustained high load, kernel‑mode preemption, memory fragmentation, and concurrent kernel launches can increase per‑token latency by 20–50%. The linear model t = t_inference + t_tool is a lower bound; the architect should add a 20% safety margin.

## 6. Architecture Consequence

Transitioning from one host to a fleet reshapes every layer of the system.

**GPU fleet sizing.** The number of hosts N must satisfy the service‑time‑augmented capacity formula N = ⌈ λ_peak · W / (C · u · ρ) ⌉ (the minimum N — the provisioned fleet adds one spare on top, the N−1 rule; the authoritative parameters are Table 17-1), where C depends on the agentic turn distribution and W is $\mathrm{E}[W_{KV\text{-}resident}]$ — the mean KV-holding time, which here is proxied by the full per-request service time (a proxy that rises with turns — each turn adds generated tokens, and adds retrieval latency *only while the KV block is retained*; a tool gap during which the engine releases KV belongs to $W_{\mathrm{e2e}}$, not to W). Two effects compound as turns grow: C falls (more tokens → more KV per request) and W rises (more per-turn retained time), so the KV‑resident population λ·W grows on both sides. For the canonical customer‑facing peak (40 rps, W≈8.6 s), in‑flight ≈ 344 and N = ⌈344/17⌉ = 21 hosts at full utilization (**31** at the 70% × 95% policy, **32 total with N−1**) with FP16 KV; FP8 KV cuts that to **15 working hosts** (10 at full utilization; **16 total with N−1**).

**Load‑balancer selection and configuration.** The choice between hardware (F5, Cloud LB) and software (NGINX, HAProxy) affects ρ and the session‑affinity model. Hardware L7 switches offer better ρ (≈0.98) but less fine‑grained traffic‑shaping; software LBs offer ρ ≈ 0.95 but can implement consistent hashing for session affinity. The architect should match the LB capability to the session model: sticky sessions → any LB; stateless → software LB with consistent hashing.

**Cross-host data infrastructure.** If any request type requires cross‑host communication (distributed retrieval, multi‑model orchestration, state sync), a dedicated backend network must be provisioned. The minimum bandwidth is B_min = φ · λ · D (the fleet aggregate derived in §17.4.4 — the expected concurrent cross‑host requests φ·λ·t_net times the per‑request effective goodput D/t_net, which simplifies to φ·λ·D), and the fabric should provide at least 2×B_min for headroom. In the canonical scenario with φ = 0.1, λ = 40 rps, D = 5 MB, B_min ≈ 0.16 Gbps (0.1 × 40 × 5 MB = 20 MB/s) — an *offered byte rate* to be set against the shared 10 Gbps (1.25 GB/s) link budget, which it uses at ~1.6% — so a 10 Gbps intra-rack network has ample headroom for the aggregate; but as §17.4.4 notes, the per‑request transfer leg (D/B_effective, whose observed-duration average D/t_net = 250 MB/s ≈ 2 Gbps in the base case) must also fit a single link within the observed duration once a request is in flight, which is the binding constraint when φ or D grows. But the architect should instrument φ and D from production telemetry and revisit the bandwidth provisioning quarterly.

**Observability across the fleet.** With N hosts, tracing a request end‑to‑end requires correlating the LB routing decision, the selected host’s inference logs, and any cross‑host data calls. Structured logging with a request‑ID field that propagates from the client through the LB to the host and back is essential. Distributed tracing (OpenTelemetry, Jaeger) should be enabled by default. Alerts should trigger when per‑host concurrency exceeds 80% of C, when LB error rate exceeds 0.1%, or when cross‑host bandwidth utilization exceeds 70%.

**Failover and redundancy.** With N ≥ 2, the fleet provides automatic failover: if one host crashes, the LB routes its traffic to the remaining N−1 hosts, reducing capacity by 1/N (N to N−1 hosts). For N = 4, a single‑host loss reduces capacity from 100% to 75% (assuming equal load distribution). The architect must decide whether this is acceptable or whether N must be larger (e.g., N = 6 for 83% residual capacity after one failure). Health‑check frequency and graceful drain procedures affect the real-world failover time, typically 5–15 seconds.

**Multi-region active-active availability is NOT priced in this chapter's arithmetic.** The multi-region caveat of Ch 16 §16.3 applies verbatim to these host counts: every host count here — and the N−1 failover/redundancy model above — is a **single-region, N−1-only** number (≈21 peak / 31 working / 32 with N−1 — the **KV screen under case (i)**; 22 peak / 33 working / 34 with N−1 under the **full-square case (ii) prefill compute screen**), so the counts and the sizing arithmetic that hangs off them **understate the cost of the canonical workload's own stated 99.9% availability requirement**. Add a separate multi-region capacity + replication cost line before the availability SLA can be considered met — remembering the §16.3 split: per-region **weight and index availability is mandatory**, while **live-KV replication across regions is an optional policy** (clients may replay or recompute context in the surviving region instead, within the recovery objectives).

## 7. What We Still Don't Know

Despite the arithmetic above, several questions remain open and would benefit from targeted research:

- **Turn-count distribution under fleet load.** Do larger fleets (N > 4) change the observed T distribution? Intuitively, more hosts reduce per-host contention, potentially lowering latency and reducing the agentic loop depth, but empirical measurement is needed.
- **Latency amplification non-linearity.** The agentic latency model from Chapter 19 frames the added orchestration overhead as β(T) = 1 + (T·L_agent / L_base), which assumes constant per‑turn orchestration overhead and a fixed base generation time. Under fleet scaling, GPU saturation may make per‑turn overhead grow with concurrent requests, introducing convexity. Empirical load‑testing across N = 1, 2, 4, 8 hosts is required.
- **Optimal fleet size for cost vs. latency.** The cost of adding a host is roughly the cost of 8×H100 (multi‑hundred-thousand dollars). The marginal latency improvement from the Nth host diminishes (diminishing returns). A cost‑per‑latency‑improved curve would help the architect justify fleet size to stakeholders.
- **Cross‑host communication patterns at scale.** The φ = 0.1 assumption may not hold for all workloads (e.g., RAG over a shared index, distributed fine‑tuning). Real‑world measurement of cross‑host traffic patterns is needed to size the backbone accurately.
- **Context‑caching efficacy across a fleet.** If many users query related topics, can a fleet‑wide KV cache or retrieval cache reduce the effective δ per request? The savings could be substantial but require cross-host cache-invalidation protocols that are not yet well understood.

## 8. End-of-Chapter Mini-Case: Going Agentic: Service-Time-Aware Fleet Sizing

**Scenario.** An AI‑product company operates a fleet of 8×H100 hosts for the canonical traffic of 2,000 users at 10 rps average / 40 rps peak, 9,200 input + 300 output tokens, no agentic layer. After six months, user growth pushes peak traffic to 100 rps, and the team introduces the agentic layer from Chapter 19 with a maximum of 3 turns (median T = 1, 95th‑percentile T = 3, per the Ch 19 illustrative turn-count distribution).

**Initial sizing analysis (service-time-aware).** At T = 3 (the 95th‑percentile, and the honest worst‑case sizing point), I(3) = 9,200 + 3·800 + 3·65 + 300 = 12,095 tokens. With FP16 KV (κ = 2.62 MB/token), per‑request KV ≈ 31.7 GB, so KV‑residency capacity C = 436 GB ÷ 31.7 GB ≈ 13.8 concurrent requests per host (conservative integer floor 13). But concurrency *in flight* is λ_admitted × W, where W is $\mathrm{E}[W_{KV\text{-}resident}]$ — proxied here by the full service time under the stated KV-retention assumption — which grows with the agentic turns: 1.08 s prefill (held at the canonical 9.2K single‑shot representative; a 12,095‑token prefill would scale to ~1.42 s) + (~495 generated tokens × ~25 ms/token = ~12.4 s decode) + ~0.4 s of per‑turn tool/retrieval latency ≈ **~13.8 s** (the tool/turn term here combines the per‑turn tool + retrieval latency; Chapter 19's `T·L_agent` ≈ 660 ms is the same class of overhead at a different per-turn rate (Ch 19: 220 ms/turn → 660 ms at T=3; this case uses ~133 ms/turn → ~0.4 s) — a single model should use one rate consistently). (Scope of this W in the KV screen: it is used as the conditional proxy for $\mathrm{E}[W_{KV\text{-}resident}]$ under the explicit assumption that the scheduler keeps the KV block through the tool leg; if the engine releases KV at the step boundary, the ~0.4 s tool term belongs to $W_{\mathrm{e2e}}$ only, $\mathrm{E}[W_{KV\text{-}resident}]$ shrinks by that term, and the in-flight counts below fall correspondingly — the counts as written are the KV-held-through-tools case. This W is the full agentic service time — decode of all generated tokens plus the grown‑context prefill. Because the prefill is held at the canonical 9.2K representative rather than the full 12,095‑token context (which would scale it to ~1.42 s and give W ≈ 14.2 s), treat this ~13.8 s as a **lower bound** on the agentic service time, and the resulting in‑flight counts and host totals as corresponding lower bounds. It is *not* the incremental orchestration‑overhead figure of ~660 ms at T=3 that Chapter 19 reports as its $T \cdot L_\text{agent}$; the two are different quantities, and it is this full W that drives concurrency and fleet size, per Chapter 19's scope note.) So at the 100‑rps peak, in‑flight concurrency ≈ 100 × 13.8 ≈ 1,380 requests, not 200. Against C ≈ 13.8 per host (conservative integer floor 13), N ≈ ⌈1,380/(13 × 0.70 × 0.95)⌉ = ⌈1,380/8.645⌉ = ⌈159.63⌉ ≈ **160 hosts** on FP16 KV at the Table 17-1 policy (the ρ = 1 u-only screen reads ⌈1,380/(13 ×0.7)⌉ ≈ 152; ≈107 at full utilization). This is the honest arithmetic the service-time model produces — the naive "1–5 hosts" rps estimate is off by ~15–150× (about one to two orders of magnitude) because it ignores both the decode duration and the added turn latency.

**KV compression changes the answer.** Switching the KV cache to FP8 (κ ≈ 1.31 MB/token, raw byte-halving — 50% of BF16) cuts per‑request KV at T=3 to ~15.85 GB and raises C to ≈27.5 per host (436 ÷ 15.85 ≈ 27.5; conservative integer floor 27), giving N ≈ ⌈1,380/(27 ×0.70 ×0.95)⌉ = ⌈1,380/17.955⌉ = ⌈76.86⌉ ≈ **77 working hosts** at the Table 17-1 policy (the u-only screen would read 74; ≈52 at full utilization). Prefix caching can reduce repeated prefill work and share identical cached prefixes when the engine supports that representation. Its additional capacity benefit depends on prefix reuse and cache allocation; no further host-count reduction is quantified here. KV precision and prefix caching are the primary levers that make agentic fleets affordable, but even with both, an agentic 70B workload at 100 rps is a *multi‑dozen‑host* fleet, not a handful.

**Decision.** At the 100-rps sizing traffic, the integer-slot FP8 bound is **77 working hosts at the 70% × 95% policy, plus one spare host for N−1 operation: 78 hosts in total** (⌈1,380/(27 × 0.70 × 0.95)⌉ + 1; the u-only variant was 74 + 1 = 75). This is a KV-residency planning minimum, not a validated deployment size. Prefix caching may reduce the requirement, but no cache-hit ratio or additional host-count saving is assumed here. The proposed design uses NGINX with consistent hashing for session affinity and OpenTelemetry tracing on each host. With the illustrative φ = 0.05 and D = 5 MB, the network rule must also use the new 100-rps traffic: B_min = φ·λ·D = 0.05 × 100 × 5 MB = **25 MB/s = 0.20 Gbps**. The 2×B_min headroom screen is **0.40 Gbps**, below the existing 10 Gbps intra-rack link rate (B_min is an offered byte rate against that 1.25 GB/s link budget); the per-request transfer leg must also fit (§17.4.4). At 77 working hosts, the planned KV-slot occupancy is 1,380/(77 × 27) ≈ **66%** (69% on the u-only 74-host variant). This is not GPU compute utilization. A Chapter 14 deployment benchmark must validate service time, SLO-goodput, failover behavior, and measured φ and D before hardware is committed. End-to-end latency including agentic overhead remains an illustrative target until measured.

**Lesson.** The fleet decision is driven by KV‑residency capacity vs. **service‑time‑scaled concurrency** (λ·W) — not by raw rps, and not by a per‑layer KV constant. The architect's checklist: (1) compute I(T) for the expected turn distribution, (2) derive per‑host concurrent capacity C from the *canonical* per‑token KV (2 × layers × hidden × bytes), and (3) convert peak admitted rps into KV‑resident concurrency via λ_admitted·E[W_KV-resident] using the **mean KV‑holding time** (equal to the full service time only under the stated KV‑retention assumption). The full service time is prefill + decode of all generated tokens plus per‑turn tool latency *while KV is retained*; with it, step (4) computes N = ⌈λ·W/(C·u·ρ)⌉ + N_spare (Table 17-1) — a capacity requirement, to be combined as max(capacity, tail‑latency) before deployment. Steps (5) and (6): apply the cheapest capacity levers first — KV precision (FP8), prefix caching, attention architecture (GQA/MQA) — before buying hosts, and validate throughput and latency with a benchmark, not an assumption. A multi‑dozen‑host FP8 fleet costs meaningful GPU capital, but avoids both wasteful over‑provisioning and a costly re‑platform when traffic doubles.
