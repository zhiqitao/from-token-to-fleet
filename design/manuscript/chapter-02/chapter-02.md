# Chapter 2 — What Actually Happens During Inference

## The Architect's Question

After this chapter we should be able to reason about the two fundamental modes of LLM inference — prefill and decode — and to identify which system constraint each mode exposes. We should be able to compute the bandwidth and FLOP demands of a given workload, compare them against real hardware limits, and understand why, at the canonical low-batch operating point, decode sits in the memory-bandwidth-bound *regime* (weight-only arithmetic intensity ≈ 1 FLOP/byte, far left of the roofline ridge) while prefill sits in the compute-bound regime — and that this is a regime statement, not a universal rule: at other batch sizes and context lengths the binding constraint can shift. A regime label is also not a claim that the weight read saturates HBM. On the canonical 8×H100 host each GPU streams only its 17.5 GB shard — ~21% of peak bandwidth over the 25 ms step — so the binding terms at that operating point are the TP collectives, kernel efficiency, sampling and scheduling, and the ~9.2K-token KV attention read, not the weight read. The "bandwidth-bound" verdict that comes from comparing 5.6 TB/s against one device's 3.35 TB/s is the hypothetical whole-model-on-one-GPU case, labeled as such in §2.2 and Table 2-2 (Ch 8 develops the roofline). This distinction directly shapes architectural decisions: whether we need more GPUs, whether we can disaggregate prefill from decode, and how we size memory and compute in a fleet. After this chapter we should see inference not as a single monolithic cost but as two opposite-bound processes that require different levers.

## 1. Concept

Inference is the process of turning a sequence of input tokens into a sequence of output tokens using a trained neural network. In an autoregressive model, every generated token requires a fresh forward pass, but the computation split between the prefix (the prompt) and the suffix (the generated output) is fundamentally different.

**Prefill** is the first pass over the prompt. The model reads every token of the input context, computes attention over the entire prefix, and produces the first output token. During prefill, the model attends over all input positions, so the *attention* work grows with the square of the context length. (The full prefill also has a substantial *linear-in-L* component — the weight-matmul FLOPs, $2NL$ (where $N$ = model parameters and $L$ = tokens processed) — which does not grow quadratically; the quadratic term is the dense-attention pairwise component, developed in Ch 8 and Ch 22.)

*Timing convention (used throughout the book).* We attribute the **first sampled token to prefill**: prefill = processing the prompt + sampling token 1, and decode = the per-token loop that begins with token 1 as its first *input* and produces token 2 onward. This is the standard TTFT convention — time-to-first-token includes the first token's sampling, so the first token is the last output of prefill, not the first output of decode. (Some engines split this differently — e.g. counting the first token's forward pass as the first decode step — but the difference is one token's worth of latency, and every formula and figure in this book uses the convention above.)

*Written as a sum, end-to-end TTFT is* $\text{TTFT}_{\text{e2e}} = \text{retrieval} + \text{admission/queue} + \text{tokenization/transfer} + \text{prefill}$. It carries **no separate "first decode step" term**: under the convention above, the first token's forward pass is sampled inside prefill, so a term for it would count that work twice. The same formula is quoted verbatim in §4.3, and the ~1.08 s prefill residual used in §2.3 is the prefill term of that two-term budget (retrieval + prefill), with no allowance for the other terms. *This is the book's defining convention for TTFT, not an evidence-tagged measurement claim.*

**Decode** is the per-token generation that follows. After prefill, each new token only attends to the cached keys and values from the prefix plus all previously generated tokens. In the *batch-1-equivalent* weight-streaming model we use for this first-pass arithmetic, the per-step cost has two parts: the **weight-read** (the entire model weight matrix from HBM, constant in context length because the autoregressive pass reuses the same parameters every step) and the **attention over the growing KV cache** (linear in context length, since each new token attends to all cached keys/values). At the canonical operating point the weight-read dominates, so the per-step cost is *approximately* constant in context length — but that is a regime statement, not an identity; the attention term grows with context and is the one that eventually binds at long context (Ch 8, Ch 22). (In a real serving stack, batching and weight-read amortization change this per-request picture substantially; that is the subject of later chapters.)

The critical architectural insight, at the canonical low-batch operating point: prefill *tends* to be compute-bound (high arithmetic intensity — the whole prompt is processed in one parallel pass), while decode *tends* to be bandwidth-bound (low weight-reuse efficiency — each step re-reads the model weights for a single token: 140 GB in aggregate, or a 17.5 GB shard per GPU on the canonical 8×H100 host at TP = 8). These are the typical bottlenecks, and confusing them is the most common architectural misstep. But neither is a universal physical law: the characterization is an operating-point property of model × workload × kernel × hardware (batch size, attention length, and kernel fusion all shift it), and the roofline framework in Ch 8 is what identifies which regime a given kernel actually sits in.

One detail the figure makes explicit is *when* a token's K/V enters the cache. The first decode step, precisely: (a) prefill populates the cache with the prefix K/V and samples the first token; (b) that first token is the *input* that seeds the decode loop (the initialize path in Fig 2.1); (c) each decode step takes one input token, runs the transformer on it — which **computes and appends that input token's K/V** to the cache — attends over the cached K/V, and samples the next token from the logits; (d) the sampled next token is the *output* of this step and the *input* of the following step, whose forward pass then computes and appends its K/V. A token's K/V therefore enters the cache on the step in which it is the *input*, not on the step in which it is sampled.

Because the two phases stress *different* resources, the structure of the whole book rests on this single split.

**Where the Q/K/V and KV cache live in this picture (the bridge to Ch. 3/7).** The transformer layer computes, for each token, three learned projections — **query (Q)**, **key (K)** and **value (V)**. Attention scores are the similarity of a query to every prior key; the scores weight the values, which are blended into the token's new representation. What matters for architecture: **K and V for a token do not change once that token has been processed.** The query for a *later* token attends against them, but rewriting them would be redundant work. So decode does not recompute the prefix's K/V — it *reuses* the stored K and V from prefill. That is the KV cache: not an optimization bolted on, but the direct consequence of *which* projections are reusable and which (the query) is always new. It is also why KV memory grows with sequence length (one K and one V per token, per layer), why attention architecture and precision (GQA/MQA, KV quantization) change the bytes-per-token of what is really a memory problem, and why kernel choices like FlashAttention change the traffic, not the footprint. Ch. 3 and Ch. 7 do the arithmetic; this figure is where the causal thread starts.

**A vocabulary note that prevents a common conflation.** Several terms sound like the same thing but are *not* interchangeable, and the chapter will use them precisely:

| term | what it is | what it is **not** |
|---|---|---|
| **KV cache** | the stored K and V tensors per token per layer, saved so decode does not recompute the prefix | not an *optimization* over a shared prefix |
| **PagedAttention** | a memory-*allocation* scheme for the KV cache (splits it into fixed-size pages, cuts fragmentation/waste) | not a way to *reduce* the amount of KV state |
| **prefix caching / KV reuse** | reusing *already-computed* K/V for a shared prefix, to skip re-prefilling it | not the same as caching the KV of a *single* request's own decode |
| **prompt caching** | broader system/provider term; the book uses it to mean *reusing the KV of a shared prompt prefix across requests* | not a separate mechanism from prefix caching in this book's usage |
| **KV quantization** | reducing the *bytes* per K/V element (e.g. FP16→FP8) | not reducing the *number* of key/value entries |
| **KV offloading** | moving some KV state out of GPU HBM (to host DRAM/SSD), trading capacity against transfer latency | not shrinking the state itself |

The short version, each mechanism bound to the one constraint it attacks: the **KV cache** itself *is* the capacity demand (it is the state, and its size per sequence is what must fit); **PagedAttention** → *fragmentation* (it manages where that state lives on the device and wastes less of it); **prefix caching** → *redundant compute* (prefix caching avoids computing a shared prefix's K/V twice); **quantization** → *bytes per element* (quantization shrinks each element); **offloading** → *residency* (offloading moves some of that state elsewhere). One mechanism, one constraint, in that order — and each pairing carries its own trade-off; later chapters put numbers on them.

**The resource model (the book's recurring framework).** Inference consumes several *fundamentally different* resources, and the single most useful habit an architect can build is to name which one a given optimization or bottleneck is about. The pipeline figure above surfaces four of them, and the metric chapter (Ch. 6) and the design chapter (Ch. 12) build on the same set. The book will use these names consistently.

The discipline the book applies everywhere: **every optimization is a hypothesis about which resource it shifts and what it trades away.** FlashAttention moves the bottleneck from *bandwidth* toward *compute* (fewer HBM round-trips); KV quantization gains *capacity* at the cost of a small precision loss; prefix caching saves *prefill compute* at the cost of *cache residency*; continuous batching trades *latency* for *utilization*; P/D disaggregation trades a *homogeneous pool's* simplicity for separate *compute- vs bandwidth-optimized* pools. When the book introduces a technique, it will name the resource it targets and the resource it costs — that is the difference between reasoning and a vendor catalog. The optimization decision map (Ch 15, the *Optimization Decision Map* section) is Table 2-1 read backwards: from an observed symptom to the resource that is likely starved.

**The causal chain (how the chapters hold together).** The book is one argument, not a set of topics. The thread is:

tokens determine sequence length → sequence length determines KV growth and attention work → KV growth determines memory pressure → attention and model execution determine compute and bandwidth demand → those resource demands determine latency behavior → latency and concurrency determine scheduler requirements → scheduler behavior determines serving efficiency → serving efficiency and SLOs determine host count → host count and model topology determine interconnect and fleet architecture → fleet architecture determines cost, resilience, placement, and operational complexity.

The order above is the *physical dependency* order: what is computed from what. It is not the architect's working order. The Preface's six-question checklist (Q1–Q6) answers "How many hosts?" (Q4) from the per-host bound before it reaches "Who serves it, and how?" (Q5), because a host count can be sized from a per-host bound before the serving mechanism that sets its utilization is fixed. Read the chain as what depends on what, and the checklist as the sequence in which an architect resolves those dependencies.

Every chapter is one link of that chain, and each *deepens* the same mental model from Ch. 2 rather than restarting it. By the time the argument reaches Ch. 11 (serving) or Ch. 17 (fleet), the concepts were introduced in Ch. 2 — Ch. 2 gave the shape, the later chapters give the numbers and the decisions. If a chapter ever feels like "here is another concept," it has broken the thread.

## 2. Mental Model

Inference is two fundamentally different physical processes, distinguished by what limits them.

**In the canonical operating point — a long prompt with high arithmetic intensity — prefill is compute-bound.** It is like a massive industrial fire hose drawing one enormous burst of water out of a reservoir: the flow is huge, and the time it takes is limited entirely by the raw horsepower of the pump (compute/FLOPs) pushing the water. The pipe is wide open, but the motor is working at its absolute limit — and the burst delivers the first glass of water, the first token. (This is an operating-point property, not a fixed identity: a low-intensity prefill or a tiny prompt could shift it toward the bandwidth side — Ch. 8 makes the dependence on model × workload × kernel × hardware explicit.)

**In the canonical operating point — low batch — decode sits in the bandwidth-bound regime.** It is like pushing the water of that same 140 GB reservoir through a standard garden hose. On a single device, the full 140 GB must stream within each 25 ms step to produce one token: each step delivers one glass of water at its end, not a continuous flow. (The 140 GB hose is the single-device illustration. On the canonical 8×H100 host, each GPU streams only its 17.5 GB shard per step, which takes ~5.2 ms at peak — 21% of the 25 ms step.) The reservoir is not drained — the same weight volume is re-read every step: 140 GB in aggregate on one device, 17.5 GB per GPU on the canonical host. The pump (compute) is more than powerful enough, but the diameter of the hose (HBM bandwidth) physically cannot move that volume of water in that time frame. (Again an operating-point property, not an identity: at high batch decode can become compute-bound.)

**The regime label is not a saturation verdict.** The classification comes from arithmetic intensity — low-batch decode runs at ~1 FLOP/byte, far left of the ~295 FLOP/byte ridge — not from a per-GPU rate comparison. On the canonical 8×H100 host the weight read uses ~21% of peak HBM bandwidth, so it is *not* the binding term there; the binding terms at that operating point are the TP collectives, kernel efficiency, sampling and scheduling, and the attention read over the 9.2K-token KV cache. Reserve "bandwidth-bound" as a device verdict for the hypothetical whole-model-on-one-GPU case, where 5.6 TB/s is measured against one device's 3.35 TB/s (Table 2-2, §2.5; Ch 6 states the same scope).

When we ask "is this workload compute-bound or bandwidth-bound?" the answer depends entirely on which physical constraint we are hitting: the horsepower of the engine, or the diameter of the pipe.

**Figure convention (used throughout the book).** Arrows in the diagrams carry different meanings by context, and the reader should not assume one universal reading: a **data-flow** arrow (Fig 2.1, 11.3) shows tokens or activations moving; a **dependency** arrow shows "must be decided before"; an **influence** arrow (Fig 4.1) shows "constrains/informs"; a **causation** arrow (Fig 6.1) shows "drives / causes"; and a **conceptual-association** arrow (App. A.4) shows "relates to." Where a figure's arrows are ambiguous, the caption states the intended reading.

## 3. Worked Example

To make the distinction concrete, let us walk through the canonical enterprise Q&A scenario (Ch 4, Table 4-2): a 70B-class dense model in FP16, 1 host with 8×H100 GPUs, prompt of 1,200 tokens + 8K retrieved context (~9.2K input), 300-token output, TTFT budget 1.2 s (retrieval ~120 ms + prefill), TPOT budget ~25 ms/token. All numbers are derived from the canonical scenario; none are measurement claims. Where the book writes *Analytical bound — not a benchmark*, it marks a first-order model check under a stated bounding assumption, not a measurement of actual serving throughput.
*Scope of the single-host premise.* Throughout this chapter and the arithmetic chapters that follow, "1 host with 8×H100" is a **per-host / per-request feasibility** container: it asks whether one host can meet the per-request latency and memory SLO (TTFT 1.2 s, TPOT ~25 ms, KV residency) for a single in-flight request. It is **not** a claim that one host serves the canonical 10 rps average / 40 rps peak *arrival rate*. The per-request arithmetic here answers "does one host's compute/bandwidth/memory satisfy one request's latency budget"; the *capacity* question — how many such hosts to absorb λ = 40 rps, where in-flight concurrency λ·W ≈ 344 at the ~8.6 s service time (that occupancy and the canonical 8×H100 host definition are derived in Ch 4 §4.3 and Table 4-2) — is answered later (Ch 16–17), and is a different computation that must not be conflated with per-request feasibility. Keeping the two questions separate is the difference between sizing a host and sizing a fleet.

*Two distinct conclusions, kept deliberately separate. (1) **Regime:** weight-only arithmetic intensity places the canonical prefill point ~9.2K FLOP/byte (~7,850 FLOP/byte once the ~24 GB KV write is added to the denominator, which lowers the intensity, Ch 8) — well to the right of the ~295 ridge — so prefill sits in the compute-bound regime; decode at ~1 FLOP/byte sits in the memory-bound regime. *Basis of these intensity figures, so the chapters reconcile:* every value here divides the **linear-term** prefill FLOPs, $2NL$, by **weight bytes**. Adding the attention FLOPs to the **numerator** instead raises the weight-only value to ~10.8K FLOP/byte (the figure Ch 6, Table 6-1 quotes), while adding the ~24 GB KV write to the **denominator** is the correction that gives ~7,850. (2) **Capacity:** the stated TTFT deadline implies ~1.19 PFLOPS demand, exceeding the compared single-H100 theoretical peak (0.989 PFLOPS) — so one H100 is insufficient under that analytical deadline model. The regime classification and the capacity shortfall are independent: a workload can be compute-bound in regime yet still fit on the device, and vice versa. (Analytical bounds — not a benchmark: these are first-order model checks, not a measurement of actual serving throughput.)*

**Worked example arithmetic details:**

- **Decode bandwidth.** In autoregressive decode, generating one token requires a full forward pass of the 70B parameter matrix. At FP16 (2 bytes per parameter), the weight footprint is $M_\text{weights} = N \times 2 = 140$ GB. (The symbol is $M_\text{weights}$, not $W$: throughout the book $W$ is reserved for mean time in system in Little's law, $L = \lambda W$, Ch 4.) **This is the aggregate model-wide weight traffic** — but note the unit of comparison carefully. Name it precisely: this 140 GB is the **logical model-weight footprint used as a first-order HBM traffic approximation** (what later chapters call the **canonical weight-stream approximation**). It is the footprint that results from *reading every parameter once per decode step in a dense model with no reuse*, not a claim about physical HBM traffic in a real engine. Physical traffic depends on residency, caching hierarchy, fusion, batching, quantization, sharding, and implementation, and rises or falls accordingly. For a hypothetical single-device implementation holding the entire FP16 model, the aggregate model-weight traffic per decode step is ~140 GB; on a tensor-parallel deployment both weight residency *and* this traffic are sharded across GPUs, so the relevant comparison is per-GPU shard traffic against per-GPU HBM bandwidth, plus communication overhead. (A 140-GB FP16 model cannot reside on a single 80-GB H100 anyway, so the whole-model-on-one-GPU comparison is deliberately hypothetical.) With a TPOT budget of ~25 ms per token, the *aggregate* required bandwidth is

$$
B_\text{req} = \frac{M_\text{weights}}{\tau} = \frac{140 \text{ GB}}{0.025 \text{ s}} = 5{,}600 \text{ GB/s} = 5.6 \text{ TB/s}
$$

Since $5.6 > 3.35$, under this batch-1-equivalent weight-streaming model one H100 cannot supply the required *aggregate* weight-read rate — the decode phase is HBM-bandwidth-bound [canonical scenario][DERIVED]. - **Prefill FLOPs.** The prefill pass computes attention over the 9.2K input tokens and produces the first output token. The *parameterized-linear* FLOP floor for a dense transformer forward pass is well approximated as $2 \times \text{params} \times \text{tokens}$ (the factor of 2 accounts for multiply-add per parameter per token). Call this what it is: **the parameterized-linear FLOP floor, $2NL$, excluding explicit attention-score/value aggregation and other non-matmul overhead.** The full-attention component is *not* captured by $2NL$ — it grows ~quadratically with sequence length (Ch 22), so for a 9.2K-token prefill $2NL$ is a lower bound on total compute, not the whole story. $$
\text{prefill FLOPs} = 2 \times N \times L = 2 \times 70 \times 10^9 \times 9.2 \times 10^3 \approx 1.288 \times 10^{15} \approx 1.29 \text{ PFLOP}
$$

\text{rate} = \frac{1.29 \text{ PFLOP}}{1.08 \text{ s}} \approx 1.19 \text{ PFLOPS}

Better attention kernels are not one of them: they reduce HBM traffic, not the 2 × params × tokens FLOP floor, so at the canonical point (arithmetic intensity ~9.2K FLOP/byte >> ridge ~295) they cannot close the gap. Attention kernels are a lever for the bandwidth side of the ridge.

**Occupancy thresholds.** Two thresholds bound the *weight-matmul portion* of the step, and they rest on opposite batching models. At the canonical operating point the 5.2 ms weight read moves 21% of peak over the 25 ms step (5.2 ms is the time to stream the 17.5 GB shard at peak bandwidth); it saturates HBM above ~5 concurrent sequences per GPU (~40 per host) only in the no-amortization case where each sequence streams its own full 17.5 GB shard, with no weight-read amortization. Under amortized batching that read is shared across the batch, so the weight-matmul portion stays bandwidth-bound up to ~295 concurrent sequences per GPU (~2,360 per host) — the point where its arithmetic intensity (B tokens ≈ B FLOP/byte) reaches the ~295 FLOP/byte ridge and it becomes compute-bound. Neither number describes the full decode step: the attention portion reads KV cache at an intensity of only ~1 FLOP/byte for the full-MHA canonical model (~8 FLOP/byte for an 8:1 GQA geometry) and stays bandwidth-bound at every realistic batch size, so the real saturation threshold, which includes KV traffic (~3.01 GB/seq at the 9.2K input context per GPU), must be measured rather than read off either subset.

## 4. Measurement

How do we know whether a given workload is prefill-dominant or decode-dominant in practice? Three practical measurements:

1. **Divide the TTFT into retrieval + prefill.** Measure the retrieval latency (vector search, document fetch) separately from the prefill latency (prompt processing). In the canonical scenario, retrieval takes ~120 ms, leaving ~1.08 s for prefill on a 9.2K-token prompt. If prefill exceeds this budget, the bottleneck is compute or memory, not retrieval.

2. **Log TPOT against current sequence length, at controlled batch/concurrency.** Track the time-per-token as the generated sequence grows. This is a *scaling curve*, not a binary verdict. An **increasing** TPOT as the sequence lengthens reveals growing KV-attention cost — each new token attends over a longer KV sequence, and decode attention work and KV cache traffic generally grow with sequence length even though cached K/V projections are not recomputed. A relatively **flat** TPOT suggests weight streaming (a fixed per-step cost — reading the full 140 GB weight matrix each step) remains dominant. TPOT does not *have* to stay constant; batching, kernel choice, occupancy, and scheduling can make the observed curve complicated, so measure it rather than asserting a trend.

3. **Measure actual HBM utilization vs FLOP utilization.** Using GPU profilers (NVIDIA Nsight, vLLM stats), watch the fraction of peak HBM bandwidth consumed versus the fraction of peak FLOPS consumed. If HBM utilization is near 100% while FLOPS utilization is low, the kernel is bandwidth-bound (typical of decode). If FLOPS utilization is near 100% while HBM utilization is low, the kernel is compute-bound (typical of prefill).

These measurements cost nothing but a profiler attach and a few representative requests — and they prevent the architect from applying the wrong optimization lever.

## 5. Common Mistakes

- **Treating prefill and decode as the same bottleneck.** A dangerous mistake is assuming that what slows prefill will also slow decode, or vice versa. Prefill FLOPs scale with input length; in decode, the weight-read bytes per token are fixed, so at a given HBM bandwidth the decode rate is roughly constant per token. Confusing the two leads to over-provisioning compute for a bandwidth-bound workload, or under-provisioning compute for a compute-bound one.

- **Assuming one H100 suffices for 70B inference.** The arithmetic in §2.3 shows that a single H100 cannot hold or stream the whole 140 GB model (140 GB > 80 GB residency; and the aggregate 5.6 TB/s vs 3.35 TB/s is a hypothetical single-device comparison — on the canonical 8×H100 host each GPU streams only its 17.5 GB shard, i.e. 700 GB/s at a 25 ms TPOT) nor meet the prefill compute demand (1.19 PFLOPS required vs 0.989 PFLOPS peak, from 1.29 PFLOP / 1.08 s). Attributing 70B serveability to a single GPU ignores the opposite bottlenecks and produces an architecture that fails latency SLOs.

- **Ignoring the input/output token asymmetry.** A workload with 9.2K input tokens and 300 output tokens imposes a *substantial prefill compute burden* despite producing relatively few output tokens — output-token count alone does not determine serving cost or resource pressure. The two legs of the request have different cost structures and different optimization paths: decode is repeated per output token and dominates *wall-clock latency* (at the canonical ~25 ms/token, 300 output tokens take ~7.5 s of decode vs a ~1.08 s prefill budget), while prefill is a large one-shot burst of compute and dominates the *compute* burden (the 9.2K-input attention pass). Quoting only per-token latency or only throughput/s hides this distinction.

- **Using manufacturer-peak bandwidth/FLOPS without mapping to real kernels.** H100 3.35 TB/s HBM3 is the theoretical peak; actual sustained bandwidth for weight-read kernels may be 60–80% of peak [2°: industry rule of thumb][HYPOTHESIS][UNMEASURED] — not measured or cited here. H100 989 TFLOPS BF16 dense is the tensor-core peak; actual matmul throughput depends on kernel fusion, batching, and precision. Cross-technology numbers follow the same rule — name the SKU, not the memory class: the H200 (HBM3e successor to the H100) is 4.8 TB/s [1P][FACT: NVIDIA H200 SXM datasheet], B200-class HBM3e is ~8 TB/s [1P][FACT: NVIDIA B200 datasheet], and AMD MI300X is ~5.3 TB/s [1P][FACT: AMD Instinct MI300X datasheet] — vendor-published specifications, each read at the 2026-08-30 cutoff; verify against the specific generation in use. Citing raw numbers without kernel context is an anti-catalog error — the number must be matched to the actual serving kernel in use.

## 6. Architecture Consequence

The opposite bottlenecks of prefill and decode have immediate architectural consequences:

- **With prefill in the compute-bound regime → optimization levers:** model parallelism (splitting the 70B parameters across GPUs), more GPUs in parallel, or prefill-specific servers that dedicate hardware to the bursty preload phase. Kernel fusion (flash-attention, scaled-dot-product attention with fewer reads) is a *bandwidth-side* lever: it cuts HBM reads, so it helps when the prefill point sits on the bandwidth side of the ridge, not at the canonical ~9.2K FLOP/byte point. Lowering byte-width precision (e.g. FP8 on H100; FP4 only on Blackwell-class parts) does *not* reduce the underlying algorithmic operation count (the usual 2 × params × tokens FLOPs are approximately unchanged — the matmuls still multiply the same matrices); it lowers the bytes transferred/stored and can raise the *effective* accelerator throughput (8-bit tensor cores run at a higher peak rate). Changing format at the same byte width (BF16 in place of FP16) changes neither the bytes stored nor the H100 dense tensor-core peak: it trades mantissa precision for exponent range (10 → 7 explicit mantissa bits, 11 → 8 with the implicit leading bit), a numerical-stability choice rather than a throughput one.

- **With decode in the bandwidth-bound regime → optimization levers:** continuous batching (as implemented in vLLM) to amortize weight reads across many tokens in flight, trading per-request latency for utilization; PagedAttention (vLLM) to remove KV-cache fragmentation waste, raising effective KV capacity with no effect on weight traffic; KV cache offloading to SSD or system memory to raise KV capacity headroom, costing transfer latency and PCIe/host-DRAM traffic; P/D (prefill/decode) disaggregation (separate pools of GPUs for prefill bursts vs. decode steady state); and higher-bandwidth memory and interconnect topologies (HBM3e memory per GPU; NVSwitch/NVLink for GPU-to-GPU communication). Continuous batching amortizes weight reads and improves hardware utilization, scheduling efficiency, and aggregate goodput — but it does **not** reuse one request's transformer activations to avoid the forward-pass work of another unrelated request, so it does not reduce the mathematical FLOP count per request.

The key architectural decision this enables: **can we disaggregate prefill and decode onto different hardware?** If prefill needs more FLOPS and decode needs more bandwidth, a single homogeneous GPU pool is suboptimal. A two-pool architecture — a prefill cluster optimized for compute (more GPUs, higher FLOPS) and a decode cluster optimized for bandwidth (faster HBM, larger NVLink domains) — is therefore an architecture worth testing. Whether it actually needs fewer GPUs is not established by the asymmetry alone: it depends on achievable utilization, duplicated model residency, KV-transfer cost, interconnect topology, workload shape, burstiness, and the hardware assigned to each pool, all of which must be measured. (The asymmetry makes it a candidate worth benchmarking, not a concluded win.) This is the central theme of Chapter 11 (Serving) and the prefill/decode-disaggregation pattern (Ch 12, candidate b).

## 7. What We Still Don't Know

- **Sustained HBM bandwidth for weight-read kernels.** The 3.35 TB/s H100 figure is a theoretical peak; real serving kernels (vLLM, TGI, transformer-engine) may achieve different sustained rates depending on kernel fusion, graph optimization, and batch size. — a hypothesis to be measured on real hardware before it is cited.

- **Prefix-cache hit rate at fleet scale under realistic concurrency.** Compute that *is* re-used across requests sharing a common prefix is a different mechanism: **prefix caching** (or KV reuse), which skips the re-prefill of a shared prefix and thereby does cut real forward-pass work for that portion. The magnitude of the prefix-cache hit rate at fleet scale is not yet pinned down. — to be benchmarked with realistic concurrency patterns.

- **Cross-technology bandwidth in the target deployment.** Which generation's bandwidth is available in our target deployment, and does it change the GPU count for the canonical decode demand? The comparison to the 5.6 TB/s decode demand shifts the GPU count equation but does not change the fundamental bandwidth-bound vs compute-bound classification. — workload-dependent.

- **Effect of quantization on decode bandwidth vs prefill FLOPs.** Int4 or FP8 quantization reduces the weight bytes (e.g., 70B at FP8 = 70 GB instead of 140 GB [canonical scenario][DERIVED: 70B × 1 B per parameter, against 2 B at FP16]), which directly lowers the HBM read demand in decode; it does *not* reduce the algorithmic operation count of the matmuls (the 2 × params × tokens FLOPs are approximately unchanged), though lower precision can raise the *effective* throughput of the tensor cores at which those ops run. The direction of the shift is clear (decode bandwidth improves; prefill ceiling rises in effective rate), but the precise trade-off point where decode becomes compute-bound rather than bandwidth-bound depends on the quantization scheme and hardware support. — workload-dependent.

## 8. End-of-Chapter Mini-Case: TTFT and the Prefill/Decode Split

The architect is still in the early design conversation about the internal Q&A tool described in Chapter 1. The team has settled on a 70B-class dense model for accuracy, and they have a rough traffic estimate: a ~2,000-employee population producing the canonical aggregate traffic (~10 requests/s average, peaks ~40 rps), with prompts of ~1,200 tokens of internal documents plus ~8K retrieved context and ~300 tokens of answer.

From the unit-and-token work of Ch 1 alone, the architect can already state the hard numbers: each request carries ~9.2K input tokens and ~300 output tokens. At 10 rps average, the system must sustain ~92,000 input tokens/s in prefill and ~3,000 output tokens/s in decode. At 40 rps peak, those numbers jump to ~368,000 and ~12,000 respectively. The architect can also state the two opposite bottlenecks: prefill will be compute-bound (~1.29 PFLOP per request at 9.2K input, the linear term alone; ~1.51 PFLOP with the attention term, Ch 8), and decode sits in the bandwidth-bound *regime* on intensity (low-batch decode runs at ~1 FLOP/byte, well left of the roofline ridge). The regime label is not a forecast that the weight read binds on this host. Each GPU streams only its 17.5 GB shard, which takes ~5.2 ms at the 3.35 TB/s peak — ~21% of the 25 ms step — so weight-read bandwidth is not the binding term at this operating point (Table 2-2; §2.5). The ~140 GB/token, ~5.6 TB/s figure is the single-device aggregate: it shows the roofline point, and it is not a deployable layout, because a 140 GB FP16 model does not fit on one 80 GB H100. Do not size decode for 5.6 TB/s. The team's immediate architectural choice is whether to build a single homogeneous GPU cluster or to separate prefill and decode pools — the differing bottleneck profiles make disaggregation worth evaluating, though whether it uses fewer GPUs must be measured rather than assumed (Ch 11).

Before passing this workload to Chapter 4 (workload anatomy), the architect locks in one more number: the tokens-per-request split. This is the currency every downstream chapter will price against, and it has already been established as ~9.2K input + ~300 output per request. The rest of the design — model fitting, memory budget, latency budget, cost — can now proceed in token-denominated terms.
