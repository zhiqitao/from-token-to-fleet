# Chapter 15 — Performance Engineering: From “It Works” to “It Meets the SLO”

## The Architect's Question

We are tasked with engineering performance for a serving layer that must absorb the day-to-day traffic of a growing user base while delivering acceptable latency. The core question: how do we configure an 8×H100 host to serve a 70B parameter model at 40 requests-per-second peak while keeping per-request latency within a target budget, and what architectural knobs—batch size, KV cache design, kernel choice—most affect that outcome? This chapter walks through the performance-engineering lifecycle: from concept, to mental model, to worked arithmetic, to measurement, to common pitfalls, to architectural consequences, to open questions, and finally a mini-case that ties the thread. 

## 1. Concept

Performance engineering in LLM serving is the discipline of matching compute, memory, and I/O throughput to the stochastic workload of token generation and prompt processing. Unlike traditional web serving, where request‑cycle overhead dominates the tail, the dominant cost in LLM inference is the arithmetic intensity of transformer matrix multiplications and the memory bandwidth consumed by KV cache reads and writes on every token step. The serving system must therefore optimize three inter‑dependent quantities: token throughput (tokens/s), per-token latency, and GPU memory utilization. These are governed by the model FLOP count, the chosen kernel (e.g. FlashAttention vs. scaled‑dot‑product), and the batching strategy (static vs. dynamic, continuous vs. chunked). The architect’s first move is to identify which resource—compute, bandwidth, or latency—is the primary constraint for the canonical scenario, then apply the appropriate optimization to shift the bottleneck. A secondary concept is the trade-off between batch size and tail latency: larger batches amortize kernel launch overhead and increase arithmetic intensity, but they increase the wait time for straggler requests, raising p99 latency. The designer must therefore balance arithmetic gain against tail‑latency penalty, a tension that shapes every later architectural decision.

## 2. Mental Model

We model the serving request lifecycle as a pipeline of computational phases with a cross‑cutting state‑management plane. The compute phases run in order: (1) request preprocessing / tokenization, (2) prefill, (3) iterative model decode, (4) token sampling / selection, (5) detokenization / streaming. **KV management is not a temporal stage after generation** — allocation, growth, paging, reuse, eviction, and (in a disaggregated deployment) transfer occur throughout the whole request lifetime, so we draw it as a state‑management plane that spans prefill and decode rather than a step that follows them. Each compute phase has a resource ceiling: compute‑bound phases are limited by TFLOPS, memory‑bound phases by GB/s of GPU HBM bandwidth. The architecture designer must identify which phase is bottlenecked for the canonical scenario and then apply the appropriate optimization—kernel fusion, cache reuse, or batching—to shift the bottleneck. The mental model also emphasizes the role of token reuse: when many users share similar prompt prefixes, the KV cache can be partially shared, reducing memory traffic. This reuse effect is difficult to quantify without workload profiling, but it is a first‑order consideration in multi‑tenant serving. The model also captures the interaction between sequence length and memory cost: attention quadraticities (O(L²) FLOPs and O(L²) memory per head once the $QK^{T}$/softmax score matrix is materialized) mean that long contexts (9,000+ tokens) disproportionately strain both compute and HBM bandwidth, making kernel choice (FlashAttention vs. SDPA) one of the first *kernel‑level* optimizations to validate for long‑context prefill — not a demonstrated global ranking, since prefix reuse, KV precision, batching policy, P/D scheduling, weight precision, admission control, and simply provisioning more prefill capacity can each dominate depending on the measured workload.

## 3. Worked Example

Canonical scenario: ~2,000 registered users, ~5% concurrent (100 users), ~10 rps average / ~40 rps peak, prompt ~9,200 input tokens + ~300 output, the canonical 80-layer, hidden-8192, full-MHA 70B reference model (a 70B-class dense FP16 model), 8×H100 host with 640 GB GPU memory.

*Derived quantity 1 – concurrent users:* 2,000 ×0.05 = 100 users.

*Derived quantity 2 – peak token throughput demand:* At 40 rps the workload mixes **prefill** (input) and **decode** (output) tokens, and they hit the hardware differently. Prefill demand = 40 rps × 9,200 = 368,000 input tokens/s; decode demand = 40 rps × 300 = 12,000 output tokens/s. These two regimes must not be collapsed into one "380,000 tokens/s" when reasoning about compute, because long-prompt prefill commonly occupies a higher-arithmetic-intensity regime and low-batch decode commonly occupies a lower-arithmetic-intensity regime; whether either phase is actually compute- or bandwidth-bound is a property of the model × workload × kernel × hardware operating point (Chapter 8).

**A hard terminology distinction the rest of this book relies on.** Do not conflate two separate statements:

- **Kernel regime** — the arithmetic intensity of the *kernel* relative to the roofline ridge (is this one kernel compute-bound or bandwidth-bound?).
- **Workload capacity deficit** — the aggregate offered demand relative to the achievable service capacity (does the *deployment* have enough compute/bandwidth/concurrency to absorb this arrival rate?).

A workload can exceed a deployment's capacity even when the underlying kernel is not compute-bound; conversely, a compute-bound kernel does not imply the deployed fleet lacks compute. In the canonical scenario at peak, prefill exerts a large aggregate compute *demand* (a capacity-deficit signal), while the prefill *kernel's* high arithmetic intensity is what makes it land on the compute plateau of the roofline — two different facts that happen to co-occur. Keep them separate.

*Compute demand versus peak — and why this is not an MFU:* A 70B FP16 transformer needs ≈2 ×70×10⁹ FLOPs per generated token. The instantaneous prefill compute demand is 368,000 ×2 × 70×10⁹ ≈ 5.15 ×10¹⁶ FLOPs/s, against a theoretical FP16-dense peak of 8 ×989 TFLOPS = 7.91 ×10¹⁵ FLOPs/s for the 8×H100 host (989 TFLOPS per GPU, Chapter 8 canonical). Taken naively this ratio is ~6.5× — a demand that *exceeds* a single host's peak. That is a legitimate and important architectural signal: a single 8×H100 host cannot prefill the peak arrival rate on the naive dense-FLOP model, so prefill either needs to be spread across burst headroom, handled by prompt/prefix caching, disaggregated (P/D separation), or absorbed by queueing headroom at off-peak. What it must **not** be called is “MFU = 6.5”: MFU (Model FLOPs Utilization) is by definition achieved realities divided by peak — a utilization ratio that **cannot exceed 1.0**. Presenting a ratio above 1 for a utilization metric is a unit/modeling error. The honest formulation separates the two quantities. The first is a *congestion check*: is the arrival-rate FLOP demand above or below peak? Here it is ~6.5× above for prefill, so the host is prefill-starved at peak and must lean on caching/batching/queueing. The second is an *achieved MFU*: measured device FLOPs ÷ peak, which we only report from a real benchmark. For illustration we suppose it lands in the 30–40 % range for FlashAttention-based inference. The decode figure at 12,000 tokens/s is ≈ 1.68 ×10¹⁵ ÷ 7.91 ×10¹⁵ ≈ 0.21, i.e. ~21 % — again a groundable number, not a ceiling-defying one; the actual achieved value must come from the target serving benchmark. The architectural conclusion, that there is no single bottleneck for the whole request, stands — and it must be argued phase by phase. At the canonical peak, prefill shows a *workload capacity deficit* — aggregate compute demand above the host's peak (it needs more FLOPs/s than the host can supply, and leans on caching/queueing). Decode is primarily memory-bandwidth constrained, and maximum concurrency is constrained by KV residency. Each phase is established from arithmetic intensity and the roofline (Chapter 8), never from an impossible "MFU > 1." None of them is the same statement as "the prefill kernel is compute-bound." The ~6.5× figure is a **lower-bound impossibility check** (the host cannot meet peak on the naive dense model), not a fleet-sizing estimate: the real fleet count comes from the achieved prefill tokens/s under the actual latency SLO and representative traffic mix (Ch 17/20), and it is sensitive to cache-hit rate, input-length distribution, batch schedule, and sustainable efficiency — the 6.5× only says "more than one host is required," not "how many."

*KV cache memory footprint:* The KV cache grows linearly with cached context and layers; it must never be computed per-layer and then treated as the whole-model total. For the canonical full-MHA reference geometry (80 layers, hidden dimension 8,192 — the 70B-class teaching model, not a universal 70B property), the per-token footprint across ALL layers is 2 × layers × hidden × bytes = 2 ×80 ×8,192 ×2 = 2,621,440 B ≈ 2.62 MB/token (2.5 MiB; canonical value from Chapter 7) — not the 32 KB that a single-layer calculation would suggest. For a 9,500-token context, one user's KV cache is therefore ≈9,500 ×2.62 MB ≈ 24.9 GB, not ~304 MB. For the canonical workload's ~86 average in-flight requests at 10 rps (L_exec = λ × W_exec ≈ 10 × 8.6; see Ch 4 — note ~86 is the *request occupancy*, distinct from the ~100 *active-user* population), the total KV cache would be ≈86 × 24.9 GB ≈ 2,140 GB — which **does not** fit the 640 GB GPU pool; using the canonical practical KV budget (640 GB − 140 GB weights − ~64 GB runtime/workspace ≈ 436 GB), only ≈17.5 concurrent *requests* (9,500-token KV each) fit on-host for KV (436 GB ÷ 24.9037 GB; conservative integer floor 17 (aggregate bound; per-rank and fragmentation must be checked separately)), before also reserving weight residency. This is a decisive, order-of-magnitude correction to the intuitive picture: long-context KV is a first-order memory constraint, and the architect sizes concurrency by KV capacity, not by the small per-layer number. Doubling context to 19,000 tokens pushes per-user KV to ~49.8 GB (19,000 × 2.62 MB) and halves on-host concurrency to ~8.7 (436 GB ÷ 49.8 GB; conservative integer floor 8). The canonical unit-check rule (quantity/unit/formula/substitution/result/sanity) catches this class of error: if 9,500 tokens × ~2.5 MB/token ≈ 24 GB does not reconcile with the intended ~304 MB, the unit layer-count has been dropped.

*Attention FLOP comparison:* Scaled‑dot‑product attention (SDPA) for 9,200‑token prompts. Note the 2P/token figure above approximates the *parameterized dense‑matmul* work per token (2 × parameters); it does **not** capture all sequence‑length‑dependent attention work, which is accounted for separately here. Attention is two matmuls per token per head — Q·$K^{T}$ then ·V — each a multiply‑accumulate of L²·d, so in FLOPs (2 per MAC) the per‑layer cost is ≈ 4 × L² × d_model, where L=9,200 and d_model=8,192. That is 4 × 9,200² × 8,192 ≈ 2.8 × 10¹² FLOPs per layer (the full 64 heads; the per‑head figure 4 × 9,200² × 128 ≈ 4.3 × 10¹⁰ must be multiplied by the number of heads, not quoted alone). Across 80 layers that is ≈ 2.2 × 10¹⁴ FLOPs — the quadratic attention term that grows dominant at long context, matching Chapter 8's 4·n_layers·L²·d formula: the attention term is ≈17% of the parameter-matmul FLOPs (≈15% of total forward FLOPs) at 9.2K (Fig 22.1).

*Read the figure as an I/O story, not a speed-up number.* FlashAttention is **not** "faster attention" in the sense that it does less arithmetic. It computes the exact same Q·$K^{T}$, softmax, ·V sequence. What changes is *where the intermediate lives*: a naive kernel writes the L×L attention matrix to HBM and reads it back, so the materialized intermediate itself is O(L²) in memory; FlashAttention avoids materializing that full L×L matrix in HBM and instead tiles the computation so each tile stays in on-chip registers/shared memory with the softmax done online — substantially reducing HBM reads/writes through tiled on-chip computation (the precise I/O complexity is more nuanced than a clean quadratic-to-linear swap, but the materialized-intermediate traffic is what drops). Because the arithmetic intensity — FLOP/byte — rises (same FLOPs, far fewer bytes moved), the kernel moves *up* the hardware ladder of Fig 8.1 toward the compute-bound region, even though the model and the math are unchanged. That is the whole reason the speed-up is workload-dependent: it is largest for long contexts where the O(L²) intermediate dominates, and negligible for short ones where HBM traffic is already small. It is also why the improvement should be *measured* (Ch. 14) rather than quoted from a published "2–3×" figure that was never portable.

## 4. Measurement

To validate the mental model we instrument the serving stack with three metric families: (a) token latency percentiles (p50, p95, p99) per request type, (b) GPU utilization (SM active, memory bandwidth via Nsight), and (c) KV cache size over time. A minimal benchmark runs 40 rps with warm‑up, records the p95 token latency, and measures the GPU memory fraction consumed by KV cache. Repeating with different batch sizes (1, 4, 16, 32) reveals the throughput‑latency knee. The *illustrative* numbers below are scenario values to be measured on the target stack, not vendor or published figures: beyond batch‑4 the p95 latency typically rises (implying a knee near batch 4) because kernel launch overhead is amortized but inter‑request token interleaving increases cache thrashing. **On the FlashAttention "traffic reduction" claim, be precise about the units:** one often sees a FlashAttention‑class kernel reported at a *different achieved HBM bandwidth* than a naive SDPA kernel (illustratively ~150 GB/s vs ~400 GB/s for 9,500‑token contexts). That is a *rate*, not a byte count. A bandwidth figure alone does not establish that fewer *bytes/request* were transferred — it only shows the kernel's achieved memory throughput. To claim a traffic reduction, compare the **bytes transferred per request** (or read/write transaction counters) under a *matched* workload; the FlashAttention advantage shows up there as fewer materialized/intermediate bytes, not as a low raw bandwidth. **And separate the two cache concepts**: "cold‑start KV warm‑up" (populating the KV-cache blocks for a new context) is different from "model‑weight loading" (streaming the 140 GB weights into HBM) and from CUDA/JIT kernel warm‑up. A 70B cold‑start that reuses cached weights is far faster than one that must load them from scratch — but these are distinct effects, not one number. ## The Optimization Decision Map

The measurement section tells us *what is slow*; this map tells us *which lever to try next*. It is organized as a symptom → bottleneck → evidence → candidate mechanism chain, so the architect diagnoses before acting rather than applying a known technique by fashion. **Every mechanism below is a hypothesis to benchmark, not a guaranteed win** — each trades one resource for another, and whether it helps depends on the measured workload and hardware (Ch. 14).

| observed symptom | likely bottleneck | evidence / measurement | mechanisms worth evaluating | key trade-off | architecture consequence |
|---|---|---|---|---|---|
| high TTFT + compute saturated during prefill | prefill compute | FLOP utilization, prefill queue depth, prefix-cache hit rate | prefix caching, chunked prefill, faster/batched kernels, more compute, P/D separation | compute vs added latency/capacity | add prefill capacity or cache prefixes |
| high TPOT/ITL + HBM bandwidth saturated | decode bandwidth | HBM bandwidth utilization, effective bytes/token | quantization, batching up, speculative decoding, smaller active params, more bandwidth | latency vs batch/tail | add bandwidth or shrink bytes/token |
| KV exhaustion / low concurrency | memory capacity | KV bytes/token, context distribution, fragmentation, active sequences | GQA/MQA (if model allows), KV quantization, PagedAttention, context reduction, eviction/offload, prefix reuse | capacity vs transfer latency | lower per-request KV or offload |
| long-context attention dominated by memory traffic | attention I/O | attention kernel memory traffic vs compute | FlashAttention-class fused/tiled kernels | kernel adoption vs coverage | kernel choice matters for long ctx |
| low GPU util, request-lifecycle mismatch | scheduling | SLO miss %, token-size variance, queue depth | continuous batching, scheduler policy | throughput vs tail latency | scheduler is a first-class choice |
| prefill and decode interfering | heterogeneous resource demand | mixed-workload p99, phase-locked stalls | P/D disaggregation — *only after* measuring that the benefit exceeds KV-transfer + orchestration + capacity cost | separation benefit vs KV-transfer cost | possibly two pools |
| multi-GPU execution dominated by communication | interconnect / parallelism | collective time, TP/PP/EP balance, placement | retune TP/PP/EP/DP topology, placement, partitioning | parallelism vs interconnect | topology is a cost lever |

**Two cautions.** First, do not read the table as "technique X fixes symptom Y": the same symptom can come from two bottlenecks (high TPOT with a bandwidth-saturated GPU is different from high TPOT with a capacity-capped GPU), so the *evidence* column matters as much as the symptom. Second, the last two rows (P/D disaggregation, interconnect tuning) are the expensive, structural levers — they are worth testing only after the cheaper in-kernel and in-scheduler mechanisms have been measured and shown insufficient, because they change capacity, orchestration, and cost, not just a kernel constant.

## Two Mechanisms, Read as Mechanisms

Two entries in the map deserve their mechanism spelled out, because they are frequently cited by reported speed-up numbers rather than by how they work.

**Speculative decoding.** The idea is to turn one slow serial step into a *draft-then-verify* pair. A small, cheap **draft model** proposes a candidate sequence of tokens; the larger **target model** then *verifies* all of them in a single batched forward pass, accepting the ones that match its own distribution. The loop is: draft → propose candidates → target verifies → accept a prefix → continue from the last accepted token. Why this can be faster: the expensive part of decode is not the arithmetic per token but the *serialization* — each target-model step streams the weights from HBM. If the draft can propose $k$ tokens that the target accepts in one verification pass, the target's expensive weight-stream is spent once on $k$ tokens instead of $k$ times on one — a genuine reduction in HBM round-trips (the same resource the FlashAttention discussion is about, but at the whole-model scale). Why it is *not* free: the draft costs extra compute, the verification pass itself has cost, and the **acceptance rate** (how many of the proposed tokens the target actually accepts) decides the win — a low acceptance rate means the draft and verification are spent for almost nothing. It is therefore workload/model/hardware dependent: a draft that closely matches the target (or a workload that is highly predictable) accepts more. **No published speed-up is portable**: a "6×" from one model/paper is a statement about that evaluation, not a guarantee for a different model or serving stack — measure it on the target workload or treat it as a hypothesis.

One subtlety about "matching its own distribution": the target does *not* simply accept the draft tokens that happen to agree. Under stochastic sampling, accepting a proposed token outright (rather than by the exact-speculative-sampling correction that re-weighs each accepted and rejected token by the target's posterior) can bias the output distribution away from the target model's true distribution. The distribution-preserving result holds only when each proposed token is accepted or rejected by the exact acceptance/sampling procedure (the modified-rejection-sampling step of Leviathan et al., "Fast Inference from Transformers via Speculative Decoding," arXiv:2211.17192; see the Sources chapter), which re-normalizes the continuation at each step. For greedy/argmax decoding the agreement test is exact; for temperature/prompt-driven sampling it is not, and the acceptance criterion must be the correction procedure, not mere token equality.

**Chunked prefill.** A very long prompt produces a large prefill operation that can monopolize the compute for hundreds of milliseconds, stalling concurrent latency-sensitive decode work. **Chunked prefill** splits that prefill into smaller pieces and interleaves them with decode steps in the scheduler, so the GPU keeps serving decode between prefill chunks instead of blocking on one burst. The causal chain: long prompt → large prefill → scheduler/resource monopolization → decode interference → TTFT *and* TPOT both degrade → chunked prefill as a scheduling mechanism to bound the per-phase burst. The trade-off is *not* "smaller is better": a smaller chunk reduces the decode stall but adds scheduler overhead (more per-chunk bookkeeping, potentially lower prefill throughput from less parallelism within a chunk), so chunk size is an empirically-chosen middle — measure the goodput/latency knee rather than assume.

## 5. Common Mistakes

*Over‑provisioning batch size to chase throughput:* Increasing batch size improves TFLOPS utilization but degrades p99 latency because tail requests wait for larger chunks to fill. The designer must balance batch‑size‑driven arithmetic gain against tail‑latency penalty. A practical illustrative rule of thumb: choose the smallest batch size that keeps MFU above ~25 % while keeping p95 latency under the SLO target (the 25 % threshold and the knee are scenario values — measure them on the target workload).
*Ignoring KV cache growth:* A 70B model with 9,500‑token contexts consumes ≈24.9 GB of KV per user (≈2.62 MB/token × 9,500, max end-of-generation). Without cache eviction, compression, or a concurrency cap, even ~17.5 concurrent *requests* would exhaust the host's canonical practical KV budget (~436 GB after weights + runtime), so 100 concurrent full-context users require either multiple hosts, much shorter contexts, or KV compression (FP8/8-bit). **But be precise about what "evicting" a context means, because it is not one action.** Three distinct mechanisms exist. (a) *Evicting an idle/inactive prefix-cache entry* — a cached prefix not currently in service — is safe, because no active request depends on it and it can be recomputed on reuse. (b) *Offloading or recomputing the KV of an active request* whose context is still being generated changes nothing about semantics, but it costs a recompute or a transfer when the request resumes. (c) *Deliberate sliding-window or context-truncation strategies* drop older tokens of an *active* request's context. This **changes the model's effective context**: it alters what the attention can attend to, and it is a semantics change, not merely a memory optimization. LRU of inactive cached prefixes is different from truncating active KV. Do not conflate them. **KV quantization** is a separate, orthogonal lever that cuts the per-token footprint without changing semantics (FP8 ≈2.62 → ~1.31 MB/token — exactly 50% of BF16 by raw tensor byte-halving, the same FP8 constant defined in Ch 7; vLLM's cited 54% [S6] is a decode inter-token-latency slope, a latency metric, not a memory ratio, and any allocator block/metadata overhead is not vendor-measured).
*Using scaled‑dot‑product attention without FlashAttention:* For long contexts (9,200+ tokens) the quadratic memory cost of SDPA (O(L²)) dominates the FLOP cost. FlashAttention fuses read‑write‑compute and reduces HBM traffic by ~3–5× ([ILLUSTRATIVE] — kernel- and length-dependent; measure bytes/request on the target stack), raising effective arithmetic intensity. This is one of the highest-impact *kernel-level* choices (it sits among prefix caching, KV-precision, batching, and P/D disaggregation as a major lever, not the single deciding one), and it pays off specifically when memory-bound; for moderate lengths (2,000–4,000 tokens) the HBM bandwidth reduction typically translates to a ~1.3–1.8× throughput gain on H100 (illustrative — bench the specific kernel on the target hardware).
*Neglecting kernel launch overhead:* In dynamic‑batching setups, each new token generation can trigger a kernel launch. Without continuous batching or token‑level fusion, the kernel-launch overhead (illustratively ~10–20 % of GPU time on H100-class parts at this traffic) can artificially depress measured MFU.

## 6. Architecture Consequence

The measurement and mistake analysis drive three architecture decisions for the canonical deployment: (1) FlashAttention‑2 as the default attention kernel, fused with RoPE and QKV projection to minimize HBM transactions; (2) continuous batching, with the maximum chunk size chosen empirically from the measured goodput/latency knee (a chunk size of 8 tokens is an [ILLUSTRATIVE] configuration, not the recommendation — the knee must be measured on the target stack); (3) KV cache management via FP8 KV quantization (≈2.62 → ~1.31 MB/token — exactly 50% of BF16 by raw tensor byte-halving, cutting a 9,500‑token per‑user KV to ~12.45 GB; vLLM's 54% [S6] is a decode inter-token-latency slope, a latency metric, not a memory ratio, and any block/metadata overhead is not vendor-measured) plus length‑based eviction, so that under the same ~436 GB practical KV budget on‑host concurrency rises from ~17.5 to ~35.0 full‑context users (436 GB ÷ 12.45 GB). These choices together are expected to raise achieved token throughput from ~8,000 tokens/s (raw, no flash, batch‑1) toward an illustrative ~35,000–70,000 tokens/s [ILLUSTRATIVE achievable range] (with flash, continuous batch) — the exact figure must come from the target benchmark — while keeping the host's 640 GB for weights plus KV. A fourth decision, borne out of the mini‑case (Ch11 §11.8), is to design the request‑routing layer for KV cache affinity: when a user re‑submits a request, routing to the same GPU avoids cache warm‑up penalties and keeps p99 latency under the target SLO.

## 7. What We Still Don't Know

*How does token‑level sparsity in user prompts affect the actual FLOP/token cost, and can we exploit it without accuracy loss?* Sparse prompt patterns (e.g. few‑shot prefixes, cached query prefixes) could reduce the effective FLOP count, but the savings depend on the sparsity pattern and the attention implementation.
*What is the optimal continuous‑batch chunk size as a function of request arrival distribution (Poisson vs. bursty) and tail‑latency targets?* Analytical models assume Poisson arrivals, but real user traffic exhibits bursts (e.g. social‑media events) that may require larger chunks or alternative back‑pressure mechanisms.
*Can in‑flight KV cache compression (e.g. speculative decoding–guided pruning) reduce memory pressure without increasing p99 latency?* Pruning less‑important key/value pairs based on attention weight magnitudes is promising, but the accuracy‑latency trade‑off needs empirical validation across model families.
*How does multi‑tenant isolation—guarding one user’s cache from another’s—translate to multi‑GPU scaling when the model exceeds a single GPU’s 80 GB?* Model parallelism (pipeline or tensor) adds communication overhead; the performance cost of moving KV cache between GPUs during tenant rotation is an open question.

## 8. End-of-Chapter Mini-Case: The Second Host: a Kernel/Batching Gain, Not a Capacity Win

A new deployment adds 500 registered users (traffic rises to ~12.5/50 rps at the same 5 % concurrency profile). The team provisions a second 8×H100 host and (in this worked example) runs the benchmark with continuous batching and FlashAttention‑2. The p95 queueing/scheduling delay ahead of prefill — not TTFT, which at this profile is dominated by the canonical ~1.08 s prefill (Chapters 4/8; Chapter 14 measures p95 TTFT at 1.9 s for this stack) — drops from 320 ms (single host, batch‑1) to 140 ms (dual host, continuous batch), and token throughput rises from 8,000 to 70,000 tokens/s. *Do not read the 8.75× throughput jump as a capacity-side win.* It is dominated by the **kernel/batching** change (batch‑1 no‑flash → continuous batching with FlashAttention‑2), which is worth most of the multiplicative gain, **plus ~2× from adding the second host** — the two are not separable from this single outcome number.
