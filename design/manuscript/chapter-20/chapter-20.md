# Chapter 20 — Fleet-Level Optimization

## The Architect's Question

As a RAG Q&A workload scales from a single host to a fleet of serving nodes, the architect must confront a new set of trade-offs: how does aggregate throughput scale with added hardware, how does scheduling latency affect user-perceived latency, and at what point does autoscaling cease to be cost-effective? This chapter addresses these questions through concrete arithmetic, not hand-waving.

## 1. Concept

Fleet-level optimization treats the entire collection of serving hosts as a single resource pool rather than independent islands. The central insight is that aggregate system throughput is not merely the sum of individual host throughputs; it is modulated by scheduling overhead, network contention, and the cost of moving data between hosts and storage. Two cost effects must be kept distinct. The **average** cost per query declines only along the canonical 10 → 40 rps ramp, where fixed overhead (model loading, infrastructure, staff) is spread across 4× the requests and across more SLO-compliant completions per observation window (Ch 14's goodput definition). Cost per request may decline only until additional capacity steps dominate; adding idle hosts at fixed demand raises unit cost. The **marginal** cost of each added host, however, is roughly constant in this model — one host buys ~2.0 req/s (17/8.6 = 1.977, [ANALYTICAL]) at ~$20/hr, so the marginal cost stays near ~$10 per req/s per hour (Ch 17 §7 frames the Nth host as diminishing marginal *benefit*, not falling marginal cost). Unit convention for this chapter: *rps* denotes an arrival rate and *req/s* a capacity rate; both are requests per second. The economic lever is amortizing the fixed term, not the marginal one.

\Needspace{7\baselineskip}

The key concepts are:

- **Aggregate throughput**: The total queries-per-second the fleet can sustain before latency SLO violations.
- **Scheduling overhead**: The per-request cost of dispatching a query to an available host, including placement decisions and data movement.
- **Autoscaling break-even**: The point at which growth in SLO-compliant completions per observation window covers the next host's fixed cost — *average* cost per query falls as fixed costs amortize, while marginal cost per query stays roughly constant.

## 2. Mental Model

The mental model for fleet optimization replaces the single-host query pipeline with a two-level hierarchy. At the lower level, each host processes queries using its GPU/CPU pipeline. At the upper level, a scheduler routes incoming requests across hosts, handling load balancing, model parallelism where needed, and graceful degradation under overload.

The scheduler's decisions have direct impact on the tail of the latency distribution. Poor placement can cause some hosts to saturate while others remain underutilized, inflating the 99th-percentile latency even when aggregate throughput is ample. Conversely, intelligent scheduling — such as consistent hashing for session affinity or predictive placement based on historical patterns — tends to keep utilization more uniform across the fleet and reduces tail latency.

A critical assumption in this model is that the workload follows a known arrival process. For the canonical scenario (Ch 4, Table 4-2): ~10 rps average and ~40 rps peak. With ~9,200 in-tokens and ~300 out-tokens per query, a ~8.6 s service time per request (1.08 s prefill + ~7.5 s decode), and a 70B dense FP16 model running on 8×H100 (640 GB total HBM3), the fleet must sustain **~40 requests/s at peak**, which — by Little's Law — corresponds to **λ·W ≈ 40 × 8.6 ≈ 344 requests in flight** (W here is Ch 17's assumed mean KV-residency time E[W_KV-resident] ≈ 8.6 s, a conditional scenario proxy — not the end-to-end W_e2e, which adds queue, tool and inter-turn time that, under the stated assumption, holds no KV), not merely the ~100 concurrent *users* or the nominal 40 rps. The distinction between "concurrent users" (a population), the arrival rate (rps), and in-flight requests (λ·W) is exactly what Chapter 17 develops; it is the difference between sizing for a population and sizing a fleet against a latency bound.

## 3. Worked Example

Take a fleet of N hosts, each with 8×H100 running a single 70B FP16 model instance. Two capacities must be reconciled — **throughput** (tokens/s) and **KV residency** (concurrent requests) — and neither can be reduced to a single "rps" constant, because rps is workload-specific (per-request input/output tokens, context length, batch). 

#### Latency floor first, then reconcile the two capacity bounds
A 300-output-token request at a ~25 ms/token decode rate (Chapter 8) takes ~7.5 s of generation alone, plus 1.08 s prefill, so the service time is ~8.6 s per request (before tool calls). Two separate ceilings bound how many requests a host can *serve per second*, and they must be reconciled — they are not interchangeable.

#### Throughput bound (tokens/s)
A host sustains an illustrative ~35,000 tokens/s of *total* (prefill+decode) serving throughput — the conservative low end of the ~35,000–56,000 tokens/s achievable range in Chapter 15 [ILLUSTRATIVE] — distinct from the ~19,800 tokens/s *prefill-only* ideal in Chapter 8 (8 × 2,472 at 35% MFU), which counts prefill compute alone. **These two are not directly comparable as single numbers: ~35,000 is a phase-mixed *prefill+decode* total and ~19,800 is a *prefill-only* figure. To compare them one must first phase-resolve both, then compare prefill with prefill (the presented workload's prefill leg is 2.0 req/s × 9,200 = 18,400 input tokens/s) and decode with decode (2.0 × 300 = 600 output tokens/s); aggregating the two phases into one "total" rate requires an explicit cost/phase-equivalence model.** Dividing the total by the ~9,500 tokens/request gives ~3.7 requests/s — **but this is not achievable here**, because it would require ~3.7 × 8.6 ≈ 32 concurrent requests in flight, roughly double the host's KV-residency ceiling (C ≈ 17.5, conservative integer floor 17, Chapter 17). The token-throughput figure is thus a non-binding upper edge for this canonical workload.

#### KV-residency / latency bound (Little's Law)
The real ceiling is set by concurrency and KV residency time together: a host holds 17 whole concurrent full-context requests (the ~17.5 KV ceiling, Chapter 17, floored to whole contexts — no fractional admission) each for an assumed mean KV residency E[W_KV-resident] ≈ 8.6 s, so C/W = 17 / 8.6 = 1.977 ≈ **2.0 requests/s** [ANALYTICAL] at steady state — a **KV-slot upper bound on admitted rate** (defined below).

The binding per-host rate is the *minimum* of the two — here the KV/latency bound under cases (i) and (iii); a third, phase-resolved prefill-compute screen is evaluated below and binds under case (ii) (22 hosts raw, 23 with the ρ derate). This is exactly why a token-throughput number must not be divided by tokens-per-request to manufacture an "rps" here: the units do cancel (tokens/s ÷ tokens/request = requests/s), but the numerator is a phase-mixed prefill+decode total with no cost/phase-equivalence model, and the ~3.7 req/s answer would need ~32 concurrent requests against the 17-slot host capacity. The per-host request rate is a *concurrency × service-time* quantity — what makes the division wrong here is what its numerator mixes and its answer assumes, not its units.

#### What the ~2.0 req/s figure is — and is not
The ~2.0 req/s figure is a **KV-slot-based analytical UPPER bound on admitted request completion rate, conditional on an assumed mean KV residency time** — a necessary capacity screen: not a measured serving throughput, not a lower guaranteed rate, and not an SLO goodput. The *lower* bound on host count derives FROM this upper bound on the per-host rate (⌈λ/(C/W)⌉ = ⌈λ·W/C⌉); it is never a lower bound on the rate itself. It is achievable only if serving C concurrent sequences does *not* inflate W beyond the assumed ~8.6 s, and neither a compute, bandwidth, nor scheduler constraint binds first. In real continuous batching, W is a function of batch occupancy, scheduler policy, prefill interference, decode batching, the arrival process, tensor-parallel communication, and the context distribution — so C and W are not always independent constants. Treat ~2.0 req/s as an upper-bound model, and require benchmarked goodput (Chapter 14) under the target arrival process for actual fleet sizing. **Planning-bound caveat:** like the ~19,800 prefill tokens/s/host figure (Ch. 8, idealized prefill only), the ~2.0 req/s/host figure is the *KV-slot upper bound on admitted rate* named above — model-derived, **not an implied deployed rate**. **No p95/p99 performance guarantee has been shown** for any of the host counts in this chapter; the p95/p99 tail latency and achieved goodput must be measured on the target deployment (Chapter 14) before the governing 23-host sizing (21 = the KV/Little screen, case-independent; 22 = the ρ ≈ 0.95 derate of that screen — and, independently, the raw full-square case (ii) prefill compute screen, which also gives 22 and rises to 23 with the same ρ derate, the governing screen; 34 at the 70% × 95% + N−1 policy against 32 for KV-only — Ch 17 Table 17-1, u and ρ independent) is treated as validated.

#### Simultaneous feasibility check (prefill + decode coexistence)
The ~2.0 req/s/host bound assumes prefill and decode run on the same host at the same time. Evaluated at the displayed ~2.0 req/s — a deliberate stress screen, slightly above the unrounded 17/8.6 = 1.977 — the prefill demand is 2.0 × 9,200 = **18,400 input tokens/s per host** (§3). The idealized prefill ceiling is 8 × 0.989 PF/s × 35% / (2 × 70e9) ≈ **19,780 tokens/s** (Chapter 8, 35% MFU, prefill-only — **case (i), linear-only FLOP convention**). *Cross-note on MFU:* Ch 20 uses the conservative 35% planning MFU (Ch 8); Ch 22/24 use 40% sustained (Ch 24 §3.3) — the choice moves the case-(i) screen from 19 to 17 hosts. The ratio is 18,400 ÷ 19,780 ≈ **93%** under case (i); under case (ii) (full-square, ×1.1723) the ceiling falls to ≈16,870 linear-equivalent tokens/s and the ratio becomes 18,400 ÷ 16,870 ≈ **109%** (the same demand ÷ ceiling in PFLOP/s: 2 × 1.5099 ÷ 2.7692, with 2.7692 PFLOP/s the Chapter 8 35%-MFU host peak), and under case (iii) (causal-triangle, ×1.0861), ceiling ≈18,210 tokens/s, 18,400 ÷ 18,210 ≈**101%** — above 100% the prefill leg alone does not fit at 2 req/s — so the ~7% headroom under case (i) is a property of the linear-only convention, not of the hardware. Prefill must run at ~93% of the idealized prefill ceiling under case (i). This is **[ANALYTICAL]** (Axis-3 measurement status; defined with the evidence taxonomy in the Sources, Method, and Reproducibility chapter) — a prefill-load check, not a measured rate. The ~93% leaves very little headroom before decode coexistence, interference, and the actual achieved MFU. Prefill and decode share the same hardware. Batch scheduling and decode interleaving compete for the same compute. The achieved MFU is below the 35% ideal. Therefore ~2.0 req/s/host is an **analytical upper bound**, **NOT a claim that a host serves 2 req/s at SLO**. Before treating 2 req/s/host as deployable, measure the p95 TTFT, p95 TPOT, and SLO-goodput on a representative host (Chapter 14).


#### Fleet aggregate throughput (illustrative form)
Keeping the illustrative per-host req/s = Q for the algebra, aggregate throughput is

$$
\Lambda_\text{fleet} = N \times Q
$$

At the canonical peak of 40 rps, fleet size must satisfy **both** the KV-residency and the throughput/latency bounds, whichever binds first. The Little and the KV-residency bound are the same identity written in two views: λW/C = λ/(C/W). They agree at the peak, exactly as Chapter 17 notes. The additive form is a first-order capacity floor: scheduling, network-contention and data-movement effects are real but not captured here, and are measured in §4.

**Little/KV screen → 21 hosts.** With the per-host rate at ~2.0 req/s (17/8.6 = 1.977, the binding KV-slot upper bound on admitted rate above; its *reciprocal* gives the lower bound on host count), a fleet for 40 rps starts at **21 hosts**: ⌈40 × 8.6 / 17⌉ = ⌈344/17⌉ = ⌈20.24⌉ = 21. By Little's Law the in-flight count at 40 rps is λ·W = 40 × 8.6 ≈ 344, and ⌈344/17⌉ = **21 hosts** (17 whole contexts per host, no fractional admission).

**Token-throughput screen → 11 hosts (non-binding artifact).** The token-throughput ceiling gives ⌈40 / 3.684⌉ = 11 hosts, but 3.684 req/s is a phase-mixed prefill+decode rate divided by tokens-per-request: without an explicit phase-equivalence model this is an artifact, not a valid screen, and it stays non-binding here either way.

**ρ-derate → 22 hosts.** The ρ ≈ 0.95 fractional-throughput derate raises the requirement to 344 / (0.95 × 17) = 344/16.15 ≈ 21.3 → **22 hosts**. 

Separately, the independent prefill compute screen (Ch. 8, 35% MFU) gives **19 hosts under case (i)** (⌈18.60⌉, linear-only), **21 under case (iii)** (⌈20.21⌉, causal-triangle) and **22 under case (ii)** (⌈21.81⌉, full-square conservative) — note that case (ii)'s 22 is a *different* 22 from the ρ-derate's 22 (one comes from a FLOP-counting case, the other from a throughput-efficiency derate of the KV screen); they coincide in value only by arithmetic accident. 

The "far fewer hosts (~6)" figure applies only to the 10-rps average (⌈86/17⌉ = 6), not the 40-rps peak. 

The correct statement is: the fleet must satisfy every named screen, and the *larger* requirement wins — **19 hosts under case (i), 21 under case (iii), 22 under case (ii)**; with the standalone ρ = 0.95 derate applied to the prefill screen exactly as the policy arithmetic applies it, case (ii) rises to ⌈21.81 / 0.95⌉ = **23 hosts** — the largest requirement before the full policy, and on that count the fleet is **~95% prefill-saturated**: each host serves 40/23 = 1.74 req/s ⇒ 1.74 × 9,200 = 16,000 prefill tok/s against the case-(ii) ceiling of ≈16,870 tok/s, i.e. ~5% headroom for decode coexistence and interference (ρ = 0.95 is a throughput-efficiency derate: dividing the host requirement by ρ is the same as dividing each host's effective rate by ρ, so it applies to any throughput-bound screen — KV or prefill — and does not re-derive the 35% MFU assumption itself); and at the 70% × 95% + N−1 policy **34 under case (ii) versus 32 for KV-only** (⌈21.81/0.665⌉+1 = 34; ⌈344/11.305⌉+1 = 32 — Ch 17 Table 17-1, u = 0.70 and ρ = 0.95 applied as two independent factors); **all of 19/21/22/23/32/34 are illustrative planning screens under their stated FLOP/MFU assumptions, not measured SLO-goodput.** 

**Reading Fig 20.1's two gaps:** below saturation the ~5% gap between C_analytic(N) = N × 17/8.6 and C_eff(N) = 0.95 × C_analytic is the assumed throughput-efficiency derate; above saturation C_eff − S, with S = min(40, C_eff), is *unused* capacity from insufficient offered demand — not scheduling overhead. Queueing and tail-latency penalties are not determined by this two-line calculation and must be shown separately if claimed.

#### Scheduling overhead
A lightweight round-robin scheduler adds ~0.5 ms of dispatch latency per request [ILLUSTRATIVE] — negligible next to a real 7.5 s decode. The governing target is absolute: **< 100 ms p99 dispatch**, ~1.2% of the canonical 8.6 s request and, equivalently, ≤ 5% of the 2 s TTFT SLO turn budget; the fraction is derived from the absolute number, not a second constraint.

#### Autoscaling economics
Each 8×H100 host costs ~$20/hour (cloud, $2.50/GPU-hr canonical) or ~$8/hour amortized (owned) — [ILLUSTRATIVE]. The marginal cost per additional req/s is $20 ÷ (req/s gained per host); the economic lesson (declining average cost per request as fixed costs amortize across more requests) is sound, but the exact per-req/s figure is only meaningful after the real per-host throughput is benchmarked. Quantifying the break-even, with a fixed overhead of ~$40/hr (infrastructure and staff, [ILLUSTRATIVE]): at the 40-rps peak the autoscaled fleet runs the governing **23 hosts** at (23 × $20 + $40) ÷ 144,000 requests/hr ≈ **$3.47 per 1K requests**, and at the 10-rps average it runs 6 hosts at (6 × $20 + $40) ÷ 36,000 ≈ **$4.44 per 1K** — a ~22% average-cost decline across the 4× demand ramp while the marginal $10.12 per req/s per hour is unchanged. The break-even against a statically provisioned, peak-sized 23-host fleet ($460/hr = 23 × $20, no control plane) sits at 21 hosts, i.e. sustained demand ≤ ~41.5 rps: above that, autoscaling costs more than the peak-sized fleet it replaces.

## 4. Measurement

To validate fleet-level optimization claims, five core metrics should be measured at regular intervals:

\Needspace{14\baselineskip}

**Table 20-1** — Fleet-level measurement metrics

| Metric | Definition | Target |
|---|---|---|
| **Aggregate req/s (capacity)** | Total queries processed per second across all hosts | ≥ 2× peak req/s for comfort margin (stress/soak target — see note below) |
| **Scheduler-added p99 latency** | 99th-percentile time a request waits in the fleet dispatcher (NOT end-to-end — model execution is multi-second here) | < 100 ms |
| **Scheduler-added median latency** | 50th-percentile dispatch latency, scheduler overhead only | < 30 ms |
| **Scheduling overhead** | Scheduler-added latency (dispatch + placement) on top of the request's own model-execution time, as a fraction of the 2 s TTFT SLO budget | < 5% (= 100 ms) |
| **Utilization variance** | Standard deviation of per-host query rate as a fraction of mean | < 0.2 |

_Note: end-to-end median/p99 latency is deliberately **not** a fleet-level target for this canonical 9.5K-token workload — a request takes ~8.6 s in service (1.08 s prefill + ~7.5 s decode), so an *end-to-end* <100 ms p99 is infeasible (see the mini-case). Table 20-1 therefore qualifies these as scheduler-added (dispatch) latency targets only. The aggregate-req/s 2× row is a **stress/soak** target, not the planning screen: sustaining 80 req/s needs ~41–43 hosts (see §8)._

Measurement methodology: use a distributed load generator (e.g., Locust or a custom gRPC-driven pump) that sends queries at the target rps while instrumenting each host's internal metrics — GPU occupancy, kernel launch time, scheduler dispatch timestamp, and queue depth. Aggregate these via a time-series database (InfluxDB or Prometheus) and compute the above metrics over sliding 1-minute windows.

A practical pitfall: measuring only aggregate req/s without tracking per-host variance can mask saturation in individual nodes. Always report both the fleet-wide and per-host metrics.

Placement also determines the communication and failure domain. A slow or failed participant can delay an entire model-parallel group while other replicas remain healthy. Group-level completion tails, asynchronous failures and the affected requests therefore accompany per-host utilization. A placement that improves average utilization but increases cross-group contention can reduce SLO-goodput; replica isolation and group recovery require measurement before they become fleet-capacity assumptions.

The qualification gate in Chapter 18 applies before a configuration enters any capacity pool. A fallback route consumes capacity too; its quality, deadline and data-policy constraints remain part of the placement contract.

## 5. Common Mistakes

- **Treating hosts as independent**: Optimizing each host in isolation (e.g., tuning batch size per host) inflates the variance in per-host service time; the fleet's tail latency and the Table 20-1 utilization-variance target (< 0.2) are set by the slowest hosts, not by the average host.

- **Overlooking data movement cost**: In RAG workloads, the retrieved-context text that becomes the ~8,000-token portion of the ~9,200 input tokens per query must be fetched from a vector database or cache over the network, while the ~300 out-tokens are generated entirely on the host — only the final response needs to reach the user. The quantity that distinguishes architectures is bytes fetched per query: if every host fetches independently, each query moves its full context bytes, repeated for every query and every host. A shared cache layer or a colocated store fetches each distinct context once and serves later hits locally, so the saving is proportional to the cross-query context-overlap rate — not to a scaling exponent that is identical under both schemes.

- **Autoscaling too aggressively**: Adding hosts at the first sign of latency increase can be suboptimal if the bottleneck is scheduler throughput or cache contention, not compute capacity. Measure the marginal cost of adding a host before triggering a scale-out event.

- **Ignoring cold-start cost**: When a host is freshly provisioned or re-warmed after idle, loading the full model weights into HBM takes ~28–112 seconds [ILLUSTRATIVE] (a load-path assumption for a ~140 GB model over a ~10–40 Gb/s (≈1.25–5 GB/s) path — 140 GB ÷ 28–112 s ≈ 5–1.25 GB/s, i.e. ≈40–10 Gb/s — not a hardware benchmark; distinct from the much shorter KV-cache warm-up of ~2 s discussed in Chapter 15, which re-populates only the retained KV state). Autoscaling policies must account for this weight-load warm-up window when scaling out a fresh host; otherwise the fleet experiences a spike in error rate or timeout during scale-out events.

## 6. Architecture Consequence

Fleet-level optimization reshapes the serving architecture in three ways:

1. **Centralized scheduler**: A lightweight service (e.g., based on etcd or a custom placement engine) maintains real-time view of per-host utilization and makes dispatch decisions. This service must be highly available, and its dispatch overhead should stay a small fraction of the per-request SLO — for the canonical ~8.6 s service time, a sub-millisecond decision is a comfortable *target* (the round-robin baseline adds ~0.5 ms, §3), not a universal necessity: the binding constraint is that dispatch overhead not consume a meaningful share of the request/turn SLO, which depends on routing frequency and scheduling architecture.

2. **Data colocation**: Vector indexes and model weights are stored close to the hosts that consume them. This may mean running a local Qdrant or Milvus instance per host, or using a shared object store (e.g., MinIO) with read-replicas per availability zone. The goal is to minimize the distance — measured in network hops — between the scheduler's placement decision and the data fetch. But colocation is a trade, not a free win: a per-host index multiplies memory/storage, consistency, ingestion, and operational cost across the fleet, and model-weight locality is a different problem from vector-index locality. The right placement depends on the workload — compare centralized retrieval, AZ-local retrieval, replicated indexes, and cached results, and identify the traffic/latency point at which colocation's access-latency saving outweighs its replication cost. Do not conflate the two locality questions.

3. **Graceful degradation**: The fleet should have a mode where, under extreme overload, it serves stale or truncated answers rather than failing entirely. This could mean returning the top-k results from a cached embedding rather than recomputing, or surfacing a "try again" message with an estimated wait time. The architectural contract must make this trade-off explicit so product teams can set appropriate SLOs.

### The useful completion is an accepted output

For a RAG fleet the useful completion is an *accepted* output — a response that passes the deadline, integrity, quality, and safety gates in the observation window — so hosts are sized against accepted outputs per observation window, not raw work; the rejection/OOM/cancellation counters and the cost-per-accepted-completion basis follow that rule, and placement follows the measured-service-time rule (place warm replicas where measured service time, not nominal load time, sets the request path). The same accepted-completion goodput accounting applies to any fixed-output-contract workload; a video-generation fleet is the clearest parallel beyond RAG — there the accepted output is a clip passing the same four gates in the same observation window, raw work rates (frames/s, clip-seconds/s) need a stated denominator and do not normalize the nonlinear attention cost, and warm replicas trade idle cost for avoiding checkpoint downloads, initialization, compilation, and encoder loading on the request path. For a RAG fleet architect the parallel is direct: both fleets size hosts against accepted outputs in the observation window, not raw work, so the same capacity screens and placement rules apply. ## 7. What We Still Don't Know

Several open questions remain at the fleet level:

- **Heterogeneous hardware**: What happens when hosts mix H100, A100, and CPU-only nodes? The scheduler must handle different throughput ceilings and memory capacities, and the aggregate throughput calculation becomes a weighted sum rather than a simple multiple. Real-world measurements of mixed-device fleets are scarce; most published benchmarking uses homogeneous hardware, so the crossover point where heterogeneity hurts versus helps is not well quantified.

- **Multi-model serving**: Ch 18 covers routing, tiering, and quantization trade-offs for mixed model sizes; what this chapter leaves open is how to compute a fleet's aggregate capacity when per-host rates differ by model — the N × Q identity in §3 assumes a single Q — and how the scheduler should place a request whose model is not resident on the least-loaded host without breaking session affinity or the shared KV budget. Joint placement of heterogeneous model sizes under one KV budget (Ch 18 §3.3) remains unresolved.

- **Economic auto-scaling**: The break-even point between owning hardware versus cloud-on-demand depends on utilization patterns that are workload-specific. A fleet that runs at 20% utilization on average may be cheaper in the cloud; one at 80% utilization favors owned hardware. The transition point is a function of capital expenditure amortization period, electricity cost, and the volatility of user demand. Published TCO analyses typically assume steady utilization, but bursty workloads with short-lived spikes can make ownership risky unless over-provisioned.

- **Tail-latency arbitration**: When two queries compete for the same GPU HBM bandwidth, the 99th-percentile latency can spike disproportionately. We lack a general-purpose scheduler policy that guarantees a target tail latency under arbitrary arrival patterns; this remains an area of active research. Some systems use priority queues or token buckets to cap per-query bandwidth, but these mechanisms add scheduling complexity and can increase median latency.

- **Cross-query caching effects**: RAG prompts share long leading prefixes across users asking related questions, and the open quantity is the *prefix-overlap distribution* — shared leading tokens as a fraction of a query's prefill FLOPs. That fraction, not the raw token count, bounds what prefix caching (Ch 15) can save. Charged against it is the cache-management cost: invalidation, cross-replica coherence, metadata, and the loss of batch-occupancy flexibility when requests pin shared prefixes. We lack large-scale measurements of that overlap distribution and of how much of the theoretical prefill saving survives the management cost. Reuse of earlier *outputs* across askers is a separate question about answer quality and provenance, not a KV-reuse question.

With the same ρ = 0.95 derate §3 applies to every throughput-bound screen, case (ii) rises to ⌈21.81/0.95⌉ = **23**.
- **(c) Max over all screens, before the full policy:** 23 is the ρ-derated requirement, 22 the raw-screen requirement, and 23 governs the screen set before the full policy (§3: the larger requirement wins).
- **(d) Full policy:** under the 70% × 95% + N−1 policy the requirements are **34** under case (ii) and **32** for KV-only — see the planning-bound caveat below.

(⌈86/17⌉ = **6** is not a second, tighter constraint: it is the *same* identity λW/C = λ/(C/W) — the KV-residency view of §3 — evaluated at the 10-rps average instead of the 40-rps peak; at the peak both views give ⌈344/17⌉ = **21** (→ **22** with the ρ ≈ 0.95 derate), so the peak requirement governs.)

- **At 16 hosts:** 16 × (17/8.6) = 31.6 ≈ **32 req/s** — still below the 40-rps peak, so 16 hosts would not meet peak demand.
- **Marginal cost (real basis):** adding one host at ~$20/hr (cloud, [ILLUSTRATIVE]) buys ~2.0 req/s, so marginal cost = $20 ÷ (17/8.6) = $20 × 8.6 / 17 = $10.12 ≈ **$10 per req/s per hour.** (The ~$0.012 figure from Chapter 4 is a per-*request* managed-API price, not a per-req/s-per-hour rate — Chapter 4's own basis note says the two cost bases are not interchangeable — and with a real multi-second service time per request the per-host rate is ~2.0, not a hypothetical 250.)
- **The 100-ms end-to-end p99 is infeasible under the stated workload, and that is the honest answer.** A request here takes ~7.5 s of decode alone (300 output tokens × ~25 ms/token, Chapter 8), so no scheduler-overhead percentage can bring end-to-end p99 under 100 ms — model execution already exceeds the budget by ~86× (8,580 ms ÷ 100 ms) — nearly two orders of magnitude. What the scheduler *can* bound is the overhead it adds *on top of* model execution. Here that overhead is a **target, not an achieved prediction**: the dispatcher's added p99 overhead is specified as `< 100 ms p99 on the same request population — ~1.2% of the canonical 8.6 s request, and ≤ 5% of the 2 s TTFT SLO budget`, and the ~0.5 ms dispatch figure is a median/nominal value that **cannot establish p99** without a measured scheduler distribution. Treat it as an SLO hypothesis — **must be demonstrated in a load test** (Chapter 14) with the numerator/denominator defined as scheduler-added latency divided by that request's own model-execution time — before any p99 claim is made.
- **Planning-bound caveat (sizing tail).** §3's caveat governs: analytical upper bounds (the KV-slot bound on admitted rate for ~2.0 req/s; the idealized Ch 8 roofline for ~19,800 prefill tokens/s), not implied deployed rates; no p95/p99 guarantee for the governing 23-host sizing (21 = the KV/Little screen, case-independent; 22 = the ρ ≈ 0.95 derate of that screen; 23 = the ρ-derated full-square case (ii) prefill compute screen, which governs; 34 at 70% × 95% + N−1 under case (ii) versus 32 for KV-only) — the host count is a KV-residency/service-time **capacity floor** (derived from the KV-slot upper bound on the per-host rate), and the deployable host count is **max(capacity requirement, tail-latency requirement N_SLO)**, so measure p95/p99 and SLO-goodput (Chapter 14) before committing hardware. Little's Law stays a mean relation there: E[L] = λ·E[W] with E[W] the mean KV residency — never a p95/p99 W.
