# Chapter 5 — From Workload to Model Selection

## The Architect's Question

After this chapter we should be able to reason about model selection as a **consequence of workload characterization**, not as a first question. We should also be able to walk the two-part selection that defines a RAG system: (a) choosing an embedding model for the retrieval leg, and (b) choosing a generation model for the answer leg. The chapter works toward showing that "which model is best?" is the wrong first question; the right first question is "what job does this system do, and how quantitatively?"

## 1. Concept

Model selection proceeds across five surfaces, each derived from the workload characterization (Ch 4, Table 4-2):

1. **Capability / quality needed** — does the workload require multi-step reasoning, tool use, or modality handling? A workload that needs chain-of-thought reasoning needs a different model class than one that only needs fact retrieval.
2. **Latency / compute budget** — can the system meet TTFT and TPOT SLOs with the candidate model on the target hardware? This surface determines whether we need a dense 70B, a distilled 13B, or a MoE variant.
3. **Context / KV cost** — how much memory does the input context consume in the KV cache, and what does that mean for feasible context length on the target infrastructure? An 8K-context workload has a very different cost profile from a 32K-context one.
4. **Cost per token** — what is the $/million-tokens for the full request (prefill + decode) on the target infrastructure? This surface makes the economic difference between model sizes concrete.
5. **Retrieve-then-generate vs end-to-end** — does the system architecture split the job into a retrieval leg (embedding model + vector search) followed by a generation leg (base model + prompt), or does it use a single model that jointly retrieves and generates? This architectural decision drives the embedding‑vs‑generation model contrast.

The core reframe — modeled in Chapter 4 — is that **model selection is a consequence of workload characterization**. When the workload is specified in token counts, request rates, latency budgets, and economic constraints, the feasible model space narrows naturally. The architect does not start with a model and reason forward; they start with the workload and reason backward into model space.

### A model candidate includes its deployment precision

A model name alone does not identify a deployable candidate. The same checkpoint can produce different quality, memory use and execution paths under different quantization recipes.[^oct-qz-awq]^,^[^oct-qz-gptq] We therefore compare a base-model revision together with its tensor precisions, calibration or recovery procedure, export schema and serving backend. The quality gate applies to that exported deployment, including its tokenizer, prompt template and modality branches. A language-only quantization result does not establish that a vision encoder, projector or tool-use workload retains the same behavior. The mechanism and byte accounting appear in Chapter 7; Chapter 14 §14.4 (*Acceptance test for a quantized deployment*) supplies the acceptance test. [1P][FACT]

### Inference mode is a candidate, not a selection verdict

The same task can favor different inference modes at different concurrency levels. Parallel refinement (diffusion-style decoding that updates many token positions per step) is worth investigating when low-batch latency or constrained infilling dominates, but neither advantage follows from a model-family label. AR fill-in-the-middle (FIM) models — autoregressive models trained to infill a marked span — are a necessary editing baseline. For the canonical RAG workload, the inference mode is standard autoregressive generation; the selection question reduces to whether the chosen AR model, tokenizer, and serving runtime meet the SLOs. For workloads that might use non‑AR generation (editing, infilling, image‑to‑text), the mode itself becomes an additional selection dimension. Structured output adds another gate: an API that documents JSON-schema generation and a self-hosted backend that rejects grammar constraints are not interchangeable candidates.[^oct-df-struct] (Post-cutoff addendum, retrieved 2026-10-28: outside the book's 2026-08-30 evidence cutoff; retained because the pinned first-party sources are the only verifiable record of the cited behavior.) The selection question is whether the specific model, sampler and runtime meet the workload's quality, output and SLO requirements together. The mechanisms in Chapter 3 explain the candidate; the measurements in Chapter 14 decide whether it belongs in the architecture. [1P][FACT]

## 2. Mental Model

Model selection is really **system design, not model picking**. The workload is the architect's input; the model is a component that must satisfy the workload's constraints. If the workload is input-heavy (9.2K average input, 300-token output, ~30× more input than output), the system is first-order memory‑capacity‑bound (the KV cache's HBM footprint limits how many concurrent requests fit — KV HBM capacity limits concurrency, not bandwidth — at the Ch 17 concurrency screen) and prefill‑dominated in FLOPs — a first-order tendency to verify per workload, not a consequence of input-heaviness alone. If the workload were output‑heavy, the token/FLOP mix shifts toward decode, which often makes decode bandwidth or latency critical — the actual bottleneck must be measured on the target stack. The mental model holds both profiles in view: the same "which model?" question produces opposite answers depending on the token profile.

A useful image for the full pipeline:

> **Workload → Selection surfaces → Model category → Specific model**

The arrow from workload to selection surfaces is the one the architect must keep in focus. Every other arrow follows from it.

## 3. Worked Example — Embedding‑Model vs Generation‑Model Selection for the Canonical RAG Workload

Per the canonical workload (Ch 4, Table 4-2): the enterprise Q&A RAG tool — input-heavy, ~9.2K input (1,200 prompt + 8K retrieved) + 300-token output; 70B-class dense FP16 model (~140 GB) on one 8×H100 host. TTFT budget 1.2 s (retrieval ~120 ms + prefill), TPOT ~25 ms/token; p95 TTFT ≤ 2 s, p95 TPOT ≤ 35 ms.

We walk the two‑model selection for this workload.

### (a) Embedding‑model selection for the retrieval leg

The retrieval leg maps chunks of internal documents to dense vectors so that a user query can be matched to the most relevant context. The architect must choose an embedding model — specifically, its embedding dimension and parameter count — against the retrieval quality the workload demands.

Three realistic options, each with documented properties:

The ~11.1 GFLOP delta is arithmetic on Table 5‑1's model-card rows, so it is [1P][DERIVED]; the open claim that remains [ILLUSTRATIVE][HYPOTHESIS] is the separate one about whether the [ILLUSTRATIVE][ASSUMPTION] ~15% MAP uplift transfers to the target corpus.

On a GPU (~1.1 ms at ~10 TFLOP/s) the incremental cost stays well within the ~120 ms retrieval budget; on a single CPU core it does not — 371 ms at 30 GFLOP/s vs 186 ms at 60 GFLOP/s — single‑core encoding would require ≈92.8 GFLOP/s sustained per core (11.14 GFLOP ÷ 0.12 s), which is beyond the typical 30–60 GFLOP/s sustained range — so single‑core encoding does not fit the ~120 ms retrieval budget, conditional on measured single-core throughput.

The decision hinges on whether the top‑of‑range ~15% MAP gain (an [ILLUSTRATIVE][ASSUMPTION] scenario input, whose transfer is the [HYPOTHESIS], and a within‑family / controlled‑dimension upper bound that cannot be assumed to transfer across model families — §5.3(a)) translates into sufficient answer‑quality improvement to justify the ~7.7× body-only FLOP cost (~4.8× on total parameters; 14.08 vs 2.94 GFLOP per 64‑token query, which understate the ratio). The same bar that rules out bge‑large applies here: the mpnet‑vs‑MiniLM quality gap must be measured on the target corpus before the ~7.7× body-only FLOP cost is paid — a workload‑specific tradeoff, not a universal rule.

**Takeaway for the canonical RAG workload:** 768‑dim (all‑mpnet‑base‑v2) is the recommended embedding model. It balances compute, storage, and expected quality as a mid‑range candidate — compute and storage alone favour the 384‑dim option — and the quality claim itself is the §5.3(a)/§5.7 item still to validate on the target corpus, and it introduces no per‑request latency that threatens the TTFT SLO. The quality gain behind this recommendation is an unverified scenario input of up to ~15% MAP [ILLUSTRATIVE][ASSUMPTION] whose transfer to this model pair is [HYPOTHESIS], not quantified for this model pair — the same test applied to bge‑large applies here: validate it on the target corpus. The 384‑dim option is viable only if storage or compute budget is extremely constrained; the bge‑large‑en option is not justified at this scale: its quality gain over all‑mpnet‑base‑v2 is not quantified for this model pair (the table gives use cases, not metrics), and an unquantified gain would have to clear a ~3× FLOP bar (≈43 vs ≈14 GFLOPs per 64‑token embedding in the table above, the same ratio as their parameter counts) — validate the gain on the target corpus before paying it.

### (b) Generation‑model selection for the answer leg
KV cache per-token figures are at FP16 (~2.62 MB/token) unless an 8-bit (~1.31 MB/token) variant is explicitly stated.

The generation leg produces the 300-token answer given the 9.2K retrieved context. The architect must decide whether a base 70B‑class dense model, a smaller dense model, or a fine‑tuned variant best satisfies the latency, quality, and economic constraints.

#### Derived arithmetic for the 70B candidate (constructed teaching geometry)

But it is only **~15% of the wall-clock time** (1.08 s prefill vs 6.0 s decode), because prefill is compute‑intensive and batchable across concurrent requests; decode has a per-request sequential dependency but is also batched across requests (continuous batching) — batching raises GPU utilization without removing per-token latency. So the honest picture is *both*: prefill dominates the linear FLOP budget (~97% of tokens and linear FLOPs) while decode dominates single-stream wall-clock (~85% of 7.08 s on the illustrative 20 ms/token basis, where 7.08 s = 1.08 s prefill + 6.0 s decode; ~87% of 8.58 s on the canonical 25 ms/token basis, where 8.58 s = 1.08 s prefill + 7.5 s decode, Ch 4; the two percentages are decode shares at two different operating points and should not be compared as if they were one series); GPU-hour cost follows occupancy, batching and scheduling — it is not proportional to either share without a stated utilization assumption. The per‑dollar economics therefore favor models that reduce the *prefill compute* burden (smaller context, larger batch, lower per‑token FLOP) more than models that optimize decode throughput alone — but a deployment must balance both, since decode still sets the latency SLO.

### (c) Base‑model + RAG + guardrails vs fine‑tuned model

The architect must choose between two paradigms:

**Paradigm 1 — Base model + RAG + guardrails:**

- The base 70B model receives the retrieved 9.2K context via prompt injection.
- Guardrails (PII redaction, style enforcement, refusal filtering) are applied as post‑generation or prefix‑check layers.
- No model weights are trained on domain data; the knowledge source is the vector database.

**Paradigm 2 — Fine‑tuned model on domain‑specific Q‑A pairs:**

- The base model is fine‑tuned (full-parameter, or low‑rank adaptation (LoRA)) on thousands of question‑answer pairs reflecting the enterprise's terminology and reasoning patterns.
- Inference uses the fine‑tuned weights without a retrieval step, or with a much shorter retrieved context. Fine‑tuning is **not** a dependable substitute for retrieval when the requirement is factual corpus access, freshness, attribution, or precise enterprise knowledge — fine‑tuning distills *behavior, style, task patterns, format, and tool‑use policy*, not a guarantee that arbitrary facts are recalled faithfully. Whether it reduces retrieval dependence for a *particular* task is an empirical question to be measured on that task's evaluation set.
- Additional costs: training compute, storage of fine‑tuned weights, and reduced flexibility for new topics.
- **Deployment artifact:** full fine‑tuning produces a merged checkpoint (~140 GB of weights plus the stored checkpoint) that must be built, promoted and rolled back as a unit; LoRA produces a small adapter that is either served alongside the unchanged base weights or merged into a checkpoint for serving. Either way the artifact enters the model lifecycle of Ch 21 (train → evaluate → canary → promote, with rollback to the last‑known‑good checkpoint) and must be versioned per environment before §5.5's inference‑shape comparison applies.

For the canonical workload, a well‑designed RAG + guardrails pipeline *may* approach a fine‑tuned model's answer quality on in‑domain queries [HYPOTHESIS] — not a reference measurement, and **task‑, model‑, data‑, and evaluation‑dependent**; it is not derivable from the architecture alone. The two mechanisms do different work: **RAG** supplies external, mutable knowledge (grounding, provenance, freshness); **fine‑tuning** shapes behavior, style, domain reasoning patterns, format, and tool‑use policy. Either or both can improve answer quality, and they can be combined. Whether fine‑tuning reduces retrieval dependence for this workload must be established by measuring answer quality on the actual evaluation set. The economic comparison should be framed **parametrically**, not with a single number, because the break‑even depends on the quality uplift (domain‑specific) and the query volume (workload‑specific). The decision variable is the break‑even query volume $Q^*$ where the up‑front plus carry cost of fine‑tuning, divided by its quality advantage, crosses the RAG baseline:

$$
Q^*\; =\; \frac{C_\text{train} + C_\text{weights-extra}}{\Delta Q \cdot \text{value per corrected query}}
$$

where $C_\text{train}$ is the one‑time training cost (monetary, compute included), $C_\text{weights-extra}$ is the incremental storage/carry cost, and $\Delta Q$ is the (domain‑specific, must‑be‑measured) quality uplift in corrected answers per query, while *value per corrected query* is the monetary value of one additional corrected answer, in the same currency as $C_\text{train}$.

**Note:** this formula captures only the one‑time training and carry cost amortized against the quality uplift; it omits the recurring per‑query prefill/retrieval saving that fine‑tuning's shorter context (§5.3(c)) would confer, so it yields an upper bound on the true break‑even volume — a conservative (higher) estimate of the queries needed to justify fine‑tuning, in favour of RAG + guardrails, because omitting fine‑tuning's recurring saving understates its benefit.

Below $Q^*$, RAG + guardrails is economically dominant because the fine‑tuning cost is spread over too few queries to be repaid; above it, fine‑tuning may recover its upfront cost through quality gain. (Scenario structure, not a single claimed break‑even volume; the exact $C_\text{train}$, $C_\text{weights-extra}$, and $\Delta Q$ are workload‑ and domain‑specific and should be measured, not assumed.)

Fine‑tuning does **not** make the model smaller — pruning is a separate operation. A full fine‑tune keeps the ~140 GB 70B weight set (and adds a checkpoint), while a LoRA adapter is tiny but does not change the live weight footprint. Consequently the latency effect of fine‑tuning is not "smaller effective model" and cannot be assumed to cut TTFT; any TTFT change must be measured. The monetary deltas are (a) one-time training cost and (b) incremental storage; separately, the latency effect on TTFT must be measured: the RAG pipeline's ~1.08 s prefill is the baseline TTFT term, and any change from a shorter or absent retrieved context must be measured and can be material. Parametrically, fine‑tuning becomes worth it only when its total (one-time training + storage/carry) cost spread over $Q$ queries is repaid by $\Delta Q \cdot \text{value}$ — this is exactly the $Q^*$ above.

**Takeaway:** For the canonical enterprise Q&A RAG workload, the base‑model + RAG + guardrails paradigm is the default under this chapter's stated assumptions — the break-even is parametric (Q* of §5.3(c)) and not measured for this workload, so 'economically preferred' is conditional on lying below Q*. Fine‑tuning is most compelling when the query distribution is highly concentrated, the domain vocabulary is extremely specialized, and the workload volume sustains the training amortization threshold. Style, format and tool-use-policy tuning can be compelling even without a concentrated distribution or specialized vocabulary.

## 4. Measurement

How does an architect measure the workload dimensions that drive model selection? The token-counting habits of Ch 1 §1.4 apply unchanged; the three things the *selection* view adds are:

1. **Measure the token split on real employee queries, not the heuristic.** Run the model's own tokenizer on representative prompts from the target domain — the "4 chars ≈ 1 token" heuristic is for estimation only. For the canonical workload, measure the exact prompt+context token count on real employee queries before fixing the model, because the ~30× input-to-output ratio is the single biggest driver of this system's cost structure (Ch 4).
2. **Quantify the output size, since that drives decode cost and per-request latency.** The output token count determines total decode work and end-to-end decode latency; p95 TPOT depends on per-token cost and scheduling; a large-output paradigm (e.g. long-form generation) changes the model-selection calculus versus a short-output Q&A system.
3. **Know the 95th-percentile context length, not just the average.** Log the distribution of context lengths. A workload that averages 9.2K input but peaks at 32K (a variant flagged in Ch 4) requires a different KV budget and, with it, a different model-size or attention-hybridity choice. Size against the tail.

These checks let model selection be made on measured workload dimensions rather than a generic "bigger model is better" assumption.

### Model identity includes the execution path

Backend identity completes the candidate: the relevant identity includes the checkpoint revision, tokenizer, numerical representation, engine revision and device backend. A loader may recognize the model while a fused attention operator, recurrent-state update or quantized expert kernel is unavailable on the target device. A fallback can restore execution but change latency, memory use or numerical behavior. We therefore separate model-quality acceptance from backend qualification. Both must hold for the same configuration. A small successful completion does not validate long-context state, concurrent-request isolation or the intended serving SLO.[^oct-ix-t0]

## 5. Common Mistakes

- **Starting with "which model is best?" instead of characterizing the workload.** Model selection is a consequence of workload characterization: the workload's token profile, latency budget, and economic constraints are what narrow the model space; starting with a model short‑circuits the reasoning chain and leads to post hoc justification.

- **Ignoring the KV cache cost of long contexts.** A 9.2K input on a 70B model costs ~24.1 GB of KV cache (initial). An architect who does not account for this will either over‑provision infrastructure or hit SLO violations when the cache spills to host memory or SSD.

- **Quoting context window as free capacity.** The 128K or 1M token window is an upper bound, not a recommendation. Using even 9.2K of a 128K window still costs for the length actually used. The cost is proportional to the *used* length, not the *available* length.

- **Assuming embedding dimension is a free parameter.** Increasing embedding dimensionality *within a given model family or controlled configuration* can improve retrieval fidelity, but dimensionality alone does not predict quality across different embedding models. Higher dimension also raises FLOP cost, index storage, and per‑query latency, so the architect must balance these against the workload's quality requirements rather than treat dimension as a cost‑free or universally-better knob (see the caveat in §5.3(a)).

- **Over‑engineering the fine‑tuning path.** Fine‑tuning adds training compute and model/checkpoint‑management cost; depending on the adaptation and serving method, it may also add inference or operational overhead (e.g. a LoRA adapter applied dynamically at serve time can introduce overhead, whereas a merged/fully‑fine‑tuned model of identical architecture need not change the inference shape). The parametric $Q^*$ in §5.3 shows how to decide — RAG + guardrails dominates below the break‑even volume and fine‑tuning may dominate above it — but the break‑even is workload‑ and domain‑specific and must be measured before either paradigm is declared dominant for most workloads. Fine‑tuning should be a deliberate choice triggered by a measured quality gap or domain/operational requirement plus sustained query volume and economics, not a default.

## 6. Architecture Consequence

Whatever we learned here, file it under **"can I size the workload before I pick a model?"** Concretely, the decision this chapter enables is:

- Estimate tokens‑per‑request (input and output separately), and therefore tokens‑per‑second capacity and cost, before choosing a model or a serving configuration.
- Use the selection surfaces (quality, latency, KV cost, cost/token, retrieve‑vs‑generate) to narrow the model space from the full vendor catalog to a handful of viable candidates.
- For RAG workloads, select the embedding model and generation model as a two‑part decision, not a single choice. The embedding model is chosen at ingestion time (compute‑light, storage‑bound) but also carries query‑time embedding cost and latency; the generation model is chosen at serving time, with prefill often compute‑bound and decode often memory‑bandwidth‑bound — the SLO makes it latency‑bound.

This consequence feeds directly into the fine-tuning-for-specific-workloads pattern and the RAG pattern (both cataloged in Ch 26, Patterns Library): the architect first characterizes the workload, then lets the characterization drive model selection, not the other way around.

## 7. What We Still Don't Know

[1P][HYPOTHESIS]: the interaction between embedding dimension and retrieval quality across diverse enterprise domains is not yet characterized with reproducible benchmarks. Some inspected embedding models use 768 dimensions; this is not a general quality optimum and must be validated on the target corpus. The quality difference between 768 and 1024 dim varies by corpus genre (legal vs. engineering vs. creative), and we are not aware of a public study that quantifies this 768‑vs‑1024 domain‑dependence.

[1P][HYPOTHESIS]: the break‑even point between RAG + guardrails and fine‑tuned models as a function of query volume and domain specialization is **model‑ and domain‑dependent**: it is set by the $Q^*$ equation above (training + storage cost over the quality uplift), not by a universal rule of thumb. Any quoted break‑even volume is a derived scenario value; more data points and a measured $\Delta Q$ are needed before it can be stated as a general principle.

[ILLUSTRATIVE][ASSUMPTION]: guardrail latency (PII redaction, refusal checking) on generated 300‑token outputs, ~2–8 ms/request on CPU at this chapter's scenario inputs; measure on the target stack (the figure depends on the guardrail implementation and hardware).

Each of these flags is an open empirical question a team should resolve against its own target workload — resolved by measurement into [1P][FACT] or [2°][FACT], promoted to [1P][DERIVED] or [2°][DERIVED] where the resolution is arithmetic, or dropped — rather than left as an untested assumption.

## 8. End-of-Chapter Mini-Case: Choosing the Model for the Enterprise Q&A

*(Continuous scenario: the enterprise Q&A architect must now pick the model given the Ch 4 characterization.)*

An architect is assembled for a design review of the enterprise Q&A tool described in Chapter 4 — the canonical workload (Ch 4, Table 4-2). The team has agreed on the retrieval architecture: vector search with embeddings, 768‑dim all‑mpnet‑base‑v2, single‑vector (cosine/dot‑product ANN) retrieval over a 1 M‑chunk corpus.

From Ch 1's unit-and-token work and Ch 5's selection surfaces, the architect can immediately check the consequences:

- **768‑dim embeddings** are the agreed candidate; their retrieval quality is the gate still to validate on the target corpus (§5.3(a), §5.7), and their cost is ~14 GFLOPs per embedding (64‑token query, the Table 5‑1 embedding table's own row: 2 × 110M × 64 ≈ 14.08 GFLOP), with ~3.1 GB index storage for a 1 M‑chunk corpus (vs ~1.5 GB at 384‑dim) [ILLUSTRATIVE][DERIVED] — the 1 M‑chunk corpus size is a Ch 5‑local input, not part of Table 4‑2's canonical set — a persistent footprint that scales with corpus size, alongside the 70B base model.
- **9.2K input** at ~2.62 MB/KV‑token costs ~24.1 GB of cache (initial) on the 70B generation model — well within for a single request; the ~436 GB KV budget (640 − 140 − 64: 640 − 140 = 500 GB in §5.3(b), less the ~64 GB runtime reserve that Ch 7 §7.3 subtracts) supports ~436/24.9 ≈ 17.5 (floored to 17; the input-only quotient of 18 is shown only for reconciliation and is not the slot-counting basis), i.e. 17 whole‑slot concurrent 9,500‑token requests per host — a KV‑only upper bound, computed at the end‑of‑generation ~24.9 GB footprint (9,500 × 2.62 MB); against the initial 9.2K KV alone the quotient is ≈18 (436 ÷ 24.1), matching Ch 4 §4.6. The prefill budget cap of 1.08 s plus retrieval (~120 ms) sits at the 1.2 s TTFT budget (the cap is a two-term residual; the modelled host prefill is ≈0.47 s at 35% MFU, and the cap leaves no allowance for admission/queue or tokenization/transfer), with the p95 ≤ 2 s SLO giving the real margin.
- The **30× input‑vs‑output ratio** means this system is prefill‑dominated in token/FLOP volume, not in latency: at 300 output tokens and ~25 ms TPOT, decode alone is ~7.5 s versus ~1.08 s prefill, so end‑to‑end latency is decode‑dominated. Model selection must weigh KV cache cost and prefill throughput for compute and capacity, and decode throughput for latency and concurrency.
- The **base‑model + RAG + guardrails** paradigm is the chapter's default; whether it has lower TCO depends on where the workload falls relative to the parametric $Q^*$ break‑even above, which is workload‑specific and unmeasured. A common industry claim is that RAG is 10× cheaper — that ratio is not derivable from the architecture alone: the actual ratio depends on the domain‑specific quality uplift and the query volume, and must be measured rather than assumed.

The architect now has a concrete model shortlist: 768‑dim all‑mpnet‑base‑v2 for the retrieval leg, and the 70B FP16 base model for the generation leg (dense — the ~47B‑total / 12.8B‑active MoE challenger from Ch 3 was *not* rejected on residency: at ~94 GB resident it is 46 GB *below* the dense 70B's 140 GB. The dense 70B stands only as the provisional choice, because equal‑task quality, placement and measured goodput for the challenger remain [UNRESOLVED], and expert dispatch/placement is the added cost), served on 8×H100 with vLLM continuous batching (a per-host placement statement, not a fleet size: one host is memory-sane but compute-oversubscribed at the 10 rps design point — the Chapter 8 prefill screen needs ~5 hosts, ~4.7×). Under the illustrative quality assumptions, no fine‑tuning is selected at this scale — provisional, because $Q^*$ is unmeasured for this workload and the quality gap is an unverified scenario assumption (§5.7); validate the quality gap before ruling it out. The architecture decision record (to be written in Chapter 25) will reference this characterization and the selection surfaces that drove it.
