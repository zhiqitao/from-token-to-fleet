# Chapter 3 — Understanding the Model

## The Architect's Question

After this chapter we should be able to reason about what a model's parameter structure means for deployment: dense versus Mixture-of-Experts (MoE), total parameters versus active parameters per token, and what each implies for compute budgets and memory budgets. We will meet the mechanisms (how MoE routes, how attention weights are computed) not to learn how to train a model but so that, as architects, we can look at a model card and immediately know whether the quoted parameter count is what we actually pay for at inference time, and whether the KV cache will grow as expected. After this chapter we can ask: *given a workload and a model architecture, what is the real residency and compute cost per token?*

## 1. Concept

The **parameter allocation regime** of a model determines how many of its weights are touched on each forward pass. This regime is not a property of the model family name alone; it is a consequence of the training objective and the routing mechanism.

- **Dense models** activate *all* parameters for every token. A 70B dense model reads all 70B weights (or close to it) on every batch-1 decode step — the weight-read-per-token figures in this chapter are all batch-1 single-token decode values — because every layer's full hidden dimension participates in every attention and feed-forward computation. At batch size B, the reads for B requests amortize across the batch. The batch-1 figure is an idealized weight-streaming read (one request's full weight pass), not a measured physical-traffic number (Ch 2); the parameter count on the model card is the inference cost count.
- **Mixture-of-Experts (MoE) models** route each token to a *fraction* of the total parameters. A MoE model may have several hundred billion total parameters (an illustrative figure) distributed across eight experts, but only the top-2 (or top-1) experts are activated per token. The quoted total parameter count includes the unused experts; the *active* parameter count per token is the fraction that routing selects.

The architect-relevant distinction: **total parameters ≠ active parameters per token.** This inequality is the single most important number to read from a model card when sizing a deployment, because it directly changes the compute cost per token. However, the KV cache does not share this privilege — we will show why MoE sparsity saves compute but not memory.

A note on provenance: the total-versus-active distinction arises from the training regime. In dense pre-training, every token sees the full model gradient; in MoE pre-training a learned gate selects the top-k experts for each token, with an auxiliary load-balancing loss keeping assignment spread across the batch, and an unselected expert receives no gradient from that token. The routing mechanism itself (top-k, importance sampling, learned gates) is an architectural decision that outlives training and becomes a deployment fact.

Different generation paradigms therefore have different execution schedules, different state-reuse boundaries and different resource profiles. The book's prefill/decode framework describes the autoregressive text path; the total-versus-active and KV-residency frameworks still apply elsewhere, with per-token accounting replaced by per-evaluation accounting.

## 2. Mental Model

A model's parameters form a **resource pool** that is allocated differently depending on the routing regime.

- In a **dense** model, the pool is *fully allocated* every time. If the model is 70B params in FP16, we need 140 GB of weight memory available for every token. There is no "spending less" — the full 140 GB is the residency floor.
- In an **MoE** model, the pool is *fractionally allocated*. The total pool may be large (reflecting the model's capacity and training compute), but what we actually wire up per token is a slice. With top-2 routing from 8 experts, roughly 2/8 = 25% of the *expert* parameter mass is active per token (plus the always-active attention and shared layers). This fraction saves compute (fewer FLOPs) but the attention layers still see every token, so the KV cache still grows with context length just as in a dense model.

The durable mental model: **total parameters set the memory requirement floor — in a dense model, that floor is the full resident set — and active parameters per token set the per-token compute requirement.** The architect must track both numbers.

### Why MoE saves compute but not KV cache memory

The compute savings are straightforward: if only $n_a = 12.8$B of $n_t = 47$B total parameters are active per token, the FLOP count drops to the active fraction relative to a *same-size dense* model. But note the active fraction for top-2-of-8 routing is ~$12.8/47 \approx 27\%$, not single-digit — so the relative saving is about 5.5× versus the canonical 70B *dense* comparison — or 3.7× versus a same-total 47B dense model — not 20× or 30×. Concretely,

$$
\text{FLOP}_{\text{MoE/token}} = n_a \times 2 \text{ FLOP/param} = 12.8\text{ B} \times 2 \approx 0.0256\text{ T}
$$

which is $0.0256/0.14 \approx 0.183\times$ of the dense 70B figure — roughly a **5.5× reduction** in compute per token against the canonical 70B dense baseline. (Against a *same-total* 47B dense model the saving is instead **3.7×**, since $12.8/47 \approx 27\%$; the two named baselines are therefore 5.5× vs the canonical 70B dense model and 3.7× vs a same-total 47B dense model, and every ratio should say which one it uses.)

The KV cache story is the surprising part. Recall from Chapter 1 (KV cache as a concept) that the KV cache stores one key and one value tensor per token, per layer. The cache size per token scales with the canonical Chapter 1 formula (the full-MHA case, where n_KV-heads × head_dim = hidden_dim; for a GQA/MQA model substitute n_KV-heads × head_dim), $KV_{\text{per-token}} = 2 \times n_{\text{layers}} \times (n_{\text{KV-heads}} \times d_{\text{head}}) \times \text{bytes-per-value}$ (full-MHA special case: $n_{\text{KV-heads}} \times d_{\text{head}} = d_{\text{hidden}}$). Critically, **the attention mechanism processes every token in the context densely** — each token's query attends to all previous tokens' keys and values, regardless of whether the model is dense or MoE. MoE sparsity operates in the feed-forward sub-layer; it does not change the attention sub-layer's behavior.

Therefore, for the canonical dense 70B (80 layers, hidden 8192, full MHA — Ch 7) and for the ~47B challenger, at 8K–9.2K input context: the dense geometry is [canonical scenario][ASSUMPTION]; the challenger's attention geometry is [1P][FACT], with the KV arithmetic built on it [ILLUSTRATIVE][DERIVED]. Two separate claims support the challenger figures. The attention shape — 32 layers, hidden 4096, GQA with 8 KV-heads × 128 — is [1P][FACT], taken from the published config of the Mixtral 8x7B-class model (`config.json` at pinned revision fc7ac94, https://huggingface.co/mistralai/Mixtral-8x7B-v0.1, retrieved 2026-11-23). The ~47B total and ~12.8B active counts are not vendor specification: they are [ILLUSTRATIVE][DERIVED] component arithmetic on the published 46.7B/12.9B totals (Table 3-2). The two cases at 9.2K input context:

- **Dense 70B**: KV cache ≈ **12.06 GB at 8-bit** (9,200 × 1,310,720 B = 12,058,624,000 B ≈ 12.06 GB) or ≈ **24.1 GB at FP16** (9,200 × 2,621,440 B = 24,117,248,000 B ≈ 24.1 GB; the key/value storage pattern is discussed in Ch 7) [canonical scenario][DERIVED]. The 8-bit figure is the FP8 variant of the canonical FP16 constant, exactly 50% of it — the block-overhead and '54%' ITL-slope caveats are stated once in Ch 1; see Ch 7. Both figures use the same 80-layer, 8,192-hidden full-MHA geometry, so only the storage precision differs.
- **~47B MoE challenger (Mixtral 8x7B class)**: KV per token = 2 × 32 × 8 × 128 = 65,536 B = 0.0655 MB/token at 8-bit, so 9,200 × 0.0655 MB ≈ **0.60 GB** (≈1.2 GB at FP16) [ILLUSTRATIVE][DERIVED] — *smaller than the dense 70B's ~12 GB, and the whole difference is the attention shape, not the routing*: 32 layers × a 1,024-wide GQA KV width instead of the canonical 80 layers × 8,192 full-MHA width. The attention layers still emit one key and one value per token per layer; routing neither reduces nor increases that count: the fact that only 12.8B of 47B total parameters are active in the feed-forward layers changes nothing about the keys/values the attention layers store. A **dense** model with the challenger's 32L/4096H GQA shape would hold the same ~0.60 GB — hold the attention geometry fixed and dense vs MoE KV is *identical*.

In other words: MoE sparsity = compute sparsity (fewer FLOPs per token). MoE sparsity ≠ memory sparsity (KV cache still grows linearly with context length, exactly as a dense model's does at the same attention shape). Only changing the attention mechanism itself (e.g., hybrid/linear attention) can reduce the growth rate. The layers it replaces hold a fixed-size recurrent state instead of a growing per-token cache. A hybrid that still keeps some full-attention layers grows more slowly; only a model with no full-attention layers stops growing entirely (Ch 7, Fig 7.2). KV offload changes where the cache resides, not how fast it grows. MLA-style latent attention does not stop the growth: it cuts the bytes/token constant to about 1/57 for DeepSeek-class geometry (32,768/576 ≈ 57× per Ch 1, DeepSeek-V2 MLA report, arXiv:2405.04434 [1P][DERIVED]) but the cache still grows linearly with length. It belongs to Ch 1's reduced-width per-token family, not the constant-state family. This distinction — compute-sparsity versus memory-sparsity — is one an architect has to get exactly right.

> **Key takeaway:** MoE provides **compute sparsity** (far fewer FLOPs per token because a fraction of experts is active), not automatic **weight-residency sparsity** — the full expert set normally remains resident unless it is explicitly offloaded or sharded in a way that changes residency. And the KV cache budget must be provisioned from the model's own attention shape — and, where that shape is not known, at the full-MHA rate for the same layer count and hidden width (the conservative bound). Do not assume MoE reduces KV cache memory — routing never does; only a different attention shape, cache dtype or context length changes the bytes — and do not confuse active-compute savings with a residency saving. (This restates at the parameter level the sparsity lesson introduced conceptually in Ch 1 and developed arithmetically for the canonical model in Ch 7; each chapter teaches it at its own rung of the spine.)

> **Boxed rule — two distinct accounting lines.** Keep two numbers separate and never blur them:
> 1. **total parameters → weight residency.** The resident weights (all experts, for MoE) are what the GPUs must hold. For a 70B dense model this is ~140 GB FP16; for a ~47B MoE this is ~94 GB (full expert set) unless experts are explicitly offloaded.
> 2. **active parameters/token → approximate compute per token.** The routed top-k fraction (e.g. ~12.8B active) sets the FLOPs per token (~25.6 GFLOP) and the active weight-read traffic (~25.6 GB of weights read per batch-1 decode token, amortized across a batch). The active-parameter count is not a memory-freeing lever unless offloading is in play.

## 4. Measurement

How do we determine the total-versus-active split for a model we haven't trained?

1. **Model card inspection.** Most model vendors publish the total parameter count. The active-per-token count is harder to find; it requires reading the architecture documentation for the routing mechanism (top-k, top-1, importance-based). If the model card says "70B parameters" without qualification, assume dense unless it explicitly describes an MoE layout.

2. **Runtime measurement.** For a given input, profile the number of FLOPs or the memory footprint of active weights. Infer the count from the execution, e.g. with `torch.profiler` (record_shapes / with_flops) summing the shapes of the matmuls actually run, or a router hook that logs the experts selected per token; this is an empirical measurement, not a first-party spec.

3. **Architecture diagram.** For MoE models, the number of experts × parameters-per-expert gives the total; the routing hyperparameter (top-k) × parameters-per-expert gives the *routed* active per token — add the always-on attention/shared/embedding parameters for total active per token (the Mixtral-class example above — Table 3-2, §3.3.2 — is 2 × 5.7B routed + ~1.4B always-on = 12.8B, not 11.4B). This is a derived fact from the source code/release, not always on the model card.

> **Practical habit:** When we encounter a model quoted in "X billion parameters," pause and ask: *is this total or active?* For dense models they are the same; for MoE models they diverge. Misreading this is the most common source of weight-residency and compute underestimation — and, through the "sparse therefore smaller KV" shortcut, of KV-cache underestimation as well.

## 5. Common Mistakes

- **Assuming total parameters = active parameters per token.** This is one of the costliest misreads. For a MoE model, the quoted several-hundred-billion or 47B is the total across all experts; the active count per token is a fraction. The two counts drive *different* budgets: the **total** count sets **weight residency** (the full expert set must be resident — the quoted total × 2 bytes, not just the active footprint), while the **active** count sets **compute per token** (only the routed experts are read). Sizing *weight memory* from the active count under-provisions it (the un-routed experts still occupy HBM); sizing *compute* from the total count over-provisions it (the un-routed experts are not read per token). The opposite error — sizing for active parameters while forgetting that MoE routing does not reduce KV cache size — under-provisions the KV budget.

- **Confusing compute sparsity with memory sparsity.** MoE reduces FLOPs per token because fewer parameters are active. It does *not* reduce the number of keys/values written to the KV cache. An architect who assumes MoE shrinks KV cache will be blindsided by memory pressure at long context lengths.

- **Using MoE as a free lunch for long-context workloads.** The compute savings from MoE are real, but the memory cost (weights + KV cache) must be provisioned at the total-parameter scale for weight residency and at the-full-context scale for KV cache. Neither benefit is "free" in the other domain.

- **Ignoring routing overhead.** Top-k routing itself requires computing routing scores (a softmax over expert assignments). This adds a small but non-zero compute cost that is sometimes omitted from published FLOP counts. It is usually negligible compared to the feed-forward arithmetic but should be acknowledged.

## 6. Architecture Consequence

Knowing whether a model is dense or MoE, and whether the quoted parameter count is total or active, directly changes three architectural decisions:

1. **Weight residency budget.** For a dense 70B model, provision 140 GB of FP16 weight memory per host. For an MoE model with ~47B total and ~12.8B active, distinguish two numbers: the **resident** budget (the full expert set, ~47B × 2 bytes ≈ 94 GB, unless experts are offloaded/swapped) and the **active per-token** footprint (~12.8B × 2 bytes ≈ 25.6 GB read per token). The active number governs compute; the resident number governs whether the weights stay on device. Routing does not lower that floor by itself — residency is set by the *total* count, so a same-total dense model holds the same bytes; this challenger's floor is lower only because its total (47B) sits below the dense 70B's: 94 GB vs 140 GB, a 46 GB (~32.9%) saving. Offloading inactives is a further option, priced in bandwidth.

2. **KV cache provisioning.** Provision the KV cache as for a dense model of the same context length, hidden dimension and attention shape. Do not apply a MoE sparsity factor to the KV cache. If we are running a 9.2K-token input on a model with the canonical 80L/8192H full-MHA shape (dense or MoE), the KV cache memory is the same either way — plan accordingly; a model with a smaller or GQA shape (like the ~47B challenger, ~0.6 GB at 8-bit) needs fewer bytes, but that is its shape, not its routing.

3. **Parallelism and routing strategy.** MoE deployment requires a routing strategy (e.g., expert placement, dispatcher, switchboard) and often expert parallelism across GPUs. This adds infrastructure complexity (cross-GPU communication for expert routing) that dense models do not have. The architectural choice between dense and MoE is therefore not just a parameter-count decision; it is a deployment-complexity decision.

### The 2026 baseline shift: same framework, new constants

**The 2026 trend signal (forward-looking; an interpretation of the sample we surveyed, not an established industry-wide convergence).** By August 2026 the four frontier open-weight families surveyed for this edition share a notable pattern, and it is not more of the same dense scaling: extreme MoE sparsity (single-digit active-parameter fractions — Qwen 6B of 125B, Kimi K3 104B of 2.8T) coupled with **hybrid attention** (compressed/sparse/linear hybrids such as Gated DeltaNet + sparse attention) has become a common way to make long-context inference affordable. Appendix A documents these at full depth with first-party provenance; what matters here, in the model-understanding chapter, is that this is not a competing mechanism but the *same* dense-vs-MoE, total-vs-active, KV-vs-compute machinery this chapter just taught — with new constants. We hold that view explicitly as the **forward-looking direction** the architect should size toward, and flag it below as continuing future work (the frontier moves; this handbook is a living document, and Appendix A is where the moving part lives).

**Why the trend signal should not be read as "dense is dead".** This pattern among the four frontier families we surveyed describes the top of the market — the ~100B-and-up tier that includes the ~2.8T-parameter frontier models (e.g. Kimi K3, 104B active of 2.8T). It is not a claim that dense models have disappeared. On the contrary, the smaller, denser tier is alive and actively shipping in 2026 for exactly the constrained-deployment reasons this chapter teaches: **Qwen3.8-27B** ([1P][FACT], model card: https://huggingface.co/Qwen/Qwen3.8-27B) is a dense 27.8B model whose 4-bit weights fit on a single 24 GB consumer GPU, and **Muse Glimmer 30B** ([2°][FACT], source: vLLM-Recipes, citing the Meta model card) is a dense 29.6B local-agentic model that runs in ~18 GB at ~5-bit weights [2°]. These exist because the dense-vs-MoE trade is itself a *deployment* decision, not a date: MoE buys active-parameter efficiency at the cost of total-parameter memory and routing complexity — worthwhile when serving many requests from a large pool of resident weights, but hard to justify when the whole budget is one consumer GPU whose total weights already overrun. That is precisely why this book keeps its canonical on the dense tier: the canonical must serve the architect whose *whole fleet* is a handful of boxes, not only the one sizing a 2.8T datacenter model. The framework does not change between tiers — total vs active, KV per-token, and residency budgeting apply identically to a 27B dense laptop model and a 125B/6B MoE fleet model.

**Why the rest of this chapter's canonical stays a dense full-MHA model.** If the trend is MoE + hybrid, why does this book's canonical still size a dense 70B full-MHA workload? Because a dense model with full multi-head attention gives the cleanest single-constant KV formula (`2 × layers × hidden × bytes`) and the largest KV footprint for a given layer count and hidden width — the conservative worst case within the canonical 80-layer/8192-hidden geometry, and the bound this chapter sizes against. It is not the largest KV constant in the book: Ch 7 §7.4 re-derives the per-token value for other geometries, where a 100-layer, 12,288-hidden model at FP16 gives ~4.9 MB/token. Teaching against the canonical bound means the reader learns the framework on the hardest memory case within that geometry and then relaxes it. It is a deliberate teaching simplification, not a claim that in 2026 an enterprise RAG fleet really runs on dense 70B.

**One verified 2026 transfer: Qwen3.8-Flash-Next.** The model card [1P][FACT] (source: model card HF Qwen/Qwen3.8-Flash-Next, accessed 2026-08-30; A.10) is the Qwen4-architecture preview: **125B total / 6B active** (plus a separate 51B of offloadable N-gram embedding parameters), **512 MoE experts** (10 routed + 1 shared per token), and **hybrid attention** — Gated DeltaNet (GDN) on three of every four layers plus Qwen Sparse Attention (QSA) on the fourth. This is exactly the "125B/6B active MoE + Gated DeltaNet/QSA" class of model a 2026 architect actually considers. Stepping through this book's own arithmetic:

- **Active-weight read traffic per batch-1 decode token** (Ch 7's floor): the weights that must be resident for Qwen are its total set, ~125 × 10⁹ params × 2 bytes/param ≈ 250 GB (plus the offloadable N-gram); of that total, only ~6 × 10⁹ params are read per batch-1 decode token, at 2 bytes/param = ~12 GB. That read is ~1/12 the per-token weight traffic of the canonical dense 70B (140 GB → 12 GB) and ~1/21 of Qwen's own total weight footprint (~250 GB → 12 GB), but it is a *compute/bandwidth* statement, not a residency one: the total weights dominate the memory ceiling. So the *total-vs-active* split of this chapter is not a footnote — it is the difference between fitting on one host and sharding across several, and the ~250 GB total (not the ~12 GB active working set) is what must be resident unless experts are explicitly offloaded.
- **KV cache** (Ch 7/8): the canonical `2 × layers × hidden × bytes` KV formula is the full-MHA bound. Qwen's hybrid attention attacks the KV constant at the mechanism level: GDN layers keep a fixed-size recurrent state instead of a growing per-token cache, so only the remaining full-attention layers contribute per-token KV — the GDN state and the attention-layer fraction are what change stored KV. QSA's sparse micro-block attention cuts attention *reads*; it does not change the bytes stored per token. So per-token KV no longer follows the dense formula, and no KV metric for Qwen3.8-Flash-Next itself is stated anywhere in this book (the related Qwen3.8-27B is a different checkpoint in the same family). Chapter 7 works a configuration-backed version of exactly this two-term budget — Qwen3.8-27B's 16 full-attention layers priced separately from its 48 Gated DeltaNet layers — into its own history-state arithmetic (§7.3), so we do not re-derive it here. The framework question ("does it fit?") is unchanged; the *function* plugged in for KV is not the dense one.
- **Compute** (Ch 8): active-parameter FLOPs drop to ~2 ×6B per token, but the QSA/GDN layers ride different roofline points than a dense 70B prefill/decode split, so the throttled-resource conclusion must be re-derived per model (Ch 8's measurement discipline, not a one-time number).

**The architect's move is unchanged.** For the canonical dense model this book sizes memory, compute, and fleet with one clean constant set. For a 2026 MoE/hybrid model the architect does the *same* decision loop — read the model card, get total vs active, get the KV scheme's per-token function, size residency and roofline, then decide parallelism (Ch 10) and serving (Ch 11). Only the constants differ; the framework does not. Appendix A walks the four frontier models through exactly this re-derivation and flags which vendor numbers still carry a verify-on-own-hardware caveat.

## 7. What We Still Don't Know

As of 2026-08, several questions remain open and are flagged [UNRESOLVED]:

- **How often variable-k routing or capacity dropping fires in production.** The deterministic part is settled by the worked example in §3.3: top-k × parameters-per-expert plus the always-on block fixes the nominal active count per token, so model cards do not need to publish the routing distribution to make the arithmetic reproducible. The residual open question is the *effective* active count under variable-k routers, token-dropping under capacity limits, or expert-unavailable fallback — an implementation-specific exception whose frequency under real traffic nobody publishes.
- **Whether router latency offsets MoE compute savings.** The cost of computing routing scores and dispatching to experts is not always included in published FLOP counts. On some hardware the routing overhead can be significant enough to narrow the compute gap between MoE and dense.
- **KV cache behavior under MoE with expert swapping.** Expert swapping does not change KV cache size; size is set by attention geometry and sequence length. But expert weight transfers compete with KV offloading for the same host-transfer path. The open question is the *bandwidth contention* between expert weight transfers and KV transfers at a given PCIe/NVLink budget. It is workload- and implementation-dependent.

These flags exist because home-lab measurements are not reference per the evidence taxonomy; each is an open empirical question a team should validate against its own target workload, not a claim the handbook has settled.

## 8. End-of-Chapter Mini-Case: Total vs. Active Parameters, and the KV Constant

*(Continuous scenario — chained from the enterprise Q&A thread.)*

An architect is fleshing out the design of the internal Q&A tool described in Chapter 1's mini-case. The team's standing decision from Chapter 2 is the dense 70B model; a MoE model with 8 experts (roughly 47B total params, ~12.8B active per token) is the challenger under consideration. They ask: "If we go MoE, can we cut our GPU memory budget?"

From the model-understanding chapter, the architect can answer: Active-compute *traffic* yes — a per-token read volume, not a memory budget: only ~12.8B of the ~47B total is active per token, so ~25.6 GB of *active* weight is read per batch-1 decode token vs. 140 GB for a dense 70B. *Resident* memory yes as well, for this challenger — but for a reason worth stating precisely. An MoE model normally keeps its **full expert set resident** — the non-active experts still occupy HBM unless we explicitly use expert offload/swapping (Ch 3 §3.6, Ch 18), which itself costs bandwidth — so the resident budget is ~47B × 2 bytes ≈ 94 GB rather than 140 GB: a drop of 46 GB, ~32.9% of FP16 weight memory. That drop is earned by the challenger's smaller *total* parameter count (47B vs 70B), not by routing itself — a dense model of the same 47B total would hold the same 94 GB — and offloading some experts is a further, bandwidth-costed option on top. And KV cache memory no — routing does not change it: the attention layers still process every token densely and emit one key and one value per token per layer, so at a fixed attention geometry the 9.2K-context budget is the same whether the model is dense or MoE. The challenger's own shape (32 layers, hidden 4096, GQA 8 KV-heads × 128) needs only ~0.6 GB at 8-bit (~1.2 GB at FP16) for that input — but that is its attention shape, not its routing, and a dense model with the same shape holds the same bytes; where the shape is not known we provision at the dense full-MHA rate — ~24.1 GB at FP16 per 9.2K request, the canonical scenario's KV precision (Ch 4, Table 4-2), or ~12.06 GB at 8-bit — as the conservative bound. We'll also need expert-routing infrastructure on top of that.

The architect's decision therefore rests on two findings, both stated plainly. **(a) Resident weights do drop:** ~140 GB (dense 70B) → ~94 GB (the ~47B MoE) — 46 GB, ~32.9% of FP16 weight memory — earned by the challenger's smaller total parameter count, not by routing a same-size model. **(b) Routing does not change the KV bytes:** with the same attention geometry the 9.2K-context budget is unchanged; the challenger's own 32L/4096H GQA shape would need only ~0.6 GB (8-bit) / ~1.2 GB (FP16), and where the shape is unknown we provision at the dense-70B full-MHA rate (~24.1 GB at FP16 — the canonical precision — or ~12.06 GB at 8-bit) as the conservative bound; when the shape is known, use the model's own shape (~0.6 GB for the challenger). What this accounting does *not* settle is whether the challenger is the better system. Routing and expert dispatch are integrated in serving runtimes — vLLM, for example, dispatches experts over all-to-all communication behind a runtime flag ([Expert Parallel Deployment](https://docs.vllm.ai/en/latest/serving/expert_parallel_deployment/)) — so a *GPU dedicated to the routing dispatcher* is an optional design hypothesis [ILLUSTRATIVE][ASSUMPTION], not an unavoidable requirement; the real added cost is placement, and it must be compared on an actual arrangement — on the canonical single 8×H100 host (640 GB, Ch 4 Table 4-2) both 140 GB and 94 GB of FP16 weights fit, so the 46 GB saving buys KV headroom rather than feasibility, while an expert-parallel layout across GPUs trades that headroom for cross-GPU all-to-all traffic (§3.6). The team therefore does **not** select the challenger yet: quality at equal task performance, placement on the actual single-host or expert-parallel arrangement, and measured service goodput under the target workload remain unresolved [UNRESOLVED]. The Chapter 2 dense 70B decision stands as the provisional choice, and the KV cache budget is provisioned at the dense-model rate either way.
