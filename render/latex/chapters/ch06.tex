\section*{The Architect's Question}\label{the-architects-question}

After this chapter we should be able to walk into a running inference
system, read its metrics, and answer a deceptively hard question:
\emph{is this system meeting its obligations, and if not, which lever do
we pull?} Teams commonly instrument the wrong thing --- model capability
and offline quality --- and then are blind when a real workload
misbehaves. This chapter builds the metric hierarchy that turns raw
telemetry into architecture decisions: what to log, what each number
means, how to read a latency \emph{distribution} instead of a mean, and
how to tell bandwidth-bound from compute-bound purely from the counters.
After this chapter, ``the system felt slow'' becomes a falsifiable,
diagnosable claim.

\ntsection{Concept}\label{concept}


\subsection{The Metric Hierarchy}\label{the-metric-hierarchy}

Not all numbers are equal. We organize serving telemetry into three
layers, each answering a different question and each consumed by a
different role:

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\item
  \textbf{Workload metrics} --- what the system is being \emph{asked} to
  do. Requests per second (rps) and the token profile (input length,
  output length, context length). These are the independent variables
  --- the \emph{offered} load; we do not control them, we characterize
  them. Concurrency is not a workload input: it is a serving-side
  quantity derived from the arrival rate and the time in system
  (Little's law), so it belongs with queue depth on the scheduler side,
  not in this layer. The chain is population (active users) → arrival
  rate λ → in-flight requests (λ·W) → resident KV slots (Ch 4 §4.3,
  §4.6), and every link after λ is derived. \hyperref[fig:6.1]{Fig 6.1}'s workload box
  therefore carries the request rate, the token profile, and a
  \emph{concurrency} entry that denotes the request rate λ that the
  traffic offers, not a concurrency value. For the canonical
  enterprise-Q\&A RAG workload these are fixed by canonical scenario (Ch
  4, \hyperref[tab:4.2]{Table 4-2}): \textasciitilde10 rps average with \textasciitilde40
  rps peaks, \textasciitilde9,200 input + \textasciitilde300 output
  tokens per request.
\item
  \textbf{Serving metrics} --- how \emph{well} the system performs under
  that workload. Time-to-first-token (TTFT), time-per-output-token
  (TPOT), inter-token latency, and \textbf{goodput} (tokens per second
  that actually meet the SLO). These are the dependent variables; they
  are what the SLO is written against --- the canonical design budgets
  are TTFT 1.2 s / TPOT \textasciitilde25 ms, and the SLOs written
  against them are p95 TTFT ≤ 2 s and p95 TPOT ≤ 35 ms (Ch 4, \hyperref[tab:4.1]{Table 4-1}
  Latency row; Canonical Workload box). \textbf{Queue depth} is not one
  of them: it is a scheduler state, a leading indicator that helps
  explain these serving metrics.
\item
  \textbf{Resource metrics} --- \emph{why} performance is what it is.
  HBM bandwidth utilization, FLOP utilization / model FLOPs utilization
  (MFU), KV cache occupancy, and memory pressure. These reveal the
  binding constraint.
\end{enumerate}

The discipline this chapter works toward: \textbf{never jump from a
workload metric straight to a serving metric, or a serving metric
straight to a hardware conclusion.} The causal direction is
\emph{workload → resource demand → serving behavior} (the workload's
token profile drives the resource demand; the resource supply shapes how
the model behaves). Diagnosis runs the other way: a slow response
(serving) is diagnosed by asking whether the kernel is bandwidth- or
compute-bound (resource), which is only meaningful given the token
profile (workload). Skipping a layer produces superstition --- ``it's
slow, let's buy GPUs'' --- instead of a mechanism.

\subsection{Why the Wrong Metric
Persists}\label{why-the-wrong-metric-persists}

Teams default to measuring what they already have dashboards for: model
quality (accuracy, ROUGE, benchmark scores) and average latency. Both
are dangerously incomplete. Quality is the \emph{goal} and a
\emph{feasibility gate} --- a fast or cheap architecture that fails the
quality bar is disqualified before performance even matters --- but it
is not the \emph{bottleneck} that explains a resource or latency failure
once quality is acceptable; that is the role of the serving metrics.
Average latency is a single scalar that hides the tail that actually
violates SLAs. The entire thesis of this chapter is that the metric that
drives an architecture decision is usually \textbf{not} the metric the
model card advertises.

\ntsection{Mental Model}\label{mental-model}


The three metric layers form a \textbf{diagnostic chain}, like the
layers of the OSI stack in miniature:

\begin{itemize}
\tightlist
\item
  \textbf{Workload} is the \emph{traffic} --- what we are asked to do.
\item
  \textbf{Serving} is the \emph{service} --- how well we did it.
\item
  \textbf{Resource} is the \emph{engine} --- how hard the machine is
  working, and on what.
\end{itemize}

(The listing order here is by \emph{role} --- independent inputs,
dependent outputs, explanatory engine. It is not the causal order:
causation flows workload → resource → serving, which is how \hyperref[fig:6.1]{Fig 6.1}
stacks them top to bottom. The two orderings are different and both
intentional.)

When something breaks, we read upward: a p95 TTFT breach (serving)
forces us to look at the resource layer first (resource: is prefill
queuing because we're FLOP-bound?) and then the token profile (workload:
did context length grow?). The causal direction follows the system, not
the diagnosis: the workload generates resource demand, and the resource
supply shapes serving behavior --- so when numbers are healthy, the
chain shows the system meets the SLO under the observed workload.

The mental model also warns against \textbf{one number standing in for
many different things}. ``Throughput'' without a qualifier is
meaningless: is it requests per second, tokens per second, or
\emph{goodput} --- tokens per second that arrived before the SLO
deadline? We commit to always qualifying.

\ntsection{Worked Example}\label{worked-example}


\subsection{Latency Is a Distribution, Not a
Mean}\label{latency-is-a-distribution-not-a-mean}

A very common measurement error is reporting (and SLO-ing) the
\emph{average} latency. \hyperref[fig:6.2]{Fig 6.2} shows a synthetic request stream: the
body of requests follows a log‑normal distribution centered near 0.8 s
(99\% of observations), with a 1\% straggler cluster at 5.0 s
\mbox{{[}ILLUSTRATIVE synthetic mixture{]}}. That combination is deliberately
\emph{not} a two‑point ``99\% at 0.8, 1\% at 5'' distribution; it is a
realistic spread, so the percentiles below are read off the plotted
histogram rather than guessed. The plotted stream is a synthetic sample
of N = 10,000 requests --- 99\% drawn from a log‑normal with median 0.8
s and log-scale dispersion σ ≈ 0.12 (generated as exp(μ + σZ), with μ =
ln 0.8 and Z standard normal), 1\% a straggler cluster at 5.0 s --- and
the percentiles are read by linear interpolation on the sorted sample.
The two-point approximation of the mean is \[
\mathbb{E}[L] \approx 0.99 \times 0.8 + 0.01 \times 5.0 \approx 0.84 \text{ s}
\] --- looks fine. Three \emph{different} quantities circulate in this
paragraph, so we fix them once here, at first presentation, because they
are not interchangeable. (a) The two-point approximation above
substitutes the 0.8 s median for the whole 99\% body: 0.99 × 0.8 + 0.01
× 5.0 = 0.842 s (the display above rounds it to 0.84 s). (b) The
analytic mean of the mixture as specified is slightly higher, because a
log-normal with median 0.8 s and log-scale dispersion σ = 0.12 has mean
0.8 × exp(σ²/2) ≈ 0.8058 s: 0.99 × 0.8058 + 0.01 × 5.0 ≈ 0.848 s. (c)
The \emph{sample} mean of this particular draw of N = 10,000 is 0.85 s
--- the value \hyperref[fig:6.2]{Fig 6.2} displays --- and it is draw-dependent in the same
way the sample p99 is: another draw moves the last digit, while the
population value does not move. The percentiles below are read off this
sample, not off the distribution.

Read off the sample, the long tail looks like this: p50 ≈ 0.80 s, p90 ≈
0.94 s, p95 ≈ 0.99 s, and p99 ≈ 1.33 s. Every one of these is a property
of the N = 10,000 \emph{sample}, not of the distribution: the population
p99 of this 99 \% log‑normal + 1 \% straggler mixture is 5.0 s. The
sample p99 is knife-edge --- one straggler moves it. With exactly 100
stragglers (1 \% of 10,000) the interpolated sample p99 is 1.33 s. With
101 of 10,000 a straggler sits at rank 9,900 itself, both interpolation
endpoints become 5.0 s draws, and the sample p99 is 5.0 s.

\emph{Reproducibility (percentile interpolation).} The p99 position is 1
+ (N−1) × 0.99 = 9,900.01, i.e.~one hundredth of the way from rank 9,900
to rank 9,901. In this draw the sorted values are rank 9,900 = 1.30 s
and rank 9,901 = 5.0 s. Rank 9,900 is the largest non-straggler draw,
because the 100 stragglers occupy ranks 9,901--10,000. The interpolated
p99 is therefore 1.30 + 0.01 × (5.0 − 1.30) = 1.337 s --- the percentile
line falls just past the end of the body, in the empty gap between it
and the first straggler.

The mean hides the tail; percentiles expose it --- but notice how far
one has to go to expose \emph{this} tail. Under the canonical p95 TTFT
SLO of ≤ 2 s, \textbf{even this sample's p99 (≈ 1.33 s) still looks
healthy --- the population p99 is 5.0 s, sitting on the straggler
cluster.} Request latency ≥ TTFT, so a p95 TTFT-ceiling line drawn on
request latency flags a superset of TTFT violations. The 5 s stragglers
are the top 1\% of the stream --- in this sample they sit \emph{between}
the 99th and 100th percentile, so the interpolated p99 line alone does
not bring them into view. Only the p99.9 / maximum reading (or the full
distribution) surfaces them. This is the sharper lesson: a tail can hide
not just behind the mean but behind any single percentile, and the
choice of which percentile to SLO against matters. It is why we log the
full distribution and also watch the \emph{outlier fraction} (how much
probability mass sits beyond the SLO line), not just one percentile.

Why the mean is not a signal. The same request stream of 99\% @ 0.8 s +
1\% @ 5 s reported as a single number looks healthy. The two-point
approximation gives 0.84 s (≈ 0.848 s for the mixture as specified); the
simulated stream's \emph{sample} mean is 0.85 s. Yet the population p99
paints a very different picture against the 2 s p95 TTFT ceiling (the
SLO itself is stated at p95, Ch 4) --- a ceiling above the 1.2 s design
budget, not a second budget. Log the distribution; SLO against the
percentile.

Apply this to the canonical workload. We budget TTFT ≤ 1.2 s (retrieval
\textasciitilde120 ms + prefill \textasciitilde1.08 s), with a p95
ceiling of ≤ 2 s that the budget relaxes to. Suppose a flash crowd (the
\textasciitilde40 rps peak) causes prefill requests to queue on a fleet
provisioned at the full-utilization compute screen
(\textasciitilde19--22 hosts, Ch 8 §3) --- that screen is not an
SLO-goodput guarantee, so residual queueing under bursts can still push
p95 TTFT above target. If on average the batch is well-behaved, p50 TTFT
might sit at \textasciitilde1.0 s. But the jobs that arrive behind
\textasciitilde1--2 same-time prefill requests each pay the full 1.08 s
prefill of the job(s) ahead of them, so p95 TTFT drifts to
\textasciitilde2.5 s. \emph{(Fleet scope: this 1--2-jobs-ahead
illustration is the fleet-sized case. On a single 8×H100 host at the
same 40 rps peak, prefill demand is \textasciitilde18.6× that host's
sustained capacity --- Ch 8 §3, \hyperref[tab:8.1]{Table 8-1} --- so the queue is unbounded
and p95 TTFT grows until admission control intervenes; the 2.5 s figure
does not describe that case.)} The \emph{average} says ``fine''; the
\emph{p95} says ``we just violated our SLO.'' We hence log p50, p90,
p95, and p99 independently and run the SLO against the percentile, never
the mean. \mbox{{[}canonical scenario{]}}\hspace{0pt}\mbox{{[}ASSUMPTION{]}} author-chosen SLO
budget from the canonical scenario (Ch 4, \hyperref[tab:4.2]{Table 4-2}); the arithmetic is
the point, not a citation.

\subsection{Goodput vs Raw Throughput}\label{goodput-vs-raw-throughput}

Deploying a higher-throughput configuration can \emph{reduce} goodput:
goodput = raw\_rate × compliant\_fraction, where the compliant fraction
is the share of emitted tokens whose arrival time is within the SLO
deadline for their request --- so a throughput increase helps goodput
only if the compliant fraction holds. Concretely: suppose we enable
larger dynamic batching to raise raw tokens/s from 50 tok/s to 70 tok/s,
but the batch window pushes p95 TTFT from 1.8 s to 2.3 s --- above the 2
s SLO. (Register: the 50 tok/s baseline is Ch 5's single-stream
illustrative point and the 70 tok/s figure is a batched configuration.
The pair is therefore a cross-register comparison, not a like-for-like
batch-to-batch measurement; the goodput arithmetic below holds at either
register.) Scenario A \mbox{{[}ILLUSTRATIVE{]}}\hspace{0pt}\mbox{{[}DERIVED{]}}: if all of the
extra 20 tok/s land in the tail that misses the SLO, the compliant
fraction falls to f = 48 ÷ 70 ≈ 68.6 \% (the split is derived below),
and goodput is 70 × 0.686 ≈ 48 tok/s --- level, not higher. Raw
throughput is up 40\%; \textbf{goodput} (tokens that met the SLO) is
unchanged \emph{in this case}, because the SLO-compliant token count did
not grow.

The ``unchanged'' claim holds only when the extra tokens all land in the
SLO-missing tail, i.e.~the compliant fraction drops proportionally to
the raw-rate gain. Scenario B \mbox{{[}ILLUSTRATIVE{]}}\hspace{0pt}\mbox{{[}DERIVED{]}}: if the
compliant fraction falls from 96\% to 94\%, goodput is 50×0.96 = 48 vs
70×0.94 = 65.8 --- it \emph{rises} despite the p95 breach. Scenario C
\mbox{{[}ILLUSTRATIVE{]}}\hspace{0pt}\mbox{{[}DERIVED{]}}: if the compliant fraction falls to 65\%
--- a constructed split, not a measured stream --- goodput is 70×0.65 =
45.5 tok/s --- \emph{below} the 48 tok/s baseline. The dividing line is
the compliant fraction f at which the throughput gain cancels: 70 × f =
48, i.e.~f ≈ 68.6\%, so goodput falls only when the compliant fraction
drops below \textasciitilde69\%. That is what Scenario A's ``unchanged''
result requires, and it is a 27-point collapse from 96\%, not the
2-point drop of Scenario B. The three scenarios are therefore comparable
only when each states its f: \textasciitilde68.6\% leaves goodput
unchanged, below \textasciitilde68.6\% reduces it, 94\% raises it. A p95
breach is a \emph{configuration-level} acceptance signal. Request-level
SLO-goodput is a separate measurement: compute it from the compliant
fraction, not from the p95 alone.

\emph{Scope note: the 50→70 tok/s pair is a cross-register comparison
--- 50 tok/s is Ch 5's single-stream illustrative point and 70 tok/s is
a batched configuration --- and both sit in the same low-batch decode
range (Ch 5's illustrative basis, \textasciitilde14--20 ms/token across
the 50--70 tok/s range; canonical batch-1 is 40 tok/s at 25 ms/token),
not the host's aggregate serving rate (Ch 15: \textasciitilde8.5K tok/s
prefill-side, \textasciitilde35,000--56,000 tok/s batched) --- the
goodput argument holds at any consistent operating point.}

Goodput is the metric the customer experiences; raw throughput is what
the GPU achieves. The architect optimizes goodput. This is why
``faster'' hardware or bigger batches do not trivially mean a better
system.

\subsection{Detecting the Regime: Bandwidth-Bound vs
Compute-Bound}\label{detecting-the-regime-bandwidth-bound-vs-compute-bound}

The most decision-relevant resource question is: is this layer
bandwidth-bound or compute-bound? We recall the arithmetic from \hyperref[chap:2]{Chapter 2}:

\begin{itemize}
\item
  \textbf{Decode is HBM-bandwidth-bound at low batch.} The
  shard-invariant reason comes first: at batch 1 decode's arithmetic
  intensity is \textasciitilde1.0 FLOP/byte (140 GFLOP / 140 GB), far
  below the \textasciitilde295 FLOP/byte roofline ridge --- this low
  intensity, not any single device's bandwidth total, is why decode is
  starved for weights regardless of sharding. Generating one token needs
  a full forward pass over the 70B weights of the \textbf{canonical
  80-layer, hidden-8192, full-MHA 70B reference} = 140 GB (FP16) of
  reads per token --- a \textbf{batch-1-equivalent} idealized
  weight-streaming read (one request's full weight pass), not a measured
  bytes-physically-read figure. As a concrete single-device
  illustration: within a \textasciitilde25 ms TPOT budget, 140 GB /
  0.025 s ≈ \textbf{5.6 TB/s} (batch-1-equivalent) exceeds an H100's
  \textasciitilde3.35 TB/s peak \mbox{{[}1P{]}}\hspace{0pt}\mbox{{[}FACT{]}}. \textbf{Scope
  warning: this 5.6-vs-3.35 TB/s comparison is an \emph{illustrative
  single-device roofline} argument, not the canonical 8×H100 host's
  actual deployment verdict.} The 5.6 TB/s is a \emph{theoretical
  demand} that holds at batch 1 only, where one token pays the full
  weight read: the weights amortize across the b tokens of a step, so
  the required weight-read rate falls roughly as 140 GB ÷ (b × 0.025 s)
  --- the 5.6\textgreater3.35 shortfall characterizes a batch-1 stream,
  not a batched server. Two scope notes keep this honest. First, 5.6
  TB/s is the \textbf{aggregate} model-wide weight-read rate for a
  hypothetical single-device implementation; under tensor parallelism
  (the canonical 8×H100 host) the 140 GB is sharded, so each GPU only
  needs \textasciitilde0.70 TB/s against its own 3.35 TB/s
  (\textasciitilde21\% achieved HBM utilization --- 0.70 TB/s ÷ 3.35
  TB/s = 20.9\%: the canonical 25 ms TPOT is a \emph{budget} covering TP
  collectives, kernel inefficiency, sampling and scheduling, not a
  bandwidth-saturated point) --- the single-device 5.6\textgreater3.35
  bound does not itself show a per-GPU bandwidth shortfall. Second, the
  intensity reason stated first above is what makes this a roofline
  classification rather than a device verdict (the roofline and its
  ridge are developed in Ch 8). So the honest statement is: decode is
  memory-bound because its intensity is low and batching raises it, not
  merely because an aggregate 5.6 TB/s exceeds one GPU's 3.35
  \mbox{{[}canonical scenario{]}}\hspace{0pt}\mbox{{[}DERIVED{]}}. (This is an operating-point
  property, not an identity, and it is a \textbf{weight-only} statement:
  at high batch decode climbs the intensity slope. With the canonical
  9.2K KV re-read included, use one denominator rule --- count the
  weight bytes and the KV bytes whenever both terms are in the
  numerator. At batch 1 the intensity is 164.1 GFLOP (140 projection +
  24.1 attention; the attention term is 4·L·d\_model·n\_layers = 4 ×
  9,200 × 8,192 × 80 ≈ 24.1 GFLOP) ÷ (140 GB weights + 24.1 GB of
  canonical 9.2K FP16 KV) ≈ \textbf{1.0 FLOP/byte}. At batch 32 it is 32
  × 164.1 = 5,251 GFLOP ÷ (140 + 32 × 24.1 = 911 GB) ≈ \textbf{5.8
  FLOP/byte}, and it approaches the KV-only asymptote 164.1 ÷ 24.1 ≈ 6.8
  FLOP/byte as batch grows. Every one of these values is far below the
  \textasciitilde295 FLOP/byte ridge, so decode stays bandwidth-bound
  across this batch range --- Ch 8.)
\item
  \textbf{Prefill is compute-bound at the canonical long-prompt
  operating point.} The reason prefill lands on the compute plateau of
  the roofline is its high arithmetic intensity: the FLOPs per byte
  moved are far above the \textasciitilde295 FLOP/byte ridge point
  (developed in Ch 8), so the compute units --- not the HBM weight
  stream --- are the binding resource. Only after establishing that
  regime do we check the deadline: the prefill pass for 9,200 input
  tokens costs ≈ 2 ×70e9 params × 9.2e3 tokens ≈ \textbf{1.29 PFLOP of
  linear (2NL) FLOPs} (the quadratic attention term adds ≈ 0.2 PFLOP at
  9.2K --- ≈ 1.5 PFLOP full-square total, Ch 22 \hyperref[tab:22.1]{Table 22-1}), which
  against the \textasciitilde1.08 s prefill budget implies a required
  rate of ≈ 1.19 PFLOPS --- above a \emph{single} H100's
  \textasciitilde0.989 PFLOPS dense BF16 peak (FP16/BF16: same H100
  peak) (1.19 \textgreater{} 0.989). But that 1.19-vs-0.989 comparison
  is a \textbf{single-device deadline/capacity illustration}, not the
  evidence that prefill is compute-bound: on the canonical 8×H100 host
  the aggregate peak is \textasciitilde7.9 PFLOPS, so the host
  comfortably satisfies the rate --- the ``single H100 can't prefill a
  9.2K prompt in 1.08 s'' conclusion is about whether one
  arbitrarily-chosen GPU can meet the deadline, not about the kernel's
  roofline regime. Prefill being \emph{compute-bound} (rather than
  bandwidth-bound) follows from its high arithmetic intensity, not from
  the 1.19-vs-0.989 comparison. \mbox{{[}canonical scenario{]}}\hspace{0pt}\mbox{{[}DERIVED{]}}
\end{itemize}

At the resource layer, the tell is utilization: a decode kernel pinned
at \textasciitilde95\% of HBM bandwidth / \textasciitilde30\% of FLOPs
\mbox{{[}ILLUSTRATIVE{]}}\hspace{0pt}\mbox{{[}ASSUMPTION{]}} --- a hypothetical telemetry
signature --- is bandwidth-bound; a prefill kernel with
\textasciitilde90\% FLOP utilization \mbox{{[}ILLUSTRATIVE{]}}\hspace{0pt}\mbox{{[}ASSUMPTION{]}}
is compute-bound. \textbf{The same hardware, the same model --- the
boundary flips between prefill and decode.} This is precisely why
Splitwise/DistServe (and Mooncake's KV-centric disaggregation) split
prefill from decode onto different pools \mbox{{[}S4{]}}\hspace{0pt}\mbox{{[}1P{]}}\hspace{0pt}\mbox{{[}FACT{]}}: the
bottleneck-regime difference is the primary motivation for

\subsection{Reading Telemetry Into a
Decision}\label{reading-telemetry-into-a-decision}

A concrete dashboard-read → decision trace. We see: p95 TTFT climbing
(serving), KV cache hit ratio low (resource: FLOP/reuse --- prefill
recomputation), and prefill queue depth growing (serving). Workload is
unchanged. Reading up the chain: low prefix-cache hit means many
independent 9.2K prefixes are being prefill-processed from scratch on
the \textasciitilde40 rps peak --- each \textasciitilde1.29 PFLOP (case
(i), linear-only) --- aggregate prefill demand at the 40 rps peak is 40
× 1.29 ≈ 51.6 PFLOP/s against the 8×H100 sustained prefill capacity of
\textasciitilde2.77 PFLOP/s (35\% MFU, Ch 8 §3) --- \textasciitilde18.6×
oversubscribed (the datasheet-peak \textasciitilde7.9 PFLOPS gives
\textasciitilde6.5×, the theoretical ceiling only; under case (ii),
full-square attention, the same peak screens at \textasciitilde22 hosts
--- Ch 8 §3), consistent with Ch 8's 19-host screen at this peak (case
(i)), so the prefill queue grows until backpressure or prefix caching
intervenes. The decision: enable prefix / RadixAttention-style caching
(SGLang) or Automatic Prefix Caching (vLLM) so the byte-identical shared
prefix is reused instead of re-prefilled --- in the canonical workload
(1,200 prompt + 8,000 per-query retrieved, Ch 4 \hyperref[tab:4.2]{Table 4-2}) the
byte-identical share is at most the fixed system/instruction portion of
the \textasciitilde1,200-token prompt, because the 8K retrieved block
differs per query and the 1,200-token slot carries the query itself (Ch
4 \hyperref[tab:4.1]{Table 4-1}), so \textasciitilde13\% of prefill FLOPs (the whole-slot
case) is an upper bound on the cacheable fraction; prefix caching is
therefore a partial mitigation, not the fix for the 40 rps prefill queue
(§6.7 keeps the actual reduction \mbox{{[}UNRESOLVED{]}}).
\mbox{{[}S3{]}}\hspace{0pt}\mbox{{[}1P{]}}\hspace{0pt}\mbox{{[}FACT{]}} Prefix caching is a compute-saving move ---
its TTFT benefit arrives through the prefill work it removes, not
through a latency knob of its own --- and the telemetry told us that.

\ntsection{Measurement}\label{measurement}


Three practical habits anchor the architect:

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\item
  \textbf{Instrument the hierarchy, not just the app.} Deploy counters
  at all three layers from day one --- rps and token profile (workload);
  TTFT/TPOT/goodput percentiles and queue depth (serving --- queue depth
  being the scheduler state that explains the others); HBM bandwidth,
  FLOP/MFU, KV cache occupancy, memory pressure (resource). A system
  that only logs serving metrics cannot tell \emph{why}; one that only
  logs resource metrics cannot tell \emph{what it was asked}.
\item
  \textbf{Always qualify ``throughput.''} rps ≠ tokens/s ≠ goodput. The
  same number, three stories. State the SLO window (p95 ≤ 2 s TTFT)
  before quoting any rate, or the rate is meaningless.
\item
  \textbf{Log the distribution.} Capture p50/p90/p95/p99 for every
  latency metric, and the full token-length distribution (a 32K-tail
  context is a different workload than a 9.2K average). The mean is a
  summary, not a signal.
\end{enumerate}

These habits answer the book's recurring question --- \emph{what would
we actually measure here?} --- with three layers of counters at the
edge, before any architecture decision is committed.

\ntsection{Common Mistakes}\label{common-mistakes}


\begin{itemize}
\tightlist
\item
  \textbf{SLO-ing the average.} A \textasciitilde0.85 s mean (the
  figure's simulated stream; the two-point analytic approximation gives
  \textasciitilde0.84 s --- the figure's displayed value is used here)
  hides a 5 s tail. SLO against p95/p99, and watch the outlier fraction,
  not the mean.
\item
  \textbf{Optimizing raw throughput when the SLO windows it.} Bigger
  batches raise raw tokens/s but can push TTFT past its deadline,
  erasing the throughput gain. Optimize goodput.
\item
  \textbf{Jumping straight to ``buy more GPUs.''} A bandwidth-bound
  decode and a prefill-cost problem need different fixes; without the
  resource layer we guess.
\item
  \textbf{Treating hardware peak as a ceiling we can hit.} H100's 3.35
  TB/s is the theoretical HBM peak; real memory-bound kernels realize a
  fraction of it. Design headroom against real utilization, not the spec
  sheet.
\item
  \textbf{Conflating model-quality metrics with serving metrics.}
  Accuracy is the goal; TTFT is the constraint. A slow, accurate model
  fails its SLO just as surely as a fast, wrong one.
\end{itemize}

\ntsection{Architecture Consequence}\label{architecture-consequence}


The metric hierarchy directly dictates architecture. For the canonical
workload:

\begin{itemize}
\tightlist
\item
  \textbf{Bandwidth-bound decode + compute-bound prefill ⇒ P/D
  disaggregation} (Splitwise/DistServe/Mooncake) is a candidate remedy
  at scale when prefill/decode imbalance is large, scale is sufficient,
  and KV-transfer + extra pool/scheduling costs stay below the
  interference savings --- costs include KV migration, added failure
  domains, and pool sizing; compare against colocated scheduling with
  chunked prefill. \mbox{{[}S4{]}}\hspace{0pt}\mbox{{[}1P{]}}\hspace{0pt}\mbox{{[}FACT{]}}
\item
  \textbf{Repeat-prefix RAG ⇒ enable prefix caching}
  (RadixAttention/APC), which reuses the shared prompt prefix of the
  9.2K prefills (\textasciitilde13\% of prefill work in the canonical
  workload --- an upper bound, §6.3.4; the 8K retrieved block is
  query-specific) and so partially defends the p95 TTFT against the 40
  rps peaks. \mbox{{[}S3{]}}\hspace{0pt}\mbox{{[}1P{]}}\hspace{0pt}\mbox{{[}FACT{]}}
\item
  \textbf{KV cache pressure ⇒ quantize or offload KV.} FP8 KV = raw
  tensor byte-halving = 1.31 MB/token (exactly 50\% of FP16)
  \mbox{{[}canonical scenario{]}}\hspace{0pt}\mbox{{[}DERIVED{]}}; any block-allocation/metadata
  overhead is NOT vendor-measured here and must be filled by a
  deployment benchmark. (The vLLM FP8-KV blog's `54\%' \mbox{{[}S6{]}} is a
  decode inter-token-latency (ITL) slope, not a memory ratio or
  footprint coefficient --- on this book's own reading of that post's
  Table 3, not a vendor-stated interpretation \mbox{{[}1P{]}}\hspace{0pt}\mbox{{[}HYPOTHESIS{]}};
  re-verify it against the post, as Ch 1 does at its KV-cache section.)
  And vLLM KV-offloading (its own 2026-01-08 blog
  \mbox{{[}S7{]}}\hspace{0pt}\mbox{{[}1P{]}}\hspace{0pt}\mbox{{[}FACT{]}}) cuts TTFT by 2--22× in a particular
  warm-cache-hit/reuse benchmark, not a generic cold-cache improvement
  --- both are memory-layer fixes the telemetry would call for when KV
  occupancy nears capacity.
\item
  \textbf{Speculative decoding where decode bandwidth is the wall} ---
  DFlash \emph{reports} over 6× lossless acceleration, up to 2.5× over
  EAGLE-3, in its paper's evaluated configurations
  \mbox{{[}S5{]}}\hspace{0pt}\mbox{{[}1P{]}}\hspace{0pt}\mbox{{[}FACT{]}} --- because it reduces weight reads per
  accepted token. These are paper-reported results, not portable
  serving-speed figures: treat them as performance claims to re-measure
  on the target workload, not as a guaranteed speedup.
\end{itemize}

\ntsection{What We Still Don't Know}\label{what-we-still-dont-know}


\begin{itemize}
\tightlist
\item
  \textbf{Goodput in production is rarely published.} The research
  corpus gives strong qualitative and some quantitative anchors
  (Mooncake: a 525\% throughput increase (simulated) and 75\% more
  requests \mbox{{[}S4{]}}\hspace{0pt}\mbox{{[}1P{]}}\hspace{0pt}\mbox{{[}FACT{]}}, DFlash \textgreater6×
  \mbox{{[}S5{]}}\hspace{0pt}\mbox{{[}1P{]}}\hspace{0pt}\mbox{{[}FACT{]}}), but portable end-to-end goodput figures
  across real enterprise RAG workloads remain \mbox{{[}UNRESOLVED{]}}.
\item
  \textbf{Prefix-cache hit rates in mixed workloads} are
  workload-dependent; the actual reduction in prefill FLOPs from
  APC/RadixAttention for a given document-retrieval distribution is
  \mbox{{[}UNRESOLVED{]}}.
\item
  \textbf{Tail-latency drivers under batching} interact: batch size,
  arrival burstiness, and KV fragmentation each affect p99 differently,
  and their joint effect is \mbox{{[}UNRESOLVED{]}}.
\end{itemize}

\section{End-of-Chapter Mini-Case: The Post-Lunch Slowdown: Reading
Telemetry Up the
Chain}\label{end-of-chapter-mini-case-the-post-lunch-slowdown-reading-telemetry-up-the-chain}

An on-call architect is paged: ``the internal Q\&A tool got slow after
lunch.'' The dashboard shows rps at the \textasciitilde40 rps peak
(workload, up from the 10 rps baseline), p95 TTFT at 2.4 s against a 2 s
SLO (serving, breached), and KV cache occupancy at 85\% (resource,
memory pressure) with low prefix-hit ratio (resource, FLOP/reuse ---
prefill recomputation). Following the chain rather than guessing, the
architect reads: a concurrency spike (workload) with repeated full 9.2K
prefills (low prefix hit) drives prefill FLOP demand several times past
the host aggregate capacity (compute-bound). The deployment had passed
the single-request residency check --- \textasciitilde140 GB weights +
\textasciitilde24.9 GB KV ≈ 165 GB \textless{} 640 GB (Ch 7) --- but was
never sized for concurrency or for compute, let alone for the lunch
peak: 10 rps already demands 10 × 1.29 ≈ 12.9 PFLOP/s of prefill, ≈
\textbf{4.7 host-equivalents} of one 8×H100 host's \textasciitilde2.77
PFLOP/s sustained prefill capacity, and the 40 rps peak demands 40 ×
1.29 ≈ 51.6 PFLOP/s ≈ \textbf{18.6 host-equivalents}. On the single host
this mini-case assumes (deployed host count H = 1) that is a
\textasciitilde4.7× oversubscription at baseline and 18.6× at the peak
(case (i), linear-only FLOP count); the fleet oversubscription at peak
is 51.6 ÷ (H × 2.77) = 18.6/H, so an H-host fleet sized at 10 rps --- H
≈ 6, set by the KV-residency screen rather than by prefill (86 in-flight
÷ 17 slots = 5.06 → 6 hosts, Ch 4 §4.3) --- would be \textasciitilde3.1×
oversubscribed at the peak (51.6 ÷ (6 × 2.77) ≈ 3.1). The diagnosis is
therefore stated against a named denominator: the peak demands
\textasciitilde18.6× \emph{one host's} prefill capacity (18.6
host-equivalents); prefix caching is a partial mitigation
(\textasciitilde13\% of prefill FLOPs --- an upper bound, §6.3.4: the
cacheable fraction is smaller once the query tokens are excluded), not
the fix. The resolution is capacity/scheduling --- additional hosts,
chunked prefill, admission control/backpressure, or P/D disaggregation.
The architect re-checks the dashboard an hour later: p95 TTFT is back
under 2 s, and the mechanism check confirms the
\emph{capacity/scheduling} change rather than the cache: a
\textasciitilde13\% prefill reduction alone cannot close an
\textasciitilde18.6 host-equivalent gap: against \textasciitilde2.77
PFLOP/s of sustained capacity, the residual demand is \textbf{at least}
\textasciitilde44.9 PFLOP/s (51.6 × (1 − 0.13) --- this assumes the
\textasciitilde13\% upper bound is fully achieved, so the true saving is
≤ 13\% and the true residual is ≥ 44.9), i.e.~≥ \textasciitilde16.2
host-equivalents. That figure is bound-derived, not measured. Hosts were
raised from H = 1 to H = 21. That is the capacity floor, which is the
max of the named screens, not the prefill compute screen alone: case
(i)'s prefill screen needs ⌈18.6⌉ = 19 hosts, but the KV-residency /
Little's-Law screen needs ⌈344/17⌉ = 21 hosts at the peak and therefore
binds (Ch 8 §3; Ch 17). That slot screen runs on this mini-case's own
host geometry, not on an imported one: the residency check above already
fixes the host at \textasciitilde640 GB and the request slot at
\textasciitilde24.9 GB (9.5K tokens), so the same 436 GB KV budget and
17-slot whole-context ceiling apply (640 − 140 GB weights −
\textasciitilde64 GB runtime ≈ 436 GB; 436 ÷ 24.9 ≈ 17.5, floored to 17
--- Ch 4 §4.6; Ch 17). H = 21 therefore follows from this case's own 344
in-flight peak, and it agrees with Ch 17's canonical screen because both
use that one geometry; it is a floor screen, not a measurement. At 21
hosts the 344 in-flight peak requests fit the 21 × 17 = 357 resident
slots, and the peak prefill oversubscription falls from 18.6× to 51.6 ÷
(21 × 2.77) ≈ 0.9× (measured against the 21-host prefill capacity and
before any cache saving; the ≤ 13\% prefix-cache reduction can only
lower it, so 0.9× is an upper bound on the post-cache ratio at this host
count); admission control then held the residual queue inside the 2 s
p95 TTFT SLO, with the \textasciitilde13\% prefill reduction from prefix
caching contributing on top. That restores the p95; goodput restoration
is expected but not claimed here, because goodput is raw rate ×
compliant fraction and the p95 alone does not establish the compliant
fraction --- they measured the right thing at the right layer.
