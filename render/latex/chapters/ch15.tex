\section*{The Architect's Question}\label{the-architects-question}

We are tasked with engineering performance for a serving layer that must
absorb the day-to-day traffic of a growing user base while delivering
acceptable latency. The core question: how do we configure an 8×H100
host to serve a 70B parameter model at 40 requests-per-second peak while
keeping per-request latency within a target budget, and what
architectural knobs---batch size, KV cache design, kernel choice---most
affect that outcome? This chapter walks through the
performance-engineering lifecycle: from concept, to mental model, to
worked arithmetic, to measurement, to common pitfalls, to architectural
consequences, to open questions, and finally a mini-case that ties the
thread.

\ntsection{Concept}\label{concept}


Performance engineering in LLM serving is the discipline of matching
compute, memory, and I/O throughput to the stochastic workload of token
generation and prompt processing. Unlike traditional web serving, where
request‑cycle overhead dominates the tail, the dominant cost in LLM
inference is the arithmetic intensity of transformer matrix
multiplications and the memory bandwidth consumed by KV cache reads and
writes on every token step. The serving system must therefore optimize
three inter‑dependent quantities: token throughput (tokens/s), per-token
latency, and GPU memory utilization. These are governed by the model
FLOP count, the chosen kernel (e.g.~FlashAttention
vs.~scaled‑dot‑product), and the batching strategy (static vs.~dynamic,
continuous vs.~chunked). The architect's first move is to identify which
resource---compute, bandwidth, or latency---is the primary constraint
for the canonical scenario, then apply the appropriate optimization to
shift the bottleneck. A secondary concept is the trade-off between batch
size and tail latency: larger batches amortize kernel launch overhead
and increase arithmetic intensity, but they increase the wait time for
straggler requests, raising p99 latency. The designer must therefore
balance arithmetic gain against tail‑latency penalty, a tension that
shapes every later architectural decision.

\ntsection{Mental Model}\label{mental-model}


We model the serving request lifecycle as a pipeline of computational
phases with a cross‑cutting state‑management plane. The compute phases
run in order: (1) request preprocessing / tokenization, (2) prefill, (3)
iterative model decode, (4) token sampling / selection, (5)
detokenization / streaming. \textbf{KV management is not a temporal
stage after generation} --- allocation, growth, paging, reuse, eviction,
and (in a disaggregated deployment) transfer occur throughout the whole
request lifetime, so we draw it as a state‑management plane that spans
prefill and decode rather than a step that follows them. Each compute
phase has a resource ceiling: compute‑bound phases are limited by
TFLOPS, memory‑bound phases by GB/s of GPU HBM bandwidth. The
architecture designer must identify which phase is bottlenecked for the
canonical scenario and then apply the appropriate optimization---kernel
fusion, cache reuse, or batching---to shift the bottleneck. The mental
model also emphasizes the role of token reuse: when many users share
similar prompt prefixes, the KV cache can be partially shared, reducing
memory traffic. This reuse effect is difficult to quantify without
workload profiling, but it is a first‑order consideration in
multi‑tenant serving. The model also captures the interaction between
sequence length and memory cost: attention quadraticities (O(L²) FLOPs
and O(L²) memory per head once the \(QK^{T}\)/softmax score matrix is
materialized) mean that long contexts (9,000+ tokens) disproportionately
strain both compute and HBM bandwidth, making kernel choice
(FlashAttention vs.~SDPA) one of the first \emph{kernel‑level}
optimizations to validate for long‑context prefill --- not a
demonstrated global ranking, since prefix reuse, KV precision, batching
policy, P/D scheduling, weight precision, admission control, and simply
provisioning more prefill capacity can each dominate depending on the
measured workload.

\ntsection{Worked Example}\label{worked-example}


Canonical scenario: \textasciitilde2,000 registered users,
\textasciitilde5\% concurrent (100 users), \textasciitilde10 rps average
/ \textasciitilde40 rps peak, prompt \textasciitilde9,200 input tokens +
\textasciitilde300 output, the canonical 80-layer, hidden-8192, full-MHA
70B reference model (a 70B-class dense FP16 model), 8×H100 host with
640\,GB GPU memory.

\emph{Derived quantity 1 -- concurrent users:} 2,000 ×0.05 = 100 users.

\emph{Derived quantity 2 -- peak token throughput demand:} At 40 rps the
workload mixes \textbf{prefill} (input) and \textbf{decode} (output)
tokens, and they hit the hardware differently. Prefill demand = 40 rps ×
9,200 = 368,000 input tokens/s; decode demand = 40 rps × 300 = 12,000
output tokens/s. These two regimes must not be collapsed into one
``380,000 tokens/s'' when reasoning about compute, because long-prompt
prefill commonly occupies a higher-arithmetic-intensity regime and
low-batch decode commonly occupies a lower-arithmetic-intensity regime;
whether either phase is actually compute- or bandwidth-bound is a
property of the model × workload × kernel × hardware operating point
(\hyperref[chap:8]{Chapter 8}).

\textbf{A hard terminology distinction the rest of this book relies on.}
Do not conflate two separate statements:

\begin{itemize}
\tightlist
\item
  \textbf{Kernel regime} --- the arithmetic intensity of the
  \emph{kernel} relative to the roofline ridge (is this one kernel
  compute-bound or bandwidth-bound?).
\item
  \textbf{Workload capacity deficit} --- the aggregate offered demand
  relative to the achievable service capacity (does the
  \emph{deployment} have enough compute/bandwidth/concurrency to absorb
  this arrival rate?).
\end{itemize}

A workload can exceed a deployment's capacity even when the underlying
kernel is not compute-bound; conversely, a compute-bound kernel does not
imply the deployed fleet lacks compute. In the canonical scenario at
peak, prefill exerts a large aggregate compute \emph{demand} (a
capacity-deficit signal), while the prefill \emph{kernel's} high
arithmetic intensity is what makes it land on the compute plateau of the
roofline --- two different facts that happen to co-occur. Keep them
separate.

\emph{Compute demand versus peak --- and why this is not an MFU:} A 70B
FP16 transformer needs ≈2 ×70×10⁹ FLOPs per generated token. The
instantaneous prefill compute demand is 368,000 ×2 × 70×10⁹ ≈ 5.15 ×10¹⁶
FLOPs/s, against a theoretical FP16-dense peak of 8 ×989 TFLOPS = 7.91
×10¹⁵ FLOPs/s for the 8×H100 host (989 TFLOPS per GPU, \hyperref[chap:8]{Chapter 8}
canonical). Taken naively this ratio is \textasciitilde6.5× --- a demand
that \emph{exceeds} a single host's peak. That is a legitimate and
important architectural signal: a single 8×H100 host cannot prefill the
peak arrival rate on the naive dense-FLOP model, so prefill either needs
to be spread across burst headroom, handled by prompt/prefix caching,
disaggregated (P/D separation), or absorbed by queueing headroom at
off-peak. What it must \textbf{not} be called is ``MFU = 6.5'': MFU
(Model FLOPs Utilization) is by definition achieved realities divided by
peak --- a utilization ratio that \textbf{cannot exceed 1.0}. Presenting
a ratio above 1 for a utilization metric is a unit/modeling error. The
honest formulation separates the two quantities. The first is a
\emph{congestion check}: is the arrival-rate FLOP demand above or below
peak? Here it is \textasciitilde6.5× above for prefill, so the host is
prefill-starved at peak and must lean on caching/batching/queueing. The
second is an \emph{achieved MFU}: measured device FLOPs ÷ peak, which we
only report from a real benchmark. For illustration we suppose it lands
in the 30--40\,\% range for FlashAttention-based inference. The decode
figure at 12,000 tokens/s is ≈ 1.68 ×10¹⁵ ÷ 7.91 ×10¹⁵ ≈ 0.21,
i.e.~\textasciitilde21\,\% --- again a groundable number, not a
ceiling-defying one; the actual achieved value must come from the target
serving benchmark. The architectural conclusion, that there is no single
bottleneck for the whole request, stands --- and it must be argued phase
by phase. At the canonical peak, prefill shows a \emph{workload capacity
deficit} --- aggregate compute demand above the host's peak (it needs
more FLOPs/s than the host can supply, and leans on caching/queueing).
Decode is primarily memory-bandwidth constrained, and maximum
concurrency is constrained by KV residency. Each phase is established
from arithmetic intensity and the roofline (\hyperref[chap:8]{Chapter 8}), never from an
impossible ``MFU \textgreater{} 1.'' None of them is the same statement
as ``the prefill kernel is compute-bound.'' The \textasciitilde6.5×
figure is a \textbf{lower-bound impossibility check} (the host cannot
meet peak on the naive dense model), not a fleet-sizing estimate: the
real fleet count comes from the achieved prefill tokens/s under the
actual latency SLO and representative traffic mix (Ch 17/20), and it is
sensitive to cache-hit rate, input-length distribution, batch schedule,
and sustainable efficiency --- the 6.5× only says ``more than one host
is required,'' not ``how many.''

\emph{KV cache memory footprint:} The KV cache grows linearly with
cached context and layers; it must never be computed per-layer and then
treated as the whole-model total. For the canonical full-MHA reference
geometry (80 layers, hidden dimension 8,192 --- the 70B-class teaching
model, not a universal 70B property), the per-token footprint across ALL
layers is 2 × layers × hidden × bytes = 2 ×80 ×8,192 ×2 = 2,621,440 B ≈
2.62 MB/token (2.5 MiB; canonical value from \hyperref[chap:7]{Chapter 7}) --- not the 32
KiB (32,768 B) that a single-layer calculation would suggest. For a
9,500-token context, one user's KV cache is therefore ≈9,500 ×2.62 MB ≈
24.9 GB, not \textasciitilde311 MB (9,500 × 32,768 B). For the canonical
workload's \textasciitilde86 average in-flight requests at 10 rps
(\(L_{\mathrm{exec}}\) = λ × \(W_{\mathrm{exec}}\) ≈ 10 × 8.6; see Ch 4
--- note \textasciitilde86 is the \emph{request occupancy}, distinct
from the \textasciitilde100 \emph{active-user} population), the total KV
cache would be ≈86 × 24.9 GB ≈ 2,140 GB --- which \textbf{does not} fit
the 640 GB GPU pool; using the canonical practical KV budget (640 GB −
140 GB weights − \textasciitilde64 GB runtime/workspace ≈ 436 GB), only
≈17.5 concurrent \emph{requests} (9,500-token KV each) fit on-host for
KV (436 GB ÷ 24.9037 GB; conservative integer floor 17 (aggregate bound;
per-rank and fragmentation must be checked separately)), before also
reserving weight residency. This is a decisive, order-of-magnitude
correction to the intuitive picture: long-context KV is a first-order
memory constraint, and the architect sizes concurrency by KV capacity,
not by the small per-layer number. Doubling context to 19,000 tokens
pushes per-user KV to \textasciitilde49.8 GB (19,000 × 2.62 MB) and
halves on-host concurrency to \textasciitilde8.7 (436 GB ÷ 49.8 GB;
conservative integer floor 8). The canonical unit-check rule
(quantity/unit/formula/substitution/result/sanity) catches this class of
error: if 9,500 tokens × 2,621,440 B/token ≈ 24.9 GB does not reconcile
with the intended \textasciitilde311 MB single-layer counterexample, the
unit layer-count has been dropped.

\emph{Attention FLOP comparison:} Scaled‑dot‑product attention (SDPA)
for 9,200‑token prompts. Note the 2P/token figure above approximates the
\emph{parameterized dense‑matmul} work per token (2 × parameters); it
does \textbf{not} capture all sequence‑length‑dependent attention work,
which is accounted for separately here. Attention is two matmuls per
token per head --- Q·\(K^{T}\) then ·V --- each a multiply‑accumulate of
L²·d, so in FLOPs (2 per MAC) the per‑layer cost is ≈ 4 × L² × d\_model,
where L=9,200 and d\_model=8,192. That is 4 × 9,200² × 8,192 ≈ 2.8 ×
10¹² FLOPs per layer (the full 64 heads; the per‑head figure 4 × 9,200²
× 128 ≈ 4.3 × 10¹⁰ must be multiplied by the number of heads, not quoted
alone). Across 80 layers that is ≈ 2.2 × 10¹⁴ FLOPs --- the quadratic
attention term that grows dominant at long context, matching \hyperref[chap:8]{Chapter 8}'s
4·n\_layers·L²·d formula: the attention term is ≈17\% of the
parameter-matmul FLOPs (≈15\% of total forward FLOPs) at 9.2K (\hyperref[fig:22.1]{Fig 22.1}).

does less arithmetic. It computes the exact same Q·\(K^{T}\), softmax,

naive kernel writes the L×L attention matrix to HBM and reads it back,
so the materialized intermediate itself is O(L²) in memory;
FlashAttention avoids materializing that full L×L matrix in HBM and
instead tiles the computation so each tile stays in on-chip
registers/shared memory with the softmax done online --- substantially
reducing HBM reads/writes through tiled on-chip computation (the precise
I/O complexity is more nuanced than a clean quadratic-to-linear swap,
but the materialized-intermediate traffic is what drops). Because the
arithmetic intensity --- FLOP/byte --- rises (same FLOPs, far fewer
bytes moved), the kernel moves \emph{up} the hardware ladder of \hyperref[fig:8.1]{Fig 8.1}
toward the compute-bound region, even though the model and the math are
unchanged. That is the whole reason the speed-up is workload-dependent:
it is largest for long contexts where the O(L²) intermediate dominates,
and negligible for short ones where HBM traffic is already small. It is
also why the improvement should be \emph{measured} (Ch. 14) rather than
quoted from a published ``2--3×'' figure that was never portable.

\ntsection{Measurement}\label{measurement}


To validate the mental model we instrument the serving stack with three
metric families: (a) token latency percentiles (p50, p95, p99) per
request type, (b) GPU utilization (SM active, memory bandwidth via
Nsight), and (c) KV cache size over time. A minimal benchmark runs 40
rps with warm‑up, records the p95 token latency, and measures the GPU
memory fraction consumed by KV cache. Repeating with different batch
sizes (1, 4, 16, 32) reveals the throughput‑latency knee. The
\emph{illustrative} numbers below are scenario values to be measured on
the target stack, not vendor or published figures: beyond batch‑4 the
p95 latency typically rises (implying a knee near batch 4) because
kernel launch overhead is amortized but inter‑request token interleaving
increases cache thrashing. \textbf{On the FlashAttention ``traffic
reduction'' claim, be precise about the units:} one often sees a
FlashAttention‑class kernel reported at a \emph{different achieved HBM
bandwidth} than a naive SDPA kernel (illustratively
\textasciitilde150\,GB/s vs \textasciitilde400 GB/s for 9,500‑token
contexts). That is a \emph{rate}, not a byte count. A bandwidth figure
alone does not establish that fewer \emph{bytes/request} were
transferred --- it only shows the kernel's achieved memory throughput.
To claim a traffic reduction, compare the \textbf{bytes transferred per
request} (or read/write transaction counters) under a \emph{matched}
workload; the FlashAttention advantage shows up there as fewer
materialized/intermediate bytes, not as a low raw bandwidth. \textbf{And
separate the two cache concepts}: ``cold‑start KV warm‑up'' (populating
the KV-cache blocks for a new context) is different from ``model‑weight
loading'' (streaming the 140\,GB weights into HBM) and from CUDA/JIT
kernel warm‑up. A 70B cold‑start that reuses cached weights is far
faster than one that must load them from scratch --- but these are
distinct effects, not one number. Set these illustrative figures from
the target host's profiler before quoting them as fact.

\textbf{Two cautions.} First, do not read the table as ``technique X
fixes symptom Y'': the same symptom can come from two bottlenecks (high
TPOT with a bandwidth-saturated GPU is different from high TPOT with a
capacity-capped GPU), so the \emph{evidence} column matters as much as
the symptom. Second, the last two rows (P/D disaggregation, interconnect
tuning) are the expensive, structural levers --- they are worth testing
only after the cheaper in-kernel and in-scheduler mechanisms have been
measured and shown insufficient, because they change capacity,
orchestration, and cost, not just a kernel constant.

Weight quantization is a candidate intervention when weight capacity or
weight traffic is limiting. After the change, the bottleneck may move to
KV access, attention, collective communication, conversion kernels or
queueing. The next measurement therefore repeats the workload and SLO
test rather than inferring a gain from checkpoint size. More KV headroom
can permit a larger batch, but a larger batch can also increase waiting
time or decode-step duration. The useful operating point is the one that
preserves task quality and request-level SLOs, not the one that fills
the most memory. \hyperref[chap:7]{Chapter 7}'s storage sensitivity and \hyperref[fig:7.4]{Fig 7.4} describe
an input to this decision, not its performance result.

\section{Two Mechanisms, Read as
Mechanisms}\label{two-mechanisms-read-as-mechanisms}

Two entries in the map deserve their mechanism spelled out, because they
are frequently cited by reported speed-up numbers rather than by how
they work.

\textbf{Speculative decoding.} The idea is to turn one slow serial step
into a \emph{draft-then-verify} pair. A small, cheap \textbf{draft
model} proposes a candidate sequence of tokens; the larger
\textbf{target model} then \emph{verifies} all of them in a single
batched forward pass, accepting the ones that match its own
distribution. The loop is: draft → propose candidates → target verifies
→ accept a prefix → continue from the last accepted token. Why this can
be faster: the expensive part of decode is not the arithmetic per token
but the \emph{serialization} --- each target-model step streams the
weights from HBM. If the draft can propose \(k\) tokens that the target
accepts in one verification pass, the target's expensive weight-stream
is spent once on \(k\) tokens instead of \(k\) times on one --- a
genuine reduction in HBM round-trips (the same resource the
FlashAttention discussion is about, but at the whole-model scale). Why
it is \emph{not} free: the draft costs extra compute, the verification
pass itself has cost, and the \textbf{acceptance rate} (how many of the
proposed tokens the target actually accepts) decides the win --- a low
acceptance rate means the draft and verification are spent for almost
nothing. It is therefore workload/model/hardware dependent: a draft that
closely matches the target (or a workload that is highly predictable)
accepts more. \textbf{No published speed-up is portable}: a ``6×'' from
one model/paper is a statement about that evaluation, not a guarantee
for a different model or serving stack --- measure it on the target
workload or treat it as a hypothesis.

One subtlety about ``matching its own distribution'': the target does
\emph{not} simply accept the draft tokens that happen to agree. Under
stochastic sampling, accepting a proposed token outright (rather than by
the exact-speculative-sampling correction that re-weighs each accepted
and rejected token by the target's posterior) can bias the output
distribution away from the target model's true distribution. The
distribution-preserving result holds only when each proposed token is
accepted or rejected by the exact acceptance/sampling procedure (the
modified-rejection-sampling step of Leviathan et al., ``Fast Inference
from Transformers via Speculative Decoding,'' arXiv:2211.17192; see the
Sources chapter), which re-normalizes the continuation at each step. For
greedy/argmax decoding the agreement test is exact; for
temperature/prompt-driven sampling it is not, and the acceptance
criterion must be the correction procedure, not mere token equality.

\textbf{Chunked prefill.} A very long prompt produces a large prefill
operation that can monopolize the compute for hundreds of milliseconds,
stalling concurrent latency-sensitive decode work. \textbf{Chunked
prefill} splits that prefill into smaller pieces and interleaves them
with decode steps in the scheduler, so the GPU keeps serving decode
between prefill chunks instead of blocking on one burst. The causal
chain: long prompt → large prefill → scheduler/resource monopolization →
decode interference → TTFT \emph{and} TPOT both degrade → chunked
prefill as a scheduling mechanism to bound the per-phase burst. The
trade-off is \emph{not} ``smaller is better'': a smaller chunk reduces
the decode stall but adds scheduler overhead (more per-chunk
bookkeeping, potentially lower prefill throughput from less parallelism
within a chunk), so chunk size is an empirically-chosen middle ---
measure the goodput/latency knee rather than assume.

\ntsection{Common Mistakes}\label{common-mistakes}


\emph{Over‑provisioning batch size to chase throughput:} Increasing
batch size improves TFLOPS utilization but degrades p99 latency because
tail requests wait for larger chunks to fill. The designer must balance
batch‑size‑driven arithmetic gain against tail‑latency penalty. A
practical illustrative rule of thumb: choose the smallest batch size
that keeps MFU above \textasciitilde25\,\% while keeping p95 latency
under the SLO target (the 25\,\% threshold and the knee are scenario
values --- measure them on the target workload). \emph{Ignoring KV cache
growth:} A 70B model with 9,500‑token contexts consumes ≈24.9 GB of KV
per user (≈2.62 MB/token × 9,500, max end-of-generation). Without cache
eviction, compression, or a concurrency cap, even \textasciitilde17.5
concurrent \emph{requests} would exhaust the host's canonical practical
KV budget (\textasciitilde436 GB after weights + runtime), so 100
concurrent full-context users require either multiple hosts, much
shorter contexts, or KV compression (FP8/8-bit). \textbf{But be precise
about what ``evicting'' a context means, because it is not one action.}
Three distinct mechanisms exist. (a) \emph{Evicting an idle/inactive
prefix-cache entry} --- a cached prefix not currently in service --- is
safe, because no active request depends on it and it can be recomputed
on reuse. (b) \emph{Offloading or recomputing the KV of an active
request} whose context is still being generated changes nothing about
semantics, but it costs a recompute or a transfer when the request
resumes. (c) \emph{Deliberate sliding-window or context-truncation
strategies} drop older tokens of an \emph{active} request's context.
This \textbf{changes the model's effective context}: it alters what the
attention can attend to, and it is a semantics change, not merely a
memory optimization. LRU of inactive cached prefixes is different from
truncating active KV. Do not conflate them. \textbf{KV quantization} is
a separate, orthogonal lever that cuts the per-token footprint without
changing semantics (FP8 ≈2.62 → \textasciitilde1.31 MB/token --- exactly
50\% of BF16 by raw tensor byte-halving, the same FP8 constant defined
in Ch 7; vLLM's cited 54\% \mbox{{[}S6{]}} is a decode inter-token-latency
slope, a latency metric, not a memory ratio, and any allocator
block/metadata overhead is not vendor-measured). \emph{Using
scaled‑dot‑product attention without FlashAttention:} For long contexts
(9,200+ tokens) the quadratic memory cost of SDPA (O(L²)) dominates the
FLOP cost. FlashAttention fuses read‑write‑compute and reduces HBM
traffic by \textasciitilde3--5× (\mbox{{[}ILLUSTRATIVE{]}} --- kernel- and
length-dependent; measure bytes/request on the target stack), raising
effective arithmetic intensity. This is one of the highest-impact
\emph{kernel-level} choices (it sits among prefix caching, KV-precision,
batching, and P/D disaggregation as a major lever, not the single
deciding one), and it pays off specifically when memory-bound; for
moderate lengths (2,000--4,000 tokens) the HBM bandwidth reduction
typically translates to a \textasciitilde1.3--1.8× throughput gain on
H100 (illustrative --- bench the specific kernel on the target
hardware). \emph{Neglecting kernel launch overhead:} In dynamic‑batching
setups, each new token generation can trigger a kernel launch. Without
continuous batching or token‑level fusion, the kernel-launch overhead
(illustratively \textasciitilde10--20\,\% of GPU time on H100-class
parts at this traffic) can artificially depress measured MFU.

\ntsection{Architecture Consequence}\label{architecture-consequence}


The measurement and mistake analysis drive three architecture decisions
for the canonical deployment: (1) FlashAttention‑2 as the default
attention kernel, fused with RoPE and QKV projection to minimize HBM
transactions; (2) continuous batching, with the maximum chunk size
chosen empirically from the measured goodput/latency knee (a chunk size
of 8 tokens is an \mbox{{[}ILLUSTRATIVE{]}} configuration, not the
recommendation --- the knee must be measured on the target stack); (3)
KV cache management via FP8 KV quantization (≈2.62 → \textasciitilde1.31
MB/token --- exactly 50\% of BF16 by raw tensor byte-halving, cutting a
9,500‑token per‑user KV to \textasciitilde12.45 GB; vLLM's 54\% \mbox{{[}S6{]}}
is a decode inter-token-latency slope, a latency metric, not a memory
ratio, and any block/metadata overhead is not vendor-measured) plus
length‑based eviction, so that under the same \textasciitilde436 GB
practical KV budget on‑host concurrency rises from \textasciitilde17.5
to \textasciitilde35.0 full‑context users (436 GB ÷ 12.45 GB). These
choices together are expected to raise achieved token throughput from
\textasciitilde8,000 tokens/s (raw, no flash, batch‑1) toward an
illustrative \textasciitilde35,000--70,000 tokens/s \mbox{{[}ILLUSTRATIVE
achievable range{]}} (with flash, continuous batch) --- the exact figure
must come from the target benchmark --- while keeping the host's 640\,GB
for weights plus KV. A fourth decision, borne out of the mini‑case (Ch11
§11.8), is to design the request‑routing layer for KV cache affinity:
when a user re‑submits a request, routing to the same GPU avoids cache
warm‑up penalties and keeps p99 latency under the target SLO.

\ntsection{What We Still Don't Know}\label{what-we-still-dont-know}


\emph{How does token‑level sparsity in user prompts affect the actual
FLOP/token cost, and can we exploit it without accuracy loss?} Sparse
prompt patterns (e.g.~few‑shot prefixes, cached query prefixes) could
reduce the effective FLOP count, but the savings depend on the sparsity
pattern and the attention implementation. \emph{What is the optimal
continuous‑batch chunk size as a function of request arrival
distribution (Poisson vs.~bursty) and tail‑latency targets?} Analytical
models assume Poisson arrivals, but real user traffic exhibits bursts
(e.g.~social‑media events) that may require larger chunks or alternative
back‑pressure mechanisms. \emph{Can in‑flight KV cache compression
(e.g.~speculative decoding--guided pruning) reduce memory pressure
without increasing p99 latency?} Pruning less‑important key/value pairs
based on attention weight magnitudes is promising, but the
accuracy‑latency trade‑off needs empirical validation across model
families. \emph{How does multi‑tenant isolation---guarding one user's
cache from another's---translate to multi‑GPU scaling when the model
exceeds a single GPU's 80\,GB?} Model parallelism (pipeline or tensor)
adds communication overhead; the performance cost of moving KV cache
between GPUs during tenant rotation is an open question.

\section{End-of-Chapter Mini-Case: The Second Host: a Kernel/Batching
Gain, Not a Capacity
Win}\label{end-of-chapter-mini-case-the-second-host-a-kernelbatching-gain-not-a-capacity-win}

A new deployment adds 500 registered users (traffic rises to
\textasciitilde12.5/50 rps at the same 5\,\% concurrency profile). The
team provisions a second 8×H100 host and (in this worked example) runs
the benchmark with continuous batching and FlashAttention‑2. The p95
queueing/scheduling delay ahead of prefill --- not TTFT, which at this
profile is dominated by the canonical \textasciitilde1.08 s prefill
(Chapters 4/8; \hyperref[chap:14]{Chapter 14} measures p95 TTFT at 1.9 s for this stack) ---
drops from 320\,ms (single host, batch‑1) to 140\,ms (dual host,
continuous batch), and token throughput rises from 8,000 to 70,000
tokens/s. The MFU stabilizes at 38\,\%. These are \mbox{{[}ILLUSTRATIVE
SCENARIO RESULT{]}} values --- an illustrative benchmark outcome, not a
home-lab measurement; the exact figures must come from a deployment
benchmark on the target hardware/stack (\hyperref[chap:14]{Chapter 14}). The remaining
question is whether the cross‑host request routing layer can maintain
affinity KV cache residency, avoiding cache warm‑up penalties on
re‑requests. The ∼20\,\% affinity throughput gain and the ∼2.1 s
cold-start warm-up cost are themselves \mbox{{[}ILLUSTRATIVE SCENARIO
RESULT{]}} values, not measured results.

\emph{Do not read the 8.75× throughput jump as a capacity-side win.} It
is dominated by the \textbf{kernel/batching} change (batch‑1 no‑flash →
continuous batching with FlashAttention‑2), which is worth most of the
multiplicative gain, \textbf{plus \textasciitilde2× from adding the
second host} --- the two are not separable from this single outcome
number. This is a \emph{per‑host kernel/batching} improvement story, not
a claim that ``more GPUs = 8.75×.'' Were we adding a second host with no
kernel/batching change, the expected throughput gain would be roughly
the host-pool ratio (≈2×), and the fleet-sizing consequence is computed
separately in Ch 16--17 from the service-time model, not from this
mini-case's aggregate number.
