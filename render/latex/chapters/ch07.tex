\section*{The Architect's Question}\label{the-architects-question}

After this chapter we should be able to answer the architect's
fundamental constraint question: \emph{does the model and its context
fit in the memory floor before we ask whether it can compute or
communicate?} We will build the arithmetic for the KV cache from first
principles, reconcile it with the canonical \textasciitilde1.31 MB/token
figure from \hyperref[chap:1]{Chapter 1}, and contrast inference residency (weights + KV)
with fine-tuning residency (weights + gradients + optimizer states). The
goal is to make ``does it fit?'' a concrete, quantified check --- not a
back-of-the-envelope guess. Throughout, the arithmetic anchors to the
canonical enterprise-Q\&A RAG scenario (Ch 4, \hyperref[tab:4.2]{Table 4-2}):
\textasciitilde10 rps average / \textasciitilde40 rps peak traffic
served by a 70B \textbf{FP16} model on an 8×H100 host. KV cache
per-token figures are given at the referenced precision throughout:
\textasciitilde1.31 MB/token at \textbf{8-bit} (this is \hyperref[chap:1]{Chapter 1}'s
reference figure), \textasciitilde2.62 MB/token (exactly 2.5 MiB/token)
at \textbf{FP16} --- and the canonical scenario's KV constant is the
\textbf{FP16} 2.62 MB/token figure, not the 8-bit \textasciitilde1.31
MB/token number. \textbf{Color is not semantic anywhere in this
chapter's figures (FIGS 7.1--7.8):} the same concept (persistent
KV/state storage) is rendered in different hues across them, so read
each figure's own legend or note rather than carrying a color meaning
from one figure to the next. Every block is identified by a text label,
never by hue alone, so the chapter also reads correctly in grayscale.

\ntsection{Concept}\label{concept}


Memory is the first constraint because every LLM workload begins with a
residency check: can the model and its active data structures be placed
on the target hardware? The KV cache is the primary expression of this
constraint during inference: it grows linearly with context length, and
its size depends on the model's layer count, KV-head count, head
dimension (equivalently the KV width per layer) and the precision chosen
for key and value storage. Unlike FLOPs, which scale with operations per
token, the KV cache occupies memory continuously for the lifetime of a
request --- it is always resident, always consuming HBM bandwidth for
every re-read. The architect must therefore size two distinct memory
loads: the static weight footprint and the dynamic KV footprint that
varies with prompt length. Quantization (FP8, FP4, 2-bit asymmetric)
reduces both, but the KV cache is the one component whose reduction must
be quoted per precision, not as a uniform factor: FP8 KV realizes a 2×
reduction vs FP16 (raw byte-halving), while 4-bit KV's raw payload bound
is 4× (2.62 → 0.66 MB/token at this chapter's geometry); per-block
scale/offset metadata and per-token variation reduce the realized
reduction below 4×, so no specific multiplier may be assumed without the
actual layout. Weight-only quantization carries the same
raw-bound-versus-realized distinction --- its 2×--4× is a raw bit-width
bound, not a realized saving (FP8 KV realizes exactly 2× before block
metadata; MXFP4 weights realize \textasciitilde3.76× at 0.53125 B/value,
§7.3). The residency floor is weights + KV for inference; for
fine-tuning it is weights + gradients + optimizer states (+
activations/workspace), and the architect's first question is whether
this sum fits on the target GPUs. This is why ``does it fit?'' is the
architect's primary gate: before we ask whether the model can compute or
communicate, we must first establish that the working set --- weights
plus the context-dependent KV state --- resides on-GPU. If it does not,
every subsequent decision (offload, recompute, page) is a necessary
trade-off --- acceptable only when it keeps the workload within its SLO.

Unit basis (locked): the H100's quoted 80 GB is treated as decimal
80×10\^{}9 B throughout, so the canonical 8×H100 pool reads 640 GB. The
vendor-binary reading is 81,559 MiB ≈ 85.5×10\^{}9 B per part (the
first-party H100 80 GB specification's binary-quoted capacity), which
would give 2×H100 = 171.0 GB and an \textasciitilde684 GB host pool. One
conversion rule covers every capacity-dependent figure below: on that
basis the KV budget becomes \textasciitilde480 GB (684 − 140 − 64) and
the per-host concurrency ceiling \textasciitilde19 (480 ÷ 24.9037 =
19.3; floor 19), against 436 GB and \textasciitilde17.5 (floor 17) on
the decimal basis. Re-run this fit test on that basis before
procurement. On the vendor-binary basis the aggregate test flips to
passing (164.1 \textless{} 171.0 GB), but the per-rank test still fails
(70 + 12.05 + \textasciitilde8 GB reserve = 90.05 GB \textgreater{} 85.5
GB), so the ≥3-GPU conclusion is unchanged. The 2×H100 fit verdict, the
640 GB envelope, the 436 GB KV budget and the \textasciitilde17.5
concurrency all use this decimal basis.

The residency floor has two distinct regimes. For inference, the floor
is weights + KV: the model's static parameters plus the
context-dependent key/value tensors that grow with every token added to
the prompt. In fine-tuning, the floor rises further to weights +
gradients + optimizer states, because every parameter update requires
its own momentum and velocity vectors (Adam) or per-parameter scaling
(LAMB/RMSProp). The contrast between these two floors --- inference
\textasciitilde164.1 GB for a 70B model at FP16 with 9.2K input (140 +
24.1; the 9.5K-max is 164.9 ≈ 165 GB) \mbox{{[}canonical
scenario{]}}\hspace{0pt}\mbox{{[}DERIVED{]}}, fine-tuning exceeding 1 TB \mbox{{[}canonical
scenario{]}}\hspace{0pt}\mbox{{[}DERIVED{]}} --- is the architect's central memory-takeaway.

We keep two terms rigidly distinct in this chapter, and the distinction
is the antidote to ``does it fit?'' mistakes:

\begin{itemize}
\tightlist
\item
  \textbf{Residency floor} = weights + KV. This is the minimum memory
  the model's parameters and active KV tensors must \emph{occupy} for a
  single request. It is what the numbers in this chapter quote
  (\textasciitilde140 GB weights + \textasciitilde24.9 GB KV ≈ 165 GB at
  9.5K max).
\item
  \textbf{Practical host requirement} = weights + KV + runtime/workspace
  + safety margin. Deploying a model on a GPU requires additional VRAM
  for CUDA kernels, activation buffers, NCCL (NVIDIA Collective
  Communications Library) communication, a warmup/KV-allocation safety
  pool, and (on a multi-GPU host) tensor-/pipeline-parallel
  communication and staging buffers (plus any genuinely replicated
  components, e.g.~embeddings or LM head where the engine replicates
  them). On the canonical 8×H100 host this runtime/workspace term is
  \textasciitilde64 GB, turning the \textasciitilde165 GB residency
  floor into a larger \emph{deployment} footprint.
  \mbox{{[}ILLUSTRATIVE{]}}\hspace{0pt}\mbox{{[}ASSUMPTION{]}} The \textasciitilde64 GB is a
  planning reserve, not a measured constant; a representative split is
  \textasciitilde8 GB CUDA context/driver + \textasciitilde16 GB
  activation buffers (batch + intermediate tensors) + \textasciitilde8
  GB NCCL communication buffers (tensor-parallel all-reduce staging) +
  \textasciitilde32 GB warmup/KV-allocation safety pool. The exact value
  must come from a deployment benchmark on the target stack (\hyperref[chap:14]{Chapter 14}); the 436 GB KV budget (640 − 140 − 64) shifts by the same amount
  if the measured reserve differs.
\end{itemize}

When the text says a workload ``fits'' or ``does not fit,'' we are
always talking about the residency floor first; the practical host
requirement is a superset that must be checked before committing
hardware. Conflating the two is exactly what produces a ``165 GB fits in
160 GB'' error.

\subsection{Count state by lifetime, not by the model
label}\label{count-state-by-lifetime-not-by-the-model-label}

\begin{quote}
\textbf{Caveat --- inventorying state for non-autoregressive
generators.} The residency floor is a property of the set of tensors
alive at peak, not of the model label, and the KV formula prices K/V
tensors, not all persistent state. For a non-autoregressive generator,
inventory state by lifetime before applying the weights+KV arithmetic
--- resident weights, reusable context state, mutable canvas state, peak
activations and logits, kernel workspace and runtime allocations,
disjoint at the instant measured (Ch 3 develops the non-autoregressive
generation thread this caveat scopes). Capacity and cache validity are
separate checks, and the deployed sampler's live tensor shapes and
lifetimes --- not weight precision alone --- decide the practical
requirement. None of this changes the canonical autoregressive budget
above; it changes what must be inventoried before that budget's
arithmetic is reused for a different generation mechanism. \mbox{{[}DERIVED{]}}
\end{quote}

\ntsection{Mental Model}\label{mental-model}


The KV cache is \textbf{per-request state that persists across
autoregressive decode steps for the lifetime of the active sequence} ---
unlike weights, which are loaded once and reused across requests, the KV
cache is allocated per request and grows with every token added to the
context. A 9.2K prompt on a 70B model at FP16 carries \textasciitilde24
GB of KV state that must remain on-GPU for the entire prefill + decode
sequence. If it does not fit, the serving stack must page, offload, or
recompute --- each option degrades latency or throughput. The durable
mental model is: \emph{every token we add to the context exacts a fixed
memory toll, and that toll is paid in HBM every time the GPU re-reads
the cache during decode.} This is why context length is the single most
powerful lever on inference memory pressure, and why ``does it fit?'' is
the architect's primary gate.

\subsection{Persistent state is
architecture-specific}\label{persistent-state-is-architecture-specific}

The KV formula in this chapter describes keys and values retained across
autoregressive steps. A whole-clip denoiser has a different lifetime
model. Its latent video changes after each scheduler update, so video
keys and values cannot simply be retained as immutable prefix entries
for every later step. Static prompt embeddings can remain reusable, but
that is not the growing autoregressive cache. \mbox{{[}DERIVED{]}}

\emph{Note on ``does it fit?'': this residency check answers a
single-request question --- does ONE request's weights + KV fit in the
pool? It says nothing yet about how many such requests fit concurrently.
For that, an architect must subtract the runtime/activation/workspace
floor (\textasciitilde64 GB on the 8×H100 host) from the 640 GB pool
before sizing KV. We compute that concurrent capacity here --- the
\textasciitilde436 GB KV budget and \textasciitilde17.5 requests/host
(byte-accurate 17.51; conservative integer floor 17; arithmetic in this
section) --- and carry it into \hyperref[chap:17]{Chapter 17}'s fleet sizing. Keep the two
numbers separate: the \textasciitilde500 GB headroom (Ch. 4/7,
single-request) and the \textasciitilde436 GB KV budget (Ch. 17,
concurrency) answer different questions. \textbf{``Passes aggregate
bytes'' is NOT an execution result.} A fit verdict needs three distinct
gates: (1) aggregate bytes (pool ≥ residency), (2) per-rank
allocation/shard compatibility (TP shards attention heads and MLP width,
not the hidden dim: 64 query heads and 8 KV heads do not divide into 3
ranks --- 64/3, 8/3 --- and the MLP intermediate size must divide as
well; attention-head partition, runtime/workspace and topology must be
supported), and (3) a working engine/kernel/topology benchmark. 8×H100
(no sharding ambiguity at 8 shards) passes gates 1--2 for the 9.2K and
32K rows. The 3×H100 row passes gate 1 only (64 query heads and 8 KV
heads do not divide into 3 ranks) and carries the label ``passes
aggregate bytes only --- placement not established.'' The 128K row ---
also 8×H100, so TP=8 sharding is integral --- clears gate 1 and the
shard check, and its per-rank budget fits at the stated reserve (17.5 +
41.94 + 8 = 67.4 GB of 80 GB); what it does not carry is a measured
context-scaled activation/workspace reserve at 128K, so its label reads
``passes aggregate bytes + shard; long-context reserve unmeasured'' ---
a different label for a different reason.}

\emph{Attention-family sensitivity note.} The \textasciitilde2.62
MB/token (2.5 MiB) figure is the \textbf{full-MHA} (multi-head
attention) upper bound: n\_KV-heads = n\_query-heads, and n\_KV-heads ×
head\_dim = hidden\_dim, i.e.

\[
KV_{\text{MHA per-token}} = 2 \times n_\text{layers} \times d_\text{hidden} \times B
\]

Real 70B-class dense models commonly use \textbf{grouped-query attention
(GQA)}: LLaMA-2 70B, for instance, has 64 query heads but only 8
KV-heads, so per-token KV shrinks by the head ratio to

\[
KV_{\text{GQA per-token}} = 2 \times n_\text{layers} \times n_\text{KV-heads} \times d_\text{head} \times B = 2 \times 80 \times (8 \times 128) \times 2 \text{ B} \approx 0.33 \text{ MB/token}
\]

--- about \textbf{8× smaller}. For the canonical 9.2K context that is
\textasciitilde3 GB of KV instead of \textasciitilde24 GB, and the
fleet-sizing arithmetic of \hyperref[chap:17]{Chapter 17} changes accordingly (many more
concurrent requests fit for KV). We keep the full-MHA bound as the
canonical conservative teaching bound, not the \emph{chosen} model's
worst case --- the honest move is to read the model card's KV-head count
and substitute it into the GQA formula above. The framework is
unchanged; only the constant changes. (the GQA variant's per-token
constant is tracked alongside the canonical workload's other constants.)

\subsection{A smaller-model counterexample: fit is a gate, not a
prediction}\label{a-smaller-model-counterexample-fit-is-a-gate-not-a-prediction}

An illustrative 8-billion-parameter model stored entirely in FP16 has
raw weights of 16 GB. Assume 32 attention layers, eight KV-heads per
layer, a head dimension of 128 and two bytes per KV element. This is a
separate GQA example, not the handbook's canonical 70B attention layout,
and none of its constants feed the canonical tables in this chapter. The
KV storage per resident token is 2 × 32 × 8 × 128 × 2 = 131,072 bytes.

At 9,500 resident tokens, one sequence needs 1.245184 GB of raw KV. With
an explicitly assumed 4 GB reserve for runtime state and workspace, the
analytical budget is 21.245184 GB. A nominal 24 GB device passes this
preliminary capacity gate. It does not yet pass an allocation or serving
test. The reserve is an assumption, and the calculation excludes
unmodeled conversion peaks, fragmentation and additional sequences.
\mbox{{[}ILLUSTRATIVE{]}}\hspace{0pt}\mbox{{[}DERIVED{]}}

The counterexample is equally important. Ideal four-bit storage for 70
billion weights is already 35 GB before scales, alignment, unquantized
layers, KV or workspace. Neither a 24 GB nor a 32 GB card holds that
unsharded tensor. Two 24 GB cards provide 48 GB in total, but a working
placement still needs supported sharding and a feasible budget on each
rank. Shared client memory adds another constraint: the installed system
capacity must also serve the operating system and other devices. It is
not a guaranteed GPU allocation. Device capacities are first-party
specifications
(\href{https://intel.com/content/dam/www/central-libraries/us/en/documents/2026-03/datasheet-b70-gpu.pdf}{Intel
Arc Pro B70 datasheet},
\href{https://intel.com/content/dam/www/central-libraries/us/en/documents/2026-03/datasheet-b65-gpu.pdf}{B65
datasheet},
\href{https://download.intel.com/newsroom/2025/client-computing/Intel-Arc-Pro-B60-Data-Sheet.pdf}{Arc
Pro B60 datasheet}, retrieved 2026-10-28; the datasheets support the
device capacities --- the 35 GB figure is
\mbox{{[}ILLUSTRATIVE{]}}\hspace{0pt}\mbox{{[}DERIVED{]}} from 70B × 4 bits = 35 GB, not from the
datasheets.

Capacity and bandwidth answer different questions. Reading the
illustrative 16 GB of weights once at the B60's nominal 456 GB/s takes
at least about 35.1 ms in a simple weights-only streaming model; at the
B70/B65 nominal 608 GB/s the corresponding value is about 26.3 ms. These
are analytical byte-transfer floors, not measured token latencies. They
ignore attention, KV traffic, launch overhead and communication, and
they assume the nominal bandwidth is achieved. Batching or reuse can
also change the bytes moved per output token. Passing the capacity gate
therefore justifies a measurement, not a throughput or cost claim.

therefore adds 8 GiB to this component under the stated assumptions; it
does not double every memory object in the request. In notation, the
simplified history budget is
\texttt{M\_history(L)\ =\ L\ ×\ 65,536\ bytes\ +\ M\_recurrent}, where
\texttt{M\_recurrent} covers fixed-shape recurrent and convolution state
for this decode path. Temporary prefill workspaces remain outside that
expression. These are derived storage estimates, not measured
allocations. \mbox{{[}DERIVED{]}}

The serving consequence follows from the state lifetimes. Capacity
planning needs both terms, including any replication or sharding imposed
by the engine. A prefix checkpoint for an intermediate position must
preserve the time-recurrent state corresponding to that position, not
merely a list of attention pages. A preempted or branched request can
require additional snapshots, and speculative rollback needs the correct
pre-draft state. Bounded live decode state therefore does not imply free
checkpointing or unrestricted prefix sharing; the implementation
determines which extra copies are retained. \mbox{{[}DERIVED{]}}

Less history traffic can relax one memory bottleneck without removing
the weight-read or compute bottleneck. A recurrent token mixer and a
full-attention layer also expose different prefill execution
opportunities. Their kernel mix and sequence-length dependence must be
measured separately before transferring a decode-state estimate into a
throughput forecast. The architectural decision is which state
representation the engine can maintain correctly at the required
concurrency, not which family label sounds smaller.

The original memory-fit decision remains; the state function inserted
into that decision changes. This is a different model's configuration
carried as its own assumptions --- the canonical 80-layer, hidden-8192,
full-MHA numbers in this chapter are unchanged by it.

AWQ and GPTQ primarily address error control during post-training weight
quantization. AWQ uses representative activations to identify important
channels and chooses equivalent channel scaling that reduces the error
introduced by quantizing weights. ``Activation-aware'' describes the
information used by the method; it does not mean that activations are
also stored in four bits. The paper's exploratory observation about
protecting a small fraction of salient weights is not a definition
requiring those weights to remain FP16. Its scaling method seeks
protection without that irregular mixed-precision storage.
\mbox{{[}1P{]}}\hspace{0pt}\mbox{{[}FACT{]}} (\href{https://arxiv.org/pdf/2306.00978v6}{AWQ, §3}).

GPTQ instead uses approximate second-order information to compensate for
quantization error in the remaining weights as quantization proceeds.
Its original implementation targets weight quantization, not activation
quantization. Neither method name uniquely specifies a group size, scale
dtype, zero-point layout, permutation or checkpoint packing. Those
fields are needed to reproduce both accuracy and memory use. Calibration
data must represent the intended workload; a method's reported behavior
on one evaluation does not establish behavior on another distribution.
\mbox{{[}1P{]}}\hspace{0pt}\mbox{{[}FACT{]}} (\href{https://arxiv.org/pdf/2210.17323v2}{GPTQ,
§2--4}).

A container answers a different question. GGUF stores model metadata,
tensor descriptions, tensor types and aligned tensor payloads. It is not
a single numerical precision. Its tensor-type field permits different
encodings within one model. Consequently, a comparison labeled ``AWQ
versus GGUF'' confounds an error-control method with a file format
unless both sides are expanded into complete deployment configurations.
The useful comparison specifies the method, tensor encodings,
mixed-precision exceptions and execution backend. The same caution
applies to safetensors: storing tensors in a recognized container does
not establish that a loader understands their quantized schema.

(\href{https://github.com/ggml-org/ggml/blob/da8e2a54b919557b816b1c2beb432ccb766f7ce0/docs/gguf.md}{GGUF

\subsubsection{Shared scales change the storage
calculation}\label{shared-scales-change-the-storage-calculation}

OCP MXFP4 1.0 uses E2M1 four-bit values, with one eight-bit E8M0 scale
shared by a block of 32 values. E8M0 represents a power-of-two scale.
The common one-dimensional NVFP4 scheme also uses E2M1 values, but
shares an E4M3 local scale over 16 values and uses an additional FP32
tensor-global scale. Neither scheme uses an affine integer zero point in
this comparison. The local scale's encoding and granularity change the
set of representable values and its adaptation to a block's dynamic
range; smaller groups also require more scale bytes. This is a mechanism
difference, not an automatic accuracy ranking. \mbox{{[}1P{]}}\hspace{0pt}\mbox{{[}FACT{]}}
(\href{https://www.opencompute.org/documents/ocp-microscaling-formats-mx-v1-0-spec-final-pdf}{OCP
MX 1.0, §4--6};
\href{https://developer.nvidia.com/blog/introducing-nvfp4-for-efficient-and-accurate-low-precision-inference/}{NVIDIA
NVFP4 explanation, 2025-06-24}).

The next figure holds the number of logical values constant. The same 32
four-bit values require 16 payload bytes in either scheme. MXFP4 adds
one local-scale byte, producing 17 bytes per 32 values, or 0.53125
B/value. Common 1D NVFP4 adds two local-scale bytes, producing 18 bytes
per 32 values, or 0.5625 B/value, before the tensor-global scale. For a
tensor with N values in complete blocks, this example's compact NVFP4
storage is 0.5625N + 4 bytes. The four global-scale bytes are shared
across the tensor, not repeated for each block. \mbox{{[}1P{]}}\hspace{0pt}\mbox{{[}DERIVED{]}}

These rates are not the total footprint of a model. A mixed-precision
model retains some tensors at higher precision. A file adds metadata and
alignment gaps. A runtime may pad dimensions, reorder scales, create
extra representations or reserve workspace. The memory ledger therefore
separates checkpoint bytes, resident tensors, load/repack peak,
activations, KV cache and workspace. A checkpoint that fits on disk may
still fail during loading, and a successfully loaded checkpoint may not
leave enough memory for the intended context and concurrency. The exact
runtime layouts remain implementation-dependent. \mbox{{[}1P{]}}\hspace{0pt}\mbox{{[}DERIVED{]}}

\subsubsection{Worked example: scale overhead is small but not
zero}\label{worked-example-scale-overhead-is-small-but-not-zero}

A 4096 × 4096 weight matrix holds 16,777,216 values. The shape is
illustrative; the byte results follow the stated layouts. BF16 payload
occupies 33,554,432 bytes. MXFP4 with complete 32-value blocks occupies
8,912,896 bytes. Common 1D NVFP4 with complete 16-value blocks and one
FP32 global scale occupies 9,437,188 bytes. The difference comes from
the chosen scale representation and grouping, not a different number of
four-bit payload values. Both calculations exclude padding, additional
scale copies and non-weight tensors. \mbox{{[}ILLUSTRATIVE{]}}\hspace{0pt}\mbox{{[}DERIVED{]}}

An integer scheme can produce a different bill again. With groups of
128, an illustrative INT4 layout containing an FP16 scale and a packed
four-bit zero point per group uses 8,716,288 bytes for the same matrix.
Replacing the packed zero with an FP16 scaled-zero increases that layout
to 8,912,896 bytes. Equal total bytes do not make this integer scheme
numerically equivalent to MXFP4. The example explains why an estimate
needs the actual scale and zero layout rather than ``four bits plus a
little overhead.'' It does not choose an accuracy or speed winner.
\mbox{{[}ILLUSTRATIVE{]}}\hspace{0pt}\mbox{{[}DERIVED{]}}

For a separate resource sensitivity, a 70B-parameter teaching model that
stores 98\% of parameters in MXFP4 and 2\% in BF16 --- fractions
deliberately chosen, not a real checkpoint inventory --- needs 39.24375
GB of compact weight storage rather than 140 GB. Retaining this
chapter's full-MHA, BF16 KV assumptions (80 layers, KV width 8192, 9,500
tokens per sequence) leaves raw KV at 24.90368 GB per sequence. In a 640
GB aggregate pool with a fixed 64 GB reserve, the storage-only integer
ceiling rises from 17 sequences to 21, not in proportion to the weight
compression. The added KV budget does not prove that the ranks can place
it or that 21 requests meet the latency SLO. Workspace, fragmentation
and per-rank balance still need measurement, and the reserve itself may
change. \mbox{{[}ILLUSTRATIVE{]}}\hspace{0pt}\mbox{{[}DERIVED{]}}

The causal consequence is narrower than ``quantization solves memory.''
Weight compression frees one term in the memory ledger. If KV dominates
the remaining footprint, context length and concurrency can still bind.
Weight precision and KV precision remain separate decisions, with
separate scale calibration, attention-kernel support and quality
validation. KIVI's separate treatment of key and value statistics is one
example of a KV-specific method, not a consequence of choosing an AWQ
weight checkpoint. \mbox{{[}1P{]}}\hspace{0pt}\mbox{{[}FACT{]}}
(\href{https://arxiv.org/abs/2402.02750v2}{KIVI}).

\ntsection{Measurement}\label{measurement}


Four practical measurement habits follow from the arithmetic above:

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  \textbf{Compute KV cache per-token cost for the model.} The per-token
  KV footprint of a fully-cached (MHA) model is
\end{enumerate}

\[
KV_{\text{per-token}} = 2 \times n_\text{layers} \times d_\text{hidden} \times \text{bytes-per-value}
\]

(one key and one value per layer, each \(d_\text{hidden}\) wide),
evaluated at the chosen precision. For a 70B model at FP16 the answer is
\(2 \times 80 \times 8192 \times 2 \text{ B} = 2{,}621{,}440\) B
\(\approx 2.62\) MB/token (exactly \textbf{2.5 MiB/token}; 2,621,440
bytes is 2.62144 decimal MB). At 8-bit the per-token value halves to
\textasciitilde1.31 MB/token (\textasciitilde1.25 MiB; the Ch.1
reference). Do not assume the 1.3 MB/token figure applies at FP16 --- it
does not; it is an 8-bit number. When evaluating a model whose geometry
differs from this chapter's 80-layer / 8192-hidden full-MHA reference
geometry, recompute the constant factor from the general form (2 ×
layers × n\_KV-heads × head\_dim × bytes) --- a real LLaMA-2 70B is
GQA-8 (8 KV heads) at \textasciitilde0.33 MB/token, not 2.62 (see the
sensitivity note) --- a model with 64 layers and 8192 dim will have
\textasciitilde2.1 MB/token at FP16 (2 × 64 × 8192 × 2 B = 2,097,152 B),
while a model with 100 layers and 12288 dim will have \textasciitilde4.9
MB/token (2 × 100 × 12288 × 2 B = 4,915,200 B).

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\setcounter{enumi}{1}
\item
  \textbf{Log peak context length, not just average.} A workload that
  averages 9.2K input tokens but has a long tail toward 32K or 128K will
  have a very different KV cache profile. Log the 95th-percentile
  context length and re-run the KV arithmetic; the memory floor may
  shift from already exceeding 2×H100 at the 9.2K average (164.1 GB
  \textgreater{} 160 GB) toward needing most of the 8×H100 host at a
  128K tail. This is especially important for RAG workloads, where the
  retrieved context may average 8K but occasionally peak at 32K+ for
  technical documents.
\item
  \textbf{Measure inference residency as weights + KV, not weights
  alone.} It is common to see the 140 GB weight footprint (70B FP16) fit
  across \textbf{two} 80-GB accelerators and conclude that 160 GB is
  sufficient. But 140 GB of weights leaves only \textasciitilde20 GB
  before runtime/workspace and KV are added; at 9.2K input the KV cache
  adds \textasciitilde24.1 GB, pushing the total to \textasciitilde164.1
  GB --- already over the 160 GB aggregate, so the model does \emph{not}
  fit on two accelerators once KV is counted (decimal 80×10\^{}9 B
  basis, §1; on the vendor-binary basis the pool is 171.0 GB, where the
  same per-rank reserve test still fails --- §1). Always include KV when
  we state the memory floor for inference.
\item
  \textbf{Account for KV quantization when reporting residency.} If the
  serving stack uses FP8 KV, the per-token KV cost drops from
  \textasciitilde2.62 MB to \textasciitilde1.31 MB (raw tensor
  byte-halving, exactly 50\% of FP16 = 2,621,440/2 = 1,310,720 B = 1.25
  MiB), and the 9.5K max residency falls from \textasciitilde165 GB to
  \textasciitilde152 GB (weights 140 GB + KV 12.45 GB). State both the
  BF16 and FP8 residency numbers, because the choice of KV dtype changes
  the hardware requirement decisively. \textbf{Note the accounting
  basis:} the \textasciitilde1.31 MB/token figure is the raw tensor
  byte-halving of the same MHA tensors (one byte per K/V element,
  exactly half of a 16-bit (FP16/BF16) element's two bytes); it is NOT a
  vendor-measured serving footprint, and any block-layout or per-token
  scale/offset metadata overhead is not included. \textbf{Do not
  generalize a fixed ratio to all FP8-KV deployments:} the realized
  per-token footprint depends on the engine version, cache-block layout,
  scale/offset metadata, allocator rounding, and the accounting boundary
  (logical payload vs allocated cache vs observed resident memory), so
  re-derive it for the target serving stack rather than inheriting a
  multiplier. (For reference, the 9.5K total at this byte-halving basis
  is \textasciitilde152 GB --- still above a single H100, but now within
  2×H100, 160 GB.)
\end{enumerate}

\ntsection{Common Mistakes}\label{common-mistakes}


\begin{itemize}
\item
  \textbf{Assuming KV cache size scales sub-linearly.} The KV cache
  grows linearly with context length. Doubling the context from 9.2K to
  18.4K doubles the KV memory, all else equal. There is no automatic
  compression unless the attention mechanism itself is hybrid or sparse.
\item
  \textbf{Using the 8-bit KV figure (\textasciitilde1.31 MB/token) at
  FP16.} \hyperref[chap:1]{Chapter 1}'s \textasciitilde1.31 MB/token is explicitly at 8-bit
  precision. At FP16, the per-token KV cost is \textasciitilde2× that,
  ≈2.62 MB/token (2.5 MiB --- §7.4). Mixing the two figures produces
  wrong residency calls.
\item
  \textbf{Ignoring the weight + KV residency contrast.} Quoting only the
  weight footprint (140 GB for 70B FP16) and claiming it fits on one
  H100 (80 GB) is a category error. Weights alone exceed one H100; KV
  must be added.
\item
  \textbf{Quoting one KV-quant reduction for every precision.} KV cache
  quantization must be read per bit width: FP8 KV ≈50\% of FP16 (raw
  byte-halving) is the first-order raw figure before block/scale
  metadata (§4 point 4), while 4-bit KV's raw bound is a full 4× (2.62 →
  0.66 MB/token here; 0.52 → 0.13 for a 7B, §12.3) --- the realized
  saving falls below that 4× bound once block/scale metadata is counted,
  and no fixed multiplier may be assumed without the actual layout.
  Weight-only quantization's 2×--4× is the same raw bit-width bound
  applied to weights; do not transfer an expectation across precisions
  or across tensors without naming the bit width.
\item
  \textbf{Overlooking the fine-tuning residency floor.} Full fine-tuning
  of 70B requires \textasciitilde1.12 TB with Adam optimizer states ---
  roughly 1.75× the 8×H100 host. This is not a temporary overhead; it is
  the permanent memory floor for the training duration.
\end{itemize}

\ntsection{Architecture Consequence}\label{architecture-consequence}


The memory floor is the first constraint every architecture decision
respects, because unlike compute or bandwidth it cannot be moved by
better kernels or scheduling --- it is set by the model's weights, its
KV state and (for training) optimizer state, and moves only with
precision, architecture, or where the state lives. Several concrete
consequences follow for the canonical enterprise-Q\&A workload:

\begin{itemize}
\item
  \textbf{Model residency decides host count.} A 70B FP16 model (140 GB
  weights) at the 9.5K max context (9.2K in + 300 out) needs
  \textasciitilde24.9 GB of KV cache (FP16), so the max
  end-of-generation residency ≈ 165 GB --- it does \emph{not} fit on a
  single 80 GB H100, nor within the 160 GB aggregate of 2×H100 (160 GB
  \textless{} 165 GB; decimal 80×10\^{}9 B basis --- on the
  vendor-binary basis, 165 GB \textless{} 171.0 GB in aggregate but the
  per-rank test fails, §1). By \emph{aggregate memory capacity} it needs
  \textbf{≥ 3×80 GB} (240 GB) --- but note this is an
  \textbf{aggregate-HBM lower bound on card count, NOT a validated 3-way
  tensor-parallel configuration}: whether three 80-GB cards actually
  admit a 70B model depends on head/layer shard divisibility, KV-head
  routing, TP=3 support, workspace/communication layout, and per-rank
  fragmentation, none of which the aggregate sum establishes. A
  practical TP topology (e.g.~TP=4 or TP=8) must be checked against the
  serving engine and model geometry before three cards are treated as
  deployable. The canonical single host of 8×H100 (640 GB) is not
  justified by basic capacity alone --- three 80 GB GPUs already clear
  the 165 GB residency floor; the 8×H100 host is chosen for compute,
  bandwidth, topology, concurrency, implementation constraints, and
  headroom. \mbox{{[}canonical scenario{]}}\hspace{0pt}\mbox{{[}DERIVED{]}}
\item
  \textbf{KV cache quantization buys back memory, not compute.} FP8 KV ≈
  50\% of FP16 (raw byte-halving), dropping the 9.5K max residency from
  \textasciitilde165 GB toward \textasciitilde152 GB. KV quantization is
  primarily a capacity lever; it also reduces the K/V bytes read during
  decode, so it can relieve KV-bandwidth pressure, but it does not
  reduce attention FLOPs. Pull it when KV capacity binds, and benchmark
  it when decode bandwidth may also be limiting.
\item
  \textbf{Fine-tuning is a different memory regime than inference.} The
  same model that serves in \textasciitilde165 GB demands
  \textasciitilde1,120 GB under full Adam fine-tuning (weights 140 GB +
  gradients 140 GB + Adam m/v/master states 840 GB) --- roughly 1.75×
  the 8×H100 host. This is why the architect separates the serving fleet
  from the training fleet: the memory floors differ by roughly 7×
  (\textasciitilde164 GB at 9.2K vs \textasciitilde1,120 GB).
  \mbox{{[}canonical scenario{]}}\hspace{0pt}\mbox{{[}DERIVED{]}}
\item
  \textbf{Context length is the largest controllable KV lever.} Doubling
  context from 9.2K to 18.4K doubles KV (\textasciitilde24.1 GB →
  \textasciitilde48 GB); 128K context drives KV to \textasciitilde335 GB
  --- on a single 80 GB GPU that forces quantization, offloading or
  model parallelism; on the canonical 8×H100 host \textasciitilde475 GB
  total residency fits in 640 GB but leaves little headroom for
  concurrency. The architecture must set a context-length ceiling to
  keep the served model within host memory.
  \mbox{{[}ILLUSTRATIVE{]}}\hspace{0pt}\mbox{{[}DERIVED{]}}
\end{itemize}

In short: the architect sizes the host by weights + KV at the longest
supported context, treats KV quantization as a spare memory dial, and
keeps inference and training on separate memory-planning tracks.

\ntsection{What We Still Don't Know}\label{what-we-still-dont-know}


\begin{itemize}
\item
  Per-model KV state beyond K/V --- the additional per-head state and
  per-layer scale/offset metadata some attention implementations store
  alongside keys and values. The
  \texttt{2\ ×\ layers\ ×\ n\_KV-heads\ ×\ head\_dim\ ×\ bytes} formula
  prices the K/V entries themselves (§7.3 covers GQA/MQA exactly by
  substituting the model card's KV-head count), but the extra per-token
  bytes an implementation adds on top of K/V are not derived in this
  chapter and must be established per architecture and serving stack.
\item
  Quality loss from aggressive KV quantization (2-bit KIVI, or sub-4-bit
  schemes) at very long context lengths (128K+) and in MoE models. The
  primary sources anchor FP8 KV ≈50\% of FP16 (raw byte-halving); the
  \emph{quality} cost of FP8 KV is not benchmarked in this chapter, so
  any `small loss' claim is unverified here, and 2-bit asymmetric
  patterns and their interaction with RoPE and sliding-window layers are
  not fully mapped.
\item
  \begin{enumerate}
  \def\labelenumi{(\alph{enumi})}
  \tightlist
  \item
    decode-time KV offload to CPU DRAM trades TPOT/ITL and KV capacity,
    not TTFT (TTFT is already complete when decode starts); (b)
    prefix/KV reuse loaded from CPU can reduce TTFT for cache-hit
    requests --- the vLLM KV Offloading Connector's 2--22× figure is
    defined in Ch 6 (TTFT metric, warm-cache-hit/reuse benchmark)
    \mbox{{[}S7{]}}\hspace{0pt}\mbox{{[}1P{]}}\hspace{0pt}\mbox{{[}FACT{]}} and is highly prompt-size-dependent. The
    community is converging on tiered KV storage (GPU resident hot set +
    CPU/DRAM cold set), but the latency trade-offs at concurrency
    \textgreater{} 1 are not yet primary-anchored.
  \end{enumerate}
\item
  \textbf{Whether each frontier model's re-engineered KV constant
  reproduces on a serving stack.} Frontier 2026 has begun re-engineering
  the KV constant factor, not just quantizing it. All four 2026-class
  open architectures modify attention for long-context cost; DeepSeek
  and GLM report first-party KV-cache ratios, while Kimi and Qwen
  describe mechanisms with no stated KV metric (\hyperref[tab:7.3]{Table 7-3}). These are
  first-party figures, not independently reprofiled. Whether these
  constants reproduce on serving stacks, and what they imply for
  concurrency and fleet sizing, is unresolved. Size the host against the
  \emph{specific} model's KV scheme, not a universal constant.
\item
  Whether a given MoE model's governing KV constants have been validated
  per model (routing itself is settled): The total-vs-active and
  MoE-vs-dense facts of Ch 3 (total parameters ≠ active parameters per
  token; MoE gives compute sparsity, not weight-residency sparsity)
  confirm that attention layers process every token densely and emit
  key/value per token --- under the standard-MoE assumption (sparse MLP
  experts with dense attention; hybrid-attention models must be checked
  separately) --- so MoE sparsity does not reduce KV --- and the
  constants that do govern KV (attention geometry: layers, KV-heads,
  head dimension, cache dtype) need per-model validation; expert count
  belongs to weight-residency and dispatch validation, not KV sizing.
\end{itemize}

\textbf{Technical note --- per-rank fit (moved out of the caption).}
Whether a given allocation actually fits depends on tensor-parallel
sharding, KV partitioning, replication, runtime layout, per-rank
fragmentation, workspace requirements and communication topology, so
``total bytes \textless{} total HBM'' is necessary but not sufficient.
Worked TP=8 example: with a KV budget per rank of 436 ÷ 8 = 54.5 GB and
17.5 concurrent requests, a rank holds 17.5 + 8 + 54.48 = 79.98 GB =
99.97\% of an 80 GB rank, so the aggregate 17.5 is a hard ceiling ---
exactly full, with zero per-rank headroom --- not a comfortable
operating point. The per-rank quantities:

\begin{itemize}
\tightlist
\item
  weights per rank: 140 ÷ 8 = \textasciitilde17.5 GB
\item
  runtime/NCCL per rank: \textasciitilde8 GB --- the \textasciitilde64
  GB reserve is a host aggregate of these per-rank overheads
\item
  KV budget per rank: 436 ÷ 8 = \textasciitilde54.5 GB
\item
  per-request KV per rank: 24.9 ÷ 8 = \textasciitilde3.1 GB
  (tensor-parallel attention shards each request's KV across the 8
  ranks)
\end{itemize}

Per-rank budget: 17.5 + 54.5 + 8 = 80 GB --- exactly the rank's
capacity. At 17.5 concurrent requests the rank actually consumes 17.5 ×
3.11296 = 54.48 GB of KV (budget 54.5 GB, consumption 54.48 GB), so
occupancy is 17.5 + 54.48 + 8 = 79.98 GB = 99.97\% of 80 GB. A rank can
be the binding constraint even when the aggregate fits, so per-rank fit
and sharding must be validated separately (Chapters 9--10).
Byte-accurate, 436 ÷ 24.9037 = 17.51, so the conservative integer
``requests that fit'' floor is 17, not 18.

\section{End-of-Chapter Mini-Case: Sizing Memory First for the
5,000-Employee
Wiki}\label{end-of-chapter-mini-case-sizing-memory-first-for-the-5000-employee-wiki}

An architect is asked to design an internal Q\&A system over the
company's document repository. The initial ask is vague: ``We need to
let all 5,000 employees ask questions over our internal wikis.'' Before
any architecture can be defended, the architect must turn this vague
desire into a machine-denominated statement using the chapter's core
constraint.

From the unit-and-token work of Ch 1 alone, the architect can already
establish several facts. The unit is tokens; the request shape will be
prompt + retrieved context + output; the workload is input-heavy
(retrieved context dominates) {[}ASSUMPTION --- validate in Ch 4's
workload characterization{]}; and the first number to lock down is
tokens-per-request, because every downstream decision (which model fits,
how much memory, what latency is possible) is priced against it.

Running the KV arithmetic: if each request uses \textasciitilde9.2K
input tokens (the canonical \textasciitilde1,200 prompt + 8K retrieved)
plus \textasciitilde300 output tokens, the request grows to a
\textbf{9.5K max KV sequence} by the end of generation. The KV cache per
request at 70B FP16 is \textasciitilde24.9 GB (max, 9.5K), against
\textasciitilde24.1 GB for the initial 9.2K-prefill residency. The
weight footprint is 140 GB. Total max inference residency is ≈165 GB,
which does \textbf{not} fit within the nominal 160 GB aggregate HBM of
2×80 GB H100s (decimal 80×10\^{}9 B basis, §1; the vendor-binary pool is
171.0 GB but the per-rank test still fails); practical deployment
therefore requires additional capacity, lower precision, or a larger GPU
configuration. It fits comfortably within the 640 GB aggregate HBM of an
8×H100 host. If the context is extended to 32K (e.g., wider document
retrieval), the KV cache rises to \textasciitilde84 GB, pushing total
residency to \textasciitilde224 GB --- still fitting in 8×H100 but
requiring a multi-GPU node.

The architect can now speak the system's currency: tokens, KV bytes, and
the residency floor. The next step --- turning ``5,000 employees'' into
\textasciitilde2,000 registered users, \textasciitilde100 concurrent
typical / \textasciitilde400 at peak, \textasciitilde10 requests/s
\mbox{{[}canonical scenario{]}}{[}ASSUMPTION, from Ch 4 \hyperref[tab:4.2]{Table 4-2}{]}, and a
specific model-and-hardware choice --- applies \hyperref[chap:4]{Chapter 4}'s
workload-anatomy method, already developed before this chapter. Here the
point is narrower and sharper: we can now say, with quantified memory
numbers, whether the system fits on the available hardware, and we can
compare inference vs.~fine-tuning residency floors before committing to
an architecture decision. This is the chapter's payoff: the vague
request has been translated into concrete constraint numbers, and the
architect can defend a recommendation based on whether the workload
fits, not on intuition alone.
