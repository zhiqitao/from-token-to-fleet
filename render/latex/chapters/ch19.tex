\section*{The Architect's Question}\label{the-architects-question}

In large-scale RQA (retrieval-augmented QA) pipelines serving thousands
of users (tens to \textasciitilde100 concurrent at the canonical 10
rps), the transition from static LLM calls to agentic orchestration
raises fundamental trade-offs: increased capability versus increased
latency, higher per-request token consumption versus better answers, and
richer multi-step reasoning versus harder-to-debug execution paths. This
chapter addresses the architect's central question: how to design
agentic layers that amplify intelligence without unsustainably inflating
cost and latency.

\textbf{Terminology.} Throughout the book, ``RAG question-answering
workload'' is the controlled term for retrieval-augmented question
answering; this chapter uses \textbf{RQA} for the retrieval-augmented QA
workload, single-shot or agentic (the retrieval leg plus one or more
generation turns), and always defines it on first use; ``RAG'' alone
refers to the broader retrieval-augmented-generation family.

We begin from the canonical deployment scenario (Ch 4, \hyperref[tab:4.2]{Table 4-2}):
\textasciitilde10 requests/second average and \textasciitilde40
requests/second peak. Each request carries \textasciitilde9,200 input
tokens and produces \textasciitilde300 output tokens. The base model is
a 70B dense FP16 engine running on 8×H100 GPUs (640\,GB total memory).
The agentic layer sits above this foundation, introducing tool use,
retrieval, and multi-step reasoning. The question we answer is how much
additional overhead this layer introduces, whether the quality gain
justifies the cost, and how to size the infrastructure accordingly.

\ntsection{Concept}\label{concept}


An agentic system is one in which the LLM does not merely complete a
single prompt but iteratively decides which actions to take --- calling
tools, querying databases, running checks, and then reasoning about the
results before producing a final answer. The core idioms are:

\begin{itemize}
\tightlist
\item
  \textbf{Tool use}: The model emits a structured call (often JSON) to
  invoke an external function --- a search API, a database query, a code
  interpreter, or a guardrail validator.
\item
  \textbf{Retrieval}: Within each turn, the agent may trigger a vector
  search, re-rank results, and feed the top-k passages back into the
  prompt.
\item
  \textbf{Multi-step reasoning}: The agent maintains an internal
  ``thought'' chain, appending each new observation and its
  interpretation before deciding on the next action.
\item
  \textbf{Guardrails}: Pre- and post-hoc checks that validate whether
  the model's intended action is safe, on-topic, or within budget.
\end{itemize}

The agent loop terminates when a stop condition is met: a final answer
is emitted, a maximum turn count is exceeded, or a guardrail blocks
further progress. This design pattern replaces the ``single-shot''
prompt --- one LLM call, one response --- with a dynamic sequence of
calls whose length is data-dependent.

The architect must decide not only which tools the agent may call but
also how to instrument each call for latency and token accounting, and
how to set termination thresholds so that the system degrades gracefully
under load.

\ntsection{Mental Model}\label{mental-model}


The mental model we adopt visualizes the agent as a state machine with
four recurring states: \textbf{Plan}, \textbf{Execute},
\textbf{Observe}, and \textbf{Decide}. In each cycle:

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  \textbf{Plan}: The model reads the current context (original user
  query + accumulated observations) and emits a plan --- either
  ``proceed with final answer'' or ``call tool X with parameters Y.''
\item
  \textbf{Execute}: The system routes the tool call to the appropriate
  backend, waits for results, and formats them back into text.
\item
  \textbf{Observe}: The result text is appended to the conversation
  history, and the token count is updated.
\item
  \textbf{Decide}: The model evaluates whether the observation resolves
  the user query or whether another cycle is needed.
\end{enumerate}

Plan and Decide are two evaluations of one model invocation per cycle
(the Decide verdict is the next cycle's Plan input); the capacity model
counts one LLM call per turn plus the terminal synthesis call (§4).

This loop is deterministic in structure but data-dependent in length. A
simple query (``What is the capital of France?'') may terminate at
Plan/Decide --- the plan is ``proceed with final answer,'' so no Observe
round-trip is needed --- while a complex RQA request (``Compare the
performance of Model A on dataset X against Model B on dataset Y, using
the last three papers from arXiv as evidence'') may traverse three or
more cycles.

The critical insight for capacity planning is that each cycle incurs a
fixed overhead: one LLM inference turn plus any tool-call latency --- in
the simplified execution model this chapter prices; §4 generalizes it to
an execution trace (a turn may contain zero or more model invocations
and tool calls). The variable portion is the number of cycles the model
chooses. Our mental model therefore separates \emph{fixed cost per turn}
from \emph{variable turn count}, and we will quantify both in the next
section.

\ntsection{Worked Example}\label{worked-example}


Take a user query routed to an agentic RQA pipeline. The pipeline's
default policy is a maximum of 4 turns; if the model has not terminated
by then, the system returns a fallback answer ``I'm sorry, I couldn't
find a definitive answer within the allowed reasoning steps.''
(\textbf{Scope note on the turn cap.} This worked example uses a
\emph{default} cap of 4 to illustrate the binding worst case and the
token-amplification curve out to T = 4. The \emph{recommended
operational} policy --- deployed in the §8 mini-case and used for fleet
sizing in \hyperref[chap:17]{Chapter 17} --- caps turns at 3, per the §4 guidance and the
95th-percentile sizing rule (size for the 95th-percentile turn count ---
§4's illustrative distribution gives p95 T = 3); the 2\% of requests
that exceed the limit fall back to single-shot. \hyperref[tab:19.1]{Table 19-1}'s ``T = 4
(over cap)'' column is therefore an \emph{out-of-policy bounding} case,
not an in-policy turn count.)

\textbf{Call 1 (initial prompt)}:

\begin{itemize}
\tightlist
\item
  Input: 9,200 tokens (user query + retrieved passages)
\item
  Model emits a tool-call: \texttt{search(query="relevant\ concepts")}
\item
  System routes the call to the search backend, returns top-5 passages
  (≈ 800 tokens of snippets)
\item
  Total tokens after Turn 0: 9,200 + 800 = 10,000
\end{itemize}

\textbf{Call 2}:

\begin{itemize}
\tightlist
\item
  Input: 10,000 tokens (history + new passages)
\item
  Model emits a second tool-call:
  \texttt{db\_query(sql="SELECT\ ...\ WHERE\ condition")}
\item
  Latency: 85\,ms (local PostgreSQL on H100 host)
\item
  Result: 350 tokens of tuple rows
\item
  Total tokens after Turn 1: 10,000 + 350 = 10,350
\end{itemize}

\textbf{Call 3}:

\begin{itemize}
\tightlist
\item
  Input: 10,350 tokens
\item
  Model decides to synthesize: emits a final answer
\item
  Output: 300 tokens
\item
  Conversation ends
\end{itemize}

This trace is 2 tool round-trips ⇒ T = 2 and 3 model invocations under
§4's convention.

\textbf{Token accounting}:

\begin{itemize}
\tightlist
\item
  Base single-shot: 9,200 input + 300 output = 9,500 tokens
\item
  Agentic: 10,350 input + 300 output = 10,650 tokens
\item
  Amplification factor: 10,650 / 9,500 ≈ 1.12× (this specific
  hand-worked trace, tool outputs 800 + 350; the per-turn convention of
  §4/\hyperref[tab:19.1]{Table 19-1} --- δ=800 + γ=65 per turn --- gives α(T=2) = (9,500 +
  2×865)/9,500 = 11,230/9,500 ≈ 1.18× --- different conventions, not a
  discrepancy)
\end{itemize}

A harder query that exhausts all 4 turns is the upper-bound case. Using
the chapter's per-turn convention (each turn adds δ≈800 tokens of
retrieved context plus γ≈65 tokens of model-generated reasoning), the
token trajectory grows approximately linearly: after \emph{k} turns,
total input tokens ≈ 9,200 + k·(800+65), and total output ≈ 300 (final
answer) --- the intermediate reasoning (≈65 tokens per turn) is retained
inside the input context above, not counted again as output. After 4
turns, input ≈ 9,200 + 4×800 + 4×65 = 12,660 tokens, output ≈ 300
tokens, giving a total of \textasciitilde12,960 tokens. The
amplification factor vs.~single-shot is 12,960 / 9,500 ≈ 1.36×.

This worked example demonstrates that the cost increase is moderate for
short reasoning paths but compounds as the agent loops deeper. The
architect must weigh the probability of deep loops against the budget
per request.

\ntsection{Measurement}\label{measurement}


To plan capacity and set budgets, we derive three quantities from the
example above and the illustrative turn distribution below. A production
deployment must estimate these quantities from its own telemetry.

First, a scoping note that matters more than any single number: a
production agent turn is \textbf{not} guaranteed to be exactly ``one LLM
inference + one tool call.'' A turn may contain zero or more model
invocations, parallel or chained tool calls, retrieval + reranking,
model-generated reasoning, tool output, context compaction, or cached
prefixes.

Treating ``1 turn = 1 LLM call + 1 tool call'' is a \emph{simplified
execution model}, useful for first-pass arithmetic but not the general
agent model. A more faithful capacity model is an \textbf{execution
trace}: request → model invocation(s) → tool invocation(s) →
observation(s) → model invocation(s) → final response, with its own
token and latency totals. The amplification framework below (token
\emph{α}, latency \emph{β}) is one concrete, simplified instantiation of
that trace --- it is what an architect can compute before instrumenting
a real system.

It must be validated against measured traces afterwards.

\subsection{Per-agent-turn token
amplification}\label{per-agent-turn-token-amplification}

Let \emph{T} be the number of agent turns and \emph{I₀} the initial
input tokens (9,200 in our scenario). Each turn adds \emph{δ} tokens of
retrieved context and \emph{γ} tokens of model-generated reasoning. The
total token count after \emph{T} turns is:

\[
\text{Total}(T) = (I_0 + T \cdot \delta + T \cdot \gamma) + O_\text{final}
\]

where \(O_\text{final}\) is the final output (≈300 tokens). The per-turn
amplification \emph{α} is the ratio of total tokens to the single-shot
baseline \(I_0 + O_\text{final}\):

\[
\alpha(T) = \frac{I_0 + T\cdot\delta + T\cdot\gamma + O_\text{final}}{I_0 + O_\text{final}}
\]

With \emph{δ} = 800, \emph{γ} = 65, \(O_\text{final}\) = 300, and
\emph{T} = 3:

\[
\alpha(3) = \frac{9{,}200 + 3\cdot800 + 3\cdot65 + 300}{9{,}200 + 300} = \frac{9{,}200 + 2{,}400 + 195 + 300}{9{,}500} = \frac{12{,}095}{9{,}500} \approx 1.27\times
\]

For \emph{T} = 4: α(4) ≈ 1.36× as computed in the worked example. In
production, the distribution of \emph{T} depends on query complexity.
Consistent with the mini-case telemetry in §8 (68\% T = 1, 25\% T = 2,
5\% T = 3, 2\% fallback), the illustrative turn distribution here has
median \emph{T} = 1, 90th percentile \emph{T} = 2, and 95th percentile
\emph{T} = 3 (conditional on a completed agent run --- the §7/§8
convention) \mbox{{[}ILLUSTRATIVE{]}}\hspace{0pt}\mbox{{[}ASSUMPTION{]}} --- derived from the §8
distribution.

\textbf{What α does and does not measure.} \emph{α} measures
\textbf{retained/accumulated task context} under the simplified turn
model --- the unique content that must be held (and, absent compaction,
resent as context) as the conversation grows. It is \textbf{not} the
total model-processed or API-billed token multiplier: if the model is
invoked repeatedly on the growing prefix, that retained context may be
counted in \emph{multiple} input calls, and the per-call outputs must be
counted separately. So α ≈ 1.27× at \emph{T} = 3 says the \emph{context}
is \textasciitilde27\% larger than single-shot --- it does \emph{not}
say the task costs 1.27× the API spend or 1.27× the prefill FLOPs.
Compute actual task tokens by summing the inputs and outputs of every
model invocation, with cached-token accounting recorded separately:

\[\text{task\_input} = \sum_i \text{input}(call_i), \qquad \text{task\_output} = \sum_i \text{output}(call_i)\]

with \texttt{cached}, \texttt{uncached}, and \texttt{billed} token
quantities recorded separately (a prefix-cache hit means a call's input
is not re-processed from scratch, so billed/FLOP input differs from
context-carried input). \textbf{Boundary rule.} A call's \emph{input}
never contains \emph{its own} output tokens (a later call's input does
carry earlier calls' outputs and tool results --- which is exactly why Σ
per-call inputs double-counts carried context and exceeds the retained
12,095), so \texttt{task\_input} must sum per-call inputs only --- never
the ``Total tokens (incl.~300 output)'' column (10,365 / 11,230 / 12,095
/ 12,960 are \emph{retained context + final output}, i.e.~the α and Ch
17 KV quantities). The event-level ledger below derives
\texttt{task\_input}, \texttt{task\_output}, peak residency, and billed
tokens for the T = 3 trace under a stated cache policy.
Concurrency/queueing and economics follow the call-trace totals, not α.

\subsection{Tool-call latency budget}\label{tool-call-latency-budget}

Crucially, the agentic layer adds latency \textbf{on top of} the base
answer generation, not instead of it. We keep two terms rigidly
separate:

\begin{itemize}
\tightlist
\item
  \textbf{Base inference latency \emph{L}base} --- the time to generate
  the final answer itself. Under the canonical model this is
  \textasciitilde8.6 s: 1.08 s prefill (Ch 8) + \textasciitilde7.5 s
  decode of the 300-token answer at \textasciitilde25 ms/token (Ch 8).
  Every agentic request pays this at least once, and usually again for
  the intermediate reasoning the loop generates (the T·γ tokens).
\item
  \textbf{Agent orchestration / tool-call overhead \emph{L}agent} ---
  the per-turn cost of the loop \emph{around} the model: per-invocation
  orchestration overhead --- scheduling, KV-slot setup, kernel launch
  --- excluding model compute, plus the tool backend round-trip. On
  8×H100 the per-turn agent step averages \textasciitilde120 ms for a
  10,000-token context; tool backends (search, SQL) add 50--150 ms
  depending on data volume. So per-turn orchestration overhead
  \emph{L}agent ≈ 220 ms (median). The 120 ms is orchestration around
  the model, not model compute: at \textasciitilde25 ms/token it would
  buy under 5 tokens, while each turn's model work --- prefill of the
  grown prefix plus the 65-token \emph{γ} decode (\textasciitilde1.6 s)
  --- is counted in the full service time \emph{W} below, not in
  \emph{L}agent.
\end{itemize}

\[
L_\text{agent} = \lambda_\text{step} + \lambda_\text{tool}
\]

where \(\lambda_\text{step} \approx 120\) ms (per-invocation system
overhead --- scheduling, KV-cache slot allocation, kernel launch --- not
model FLOP time; the model's own per-turn work, prefill of the grown
prefix + decode of \emph{γ}, is carried inside \emph{W}, ≈ 3.0--3.1 s
marginal per turn) and \(\lambda_\text{tool} \approx 100\) ms (median,
tool backend). For \emph{T} turns the \textbf{added} orchestration
overhead is \(T\cdot L_\text{agent}\) ≈ 220 ms at the median \emph{T} =
1, ≈ 440 ms at the 90th percentile \emph{T} = 2, and ≈ 660 ms at the
95th-percentile \emph{T} = 3. These percentiles are conditional on a
completed agent run (the §7/§8 convention; see §8 for the turn
distribution). \emph{T} is capped at 3; the 2\% fallback adds zero turns
to this incremental expectation, and its failed-attempt work is counted
unconditionally in the §8 fallback ledger. These are the
\textbf{incremental agent-orchestration} numbers, not the full request
latency --- see the next section.

\subsection{Multi-step reasoning cost}\label{multi-step-reasoning-cost}

The ``cost'' of multi-step reasoning has two facets: token amplification
(already quantified as \emph{α}) and latency. The \textbf{incremental
added latency} --- the base generation plus the added orchestration
overhead --- is:

\[
L_\text{orch}(T) = L_\text{base} + T \cdot L_\text{agent}
\]

where \(L_\text{base} \approx 8.6\) s is the canonical full answer
generation (1.08 s prefill + 7.5 s decode of 300 output tokens) and
\(T \cdot L_\text{agent}\) is the added agent-orchestration overhead (≈
220 ms per turn). So the agentic layer does \emph{not} replace the
\textasciitilde8.6 s generation with \textasciitilde440 ms --- it
\emph{adds} a few hundred milliseconds of orchestration/tool overhead on
top of a request that already takes \textasciitilde8.6 s to generate its
answer.

\textbf{Scope note --- two different quantities, separated in \hyperref[tab:19.1]{Table 19-1}.} The \(L_\text{orch}(T)\) above holds the base generation at the
\emph{single-shot} decode (300 output tokens) and adds only the per-turn
orchestration overhead; it deliberately isolates \emph{how much the
agentic layer's orchestration adds}. The \textbf{full} agentic service
time --- the quantity used for fleet sizing in \hyperref[chap:17]{Chapter 17} --- must
additionally account for (a) the decode of the per-turn model-generated
reasoning tokens (\(\gamma \approx 65\) tokens/turn, at
\textasciitilde25 ms/token ≈ 1.6 s/turn) and (b) the prefill of every
call's input. A T-turn trace is \textbf{T+1 model invocations}, and
under the no-prefix-cache (no-reuse) policy each invocation re-reads the
grown prefix. The authoritative evaluator
(\texttt{render/agent\_trace.py}) therefore sums the prefill of
\textbf{all} calls, not just one:

\[
W(T) = \underbrace{\sum_{k=0}^{T} \tau_\text{prefill}\!\left(I_k\right)}_{\text{every invocation's prefill}} + 25\text{ ms/token}\cdot\big(O_\text{final} + T\cdot\gamma\big) + T\cdot\lambda_\text{tool/retr}
\]

where \(I_k = 9{,}200 + k(800+65)\) for call \(k\). The tool/retrieval
leg here uses \hyperref[chap:17]{Chapter 17}'s \textasciitilde133 ms/turn rate; the
chapter's own \(T\cdot L_\text{agent}\) (\textasciitilde220 ms/turn) is
the \emph{orchestration-only} incremental overhead, a different quantity
(see below). Under the \textbf{no-reuse} policy the T = 3 trace (inputs
9,200 + 10,065 + 10,930 + 11,795 = \textbf{41,990}) yields a prefill sum
of \((41{,}990 / 9{,}200)\times 1.08 \approx 4.93\) s (prefill time
taken as proportional to tokens --- case (i), linear-only, per Ch 22
\hyperref[tab:22.1]{Table 22-1}; the quadratic attention term adds +17.2\% at 9.2K under case
(ii) and grows with context, giving
\(W_\text{no-reuse}(3) \approx 18.68\) s under case (ii) and
\(\approx 18.19\) s under case (iii) rather than 17.70 s), so:

\[
W_\text{no-reuse}(3) = 4.93 + 12.375 + 0.399 \approx \mathbf{17.70\text{ s}}
\]

Under a \textbf{100\% prefix-reuse} policy only the incremental prefix
(9,200 + 3×800 = 11,600 --- the γ reasoning tokens were generated in the
prior call, so their KV already exists) is pre-filled, giving
\(W_\text{reuse}(3) \approx 14.14\) s. \textbf{W sums all four prefills;
a single-prefill approximation would omit three of them.} The two
scenarios are distinct lead calculations; the manuscript never
interpolates informally between them. The other columns, no-reuse:
\(W(0) = 8.58\) s, \(W(1) = 11.52\) s, \(W(2) = 14.56\) s,
\(W(4) = 20.95\) s; reuse: \(W(1) = 10.44\) s, \(W(2) = 12.30\) s,
\(W(4) = 16.02\) s. So: the \textbf{incremental orchestration overhead}
is \(T \cdot L_\text{agent}\) (\textasciitilde660 ms at T = 3,
\(\beta \approx 1.08\times\)), while the \textbf{full end-to-end service
time} of a no-reuse agentic request is \textasciitilde17.70 s at T = 3
(\textasciitilde14.16 s with prefix reuse) --- the two are
\emph{different quantities}, and the latter is what sets concurrency and
fleet size. They are also \textbf{not additive}:
\(T \cdot L_\text{agent}\) is this chapter's 220 ms/turn orchestration
budget (\(\lambda_\text{step} + \lambda_\text{tool}\)), whereas W's tool
leg is \hyperref[chap:17]{Chapter 17}'s \textasciitilde133 ms/turn tool/retrieval-only rate
(λ\_tool ≈ 100 ms is this chapter's median tool-backend round-trip,
50--150 ms; W's 133 ms is Ch 17 §8's mean tool+retrieval rate including
re-ranking) --- \hyperref[chap:17]{Chapter 17} §8 itself notes that a single model should
use one rate consistently --- and W already carries the per-turn model
work inside the γ decode. \hyperref[tab:19.1]{Table 19-1} therefore reports them as two
separate rows: \emph{Base + orchestration subtotal (Lbase + T·L\_agent)}
(\textasciitilde8.8 / \textasciitilde9.0 / \textasciitilde9.3 /
\textasciitilde9.5 s) and \emph{Full agentic service time W (Ch 17 §8)},
with the no-reuse / reuse columns given separately; the latter match
\hyperref[chap:17]{Chapter 17}'s fleet-sizing tables at the same T. The latency
amplification is better expressed as overhead, not a multiple of a
sub-second single-shot number:

\[
\beta(T) = \frac{L_\text{base} + T\cdot L_\text{agent}}{L_\text{base}} \approx 1 + \frac{T \cdot 220\text{ ms}}{8.6\text{ s}}
\]

At \emph{T} = 3, \(\beta(3)\) is 1 + 660 ms / 8.6 s ≈ \textbf{1.08×}:
the \textbf{orchestration-only} component adds \textasciitilde8\% ---
the agent loop is \emph{not} ``2--6× slower'' in the orchestration
sense. But \(\beta\) measures only the incremental orchestration
overhead, \textbf{not} the full task slowdown. The full service time of
a three-turn task grows from \textasciitilde8.6 s (single-shot) to
\textasciitilde17.70 s under no-reuse (\textasciitilde2.06×) once the
per-turn reasoning decode (\textasciitilde65 γ tokens/turn) and the
re-prefill of every grown turn are counted --- a full increase of
\textasciitilde9.1 s (to \textasciitilde14.16 s / \textasciitilde1.65×
with 100\% prefix reuse, a full increase of \textasciitilde5.6 s). So
\(\beta\) is \(\beta_\text{orch}\) (orchestration-only), and the true
task-level multiplier is
\(L_\text{task E2E}/L_\text{base} \approx 2.06×\) (no-reuse) at \emph{T}
= 3 (\textasciitilde1.65× with prefix reuse). The bound that actually
matters: the \emph{added} orchestration overhead is \textasciitilde220
ms per turn (budget it), while fleet sizing follows the \emph{total}
request time --- the \textasciitilde17.70 s no-reuse full service time,
not the \textasciitilde8.6 s single-shot generation.

These derived quantities give the architect concrete numbers to set
policies: cap \emph{T} at 3 unless the quality gain is statistically
significant, and allocate \textasciitilde220 ms \emph{per turn} in the
orchestration-latency budget.

\subsection{Internal depth, agent turns, and training
rollouts}\label{internal-depth-agent-turns-and-training-rollouts}

An internal depth iteration is not an agent turn. A recurrent model can
repeat an internal block within one model invocation without emitting a
tool call. An agent turn can contain prefill, internal computation,
output generation, and tool interaction. A training rollout is a third
object: a trajectory collected for the training procedure, not a
request-time turn budget. This distinction prevents a training method or
internal execution setting from being mistaken for the orchestration
trace that the fleet must serve.\footnote{Geiping et al., \emph{Scaling
  up Test-Time Compute with Latent Reasoning: A Recurrent Depth
  Approach}, arXiv:2502.05171v2, 17 February 2025,
  \url{https://arxiv.org/abs/2502.05171v2}; Ornith Team,
  \emph{Ornith-1.5: From Self-Scaffolding to Self-Improvement}, August
  2026, \url{https://ornith.ai/ornith_1_5.html}. These primary accounts
  distinguish recurrent internal computation and training trajectories;
  neither establishes the request-time turn count of the book's
  hypothetical agent; pass@k itself is defined in Chen et al.,
  \emph{Evaluating Large Language Models Trained on Code},
  arXiv:2107.03374 (2021). Sources inspected 28 October 2026 as part of
  the separately dated addendum, not a refresh of the August comparison
  tables.}

\textbf{Sidebar --- model qualification (evaluation detail; cf.~the
book's model-selection chapter).} Model qualification records the
benchmark harness, context policy, reasoning effort, sampling settings,
and success metric with the model revision. A best-of-several-trials
result is not interchangeable with pass-at-one. Averaging independent
single-attempt success indicators can estimate pass-at-one only under
the declared sampling and task protocol. An advertised context window
does not establish useful long-context quality, target concurrency, or
the cost of serving it. The deployment decision follows measured task
success, invocation traces, and SLO-goodput, not a model-family label
alone. §6's p\_success must be measured under the declared qualification
protocol.

\ntsection{Common Mistakes}\label{common-mistakes}


\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\item
  \textbf{Unbounded or miscalibrated turn limits.} Setting the maximum
  number of agent turns too high for the task leads to runaway token
  consumption and latency spikes. A poorly scoped tool can let a model
  loop until token or deadline limits stop the request. \mbox{{[}HYPOTHESIS{]}}
  The right cap is task-calibrated: measure the distribution of useful
  completion turns, loop-failure turns, and marginal value per turn for
  the workload, then set the cap where marginal value drops off (the
  canonical policy caps at 3, with a 2\% fallback to single-shot --- §4,
  §8); the number is a policy parameter, not a constant.
\item
  \textbf{Neglecting token accounting per turn.} Many architects track
  only the initial input tokens and forget that each retrieval or tool
  call adds context that persists for all subsequent turns. Turn
  \emph{T} therefore sees an input base that grows linearly with
  \emph{T}. Concretely the append-only total is I₀ + T·δ + T·γ +
  O\_final = 9,200 + 800T + 65T + 300, which at 2.62 MB/token takes FP16
  KV from 24.9 GB (single-shot, 9,500 tokens) to 34.0 GB (four turns,
  12,960 tokens).
\item
  \textbf{Overlooking tool latency variance.} A tool that typically
  responds in 30\,ms may, under cache misses or lock contention, take
  2\,s. Without a timeout and fallback, the entire agent loop blocks.
  Always instrument timeouts and provide a ``best-effort'' fallback
  path.
\item
  \textbf{Confusing `agentic' with `more prompts'.} Adding extra prompts
  without a structured loop (Plan/Execute/Observe/Decide) does not give
  the model reasoning power; it just inflates token count. The agentic
  value comes from the model's ability to reinterpret prior observations
  and decide the next action.
\item
  \textbf{Skipping guardrails.} Without pre-call validation (e.g., query
  sanitization, budget checks) and post-call verification (answer
  relevance, hallucination detection), agentic systems can produce
  plausible but incorrect or unsafe outputs. Guardrails are not optional
  --- they are the safety net that makes \emph{bounded} loops safe in
  production. A production agent needs explicit termination, budget,
  recovery, and escalation policies: hard turn/token/cost/wall-time
  limits, tool timeouts, cancellation, idempotency/retry discipline,
  state checkpointing, and human escalation. A logical multi-step task
  may be resumed across bounded execution windows rather than granted
  unlimited resources --- guardrails make the loop \emph{safe}, not
  \emph{unbounded}.
\end{enumerate}

\ntsection{Architecture Consequence}\label{architecture-consequence}


Introducing an agentic layer reshapes the system architecture in seven
ways:

\textbf{State-management policy sets the trajectory.} Before quantifying
context/KV growth, the architect must decide the \emph{state-management
policy}, because that policy --- not the model --- determines whether
context grows unbounded. The quantitative path that follows (\hyperref[fig:19.2]{Fig 19.2})
uses an \textbf{append-only bounding case} with this exact retention
policy: (i) the initial prompt is retained in full; (ii) each turn's
tool outputs are retained in full (not externalized); (iii) the model's
per-turn reasoning tokens are visible and retained in the context (not
hidden); (iv) no prefix cache is assumed to be reused across turns (each
turn's request is rebuilt from the full accumulated context); (v) no
truncation or compaction is applied. Under that policy the context is
only ever appended and never evicted, so it is the worst case --- a
deliberate upper bound, not the deployed design. Two token counts must
be kept distinct: the \textbf{billable tokens} (what the API charges, =
Σ over turns of the full accumulated context each turn sends --- 41,990
input tokens for the T = 3 no-reuse trace of §4, not the single final
context of 12,095) and the \textbf{KV-resident tokens} (what occupies
the cache, = the same accumulated context under this no-reuse policy);
the two differ by the Σ-per-call vs peak-resident distinction even
without caching; prefix caching additionally lowers the billable count
while the KV-resident count stays. The durable architectural lesson is
that the growth rate is set by the policy levers --- summarization
(compress the accumulated history each turn), truncation (drop the
oldest context beyond a budget), externalized tool state (store
retrieval results out-of-band rather than in-context), replay policy
(re-derive rather than retain), and cache policy (prefix caching, KV
precision). A design that applies these levers can hold context roughly
flat while an append-only design grows it \textasciitilde36\% by turn 4;
the append-only number is the \emph{stress case} that bounds what the
system must tolerate if the levers fail, not the expected operating
point. \hyperref[fig:19.3]{Fig 19.3} then compares that bounding case with the compaction and
cache-policy levers named above and shows that they move different
\emph{quantities}, not different amounts of the same one.

\textbf{Inference scaling.} The base model (70B FP16, 8×H100) must now
serve variable-length contexts, and --- critically --- the KV-residency
conclusion is far more severe than a per-latency convenience because the
canonical per-token KV is \textasciitilde2.62 MB/token (\hyperref[chap:7]{Chapter 7}'s
full-MHA reference geometry). A request that triggers 4 agent turns
carries \textasciitilde12,960 tokens vs.~9,500 for single-shot (\hyperref[tab:19.1]{Table 19-1}) --- that is not a ``35\% GPU memory'' tweak but a move from
\textasciitilde24.9 GB KV per request (9,500 tokens × 2.62 MB) to
\textasciitilde34.0 GB (12,960 ×2.62 MB) --- roughly a 36\% growth, on
top of an already-large KV footprint. At the canonical workload's
\textasciitilde86 average in-flight requests at 10 rps
(\(L_{\mathrm{exec}}\) = λ × \(W_{\mathrm{exec}}\) ≈ 10 × 8.6 per Ch 4;
distinct from the \textasciitilde100 \emph{active-user} population) with
the median single-turn profile (\textasciitilde27.2 GB/request at 10,365
tokens), using the base-system in-flight count (86 = 10 × 8.6, Ch 4) as
a lower bound --- the agentic T = 1 service time \emph{W} ≈ 11.52 s
would raise in-flight to \textasciitilde115 and aggregate KV to
\textasciitilde3.1 TB --- the aggregate KV alone is already
\textasciitilde86 × 27.2 GB ≈ 2.3 TB --- far beyond one host's
\textasciitilde436 GB KV budget, so \textbf{agents do not just stress
memory, they force a fleet} (\hyperref[chap:17]{Chapter 17}). The architect must therefore
treat context growth as a first-order capacity driver: cap \emph{T},
cache prefixes, or quantize KV (FP8), as these levers can repeatedly
beat adding hosts on price --- each relaxes the KV-capacity ceiling
without commissioning new hardware (see Ch 25 §8 for the FP8 KV
arithmetic: 436 GB ÷ 12.45 GB ≈ 35 concurrent vs 17.5 at FP16). Note we
must be precise: the per-request KV is set by the model's canonical
per-token KV (all layers), not by per-layer figures; the honest number
is tens of GB per request, which is exactly why agentic depth is a
fleet-sizing problem. Agentic traffic is structurally more prefill-heavy
--- the prefill/decode ratio rises from ≈0.14 single-shot to ≈0.40 at
T=3 (1 → T+1 = 4 prefills per request) --- so chunked prefill, prefix
caching and prefill/decode scheduling that were optional for single-shot
traffic become first-order here (see Chs. 10/15).

\textbf{Three policies, three different levers.} The append-only bar is
the \emph{stress case} of \hyperref[fig:19.2]{Fig 19.2} --- nothing is evicted, so the
footprint grows \textasciitilde36\% by turn 4 (24.9 → 34.0 GB), driven
purely by cumulative context, not by extra requests. Compaction
(summarize or truncate the accumulated history each turn) moves the
\emph{footprint} itself and can hold it roughly flat. Prefix-cache
eviction moves neither: the request still carries the full accumulated
context (34.0 GB at turn 4), so its own KV is unchanged --- what changes
is the reusable cached prefix, which is freed and must be re-prefilled
on the next turn. Billable tokens and KV-resident tokens therefore
diverge as soon as a prefix cache is in play (the distinction drawn
above). Only the append-only number is derived here; the two policy bars
are qualitative \mbox{{[}ILLUSTRATIVE{]}}.

\textbf{Task economics.} The deepest shift an agentic workload imposes
is a change in \emph{what the architect optimizes}. For conventional
inference, the unit of cost is the token: the architect optimizes token
economics --- cost per token, latency per token, KV per token. For an
agentic system, the unit of value is the \emph{task}: the architect
optimizes task economics, because a task consumes a variable,
data-dependent number of model calls, tool calls, and tokens, and may
fail. The right denominator is therefore \textbf{cost per successful
task}, not cost per token:

\[
\text{cost per successful task} \approx \frac{\begin{aligned}
&\text{model calls/task} \times (\text{input tokens/call} \times \$/\text{in token} + \text{output tokens/call} \times \$/\text{out token} + \text{cached tokens/call} \times \$/\text{cached token}) \\
&{}+ \text{tool calls/task} \times \$/\text{tool} \\
&{}+ \text{retries/task} \times \text{cost/retry}
\end{aligned}}{p_{\text{success}}}
\]

where \(p_\text{success} > 0\) is the task success rate and the input
tokens billed across the task's calls are the execution-trace totals ---
Σ per-call input + output tokens (41,990 + 495 uncached, §4 ledger) ---
not the agentic factor \emph{α} from Section 4, which is only the
retained-context ratio (cumulative-context total vs the single-shot
equivalent; billed ≈ 4.47× vs α = 1.27×). Two consequences follow.
First, a more expensive model that completes tasks in one turn can be
cheaper \emph{per successful task} than a cheap model that needs three
turns --- the amplification term can dominate the base price. Second,
the success rate is as important as the unit cost: a 10\% cheaper
pipeline that fails 5\% more often can be net more expensive once
retries and human intervention are counted. This is a genuinely
different objective from \emph{cheapest tokens}, and it is why agentic
workloads cannot be priced or capacity-planned with the single-shot
token arithmetic alone. An architect should instrument tasks (success,
turns, calls, retries) and optimize cost per successful task, exactly as
an architect of a deterministic service optimizes cost per completed
request.

\textbf{Tool backend provisioning.} Search indexes, SQL pools, and code
interpreters become first-class infrastructure components. Their
capacity (concurrent queries, connection pool size, query throughput)
must be dimensioned alongside the LLM GPU pool. A bottleneck in the tool
backend will manifest as increased \(\lambda_\text{tool}\), which
directly inflates the per-turn latency \emph{L} and therefore the
overall request latency.

\textbf{Observability requirements.} Each turn generates a tuple of
(turn number, model input tokens, tool call, tool latency, tool output
tokens, decision). Correlating these tuples across turns for a single
request, and across requests for the fleet, requires structured logging
and tracing. Without it, debugging why a request took
\textasciitilde9\,s and consumed 15,000 tokens is nearly impossible.

\textbf{Fallback \& degradation pathways.} Because the agentic layer
introduces data-dependent depth, the system must have graceful
degradation: if the turn limit is reached, return the best partial
answer so far, or fall back to a simpler single-shot prompt. This
preserves user experience even when the agent fails to converge.

\ntsection{What We Still Don't Know}\label{what-we-still-dont-know}


Despite the quantified arithmetic above, several questions remain open
and would benefit from targeted research:

\begin{itemize}
\tightlist
\item
  \textbf{Turn-count distribution shift with model scale.} Do larger
  models (e.g., a 405B FP16 model) exhibit different \emph{T}
  distributions? Does the ability to ``see more'' reduce the need for
  multi-step loops, or does the model reason more deeply and actually
  increase \emph{T}?
\item
  \textbf{Token amplification vs.~answer quality curve.} We can compute
  \emph{α(T)} from the illustrative token counts, but we have not firmly
  established the marginal quality gain per additional turn. Is the
  1.27× → 1.36× move from \emph{T} = 3 to \emph{T} = 4 worth the 7\%
  token increase? A/B tests across query categories would help.
\item
  \textbf{Latency tail under spike load.} Our 95th-percentile
  \emph{added} orchestration latency of \textasciitilde660\,ms (T = 3,
  the scenario turn cap; conditional on a completed agent run, with the
  fallback-inclusive ledger in §8 giving the same p95 but p99 = 860 ms)
  assumes GPU inference time is constant. Under traffic spikes, GPU
  saturation can increase inference latency non-linearly. Empirical
  measurement under controlled load is needed to validate the linear
  \emph{T·L} model.
\item
  \textbf{Optimal tool design for minimal turn count.} Some tools could
  return more comprehensive results in a single call, reducing the need
  for multiple rounds. The design space of ``rich vs.~narrow'' tools and
  its impact on \emph{T} is underexplored.
\item
  \textbf{Cross-user context caching.} If many users ask related
  questions (e.g., ``What does the policy say about X?''), can we cache
  intermediate retrieval results and avoid redundant tool calls? The
  savings could be substantial but require careful invalidation logic.
\end{itemize}

\section{End-of-Chapter Mini-Case: Agentic Turn Distribution and KV
Growth}\label{end-of-chapter-mini-case-agentic-turn-distribution-and-kv-growth}

\textbf{Scenario.} An enterprise RQA system serves 2,000 knowledge
workers. The baseline single-shot configuration uses a 70B FP16 model on
8×H100, with 9,200 input tokens and 300 output tokens, at 10 rps average
/ 40 rps peak. The team introduces an agentic layer with a maximum of 3
turns, using the chapter's per-turn convention (δ≈800 + γ≈65 ≈ 865
tokens/turn). The guardrail budget caps total input at 13,000 tokens ---
a safety margin above the append-only worst case (12,660 at T = 4, \hyperref[tab:19.1]{Table 19-1}), so the turn cap binds before the guardrail does.

\textbf{Measurement results.} The scenario's 30-day telemetry shows
\mbox{{[}ILLUSTRATIVE{]}}\hspace{0pt}\mbox{{[}ASSUMPTION{]}} --- the same turn distribution §4
labels illustrative, here as scenario data rather than a reported
production trace:

\begin{itemize}
\tightlist
\item
  68\% of requests terminate in 1 turn
\item
  25\% terminate in 2 turns
\item
  5\% terminate in 3 turns
\item
  2\% exceed the turn limit and fall back to single-shot
\end{itemize}

\textbf{Token and latency impact (added orchestration overhead).} Using
the chapter's per-turn convention (each turn adds δ=800 retrieved + γ=65
reasoning = 865 tokens), and treating the 2\% fallback as single-shot
(zero added turns \emph{for this retained-context expectation} --- its
failed-attempt work is counted unconditionally in the fallback ledger
below), the expected input tokens across the distribution are:

\begin{itemize}
\tightlist
\item
  Expected input tokens: 0.68×(9,200+865) + 0.25×(9,200+1,730) +
  0.05×(9,200+2,595) + 0.02×9,200 ≈ 6,844 + 2,733 + 590 + 184 ≈
  \textbf{10,350 tokens} (expected total incl.~300-token output ≈
  10,650).
\item
  Amplification \emph{α}: 10,650 / 9,500 ≈ \textbf{1.12×} --- about a
  \textbf{12\%} token overhead. (The 2\% fallback is explicitly included
  here at zero added turns: it adds no \emph{retained} agent tokens, so
  its contribution to this expectation is 2\% × 0 = 0, which the
  weighted sum above keeps. This expectation is over \emph{retained
  context}; the fallback's failed-attempt tokens are counted in the
  unconditional ledger below.) These §8 expectation totals (10,350 /
  10,650 / 1.12×) coincidentally equal the §3 hand-trace totals; one is
  an expectation over the turn distribution, the other a single trace
  --- different objects.
\item
  \textbf{Conditional completed-agent percentiles (explicit label).}
  Added agent-orchestration overhead (per-turn step + tool) is 220
  ms/turn. Because 68\% terminate in one turn, the \textbf{median turns
  is T = 1}, so the median added overhead is \textbf{1 × 220 ms ≈ 220
  ms}; the \textbf{90th-percentile} is T = 2 (conditional cumulative
  \textbf{94.9\%} by T ≤ 2) → \textbf{440 ms}; and the
  \textbf{95th-percentile} is T = 3 (conditional cumulative 100\% by T ≤
  3) → \textbf{660 ms} --- \emph{not} T ≈ 4, since the scenario caps
  turns at 3 and the 2\% fallback is modeled as an immediate single-shot
  fallback, not a fourth attempted turn. \textbf{Percentile
  conditioning:} these percentiles are computed over the
  \textbf{non-fallback (completed-turn) request distribution} --- they
  are \emph{conditional on a completed agent run} (98\% of requests;
  renormalized cumulative 69.4\% by T ≤ 1, 94.9\% by T ≤ 2, 100\% by T ≤
  3), so the conditional p50/p90/p95 = \textbf{220 / 440 / 660 ms} with
  mean ≈ \textbf{299 ms} and a maximum of 660 ms. Under this convention
  the 2\% fallback is a high-tail/failure category that incurs
  \emph{zero added turns} (single-shot) --- the \emph{incremental} agent

\textbf{Architectural actions.} The team sets the turn limit to 3,
instruments each turn's token and orchestration latency, adds a context
cache for the search tool, and adds prefix caching (or compaction) for
the grown prefix --- billed 4.47× → ≈1.29× and W 17.70 s → 14.16 s at
100\% reuse, KV residency unchanged. With a cache hit rate of 30\% on
recurring queries, the \emph{newly-fetched} portion of δ drops to
\textasciitilde560 tokens per turn (70\% of 800; the cached 30\% is not
re-fetched) --- a 30\% cut in retrieval re-fetch transport.
\textbf{Note:} the \emph{retained} context still carries the full 800
tokens per turn (cached or not), so absent a concrete context-reduction
policy this cache yields no LLM-token or KV-resident saving; the
re-fetch cost and the KV-resident length are distinct (see the
billable-vs-KV-resident distinction in §6). The median added
orchestration overhead is still T = 1 → \textasciitilde220 ms. The claim
``meets an SLA of \textless1 s'' must be scoped carefully: the
\emph{added agent-orchestration} latency is comfortably under 1 s, but
the \textbf{end-to-end} request is \textasciitilde9 s because of the
base generation. The architect therefore scopes the \textless1 s SLA to
orchestration overhead \emph{excluding} final generation, and treats
end-to-end as bounded by the \textasciitilde8.6 s base generation in the
incremental view (or by the full service time \emph{W} ≈ 11.5 s at the
median T = 1 in the fleet-sizing view).

\textbf{Lesson.} The agentic layer had three distinct token effects that
must be labeled separately: (a) \textbf{retained-context length} grows
\textasciitilde12\% \textbf{distribution-weighted} (α = 1.12×, from the
expected 10,650 / 9,500 --- this is a weighted expectation over the §8
turn distribution; the per-turn α values are 1.09× at T=1, 1.18× at T=2,
1.27× at T=3, 1.36× at T=4) --- this is \emph{context}, not processed or
billed tokens; (b) \textbf{processed model tokens} across all
invocations grow \textasciitilde152\% per submitted request (2.52×, from
the distribution-weighted 100-request ledger: 23,927 / 9,500), because
in this no-prefix-reuse request mix the model re-reads the grown prefix
on each call; (c) \textbf{billed spend} depends on the prefix-cache
policy and provider rates --- under 100\% prefix reuse only the
incremental prefix is billed, under no-reuse all of it is. It added, at
the median T = 1, \textasciitilde220 ms of orchestration latency (on top
of an \textasciitilde8.6 s base generation), but improved answer
correctness on multi-step reasoning queries by an estimated 22\% in an
illustrative human-eval reading \mbox{{[}ILLUSTRATIVE{]}} scenario result, not
a reported production measurement. The trade-off was acceptable on the
modeled terms --- full service time rises from \textasciitilde8.6 s to
W(1) ≈ 11.52 s (+34\%) and processed tokens to 2.52×, against an
estimated +22\% correctness \mbox{{[}ILLUSTRATIVE{]}}; judged on orchestration
overhead alone (220 ms) it would look far cheaper than it is; the
verdict is against cost per successful task (§6), not the
\textasciitilde220 ms orchestration overhead --- and context caching cut
the retrieval re-fetch cost (transport only --- the retained context is
unchanged). The architect's key decisions were: (a) capping turns at 3,
(b) adding a search cache, and (c) providing a single-shot fallback when
the limit is hit. \textbf{Do not quote the \textasciitilde12\%
retained-context growth as a \textasciitilde12\% compute/cost increase}
--- the processed-token multiplier is \textasciitilde2.52× in this
no-reuse mix.
