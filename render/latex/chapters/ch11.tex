Serving is a small set of composable mechanisms --- continuous batching,
paged/blocked KV cache, prefix caching, and prefill/decode
disaggregation --- that turn a static in-memory model into a live
multi-request system. The architecture choices that matter are which of
these are adopted and how they share the host's KV budget, because the
latency SLO is met by the batch and cache strategy rather than by the
model alone.

\section*{The Architect's Question}\label{the-architects-question}

After this chapter we should be able to answer the operational half of
deployment: \emph{the model is in memory and the requests are arriving
at \textasciitilde10 per second --- how do we actually serve them
without violating our latency SLO?} We will develop the serving
mechanisms that turn a static model into a live, multi-request system:
how requests are batched, how KV cache memory is managed, how repeated
prefixes are reused, and when to split prefill from decode onto separate
pools. After this chapter, serving is not a black box --- it is a
sequence of explicit architectural choices, each with a measurable
consequence.

\ntsection{Concept}\label{concept}


Serving is a small set of mechanisms, invented roughly in order:

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\item
  \textbf{Batching} --- running multiple requests through the model
  together to amortize the weight reads. The key modern advance is
  \textbf{continuous (iteration-level) batching} introduced by
  \textbf{Orca (OSDI 2022)}: instead of waiting for an entire batch to
  finish, the scheduler admits and evicts requests at every decoding
  step, filling the GPU's idle slots as soon as they free up.
  \mbox{{[}S1{]}}\hspace{0pt}\mbox{{[}1P{]}}
\item
  \textbf{PagedAttention / vLLM (SOSP 2023)} --- managing the KV cache
  in fixed-size blocks (like a virtual-memory page table) so that
  different requests' KV caches no longer need contiguous memory,
  slashing fragmentation and letting the serving engine pack far more
  concurrent requests. \mbox{{[}S2{]}}\hspace{0pt}\mbox{{[}1P{]}}
\item
  \textbf{Prefix caching} --- recognizing that many requests share
  context (e.g.~the same retrieved documents), and caching the KV of the
  common prefix so a new request does not re-prefill it.
  \textbf{RadixAttention (SGLang)} and \textbf{Automatic Prefix Caching
  (vLLM APC)} are the canonical implementations. \mbox{{[}S3{]}}\hspace{0pt}\mbox{{[}1P{]}}
\item
  \textbf{P/D disaggregation} --- splitting the compute-bound
  \emph{prefill} stage from the bandwidth-bound \emph{decode} stage onto
  separate pools, because they bottleneck on different resources.
  Pioneered by \textbf{Splitwise (ISCA 2024)} and \textbf{DistServe
  (OSDI 2024)}; \textbf{Mooncake} takes the KV-centric view,
  transferring KV caches from the prefill pool to the decode pool (with
  CPU/DRAM/SSD offload) and reports up to \textbf{525\% throughput lift}
  in long-context simulation and \textbf{75\% more requests} on a real
  Kimi workload. \mbox{{[}S4{]}}\hspace{0pt}\mbox{{[}1P{]}}
\end{enumerate}

These mechanisms compose: continuous batching is the baseline,
PagedAttention makes it memory-efficient, prefix caching makes it
cheaper, and P/D disaggregation makes it scale.

\ntsection{Mental Model}\label{mental-model}


Serving is \textbf{managing three precious resources against a stream of
arrivals}: GPU compute (FLOPs, bound in prefill), GPU memory bandwidth
(HBM, bound in decode), and GPU memory capacity (HBM bytes, bound by KV
cache). Each mechanism trades one of these:

\begin{itemize}
\tightlist
\item
  \textbf{Batching} improves compute and bandwidth utilization by
  amortizing the fixed per-step weight reads across more requests.
\item
  \textbf{PagedAttention} improves memory capacity by eliminating KV
  fragmentation.
\item
  \textbf{Prefix caching} reduces memory capacity and prefill compute by
  reusing already-computed KV.
\item
  \textbf{P/D disaggregation} lets the prefill pool run at high compute
  utilization and the decode pool at high bandwidth utilization
  simultaneously, instead of one pool being starved.
\end{itemize}

The mental model is a \textbf{resource budget}: a request arrives,
consumes some FLOPs (prefill), some bandwidth (decode), and some memory
(its KV cache) for its lifetime. Serving architecture is about sizing
and scheduling those three budgets so the SLO holds across the burst.

\ntsection{Worked Example}\label{worked-example}


\subsection{The Canonical Workload in a Serving
System}\label{the-canonical-workload-in-a-serving-system}

Recall the canonical enterprise-Q\&A RAG workload (Ch 4, \hyperref[tab:4.2]{Table 4-2}):
\textasciitilde10 rps average, \textasciitilde40 rps peak; each request
carries \textasciitilde9,200 input tokens and \textasciitilde300 output
tokens; TTFT budget 1.2 s, TPOT \textasciitilde25 ms/token.
\mbox{{[}ASSUMPTION{]}}

\subsection{Discrete Batching Wastes the
GPU}\label{discrete-batching-wastes-the-gpu}

Naive \textbf{discrete (static) batching} accumulates requests until a
batch fills, then runs them to completion, then starts the next batch.
Problems compound at this workload's 9.2K-input shape:

\begin{itemize}
\tightlist
\item
  Requests arrive in \emph{bursts} (recall the \textasciitilde40 rps
  peak). Discrete batching forces early-arriving requests to
  \textbf{wait} for the batch to fill, inflating TTFT toward the 2 s SLO
  breach.
\item
  The batch is locked until its \emph{slowest} member finishes
  (fits-all-in-one-run), so a short 100-token output tails behind the
  longest while the GPU finishes the whole batch --- idle bubbles at the
  end of every batch.
\item
  Batch boundaries create periods where the GPU drains (no work) then
  floods --- utilization is spiky around the mean.
  \mbox{{[}ILLUSTRATIVE{]}}\hspace{0pt}\mbox{{[}DERIVED{]}}
\end{itemize}

\subsection{Continuous Batching Fills the
Bubbles}\label{continuous-batching-fills-the-bubbles}

\textbf{Continuous batching (Orca \mbox{{[}S1{]}}\hspace{0pt}\mbox{{[}1P{]}})} eliminates the
batch boundary: at every decode step the scheduler accepts any new
prefill-ready request and evicts any finished one, so decode slots never
sit idle. In the canonical stream, a 300-token decode at
\textasciitilde25 ms/token occupies a slot for \textasciitilde7.5 s;
while a long decode runs, the freed FLOPs are continuously refilled by
new short requests. The utilization gain is the difference between spiky
discrete batches and a continuously-fed pipeline. Rather than stipulate
a single percent, the mechanism makes the GPU the steady bottleneck
instead of the scheduler. \mbox{{[}ILLUSTRATIVE{]}}\hspace{0pt}\mbox{{[}DERIVED{]}}

Tax}\label{pagedattention-killing-the-fragmentation-tax}

In re-packaged (naive) serving, each request's KV cache for 9.2K input
is \textasciitilde24.1 GB (FP16, \textasciitilde2.62 MB/token × 9,200,
initial KV) \mbox{{[}ILLUSTRATIVE{]}}\hspace{0pt}\mbox{{[}DERIVED{]}}. If served contiguously,
variable-length completions leave fragmented, unusable holes --- exactly
like a fragmented heap. \textbf{PagedAttention/vLLM \mbox{{[}S2{]}}\hspace{0pt}\mbox{{[}1P{]}}}
allocates KV in fixed blocks shared and evicted like page frames, so the
\textasciitilde24.1 GB per request is packed densely and more concurrent
requests fit in the same 640 GB node \mbox{{[}ILLUSTRATIVE{]}}\hspace{0pt}\mbox{{[}DERIVED{]}}.
The win is \emph{more concurrency under the same SLO}, not faster
single-request math.

\subsection{Prefix Caching: Don't Re-Prefill the Same
Documents}\label{prefix-caching-dont-re-prefill-the-same-documents}

The RAG request's 8K retrieved-context tokens are largely shared across
queries (same documents). Without caching, every request re-runs the
\textasciitilde1.29 PFLOP prefill for those 8K tokens
\mbox{{[}ILLUSTRATIVE{]}}\hspace{0pt}\mbox{{[}DERIVED{]}}. \textbf{RadixAttention / APC
\mbox{{[}S3{]}}\hspace{0pt}\mbox{{[}1P{]}}} caches the KV of common prefixes, so a new request
reuses the shared-document KV and prefills only the unique query tail
--- cutting the dominant prefill FLOPs and TTFT for repeated-context
traffic \mbox{{[}ILLUSTRATIVE{]}}\hspace{0pt}\mbox{{[}DERIVED{]}}. \emph{Layout caveat:} this
reuse requires the shared documents to sit at a \textbf{fixed prefix
position} in the prompt (e.g.~system prompt → retrieved documents →
unique query tail). If the unique query precedes the documents, the
causal K/V of the document span differs per query and no prefix is
reusable --- the savings above assume the documents-then-query layout,
which the architect must verify in the actual prompt template.

Prefix reuse is also only one of the state-preservation requirements a
serving system must meet: preemption, speculative rollback, and
adaptive-depth execution all constrain what a cache may evict or reuse
--- see the serving qualification in §4.

\subsection{When to Disaggregate: Prefill and Decode Want Different
Pools}\label{when-to-disaggregate-prefill-and-decode-want-different-pools}

Recall from Ch2/Ch6: prefill is \textbf{compute-bound}
(\textasciitilde1.29 PFLOP → \textasciitilde1.19 PFLOPS required vs
0.989 PFLOPS peak), decode is \textbf{bandwidth-bound} (the whole-model
weight-read rate of \textasciitilde5.6 TB/s if served by one device vs
3.35 TB/s per GPU; under the canonical 8×H100 host it is sharded to
\textasciitilde0.70 TB/s per GPU, and the shard-invariant cause is the
low \textasciitilde1.0 FLOP/byte intensity, Ch 6) \mbox{{[}1P{]}}\hspace{0pt}\mbox{{[}DERIVED{]}}.
Serving both from one pool forces a compromise: batch for prefill and it
slows decode; optimize for decode and prefill starves. \textbf{P/D
disaggregation (Splitwise/DistServe/Mooncake \mbox{{[}S4{]}}\hspace{0pt}\mbox{{[}1P{]}})} runs
prefill nodes at high FLOP-utilization and decode nodes at high
bandwidth-utilization, transferring KV across via the fabric
(\textbf{\hyperref[fig:11.3]{Fig 11.3}} shows the two-pool topology and what moves between
them). Mooncake's reported up to 525\% long-context throughput and +75\%
request count are the quantitative anchor \mbox{{[}S4{]}}\hspace{0pt}\mbox{{[}1P{]}}. For the
canonical single-host (\textasciitilde10 rps) this disaggregation is
premature; it pays off only when the workload outgrows a node and the
two phases' resource conflicts become binding.

The state crossing between prefill and decode pools is a different
communication object from a TP activation reduction. Its endpoints,
ownership, block layout, and transfer frequency must be stated
independently. A KV-transfer path may use point-to-point or specialized
transfer facilities rather than a group collective. The service budget
includes transfer and orchestration on the request's critical path; it
does not count a whole KV cache again on every ordinary decode step. Ch
9 provides the directional byte convention; this chapter determines when
moving ownership is worthwhile.

\ntsection{Measurement}\label{measurement}


Good serving telemetry answers ``are we meeting the SLO while keeping
the GPU busy?'':

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\item
  \textbf{Measure goodput, not raw throughput} --- tokens/s that arrive
  before their SLO deadline (Ch6). Continuous batching is only a win if
  it raises goodput.
\item
  \textbf{Measure KV utilization} --- fraction of the 640 GB node memory
  consumed by live KV vs weights. PagedAttention and prefix caching both
  raise the effective KV packing; track it.
\item
  \textbf{Measure prefill-vs-decode utilization separately} --- a
  FLOP-bound prefill core and a bandwidth-bound decode core running on
  one pool tells us when to disaggregate.
\item
  \textbf{Measure the scheduler's real occupancy} --- idle decode slots,
  queue wait, and the tail of TTFT under load, not the average.
\end{enumerate}

\subsection{Serving qualification: model support is not serving
capability}\label{serving-qualification-model-support-is-not-serving-capability}

Model support is not a complete serving capability. A hybrid model can
require both paged history and bounded recurrent state. A looped-depth
model can require iteration-specific caches. Prefix reuse, preemption,
and speculative rollback must preserve the state that the next execution
actually consumes. An early-exit interface also needs a runtime path
that avoids the skipped work, rather than selecting logits after all
work has already run. A capability record can therefore identify the
exact model revision, engine revision, state representation, cache
policy, precision, and supported execution paths; kernel or module
speedups remain separate from end-to-end goodput at the service SLO.
\mbox{{[}DERIVED{]}}

Adaptive depth changes the scheduler's unit of work. Requests that exit
at different iterations can leave an initially uniform batch with
different amounts of remaining computation. A runtime may compact active
requests or group them by depth, but compaction, cache indexing, and
synchronization consume resources. Padding every request to the deepest
active iteration can preserve batching convenience while eliminating the
hoped-for arithmetic saving. These are alternative implementation
choices, not measured features. \mbox{{[}DERIVED{]}}

Latency evaluation must retain the depth distribution. Average passes
per token does not determine p95 token latency: difficult tokens, long
histories, and queueing can coincide. A comparison therefore fixes the
prompt population, output length, quality criterion, and SLO, then
records actual pass counts, state allocation, and elapsed time by phase.
When prefill and decode use different cache policies, one aggregate
cache-reduction factor hides the capacity bottleneck. \mbox{{[}DERIVED{]}}

The economic denominator is completed, quality-compliant work within the
service target. A reduced core-work budget is useful only if it
increases that useful output or lowers the resources required to produce
it. Routing a difficult request to more depth can be rational even when
its per-token cost rises. Conversely, premature exits that can require
retries can raise task cost despite shorter first attempts. A
training-time self-improvement loop and an inference-time depth loop are
different mechanisms; sharing the word ``iteration'' assigns no
inference-time saving to either. \mbox{{[}DERIVED{]}}

\ntsection{Common Mistakes}\label{common-mistakes}


\begin{itemize}
\item
  \textbf{Assuming bigger batches always help.} Bigger discrete batches
  raise raw tokens/s but push TTFT past the SLO, zeroing goodput (Ch6).
  Continuous batching exists precisely to uncouple batch size from wait.
\item
  \textbf{Serving KV contiguous and watching fragmentation.}
  PagedAttention removes the fragmentation tax; skipping it wastes
  memory under concurrency.
\item
  \textbf{Re-prefilling shared context.} Without prefix caching,
  repeated RAG documents are recomputed per request --- one of the most
  wasteful failures for this workload.
\item
  \textbf{Choosing P/D disaggregation too early.} Splitting pools adds
  fabric + orchestration; for a single host it is overhead without the
  resource conflict that motivates it.
\item
  \textbf{Believing speculative decoding (DFlash reports \textgreater6×
  lossless acceleration, up to 2.5× faster than EAGLE-3
  \mbox{{[}S5{]}}\hspace{0pt}\mbox{{[}1P{]}}) is a serving baseline.} These are paper-reported
  results under the paper's evaluation setup, not portable serving-speed
  figures. Speculative decoding is an optimization for bandwidth-bound
  decode, not a requirement, and must be validated on the workload.
\end{itemize}

\ntsection{Architecture Consequence}\label{architecture-consequence}


The serving mechanisms dictate the deployment choices:

\begin{itemize}
\item
  \textbf{Baseline (canonical single-host):} continuous batching
  (vLLM/Orca) is near-mandatory to hold TTFT under the SLO (1.2 s, p95 ≤
  2 s) at 10 rps input-heavy load; PagedAttention ensures the
  \textasciitilde24.1 GB-per-request KV pack fits; prefix caching is the
  highest-leverage optimization because the workload is repeated-context
  RAG. This matches the memory and compute conclusions of Ch4/Ch7 for
  the \textasciitilde10 rps \emph{average} baseline; at the
  \textasciitilde40 rps peak the KV budget forces replication, which
  \hyperref[chap:17]{Chapter 17} sizes. \mbox{{[}S1{]}}\hspace{0pt}\mbox{{[}S2{]}}\hspace{0pt}\mbox{{[}S3{]}}\hspace{0pt}\mbox{{[}1P{]}}
\item
  \textbf{Scaling up:} those three carry the workload far before
  disaggregation is justified. FP8 KV (raw tensor byte-halving = 1.31
  MB/token, exactly 50\% of BF16) \mbox{{[}ILLUSTRATIVE{]}}\hspace{0pt}\mbox{{[}DERIVED{]}} and KV
  offloading are memory levers available without restructuring.
\item
  \textbf{Beyond a node:} when prefill FLOPs and decode bandwidth fight
  on one pool, P/D disaggregation (Splitwise/DistServe/Mooncake) is the
  architecture of choice, with Mooncake's KV-transfer engine moving
  caches between pools. \mbox{{[}S4{]}}\hspace{0pt}\mbox{{[}1P{]}}
\end{itemize}

\subsection{What the capability table does not
promise}\label{what-the-capability-table-does-not-promise}

\textbf{A recognized quantization name is not an end-to-end support
claim.} A deployment needs a chain of compatible choices: checkpoint
schema, model graph, tensor layout, operator coverage, runtime
dependencies, and device instructions. ``Supports four-bit weights''
does not establish support for a model's grouped expert GEMMs, attention
variant, modal branches, or KV format. A backend may accept a checkpoint
and select a different arithmetic path, reject a particular shape, or
need a temporary higher-precision representation; the serialized tensor
layout and the kernel-required runtime layout are different objects. A
missing compatible path is a deployment failure, not a guaranteed
fallback. \mbox{{[}1P{]}}\hspace{0pt}\mbox{{[}DERIVED{]}} Implementation-specific examples are
dated separately.

The deployment record therefore includes the exact model and engine
revision, device architecture, driver/toolkit and library versions,
quantized tensor inventory, selected kernels, and fallback logs. It also
records cold-load peak and steady HBM separately. This record determines
whether the configuration can be reproduced; a single support-table
checkmark does not. Allocator or scheduling limits then determine how
much of the remaining memory can become usable KV capacity without
violating latency targets. Smaller weights do not justify increasing
admitted concurrency until the new operating point is measured.
\mbox{{[}DERIVED{]}}

\textbf{A serving feature belongs to an algorithm path.} The capability
table is a map of mechanisms, not a guarantee that every supported model
can combine every row. Diffusion language models make this qualification
especially important. A paged allocator can manage buffers without
proving that their contents remain valid across refinement. A
prefix-cache key must describe finalized token content and compatible
state, not an unresolved mask canvas. Grammar constraints, quantized
loading, graph capture, and distributed parallelism also depend on the
selected model implementation and sampler. \mbox{{[}1P{]}}\hspace{0pt}\mbox{{[}FACT{]}}

Requests can require different numbers of refinement rounds. A lockstep
batch waits for its slowest active member unless the scheduler can
preserve unfinished state and admit or complete requests independently.
The SGLang diffusion scheduler inspected on 2026-10-28 (revision
a1966e1) implements a first-done-first-out path that retains partial
block state.\footnote{SGLang documentation and source at pinned revision
  \texttt{a1966e1b5d8b750b494d7e53cca1d2464f960038},
  §``First-Done-First-Out (FDFO) Scheduling'':
  \url{https://raw.githubusercontent.com/sgl-project/sglang/a1966e1b5d8b750b494d7e53cca1d2464f960038/docs/docs/supported-models/diffusion_language_models.mdx}
  ; scheduler comment ``keep partial state and KV for the next FDFO
  round'':
  \url{https://raw.githubusercontent.com/sgl-project/sglang/a1966e1b5d8b750b494d7e53cca1d2464f960038/python/sglang/srt/dllm/mixin/scheduler.py}
  . Retrieved 2026-10-28; source-inspected, not executed.} This is
explicit iteration-aware scheduling, not evidence that the
autoregressive token loop works unchanged --- an observation about that
inspected revision, dated 2026-10-28 and outside this edition's
2026-08-30 evidence snapshot. Tail latency depends on the distribution
of rounds, block sizes, queueing, refresh, and cancellation, not merely
the average accepted tokens per round. \mbox{{[}1P{]}}\hspace{0pt}\mbox{{[}FACT{]}}; latency
interpretation \mbox{{[}DERIVED{]}}

A prefill/decode-style split must place context encoding, block
refinement, and finalization on explicit resources. Any transferred
state, repeated attention to that state, and finalization work belong in
the service budget. The familiar principle survives: specialization is
useful only when its benefit exceeds transfer and orchestration costs.
The objects being transferred cannot be inferred from an autoregressive
KV formula alone. \mbox{{[}DERIVED{]}}

\textbf{The complete backend path.} A serving engine needs more than a
visible accelerator. It needs a compatible model implementation,
numerical representation, attention path, cache management, kernel set,
runtime and driver. Distributed execution adds a collective backend and
a supported transport. \hyperref[fig:11.4]{Fig 11.4} separates these dependencies from the
final qualification decision. Its columns are alternatives, not
interchangeable APIs.

A compact qualification record can contain seven gates:

\begin{enumerate}
\def\labelenumi{\arabic{enumi}.}
\tightlist
\item
  Exact device, checkpoint, tokenizer, engine, and dependency identities
  are fixed.
\item
  Each rank fits weights, KV, workspace, and temporary conversion state.
\item
  Required operators, weight/activation/KV formats, and attention
  layouts execute correctly.
\item
  Scheduling, cache reuse, graph behavior, and any fallback are
  observable.
\item
  Required collectives work on the deployed topology and message sizes.
\item
  Long-context quality, concurrent-request isolation, and failure
  recovery pass.
\item
  Measured tail latency and quality-qualified goodput satisfy the
  workload contract.
\end{enumerate}

A failure closes the proposed configuration. A different configuration
can be evaluated, but a reduced context, changed quality threshold, or
disabled feature is a changed deployment --- not an unnoticed repair to
the original result.

\subsection{The serving concerns transfer; the text mechanisms do not
transfer
automatically}\label{the-serving-concerns-transfer-the-text-mechanisms-do-not-transfer-automatically}

A video service still schedules requests, manages live state, reuses
valid work, and chooses resource-specialized pools. The mechanisms
implementing those concerns differ. The inspected full-clip Wan path
does not emit a completed next frame at each denoising step.\footnote{Wan2.2
  TI2V sampling loop at pinned commit
  \texttt{1ea34ff48f87168174e12956e200b1d908b1c5ff} --- denoising steps
  update the full clip latent; frames are produced by the VAE decode
  after sampling:
  \url{https://github.com/Wan-Video/Wan2.2/blob/1ea34ff48f87168174e12956e200b1d908b1c5ff/wan/textimage2video.py}
  . Retrieved 2026-10-28; source-inspected, not executed.} A step
boundary can be a scheduling or cancellation point if the runtime
exposes it, but it is not automatically a text continuous-batching
boundary. Jobs with different shapes, samplers, guidance branches, and
timestep schedules may be difficult or wasteful to batch together.
\mbox{{[}1P{]}}\hspace{0pt}\mbox{{[}FACT{]}} model execution; \mbox{{[}ILLUSTRATIVE{]}}\hspace{0pt}\mbox{{[}HYPOTHESIS{]}}
scheduling consequence.

A useful admission record therefore includes the checkpoint revision,
task type, exact height and width, frame count, audio/reference inputs,
schedule, guidance method, precision, and parallel layout. Shape-aware
buckets limit padding and kernel recompilation. A deadline-aware
dispatcher can separate interactive previews from full-quality
completion. It must include queue age and avoid starving long jobs. A
low-step preview is a separate quality contract unless the
implementation proves that its state can continue into the final recipe.
A preview image, first decoded frame, and finalized downloadable clip
are three different completion events.

Per-request memory limits follow measured peaks for each admitted
configuration. The largest VAE reconstruction, full-clip attention
workspace, compiler workspace, and overlapping transfers can bind even
when the weight set fits. Offload and quantization change those peaks
only where the actual kernels support the chosen representation. A
quantized checkpoint file alone does not establish faster execution,
adequate reconstruction quality, or a supported attention backend.
\mbox{{[}1P{]}}\hspace{0pt}\mbox{{[}FACT{]}} documented offload paths;
\mbox{{[}ILLUSTRATIVE{]}}\hspace{0pt}\mbox{{[}HYPOTHESIS{]}} deployment consequences.

Parallelism also changes the cost of a step. Sequence or context
parallelism partitions video positions and exchanges attention data.
Tensor parallelism partitions model operations and introduces its own
collectives. Weight sharding is a residency technique, not a synonym for
either. Wan2.2's official multi-GPU path combines FSDP and Ulysses; the
Ulysses strategy's attention-head divisibility requirement is part of
the deployable configuration.\footnote{Wan2.2 official README,
  ``Multi-GPU inference using FSDP + DeepSpeed Ulysses''
  (\texttt{-\/-ulysses\_size\ 8}), pinned commit
  \texttt{1ea34ff48f87168174e12956e200b1d908b1c5ff}:
  \url{https://github.com/Wan-Video/Wan2.2/tree/1ea34ff48f87168174e12956e200b1d908b1c5ff}
  . The head-divisibility requirement for the Ulysses strategy is stated
  in Wan's official README at commit
  \texttt{9737cba9c1c3c4d04b33fcad41c111989865d315}:
  \url{https://raw.githubusercontent.com/Wan-Video/Wan2.1/9737cba9c1c3c4d04b33fcad41c111989865d315/README.md}
  (``\texttt{num\_heads} should be divisible by
  \texttt{ulysses\_size}''). Both retrieved 2026-10-28.} More aggregate
GPU memory does not establish that an arbitrary partition or mixed-speed
GPU group is valid or fast. Repeated synchronization can make the
slowest device or weakest link determine the step time.
\mbox{{[}1P{]}}\hspace{0pt}\mbox{{[}FACT{]}} supported path; \mbox{{[}ILLUSTRATIVE{]}}\hspace{0pt}\mbox{{[}HYPOTHESIS{]}}
performance boundary.

The end-to-end clock starts at request acceptance and ends only after
the promised media artifact is available. Model denoising, VAE decode,
frame transfer, video encoding, audio muxing, safety checks, storage
upload, and delivery can all extend that clock. Encoder-heavy
postprocessing may merit a separate CPU or GPU pool, but the transfer
and queue cost must be measured. A text prefill/decode split does not
prove that the same split is useful here.

\section{End-of-Chapter Mini-Case: Which Serving Mechanism to Reach
For}\label{end-of-chapter-mini-case-which-serving-mechanism-to-reach-for}

This is an illustrative scenario, not a measured result.
\mbox{{[}ILLUSTRATIVE{]}}\hspace{0pt}\mbox{{[}ASSUMPTION{]}} An architect examines one 8×H100
replica in the canonical internal Q\&A service, whose aggregate service
peak is 40 rps. Suppose that replica's assigned load produces p95 TTFT
of 2.2 s against a 2 s SLO. The first checks are whether continuous
batching and PagedAttention are active: the baseline KV for 9.2K inputs
is about 24.1 GB per request, so allocation behavior matters. Repeated
RAG documents then make prefix caching a candidate because valid
shared-prefix KV can avoid repeated prefill work. Suppose a controlled
test at the same assigned load and request mix brings p95 TTFT below 1.8
s. That assumed result would support the cache change for this replica;
it would not establish service capacity at 40 rps. P/D disaggregation
and speculative decoding remain separate candidates, not required steps
in this diagnosis.

Scope note: with the baseline mean service-time assumption of 8.6 s, the
aggregate 40 rps peak implies approximately 344 in-flight requests. The
baseline unshared-KV capacity quotient is about 17.5 complete requests
per host, conservatively floored to 17 integer slots. \mbox{{[}canonical
scenario{]}}\hspace{0pt}\mbox{{[}DERIVED{]}} That baseline requires multiple replicas; a
per-request TTFT result does not size the fleet. Any capacity credit for
sharing must follow measured prefix-cache occupancy, hit rates, service
time, and tail latency under the admitted workload. \hyperref[chap:17]{Chapter 17} applies
joint residency and throughput constraints, headroom, and failure
reserve. The replica's latency result and the service's capacity
decision remain distinct.
